canon's strategy memory (S6/S7/S8) turns accumulated verdict
trajectories into retrievable, promotable insight — role-namespaced:
`planning`, `design`, `dev`, `test`, `review`, and others share one
backbone but evolve separately.

canon's position is that strategy memory is only worth retrieving if its
text is grounded in artifacts outside the model — otherwise a retrieval
loop just recycles the model's own output back into itself.

## The flywheel

```
    → distill: success → quarantined strategy, review finding → guardrail
    → eligibility gate (occurrence or paired CRN)
    → paired evaluation + policy-pinned SSH approval
    → activate in git tier (versioned, PR-reviewed)
    → retrieve-before-task (role + regime scoped, advisory)
    → later agent runs (uplift not yet measured) ↻
```

## Two tiers, two stores

- **Warm — trajectories (Parquet).** `ParquetTrajectoryStore` under
  `<repo>/.canon/learn/trajectories/`: verdict-keyed rows written by
  ingest. Local, rebuildable, `.gitignore`d — never hand-committed.
- **Durable — strategies (git).** `ParquetStrategyStore` plus
  git-tracked `<repo>/.canon/strategies/<role>/<id>.md` files: the
  distilled, PR-reviewable `StrategyItem`s a promotion writes into and
  a demotion soft-flags.

A trajectory names its concrete artifact — the scenario, handoff, or
task it was derived from — and carries the prose the underlying evidence
record actually holds: a reviewer's pin, a divergence finding's
narrative, a task's evidence note. So a distilled strategy quotes real
evidence instead of a summary of canon's own ingest:

```
# before — the trajectory described the adapters that produced it
2 verdict(s) derived from canon-ingest artifact adapters for regime test/canon/platformer/41fdd8c50ee6

# now — the title names the artifact, the content quotes the evidence
platformer.session.04: resolved divergence
resolved divergence: Fixed and independently re-verified+attested at 505a668efedaed6dfb5e125a0d927f118b2dfad1 (dev-fix wave 8d3c1506..505a668e; movement.03/session.03 at ea77374)
```

A record carrying no prose is not a ceiling, because canon's join spine
exists so a record does not have to hold every fact about itself. Two
joins supply the text the event itself lacks:

- **Antecedent findings.** A verdict-bearing event distills together with
  the prose-bearing non-verdict events on the same artifact that preceded
  it. A `resolved` divergence therefore carries the `open` ship-blockers
  it closed — the pitfall and its demonstrated fix in one item, which is
  the most useful shape a strategy can take. Open findings stay
  non-verdict: they never mint a verdict, reward, or trajectory of their
  own.
- **Scenario titles.** A trajectory whose artifact is a scenario names it
  in human terms, so an attestation says what it attested.

```
platformer.session.04: resolved divergence — Idle and resize sessions stay error-free
    resolved divergence: Fixed and independently re-verified+attested at 505a668e...
    preceded on this artifact by:
      - open divergence: SHIP-BLOCKER src/render/PixiStage.tsx:28-32 assigns app before
        awaiting loadTextures ... Centralize teardown behind an idempotent owner.
      - open divergence: SHIP-BLOCKER src/App.tsx:45-46 calls sim.setPaused() inside a
        React updater ... Compute the next pause state outside the updater.
```

<Aside type="note">
  `records::Review` really does carry no prose — only `reviewer`, `pin`,
  and `provenance_ref`. Its attestations read as evidence anyway because
  they are joined to the scenario they attest and to the findings filed
  against it, not because the record grew a field. Antecedents are
  ordered by `(at, line)`, deduped, and capped, so this text stays
  deterministic.
</Aside>

Strategy memory is **rebuilt, not recomputed once**: `canon ingest
artifacts` re-derives distilled strategies from the current trajectory
set (`rebuild_namespace`) every time it runs. That re-derivation is
deterministic — a second ingest pass over the same artifacts derives
byte-identical trajectory content, so the duplicate skip the rebuild
rests on still fires and repeated runs don't churn. The rebuild is
non-destructive — it never deletes a strategy the raw trajectory rows
don't touch, so a rebuild can't silently drop a hand-promoted strategy.
There is no standalone `canon learn` rebuild command; the only `canon
learn` subcommand is `promote`.

## Rewarding a trajectory

Each role has its own reward function — never one formula applied
uniformly. `dev`'s reward is a weighted composite (`pr-merged 0.4 +
ci-pass 0.3 + no-rollback 0.3`, floored to `0.1` on a rollback or CI
failure, shortcut to `1.0` on human approval). Other built-in roles
share a provisional default (`0.9` success / `0.3` failure / `0.5`
pending) until real cross-role data justifies their own formula.

A trajectory is marked with a covering verdict exactly once — moving it
off `Pending` is a one-way transition; an unknown trajectory id fails
loud rather than silently no-op'ing.

## Eligibility and activation: `crn` vs `occurrence`

A role's eligibility gate is a `canon.yaml` `learn:` config choice, not a
compile-time one:

```yaml
learn:
  promotion:
    dev:
      mode: occurrence
      n_min: 8 # optional — defaults to 5
      window_days: 14 # optional — defaults to 30
    sim:
      mode: crn
  demotion:
    hard_delete: false # optional — soft-flag is the default
    strategies_root: .canon/strategies
```

Newly distilled strategies are **quarantined by default**. The eligibility
gate is necessary but not sufficient: activation also requires an honest,
paired evaluation and an approval declared `human` whose signature
authenticates a principal pinned by policy (not humanity or authorization
outside that policy).

- **`occurrence`** — for roles whose domain doesn't support deterministic
  replay (most of `dev`/`content`/`design`/`review`). At least `n_min`
  resolved `Success` trajectories for the same regime must occur inside the
  trailing window, with no `Failure`/`RolledBack` trajectory. A contradiction
  resets the count; it is never averaged away.
- **`crn`** — for roles that can run a deterministic simulator: a paired
  common-random-number eligibility gate using the same
  `crn:config=<label>` and `crn:panel=<index>` panels across configurations.
  Too few panels or too much unexplained noise is not a pass.

A role without an explicit `promotion.<role>` entry resolves to
`occurrence`, `n_min: 5`, `window_days: 30`. Both modes read resolved
trajectory outcomes, not raw verdict rows; run `canon ingest artifacts` first.
Neither mode alone proves a quality uplift.

## Promoting, approving, and rolling back

```bash
canon ingest artifacts
canon learn approve 01J...ULID --evaluation evaluation.json \
  --principal alice --repo .
# `request` is an exact alias for `approve`
canon learn promote 01J...ULID --repo . \
  --evaluation evaluation.json --approval approval.json
```

`PromotionEvaluation` is an external adapter's JSON bundle. It binds the
quarantined candidate, its strategy and source-trajectory digests, paired
baseline/candidate result digests, and non-empty corpus/evaluator/context/
policy/model/tool provenance. Its finite `paired_metrics` MUST include
`pairs`, `uplift`, and `regressions`; pairs must match the result count,
`uplift` must be positive, and regressions must be zero. Missing or unknown
metrics, duplicate/shared result digests, a mismatched integrity digest, or a
non-passing decision is rejected. Canon does not run the evaluator, and this
repository currently publishes **no measured uplift result**.

`canon learn approve`/`request` prints an unsigned payload: namespace
`canon-learning-approval-v1`, subject `strategy:<id>`, evaluation digest,
RFC3339 `approved_at`, and `payload_hex`. It never reads a private key or
sets `verified`. Decode those exact bytes and sign them externally with
`ssh-keygen -Y sign -n canon-learning-approval-v1`. Put the armored detached
signature in `PromotionApproval.signature`, set `signer_key` equal to the
principal, and use `approver_role: human`.

The signed canonical JSON is equivalent to:

```json
{"namespace":"canon-learning-approval-v1","subject":"strategy:<id>","project":null,"artifact_sha":"<evaluation_digest>","run_id":null,"surface":[],"effects":[],"actor":"<principal>","timestamp":"<RFC3339 nanosecond timestamp>"}
```

For rollback, the subject and `artifact_sha` use
`strategy:<id>:rollback:<sha256(reason)>` and that reason digest. The signature
authenticates the configured principal, not humanity or authorization outside
the policy. The repository policy MUST pin the verifier, for example:

```yaml
approval:
  allowed_signers: .canon/allowed_signers
```

Promotion verifies that signature with `ssh-keygen -Y verify` and that
policy-pinned file. `--evaluation` and `--approval` are required together;
`--signature <path>` can attach the armored signature to the approval JSON.
Without valid paired evidence and this signature, the quarantined candidate
stays quarantined. There is no `--force`.

An ordinary contradiction demotes an already-active strategy: by default it
soft-flags the existing git file (`status: demoted`, `reason:`), or
`demotion.hard_delete: true` removes it. This is not an authenticated
rollback and does not produce a rollback record. An explicit rollback is
separate:

```bash
canon learn rollback 01J...ULID --reason "regression" --actor alice \
  --signature-file rollback.sig --approved-at 2026-10-02T12:00:00Z \
  --contradicting-trajectory-id 01J...TRAJECTORY --repo .
```

The rollback signature covers the
`canon-learning-approval-v1` subject
`strategy:<id>:rollback:<sha256(reason)>`, actor, and timestamp. The actor
must be listed in policy-pinned `approval.allowed_signers`; successful
rollback records provenance and sets lifecycle `rolled_back`.

## Retrieving before a task

```bash
canon retrieve --role dev --regime dev/canon/join-spine/9c93d024b1a2
canon retrieve --role dev --regime dev/canon/join-spine/9c93d024b1a2 --k 3 --json
```

`--regime` is the full `regime_key` string,
`<role>/<repo>/<area>/<hash>` — the same canonical serialization the
write side produces. Assemble it through the one serializer instead of
a second, drifting derivation:

```bash
canon regime-key --role dev --repo canon --area join-spine --hash abc123
```

`--role` must equal `--regime`'s own leading segment; a mismatch is a
clean usage error (exit `2`). Once role and regime agree, retrieval is
**fail-soft and always exits `0`** — a store outage, an empty store, or
a malformed row all degrade to an empty guidance list, never a nonzero
exit a caller must handle.

<Aside type="note">
  A dispatched run snapshots what `canon retrieve` returned into its own
  manifest (`Run.injected_guidance`) rather than pointing at the live
  store — a later edit or demotion can never retroactively change what
  a manifest already recorded. Replaying a run reads that snapshot, not
  a fresh retrieval.
</Aside>
