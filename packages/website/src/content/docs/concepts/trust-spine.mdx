---
title: Trust Spine
description: How canon gate turns task completion from self-reported to evidence-gated, and reads the ten stable failure classes.
---

`canon-gate` is canon's trust spine: a two-layer evidence gate over any
`EvidenceRecord`-shaped corpus. It answers two **different** questions per
artifact, and never collapses them into one "done" boolean:

- **Coverage** — does the required evidence *exist* for this artifact, per
  policy?
- **Verdict ledger** — did that evidence *pass*, by whom, and how stale is
  it now?

A `Divergent` verdict still satisfies coverage — coverage is "a test
exists", never "a test passed".

Both questions start from evidence, so neither can see a spec nobody has
attested to at all. [Spec coverage](#spec-coverage-the-worklist) is the
opt-in third question that starts from the spec corpus instead.

## The ten failure classes

Every violation `canon gate` reports carries one of these stable, grep-able
strings. They are never renamed without a coordinated fixtures+hooks
migration:

| Class | Meaning |
|---|---|
| `uncovered-cell` | A policy-required evidence cell (role × artifact) has no matching record at all — or, when `spec_coverage` is on, a scenario in the spec corpus that no evidence attests to, carries an open divergence, or whose latest verdict is `Divergent`. The detail string names which. |
| `unreviewed-promotion` | An artifact's `reviewed` lifecycle tag has no matching ledger review-record — or, with `spec_coverage.require_review` on, an in-scope scenario has no qualifying `Review` (none at all, or only reviews by its own evidence actor). |
| `trust-below-required` | The artifact's trust level is below `policy.yaml`'s `trust_required` — release-scoped only (`canon gate check --release`). |
| `stale-evidence` | A passing record degraded to stale: its declared surface changed since its `evidence_sha`, or HEAD moved past `staleness.max_commits_behind`. Only ever degrades an already-green record. Also: a file bound to a latest evidence record whose bytes are gone from both the artifact store and the working tree. |
| `malformed-evidence` | A candidate record doesn't parse, is misfiled, or carries an unparseable interim tag. Malformed evidence is no evidence. |
| `flagged` | The human-only `flagged` overlay is set — never green regardless of any passing evidence. |
| `unevidenced-flip` | `canon gate task <task_id>` was asked to flip a checkbox with no matching, non-`Divergent` `EvidenceRecord`. |
| `fabricated-evidence` | The evidence note attached to a flip contains a blocklisted marker (`"would pass"`, `"TBD"`, `"n/a"`) or a bare `verified` claim with no attached command result. |
| `open-blocker` | With `spec_coverage.require_review` on, a review finding whose latest version is severity `blocker` and disposition `open`, on a change adopted by an in-scope subject. The subject string is `<change_id>#<round>.<seq>`. |
| `false-success` | A scenario's latest audit record (`canon evidence add --kind audit`) is `refuted`: an external evaluator found a counterexample. Always on, whatever the policy or sampling, and it overrides any declared faithful verdict until a newer audit (`confirmed` or `indeterminate`) clears it. The detail names the evaluator, its version, its sha256 and the counterexample paths. |

## Spec coverage: the worklist

Coverage and the verdict ledger both enumerate from evidence, so a
`.feature` scenario that is specced and never touched is invisible to
them — there is no record to group. That is the one case a spec-driven
tool most needs to catch, so `spec_coverage` inverts the direction: it
starts from the Scenario corpus `canon inventory sync` indexed and
left-joins evidence onto it. What falls out is a worklist. An
unimplemented spec and a mismatched one are both work items, and both
report as `uncovered-cell` with a detail naming which.

It is **off unless a repo opts in.** A spec-driven team writes specs
before it implements them, so a check that were on by default would go
red the moment the workflow started working. An absent section derives
zero violations:

```yaml
# .canon/policy.yaml
spec_coverage:
  require_evidence: true
  scope: [building, verifying]
  exclude_lanes: [process]
  require_cases: [failure]
```

`scope` narrows what can *block* to scenarios linked — via their
`@subject:<id>` Gherkin tag — to a Subject in one of those
[lifecycle states](/concepts/canon/). An area with no Subject at
`building` or `verifying` blocks nothing, which is what keeps a partly
specced repo honest: the unspecced parts are visibly absent rather than
silently green. Leave `scope` out and every scenario is in scope.

`exclude_lanes` takes a second, independent cut after `scope`. A
scenario's **lane** — its `@lane:<value>` tag, carried onto the indexed
`Scenario` record — says what kind of requirement it is: `behavior`
(what the product does), `design` (how it looks and moves),
`architecture` (how the code is shaped), or `process` (how the team
works — what a review report may claim, how acceptance is run). The
base set is `canon.core`'s; a repo replaces it through its own `lane`
vocabulary enum. A `process` rule has no code surface and can never be
`faithful` from a test, so listing it here keeps a real rule out of a
number it would only pollute. Absent, nothing is excluded.

`require_cases` closes the gap evidence presence cannot see: a surface
whose every scenario is attested but all of them describe the golden
path. A scenario's **case** — its `@case:<value>` tag — says which path
of the behavior it specifies: `happy`, `failure` (a refusal, error, or
denied action), or `edge` (a boundary such as an empty set, a limit, or
a duplicate). Every feature surface (`<area>.<surface>`) with in-scope
scenarios must carry at least one scenario of each listed case, or the
surface is reported as `uncovered-cell`; `canon subject status <id>
shipped` refuses on the same rule. An untagged scenario satisfies no
case, so an unclassified corpus reports every surface rather than
passing. Absent, nothing is required.

A present-but-malformed section is never silently equivalent to an absent
one — it is reported and then fails the check, so a typo (or a
non-slug lane, or a malformed `require_review`) cannot quietly disable the gate.

### Independent review

Evidence says a test exists; it does not say anyone other than its
author looked at the work. `require_review` (absent by default — nothing
changes until a repo sets it) asks for that second look before a
subject is claimed done:

```yaml
spec_coverage:
  require_evidence: true
  require_review:                 # `{}` takes every default
    scope: [verifying, shipped]   # default; [] = every scenario
    distinct_actor: true          # default
    block_on_findings: true       # default
```

Every scenario whose subject is in `require_review.scope` (independent of
`spec_coverage.scope`; `exclude_lanes` still exempts) needs a `Review`
record — `canon review add --project-id <root> --scenario-id <id>
--reviewer <who> --role reviewer --pin <sha> --upstream-ref <ref>
--session-id <session>`, which writes directly (there is nothing to promote).
With `distinct_actor`, both the review's `reviewer` and its actor must differ
from every actor on that scenario's evidence, and a review that carries a
session must come from a session other than any evidence session
(`evidence add --session-id`), so an agent cannot review its own work under
another id. A record without a session never matches one, so older records
count by actor alone. A missing or self-only review is
`unreviewed-promotion`. A review carries no verdict; the ship gate still
checks verdicts.

A review pins what it saw: `review add` records the scenario's source
digest and its latest evidence records, and the review counts only while
both are unchanged. Edit the `.feature` file (and sync it) or re-attest
the scenario, and the review is stale — `unreviewed-promotion` naming the
spec, the evidence, or both. Only a `signed` review counts; a reviewer run
recorded `--outcome indeterminate` or `unavailable` is a gap, and the
latest review per reviewer wins. Reviews written before 0.15 carry no
pins, but each names the commit it reviewed (`pin`). The gate reads the
scenario there through `git`, with the same per-scenario digest `inventory
sync` computes: a review stays current while that digest equals today's
and no declared evidence is newer than the review, and is stale
otherwise. When the commit, or the scenario at it, is not in the clone
(a shallow checkout, rewritten history), the review is undecidable and
still counts — a missing commit is never a violation. `gate check` prints
one `advisory: N review(s) predate review pinning (0.15) and were checked
against the commit each one pinned: C current, S stale, U undecidable …`
line. A stale one whose scenario already has another current review is
counted as superseded; only the scenarios still owed a review are named
for re-review. In CI, check out full history
(`actions/checkout` with `fetch-depth: 0`) for the gate job.

With `block_on_findings`, review findings (`canon finding add
--severity blocker|should-fix|note`) are read at their latest version per
`(change_id, round, seq)`. An open `blocker` on a change an in-scope
subject adopted is `open-blocker` until it is closed — `fixed` with
`--resolution-sha <sha>`, or `rejected` or `deferred`:

```
open-blocker c-demo#1.1 — open blocker finding by `reviewer-2` on change `c-demo` (subject `demo-subject`): unbounded subprocess wait; fix it and `canon finding close --disposition fixed --resolution-sha <sha>`, or close it as rejected or deferred
```

`should-fix` and `note` findings never block.

A subject moved past these checks with `canon subject status
--override-reason` (see [CLI reference](/cli/)) keeps the exact gaps
its waiver recorded visible as advisories after the violations, without
failing the gate. A gap that appears later is not covered and fails as
usual:

```
review waivers: 1 advisory(ies) — not failing the gate:
  waived unreviewed-promotion world.demo.01 — no review record ... [waiver: subject `demo-subject` moved to verifying by `lead`: reviewer out until Monday]
```

`canon context` lists the finding severities, dispositions, Review
fields, and the active `require_review` setting.

## Audits: an outside check on success

A declared verdict is the author's word. An audit is a second opinion
from an external evaluator — canon never generates or runs one; it
records the result:

```bash
canon evidence add --kind audit --project-id root --scenario-id cart.add.01 \
  --ref "judge run 42" --role reviewer \
  --evaluator-id judge --evaluator-version 1.2 \
  --evaluator-digest <sha256, 64 lowercase hex> \
  --audit-result refuted --report junit:audit/counterexample.xml
```

`--kind audit` requires the four evaluator flags plus `--scenario-id` and
`--project-id`, and refuses `--task`, `--verdict`, `--surface-ref` and
`--approval-*`. The record carries `audit: {evaluator_id,
evaluator_version, evaluator_digest, result}` and a derived verdict
(confirmed → faithful, refuted → divergent, indeterminate →
not-applicable). Audits fold apart from declared records, so an audit
never becomes the scenario's latest declared verdict. Optional
`--report`/`--artifact` counterexamples are bound and re-checked like any
other binding.

A `refuted` latest audit is `false-success` everywhere, and
`canon subject status <id> shipped` refuses it. To require audits, sample
them:

```yaml
spec_coverage:
  require_audit:
    rate: 0.1                    # required, in [0, 1]
    seed: "2026-q4"              # optional; default ""
    scope: [verifying, shipped]  # default; [] = every scenario
```

A scenario is sampled iff the first 8 bytes of
`sha256(seed || 0x00 || project_id || 0x00 || scenario_id)`, read as a
big-endian u64, are below `rate · 2^64` (compared exactly against
`ceil(rate · 2^64)`: rate 0 samples nothing, rate 1 everything).
`exclude_lanes` applies. A sampled in-scope scenario whose latest audit is
missing or `indeterminate` is `uncovered-cell`, and the ship guard
refuses it when `scope` covers `shipped`. A malformed `require_audit`
makes the whole `spec_coverage` section unusable. `canon status` shows
sampled, confirmed, owed and refuted counts.

## Dropping a binding on purpose

Re-attesting a scenario must not quietly lose its proof. When the
scenario's current latest record of the same fold (declared, or audit for
an audit; staged or committed) binds files the new record does not,
`canon evidence add` refuses (exit `2`) and names them. Re-bind them (new
bytes at the same path are fine), or drop them explicitly:

```bash
canon evidence add ... --drop-attachment reports/old.xml \
  --drop-reason "suite split into reports/unit.xml"
```

`--drop-attachment` is repeatable; `--drop-reason` is one line and
required with it. The drop is recorded as `attachment_drop: {paths,
reason}` and listed by `canon status` under `dropped bindings`.
Task-only evidence has no drop guard.

## Experimental: evidence binding

An evidence record is an attestation — canon never runs `--ref`, and it
cannot run every language and agent-driven QA tool a team uses. Binding
(off by default) lets a record point at files the team's own runner or
agent already produced:

```bash
# any file — a trace, screenshots, an agent QA log — bound by sha256
canon evidence add ... --artifact test-results/cart-trace.zip
# a JUnit XML / Cucumber JSON report: also records the matched case and outcome
canon evidence add ... --report junit:target/nextest/default/junit.xml
```

A report case is bound when the scenario id is its own: the first
scenario-id-shaped token of its full name (classname, then name), or a
Cucumber tag equal to it. A case named `game.session.04: restarting as
in game.session.01` binds to `game.session.04` only. Each bound case
keeps its own outcome; `--report-case` (repeatable) adds more and
never hides one. A `faithful` verdict is refused when any bound case
failed. Whether the gate cares about strength is a policy switch:

```yaml
experimental:
  evidence_binding:
    mode: warn          # off (default) | warn | require
    strength: artifact  # artifact (any bound file) | report (a passing case)
    case: [failure]     # optional: only these scenarios are held
```

`warn` lists scenarios below `strength` after the gate result without
failing it; `require` makes each an `uncovered-cell`. Canon still cannot
tell whether a bound test truly exercises the scenario — binding narrows
the trust gap, it does not close it.

## Bound evidence stays provable

`--artifact`/`--report` copy each bound file into
`.canon/artifacts/sha256/<hex>`, a content-addressed store tracked in git
— commit it with the ledger. Files over 25 MiB are refused (exit 2) unless
`--max-artifact-mib` raises the limit. `canon gate check` re-checks every
file bound to a latest evidence record, whatever its subject's status:

- an intact stored blob → clean, even after the working-tree file is
  rewritten (a smoke script that rewrites its report every run no longer
  orphans the evidence);
- no blob, but the working-tree file still has the recorded digest →
  clean, with an advisory pointing to `canon evidence vault`, which stores
  those bytes (records from before 0.14);
- anything else → `stale-evidence`, naming the path, the recorded digest,
  and what the store and working tree hold now, and whether the stored
  blob was altered (it no longer matches its name) or is gone. Re-run and
  re-attest.

## The trust ladder

Artifacts climb: **draft → reviewed** (agent + review-record) **→
ratified** (human). Bare promotion without a matching review-record is
`unreviewed-promotion`. `flagged` is human-only, never green, and clears
only via a human-attributed clear-record — a one-way ratchet.

## Checking a repo

```bash
canon gate check --repo .            # ordinary evaluation
canon gate check --repo . --release  # + trust-below-required
```

`canon gate check` is the dispatcher: it assembles coverage + ledger +
staleness + spec-coverage + bound artifacts + the always-on trust-ladder check and prints
every violation grouped by failure class. `--release` additionally engages
the release-scoped `trust-below-required` check — the trust-ladder check is
never dropped when `--release` is passed. Exit `0` clean, `1` gate-red (any
violation), `2` usage/load failure (unreadable ledger, corrupt
`canon.yaml`).

## Gating a task checkbox flip

```bash
canon gate task s5-trust-spine-gate#5.2 --repo .
```

`canon gate task <task_id>` is the evidence-gated flip of one checkbox row
in a change's plan document. It resolves `<task_id>` (`<change_id>#<n>`)
through canon's own `.canon/changes/` (read first, with no `plans:` entry)
and then `canon.yaml`'s `plans.sources` — the first dialect whose
write-back locates the task wins, so the flip is plan-dialect agnostic
(canon's own `tasks.md`, external `openspec` change dirs, `superpowers`
plan docs). A repo with no `plans:` section falls back to the compat
default `[{ dialect: openspec, root: <repo> }]`. Canon only reads
external plans with this one exception: for a task from an external
plan, the flip writes the checkbox in that plan's own `tasks.md`. It
requires a matching, non-`Divergent` `EvidenceRecord` in the ledger, and
flips `- [ ]` → `- [x]` with an appended evidence note **only** on a clean
check. The note sums up every record bound to the task on one line —
`3 evidence records (2 faithful, 1 not-applicable); latest: <summary>`.
Missing evidence, a `Divergent` verdict, or a fabricated evidence
note leaves the row byte-unchanged and exits `1` with the blocking
violation on stderr. After a flip the plan source is re-ingested, so
`canon query --kind task` agrees with the checkbox. An already-`[x]` row is an idempotent no-op. An
unknown `task_id` is reported, never silently ignored.

## Staging → promote

```bash
canon gate promote --repo .              # land every staged candidate
canon gate promote --repo . --dry-run    # preview only
```

Every well-formed record under `.canon/ledger/_staging/` is re-validated
with the same checks the gate applies, assigned a monotonic per-(role,
surface) `run_seq` — gap-free within one invocation, continuing from the
committed tier's own max — and moved into the committed ledger. A
malformed or unpartitionable candidate is refused: exit `1`, no `run_seq`
consumed, the staging file left in place for a reviewer to fix. `--dry-run`
prints the plan without writing or deleting anything.

## Installing the hook seam

```bash
canon gate install-hooks --repo .
```

Idempotent, diff-only: merges a hook entry into both
`.claude/settings.json` and `.codex/hooks.json`, additive only, never
touching an existing entry in the same matcher group. Running it twice
with no manual edits between reports "no diff" and writes nothing. When
neither file already invokes `canon gate`, it also emits
`.canon/scripts/canon-gate-pre-commit.sh` (advisory by default; set
`CANON_GATE_ADVISORY=0` to block the commit on a failing gate).

## Proving the gate itself

```bash
canon gate selftest
```

Runs the shipped fixture corpus — one fixture per failure class, all ten
including `false-success`, each a
deliberately broken corpus proving that class fires and only that class.
Run this after touching the gate's own code, before trusting any other
`canon gate check` run's green.

## Reading a violation

Every printed line is `<failure-class> <subject> — <detail>`. `<subject>`
is the artifact's own join-spine identity (`task_id` preferred, then
`scenario_id`, then `run_id`) — grep the ledger or `tasks.md` for it
directly, never guess.
