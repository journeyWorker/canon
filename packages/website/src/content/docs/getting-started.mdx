canon ships as **one Rust core behind an npm launcher**: prebuilt platform
binaries are npm `optionalDependencies`, and a thin JS shim picks the right
one. If you have [Bun](https://bun.sh), you already have everything you need.
The npm package is `@journeykit/canon`; the installed binary is still `canon`, so
`bun add -g @journeykit/canon` followed by plain `canon <cmd>` also works.

```bash
bunx @journeykit/canon --help
```

**Prebuilt:** macOS arm64 · Linux x64 (glibc) · Windows x64. Other
platforms (Intel Mac, musl/arm64 Linux, Windows arm64) build from source
with a local Rust toolchain
(`cargo build --release -p canon-cli`).

## See it in 5 minutes: a gate fail, then pass

Before wiring canon into a real repo, watch the trust spine work on a
throwaway demo. `canon demo` scaffolds a tiny evidence loop — no concepts
required up front.

```bash
mkdir canon-demo && cd canon-demo

bunx @journeykit/canon demo init      # scaffold a throwaway evidence loop
bunx @journeykit/canon gate check     # RED  — the gate refuses
bunx @journeykit/canon demo review   # record the reviewer's evidence
bunx @journeykit/canon gate check     # GREEN — the gate passes
```

The first `gate check` fails, naming the exact missing evidence:

```output
canon gate check: 1 violation(s)

uncovered-cell (1):
  uncovered-cell auth.login.01 — policy-required cell 'reviewer' has no matching-role evidence record
```

The `dev` voice recorded evidence for scenario `auth.login.01`, but
`policy.yaml` requires an independent `reviewer`. No reviewer evidence → the
cell is uncovered → the gate is red. `demo review` records that evidence, and
the same check turns green:

```output
canon gate check: clean (0 violations)
```

That red → green flip *is* canon: completion is gated on evidence that exists,
is attributed, and is fresh — never on a self-report. See
[Trust spine](/concepts/trust-spine/) for the full failure-class table.

**Done when:** the second `canon gate check` exits `0` with `clean (0 violations)`. Add `--json` to any command for the same result as `{ok, data, meta}`, with the next step in `meta.next`.

## Set up a repo

<Steps>

1. **Scaffold the config.** From your repo root:

   ```bash
   bunx @journeykit/canon init
   ```

   This writes a working `canon.yaml` skeleton — storage `tiers:`, record
   `routing:`, `specs:` with its default root `.canon/specs` (`.feature`
   files at `<root>/kind=feature/area=<area>/<surface>.feature`, authored
   and git-tracked), and a `plans:` section with `sources: []`.
   Canon's own changes live in `.canon/changes/` and need no entry there;
   its comments show how to list external plans you prepare (commented
   `openspec` and `superpowers` examples), which canon only reads. It also
   writes:

   - **`.canon/policy.yaml`**, a starter policy that turns `spec_coverage`
     on: every scenario needs evidence, every feature surface needs a
     `@case:failure` scenario, and work on a subject claimed done needs an
     independent review. That is the default `strict` level;
     `--policy standard` leaves out the review and `--policy light` also
     the failure case, keeping them as commented lines to uncomment when
     you raise the level. The first line, `# canon policy level: <level>`,
     names it, and `canon status` shows it. The gate grades the work
     against the policy, so a human approves it, in the same answer that
     approves a subject's brief, and the agent records that answer with one
     call, `canon brief approve --approver <the human> --note "<their words>"
     --relayed-via <the question tool>` (the record says an agent relayed it),
     which records both; until then `canon gate check` and `canon status` print an advisory.
   - **A canon block in `AGENTS.md`**, between `<!-- canon:begin -->` and
     `<!-- canon:end -->`. It tells any agent that features are managed
     with canon, lists the working loop, and points to `canon status` and
     the canon skill. The loop stops for a human once per scope: a new
     subject, or a change to an approved subject's scope, needs one answer
     approving the brief and the policy. Inside an approved scope the
     agent fixes, follows up, gets each change independently reviewed and
     ships without stopping. The file is created if absent; otherwise only
     the text between the markers is canon's. Markers count only as
     standalone lines outside code fences; a duplicate or unmatched marker
     is refused and nothing is written.
   - **The canon skill, for the harnesses you pick.** On a terminal,
     `init` asks which harnesses get it, with the ones whose `.claude`,
     `.codex`, `.omp` or `.pi` directory exists checked; `--providers
     claude,codex` (or `none`) answers without asking. Without a terminal
     or the flag it takes the detected ones, and with none detected it
     installs nothing and names `canon skills install --providers=<list>`.
     The answer is recorded as `skills: { providers: [...] }` in
     `canon.yaml`. `.agents` alone does not select Codex.

   `--no-agents-md` and `--no-policy` skip those two. `init` never
   overwrites an existing `canon.yaml` or `policy.yaml`; rerunning it only
   refreshes the `AGENTS.md` block. Validate an existing config any time
   with:

   ```bash
   bunx @journeykit/canon init --check
   ```

   Start a change under a subject with no config edits:

   ```bash
   bunx @journeykit/canon subject new auth --domain dev --title "Auth"
   bunx @journeykit/canon change new add-login --subject auth --title "Add login"
   ```

   `change new` writes `.canon/changes/add-login/brief.md` and adopts the
   change into the subject; it writes no `tasks.md` (that is an optional
   work note nothing gates on). The brief is a PRD skeleton in
   the request's language (`canon.yaml`'s `language:`, which `canon init --language ko` writes, overrides what `canon brief check` detects): intent,
   desired outcome, a user flow of steps `F1`, `F2`, …, step detail,
   acceptance, questions and assumptions, out of scope. The agent fills it
   in and runs `canon brief check` until it has no blockers and each prose
   advisory is fixed or waived with a reason, then shows it to the human with
   `canon brief show add-login --body` (the brief as it is, and its digest) and
   asks, in that language, with the harness's question tool (`ask` in omp,
   `AskUserQuestion` in Claude Code, otherwise in the chat). Only an explicit
   approval counts; a question or a condition is a revision request. When the
   human approves it, the agent records the answer with `canon brief approve
   add-login --approver <the human> --note "<their words>" --relayed-via <the
   question tool> --digest add-login=<the digest shown>`, which writes the
   `Approved:` line, bound to the brief's text and marked as relayed, and the
   policy approval together. `approval: { relay: deny }` in `canon.yaml`
   refuses that, and the human runs the command. A
   brief edited afterwards is no longer approved until the human answers
   again. Each scenario points at the step it proves
   (`canon scenario new --flow F1`), and `canon status` lists each step
   with its scenarios, flagging a step with no scenario or no failure case;
   `canon status` reads the approval in each change the subject answers
   for (tagged by its scenarios, approved, or a chore) and lists them in `briefs`, and asks for a human only when it
   is missing. Work that changes nothing a user can observe (a dependency,
   build or refactor change) is `canon change new <slug> --change-kind chore`, with a
   short brief and no new scenarios. A change from an external plan (an
   openspec `proposal.md` listed under `plans.sources`) gets its brief in
   `.canon/changes/<change>/brief.md` too, with a `Source: <path>` line
   pointing at the plan; canon never edits the plan. Fixes and follow-ups
   stay in the approved change; a new `canon change new` is a new scope
   that needs the human's approval.

2. **See the authoring surface.** Before writing any canon artifact, ask
   the repo what vocabulary and schemas it resolves to:

   ```bash
   bunx @journeykit/canon context
   ```

   This is a capability *query*, never validation — it always exits 0 and
   prints record kinds, enum domains, join-key grammars, and policy-derived
   requirements. Add `--json` for a machine-readable surface.

3. **Index your spec corpus.** If the repo keeps Gherkin `.feature` specs
   under a configured `specs.roots[]` entry:

   ```bash
   bunx @journeykit/canon format          # validate the corpus first
   bunx @journeykit/canon inventory sync   # materialize the scenario ledger index
   ```

4. **Ingest agent sessions.** Fold transcripts from Claude Code, Codex, and
   other registered agent CLIs into tiered storage — incrementally, via a
   per-source watermark:

   ```bash
   bunx @journeykit/canon ingest sessions
   bunx @journeykit/canon ingest sessions --watch   # keep polling
   ```

5. **Gate your work.** The trust spine checks coverage, the verdict ledger,
   and staleness — completion is evidence-gated, never self-reported:

   ```bash
   bunx @journeykit/canon gate check
   ```

6. **Read the room.** Generate the repo status report (generated, never
   edited) or open the local dashboard:

   ```bash
   bunx @journeykit/canon report
   bunx @journeykit/canon dashboard
   ```

</Steps>

**Done when:** `canon status` shows the subject's brief approved and every flow step with a scenario, and `canon gate check` exits `0`. `canon status` names what is missing, and `meta.next` the command to run.

## Record work: `--input`, `--rev`, `--json`

Every write command takes `--input`: its arguments as one JSON object (keys
are the option names in camelCase, plus `operands`), given inline, as a file
path, or as `-` for stdin. A JSON array or NDJSON is a batch: every element is
validated before anything is written. `canon schema <command> --json` prints
the input schema and an example.

```bash
canon scenario new auth.login.02 --title "Sign out"
canon evidence add --scenario auth.login.02 --class test-run --ref "npm test" --role implementer
```

The same calls as one batch, validated before anything is written:

```text
canon scenario new --input <JSON|FILE|->
canon evidence add --input <JSON|FILE|->
```

where the input is `[{"operands": ["auth.login.03"], "title": "Session expires"}, {"operands": ["auth.login.04"], "title": "Remember me"}]`.

A record that names code (`evidence add`, `review scenario`, `finding add`)
takes `--rev <git revision>`, default `HEAD`. Uncommitted code is allowed: the
record carries a `codeTree` and `worktreeDirty`, and a review survives the
commit as long as the code tree is the same. Outside git, or in a repo with no
commits, such a command refuses with `NO_COMMIT`.

**Done when:** `canon gate check` exits `0`, and `canon subject show <id>`
lists no uncovered scenario; both print the next step in `meta.next` when
something is left.

## For agent harnesses

The canon guide is not a set of files in your repo. It is built into the
binary and matches its version: an agent reads it with

```bash
canon skills show canon          # the core guide
canon skills show canon --full   # the core guide plus every reference
canon skills show role-reviewer  # one reference, by name
```

`canon skills install` writes only a **stub** `SKILL.md` per selected
provider: Claude gets `.claude/skills/canon/SKILL.md`, Codex gets
`.agents/skills/canon/SKILL.md` (Codex scans `.agents/skills`, never
`.codex/skills`), OMP gets `.omp/skills/canon/SKILL.md`, and Pi gets
`.pi/skills/canon/SKILL.md`. The stub carries the skill's frontmatter, so the
harness still discovers it, and one short body that sends the agent to
`canon skills show canon`. Nothing else is projected, so an upgrade never
leaves stale guide text in the repo. OMP/Pi are passive bundles; their
retrieve pre-dispatch script is a sidecar only, not a native hook.
`canon init` already installed the stub for the harnesses you picked.
`skills install`, `check` and `doctor` follow `canon.yaml`'s
`skills.providers`; a repo without that key (set up before 0.17) uses the
providers its install lock records, then the detected `.claude`, `.codex`,
`.omp` and `.pi` directories. Nothing undetected is ever added. Pass
`--providers` to change the list; install records it in `canon.yaml`:

```bash
# write the stub for all four providers and record the list
bunx @journeykit/canon skills install --providers=claude,codex,omp,pi

# inspect projections without writing
bunx @journeykit/canon skills check
bunx @journeykit/canon skills doctor

# surface role-scoped strategy memory before a task starts
bunx @journeykit/canon retrieve --for-role dev --regime "$(bunx @journeykit/canon regime show --role-segment dev --repo-name my-repo --area core --hash abcdef012345)"
```

`skills check` and `skills doctor` are read-only: `check` reports missing or
stale stubs, while `doctor` reports provider, drift, and legacy-remnant
diagnostics across all four managed roots without deleting user files. The
install lock records the canon version that wrote it, so after you upgrade
canon both say "installed by canon X, this canon is Y — run
`canon skills install`" until you reinstall. `doctor` also names a canon
projection left for a harness that is no longer selected (`stray:`, with the
`rm -r` that removes it), and other skills in the same provider roots whose
description claims build work, meaning one sentence pairs a build verb
(build, create, implement, …) with a build object (site, app, game, feature,
tool, service, …): if an agent picks one of those for build work, canon's
loop will not run. It only reports them.

**Done when:** `canon skills check` reports no missing or stale stub, and
`canon skills show canon` prints the guide.

## Upgrading from 0.27

0.28 changed the command grammar with no aliases: an old spelling is a usage
error whose hint names the replacement. To bring a 0.27 repo along, run

```bash
canon migrate
canon migrate --commit --plan-digest 0123456789abcdef
canon skills install
```

The first command only previews: it prints the `planDigest` and the effects
(moved spec roots, rewritten `canon.yaml`, hooks and scripts, ledger layout),
and changes nothing. The second applies exactly that plan, with the digest
from the preview in place of the sample value, and backs up each rewritten file
under `.canon/migrate-backup/`. The third replaces the old projected guide with
the stub. `canon status`, `canon gate check` and `canon context` warn on a 0.27
repo and put `canon migrate --json` first in `meta.next`.

**Done when:** `canon status` no longer warns about a 0.27 repo and `canon
gate check` runs clean or names real violations.

Strategies are distilled from your team's own verdicts, quarantined by
default, and activated only after paired evaluation plus policy-pinned SSH
approval — see [Strategy memory](/concepts/strategy-memory/) for the full
flywheel. This repository publishes no measured uplift result.

## Opting out

canon keeps its data under a single `.canon/` directory (with `canon.yaml` at
the repo root). Project-local skill projections additionally live under the
selected provider roots (`.claude`, `.agents`, `.omp`, and/or `.pi`). To back
out completely, delete `canon.yaml`, `.canon/`, and any selected skill roots
you no longer want — that's the whole project-local footprint.
