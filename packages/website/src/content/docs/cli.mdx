`canon` is a single binary with one subcommand per capability. Run `canon
<command> --help` (or `canon <command> <subcommand> --help`) for the
authoritative flag list at any time — this page mirrors that output.

Most subcommands accept `--repo <dir>` (default `.`): the literal `.` default
walks `cwd`'s ancestors for the nearest `canon.yaml`; any other explicit path
is used as-is, no walk. Several also accept `--json` for machine-readable
output instead of the default human-readable table/summary.

## Try it

A self-contained first-run demo — see a gate fail, add evidence, watch it pass.
No prior setup required.

| Command | What it does |
|---|---|
| `canon demo init [--repo <dir>]` | Scaffold a throwaway evidence loop: the real `canon init` config, a `reviewer`-requiring `policy.yaml`, and one seeded `dev` evidence record — leaving `canon gate check` red with `uncovered-cell auth.login.01`. Refuses to overwrite an existing `canon.yaml`. |
| `canon demo attest [--repo <dir>]` | Record the missing independent-`reviewer` evidence for the demo scenario, turning the same `canon gate check` green. |

## Setup

Scaffold a repo's config, inspect what it resolves to, and materialize the
single provider-aware `canon` companion skill. Canon's CLI commands remain
explicit; the skill only routes an agent to lazy references.

| Command | Description |
|---|---|
| `canon init [--repo <dir>]` | Scaffold a fresh, working `canon.yaml` (`tiers:`/`routing:`/`specs:`/`plans:`) at `<repo>/canon.yaml`. Refuses to overwrite an existing file. Prints `canon skills install` as the next step. |
| `canon init --check-config [--repo <dir>]` | Read-only validate an existing `canon.yaml`, chaining the same strict loaders `inventory sync`/`ingest plans`/`tier age` use. |
| `canon context [--repo <dir>] [--json]` | Emit the resolved authoring surface: record kinds + envelope fields, enum domains, join-key grammars, partition layout, policy-derived requirements, capability version. A capability *query* — always exits 0, even when `fmt --check`/`gate` would report diagnostics. |
| `canon context-pack create --manifest <repo-relative.json> [--repo <dir>] [--json]` | Create an immutable, content-addressed context snapshot from the explicitly selected files in a repository-local JSON manifest. Concise output prints only the pack id; `--json` prints manifest metadata and digests. |
| `canon context-pack show <id> [--repo <dir>] [--json]` | Verify and show a stored pack. `show` rechecks the manifest and every immutable content object before returning; concise output does not include captured bytes. |
| `canon context-pack verify <id> [--repo <dir>] [--json]` | Verify a pack without returning captured content. Exits nonzero when the pack is missing, stale, or tampered. |
| `canon adapter validate --response <path> [--repo <dir>] [--json]` | Read-only validation of a provider-neutral protocol-v1 response. Core fields are strict (`run_id`, provider/model, context-pack id, status, capabilities, safe evidence refs, and nonnegative ordered telemetry); provider data is opaque under `extensions`. JSON output is a redacted normalized summary with extension key names only. `--repo` optionally checks the context pack join; no provider is executed and capability declarations are not enforcement. |
| `canon prompt register --name <name> --version <version> --manifest <repo-relative.json> [--repo <dir>] [--json]` | Register a versioned prompt bundle from an explicit repository-local manifest in the immutable content registry. |
| `canon prompt show --name <name> --version <version> [--repo <dir>] [--json]` | Select and verify a registered prompt bundle version; default output is concise metadata, while `--json` includes snapshot metadata and digests. |
| `canon skills install [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Project one canonical `canon` skill. Claude receives `.claude/skills/canon/SKILL.md`; Codex receives `.agents/skills/canon/SKILL.md` (the directory Codex scans for skills); OMP receives `.omp/skills/canon/SKILL.md`; and Pi receives `.pi/skills/canon/SKILL.md`. Every selected provider receives lazy `reference/**` and `scripts/**` sidecars. OMP/Pi are project-local passive bundles; their retrieve pre-dispatch script is a sidecar, not a native hook. Provider selection is deterministic; absent selection detects `.claude`, `.agents` or `.codex` (Codex), `.omp`, and `.pi`, and defaults to Claude+Codex when none exists. A legacy `.codex/skills/canon.md` + `.codex/skills/canon/**` projection from canon 0.13.0 or earlier is removed file by file when its bytes still match the install lock; edited or user files stay, and `.codex/skills` is removed only if it ends up empty. |
| `canon skills check [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Read-only report of missing or stale canonical projections, the target-owned content manifest, and any leftover legacy `.codex/skills` Codex projection (with its fix command); exits 1 on any of them. |
| `canon skills doctor [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Human-readable provider, drift, and legacy-remnant diagnostics across all four managed roots and the legacy `.codex/skills` root, naming the fix command for a legacy Codex projection. It never deletes user files. |

Canon contributors may use the legacy `canon skills install --source
canon/skills-dev --target .` materializer; it is not part of the consumer
installation flow.

## Subjects

Author and drive the durable product unit — canon's 13th record kind —
through its lifecycle, and adopt imported plan changes under it. See
[The Canon Concept](/concepts/canon/#subjects) for the subject-write-first
loop; "feature docs" always means Gherkin `.feature` files, a "subject"
is the management record.

| Command | Description |
|---|---|
| `canon subject new <id> --domain <d> --title <t> [--summary <s>] [--owner-role <r>] [--repo <dir>] [--json]` | Author a `Subject` (kebab-slug `<id>` is the durable `subject_id` join key). `--domain` is a vocabulary-defined kebab slug — base set `planning`/`design`/`dev`/`data`/`test`, extended per-repo via `.canon/vocab`. Starts at status `proposed`; `--owner-role` defaults to `implementer`. Envelope + policy validated at write. |
| `canon subject adopt <change_id> --subject <id> [--repo <dir>] [--json]` | Link an imported plan `Change` (from `canon ingest plans`) to a `Subject`: stamps `Change.subject_id` and appends to the subject's `change_ids`. |
| `canon subject status <id> <state> [--override-reason <text>] [--actor-id <id>] [--repo <dir>] [--json]` | Policy-gated transition along `proposed → specced → building → verifying → shipped` (plus any → `retired`). `verifying → shipped` additionally requires the subject to own at least one scenario — one whose `@subject:<id>` tag `canon inventory sync` has indexed — and every owned scenario to carry a latest non-Divergent verdict; a violation prints by failure class, exits `1`, and leaves the record unchanged (fail closed). With `spec_coverage.require_review` set, it also prints on stderr which review checks it ran or skipped, and a move into a `require_review.scope` status with gaps (`unreviewed-promotion`, `open-blocker`) is refused the same way. `--override-reason "<one line>"` waives only those two classes — never ship-gate verdict or case gaps — and records `status_override` (`to`, `reason`, `waived`: the exact `{class, subject}` violations it let through, `actor` from `--actor-id`, default `canon`) on the new record. A gap it did not record, such as a blocker raised later, still fails the gate; a blank or multi-line reason exits `2`. The waiver clears on the subject's next status write. Without `require_review`, nothing changes. |

## Corpus

Validate and grow a Gherkin `.feature` spec corpus.

| Command | Description |
|---|---|
| `canon format <ROOT> [--repo <dir>]` (alias `canon fmt`) | Validate a corpus root (e.g. `spec/`) against the artifact-family schemas + layout descriptors. Validating is the only mode, so `--check` is now the default and is accepted only for compatibility. |
| `canon inventory sync [--repo <dir>] [--spec-root <dir>]` | Validate each configured `specs.roots[]` entry with `canon-fmt`, then materialize one `Scenario` ledger-index record per `(project_id, scenario_id)`. `--spec-root` overrides `canon.yaml` for one ad hoc root. |
| `canon scenario new <TAG> --title <label> [--subject <id>] [--lane <v>] [--case <v>] [--actor <id>] [--feature <path>] [--repo <dir>]` | Append (creating if absent) a `.feature` stub for a `<area>.<surface>.<nn>` tag: a `# canon:` provenance line directly above the tags, then `@subject:<id>` / `@lane:<v>` / `@case:<v>` if given, then the id tag and header. `--actor` (or `CANON_ACTOR`) names the provenance actor, default `canon-scaffold`; `--lane` and `--case` are checked against the repo's `lane`/`case` vocabularies. Writes no ledger record. |
| `canon feature new <SURFACE> --title <label> [--actor <id>] [--repo <dir>]` | Scaffold a fresh, zero-scenario `.feature` file for a not-yet-started `<area>.<surface>`. Fails loud rather than overwriting an existing file. |

## Ingest

Fold agent-CLI sessions, evidence artifacts, and foreign plan dialects into
tiered storage.

| Command | Description |
|---|---|
| `canon ingest sessions [--watch] [--interval-secs <n>] [--home <dir>] [--canon-yaml <path>] [--full] [--all-workspaces]` | Scan every registered session-store adapter (`omp`/`pi`, Claude Code, Codex, Hermes), normalize into `Session`/`Run`/`Event` records — including `user_directive` events captured from user turns — persist through canon-store. Defaults to THIS PROJECT's sessions (main worktree + every linked `git worktree` root); `--all-workspaces` restores the machine-wide scan. `--watch` polls (default 30s) with a per-FILE watermark so only changed transcripts reparse; `--full` ignores the watermark. |
| `canon ingest artifacts [--watch] [--interval-secs <n>] [--repo <dir>] [--json]` | Run the artifact/verdict half of the join spine: ledger/divergence/openspec-task path adapters plus the handoff records-source, derive verdicts, fold into regime-keyed trajectories, persist via canon-learn. Unlike `sessions`, a repeated `--watch` pass is not yet write-idempotent. |
| `canon ingest plans [--dialect <name> --source <dir>] [--repo <dir>] [--json]` | Import one plan dialect — `openspec` change dirs, or `superpowers` writing-plans-shaped docs (s30: `# <title>`/`**Goal:**`/`### Task N:` sections, a task done iff every checkbox in its section is checked) — into canon-model's Change/Task records, both keyed `task_id = <change_id>#<n>` through the same join. No `--watch` — plans are operator-pulled. `--dialect`/`--source` bypass `canon.yaml`'s `plans:` section for a one-shot import; both are required together. |

## Trust

The trust-spine gate, plus the native `Review`/`Divergence` verdict
producers it reads.

| Command | Description |
|---|---|
| `canon gate check [--repo <dir>] [--release]` | Run the coverage/ledger/staleness/spec-coverage/bound-artifact/trust-ladder check set, printing violations by failure class (nine: `uncovered-cell`, `unreviewed-promotion`, `trust-below-required`, `stale-evidence`, `malformed-evidence`, `flagged`, `unevidenced-flip`, `fabricated-evidence`, `open-blocker`). With the opt-in `spec_coverage.require_review`, in-scope scenarios without an independent `Review` are `unreviewed-promotion` and open `blocker` findings on adopted changes are `open-blocker`; gaps waived by `canon subject status --override-reason` print afterwards as `review waivers:` advisories without failing. Exit `0` clean, `1` gate-red, `2` usage/load failure. `--release` additionally engages the release-scoped trust check. A file bound to a latest evidence record must still be provable: from its stored blob, or (records from before 0.14) from a working-tree file with the recorded digest, which prints an `evidence artifacts:` advisory naming `canon evidence vault`; otherwise it is `stale-evidence`. |
| `canon gate task <TASK_ID> [--repo <dir>]` | Evidence-gated checkbox flip for one plan `task_id` (`<change_id>#<n>`). Fails closed — the row stays unflipped — on missing, malformed, or fabricated evidence. The row's note sums up every record bound to the task (`2 evidence records (2 faithful); latest: <summary>`), and the plan source is re-ingested so `canon query --kind task` agrees. |
| `canon gate promote [--repo <dir>] [--dry-run]` | Promote `_staging/` evidence records to the committed ledger, assigning a monotonic per-(role, surface) `run_seq`. `--dry-run` prints the plan without writing. |
| `canon gate install-hooks [--repo <dir>] [--event <name>] [--matcher <m>] [--command <cmd>] [--timeout <secs>]` | Idempotent, diff-only hook-seam install into `.claude/settings.json`/`.codex/hooks.json`, plus a generic pre-commit script. Defaults: `--event PreToolUse`, `--command "canon gate task"`, `--timeout 30`. |
| `canon gate selftest` | Run the shipped fixture corpus: every `FAILURE_CLASSES` string (all nine, including `open-blocker`) proven to fire, exact-set-match against `expected_failures.txt`. Takes no `--repo`. |
| `canon evidence add --task <id> --kind <k> --ref <r> --role <role> [--surface-ref <path-or-effect>] [--verdict <v>] [--summary <s>] [--command-result <out>] [--scenario-id <id>] [--run-id <ulid>] [--artifact <path>] [--report <junit\|cucumber>:<path>] [--report-case <name>]... [--max-artifact-mib <n>] [--repo <dir>]` | Stage one attributed `EvidenceRecord` for a plan task, then commit it with `canon gate promote` and spend it with `canon gate task`. `--surface-ref` persists a validated path or `effect:<kebab-slug>` risk binding, but remains attestation input rather than proof of changed paths. `--summary` is allowed with or without `--task` and scanned for fabrication markers; a task's flipped row shows the latest one; a line break in it is refused, because one would forge a second checked row. Risk approvals count only with a detached SSH signature verified against policy-pinned `approval.allowed_signers` and `--approval-role human`; `CANON_ACTOR`, caller text, and agent roles are not counted. **Experimental:** `--artifact` binds any repository file by sha256 and `--report` parses a JUnit/Cucumber report, recording the scenario's matched case and outcome (a `faithful` verdict over a failed case is refused); canon never runs the test. `--scenario-id` alone (with `--project-id`) attests a scenario instead of a task; a record with both answers both. Every report case carrying the scenario id is bound, `--report-case` (repeatable) adds more, and any failed bound case refuses `faithful`. Bound files are copied into `.canon/artifacts/sha256/<hex>` (tracked; commit them); a file over 25 MiB is refused unless `--max-artifact-mib` raises the limit. |
| `canon evidence vault [--max-artifact-mib <n>] [--repo <dir>]` | Store the bound files of existing evidence records (written before 0.14) in `.canon/artifacts/sha256/`: each file whose working-tree bytes still match the recorded digest is copied in, everything else is listed as not stored with both digests. Exit `0` when it ran, `2` on a ledger read or write failure. |
| `canon finding add --change-id <id> --round <n> --seq <n> --severity <s> --reviewer <name> --summary <s> [--disposition <d>] [--reviewed-sha <sha>] [--resolution-sha <sha>] [--introduced-by <sha>] [--file-ref <path:lines>] [--repo <dir>]` | Stage one code-review finding as a durable record, so a release note's count is read rather than remembered. `--seq` is required and a collision is refused. `fixed` requires `--resolution-sha`, and only `fixed` may carry one. |
| `canon finding close --change-id <id> --round <n> --seq <n> --disposition <d> [--resolution-sha <sha>] [--repo <dir>]` | Move an already-committed finding's disposition. Append-only: this writes a superseding record rather than editing history, so the round it was raised in is preserved. Reopening is a real transition. |
| `canon review add --project-id <id> --scenario-id <id> --reviewer <name> --pin <pin> --role <role> --upstream-ref <ref>` (or `--original-spec-ref <ref>`) `[--actor-id <id>] [--repo <dir>]` | Write one native, attributed `Review` record. Exactly one of `--upstream-ref`/`--original-spec-ref` is required — both or neither refuses the write. |
| `canon divergence stage --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --role <role> [--status <status>] [--reason <r>] [--expiry <e>] [--round <n>] [--detail <d>] [--repo <dir>]` | Write one unordered staging candidate carrying no `run_seq`; `--status` accepts `open`, `still-divergent`, `resolved`, or `deferred` (`deferred` additionally requires `--reason`/`--expiry`). `canon divergence promote` assigns `run_seq` later. |
| `canon divergence promote [--repo <dir>] [--dry-run]` | Batch-promote every currently-staged `Divergence` candidate, assigning each a monotonic `run_seq` within its `(project_id, role, surface)` partition. |
| `canon divergence resolve --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --role <role> [--round <n>] [--detail <d>] [--repo <dir>]` | Direct-commit a `Resolved` candidate — never touches the staging directory. |
| `canon divergence defer --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --reason <r> --expiry <e> --role <role> [--round <n>] [--repo <dir>]` | Direct-commit a `Deferred { reason, expiry }` candidate — never touches the staging directory. |
| `canon divergence status [--repo <dir>] [--as-of <date>]` | The current-state divergence burn-down view. `--as-of` governs `Deferred` expiry evaluation; defaults to now. |

## Memory

Distilled strategies, role+regime-scoped retrieval, and the dispatch-time
write seam.

| Command | Description |
|---|---|
| `canon learn promote <STRATEGY_ID> [--repo <dir>] [--evaluation <path> --approval <path>] [--signature <path>] [--dry-run]` | Activate one **quarantined** `StrategyItem` into `.canon/strategies/<role>/<id>.md`. The configured `occurrence`/paired-`crn` gate is only eligibility; activation also requires a valid paired `PromotionEvaluation` and an approval declared `human`, signed with an SSH detached signature. The evaluation requires non-empty paired baseline/candidate result digests, finite `pairs`/positive `uplift`/zero `regressions`, matching integrity/provenance, and a passing decision. The verifier uses policy-pinned `approval.allowed_signers` with `ssh-keygen -Y verify`; `--evaluation` and `--approval` are required together, and there is no `--force`. `--dry-run` does not activate. |
| `canon learn approve <STRATEGY_ID> --evaluation <path> --principal <id> [--repo <dir>] [--json]` | Validate the quarantined candidate/evaluation and print an unsigned, domain-separated `canon-learning-approval-v1` payload (`strategy:<id>`, evaluation digest, RFC3339 timestamp, `payload_hex`) for an external SSH signer. It never reads a private key or sets `verified`. |
| `canon learn request <STRATEGY_ID> --evaluation <path> --principal <id> [--repo <dir>] [--json]` | Exact alias of `learn approve`; emits the same unsigned approval payload. |
| `canon learn rollback <STRATEGY_ID> --reason <text> --actor <id> --signature-file <path> --approved-at <RFC3339> [--contradicting-trajectory-id <id>] [--repo <dir>]` | Authenticated operator rollback, distinct from ordinary contradiction demotion. Verifies an armored SSH signature over the rollback-bound payload against policy-pinned `approval.allowed_signers`, records provenance, and sets lifecycle `rolled_back`. |
| `canon retrieve --role <role> (--regime <regime_key> \| --domain <d> [--subject <id>]) [--k <n>] [--repo <dir>] [--json]` | Role+regime-scoped strategy retrieval. Give `--regime` directly, or derive it from `--domain`/`--subject` — retrieval tries area candidates `<domain>-<subject_id>` then `<domain>` in that fallback order. `--role` must equal the regime's leading segment (exit `2` on mismatch). Fail-soft: always exits `0` once that holds; a store outage degrades to an empty list. Quarantined/rejected/rolled-back/demoted rows are excluded; legacy `lifecycle: null` rows remain readable but carry no current paired-evaluation or SSH-approval provenance and are not measured-uplift evidence. |
| `canon dispatch begin --role <role> --regime <regime_key> [--context-manifest <repo-relative.json>] [--prompt-bundle <name@version>] [--agent-id <id>] [--repo <dir>] [--json]` | Mint a `Run` (status `Running`), retrieve guidance for `--role`/`--regime`, and record an immutable ContextPack lineage. An explicit context manifest selects the exact docs/tools/prompts captured; `--prompt-bundle` selects and verifies a registered immutable prompt bundle. Missing, unsafe, or tampered selections are rejected before any run id or manifest is written. |
| `canon regime-key --role <r> --repo <r> --area <a> --hash <h>` | Serialize + validate one canonical `regime_key` (`<role>/<repo>/<area>/<hash>`) from raw segments — the shell-facing counterpart to the Rust serializer every write/read path shares. Prints the key and exits `0`; exits `2` on a malformed result. |

## Surface

Read the current state: reports, the dashboard, ad hoc queries, tier
maintenance, plugin overlays, and self-checks.

| Command | Description |
|---|---|
| `canon report [--repo <dir>] [--check] [--snapshot <dir>]` | Generate the markdown status report (default), byte-diff it against the committed copy (`--check`, exit `1` on drift), or export panel marts to Parquet + `manifest.json` (`--snapshot`, wins if both given). |
| `canon dashboard [--repo <dir>] [--snapshot <dir>] [--port <n>]` | Serve the built dashboard app locally against a snapshot. Default port `4173`; an omitted `--snapshot` regenerates fresh at `.canon/dashboard-snapshot` on every run. |
| `canon query --kind <kind> [--since <ts>] [--repo <dir>] [--canon-yaml <path>] [--json] [--plugin <id>] [--change-id <id>] [--domain <d>] [--status <s>] [--include-sensitive]` | Fan out a record kind's read across every tier it may live in and merge by `at`; every invocation is recorded in `.canon/audit/access.jsonl`. `--include-sensitive` requires `.canon/policy.yaml` `query.allow_sensitive: true`. |
| `canon purge --kind &lt;session|run|event|trajectory&gt; --before &lt;RFC3339&gt; [--repo &lt;dir&gt;] [--dry-run] [--json]` | Purge matching records from the routed rung and every aging destination, including historical versions. Apply mode preflights all destinations; dry-run is non-destructive. It never deletes source transcripts or Git history. |
| `canon export --kind <kind> [--before <RFC3339>] [--after <RFC3339>] [--out <file>] [--repo <dir>] [--json] [--include-sensitive]` | Write a versioned, redacted manifest with counts and content digests. Sensitive bodies require explicit policy and flag; newly-created files are mode `0600`. |
| `canon plugin sync <PLUGIN_ID> [--repo <dir>] [--spec-root <dir>]` | Resolve `<plugin-id>`'s manifest-declared overlay(s), hand each to its registered source, write every candidate through the validate-then-write pipeline. |
| `canon selftest [--json]` | Run every registered crate's fixture-corpus self-test and diff against its EXPECTED oracle. Additive alongside `canon gate selftest`. |
