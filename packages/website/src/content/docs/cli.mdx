`canon` is a single binary with one subcommand per capability. Run `canon
<command> --help` (or `canon <command> <subcommand> --help`) for the
authoritative flag list at any time — this page mirrors that output.

Most subcommands accept `--repo <dir>`. Absent or `.`, it is the nearest
ancestor of `cwd` with a `canon.yaml`; any other explicit path is that
directory as given, no walk. A command that needs canon state and finds no
`canon.yaml` there refuses with `CONFIG_REQUIRED` (exit `2`, `--repo` named,
the hint naming `canon init` and the directory searched) instead of reporting
an empty repo as clean. `init`, `migrate`, `demo`, `context`, `regime show`,
`schema`, `skills show`, `adapter`, `context-pack` and `prompt` run without one. Every command accepts `--json` for one
machine-readable document on stdout instead of the default human-readable
table/summary; see [Driving canon from an agent](#driving-canon-from-an-agent).

## Driving canon from an agent

Every command shares one machine contract, so an agent never has to scrape
`--help` or human text. The grammar is one spec, `docs/cli/canon.cli.json`;
the parser, `canon schema`, the tables above and the guide are generated from
it.

**Discover with `canon schema`.** The first line of every `--help` points at it. One call describes the whole CLI, a group or one command:

```bash
canon schema --json               # the tree: every group and command, its effect, the shared options, and the level canon claims
canon schema finding --json       # one group: its commands
canon schema purge --json         # one command: its call surface
canon schema evidence add --schemas --json  # its JSON Schemas, the --input document schema (Input) and the validators' rejects
canon schema --as reviewer --json # the tree of one role's commands (`x-canon.as` names the role)
canon schema --errors --json      # every stable error code, its meaning and its reasons
canon schema --warnings --json    # every warning code (meta.warnings) and its meaning
```

`data.kind` says which document came back. The `tree` has `level` (`L2`), `options`
and `commands`. `options` defines once every option that two or more commands
define identically (`--repo`, `--as`, `--actor`, `--session`, `--role`, …); a command
names such an option instead of repeating it. `commands` lists every group and command
once, a group before its commands, each with `command`, `summary` and, for a command,
`effect` and `x-canon.roles`, for a group `kind: "group"`; there is no `path`. `x-canon.roles`
is the string `"all"` for a command all four roles use, and otherwise an array of role names
(the empty array is a command only a human runs); the root of the tree says so in
`x-canon.rolesForm`. A `group`
has `command`, `summary` and its direct `commands`. A `command` document is the call
surface and nothing more: `summary`, `effect` (`read`, `write` or `destructive`),
`idempotency` (not for a read), `effectNote`, `operands`, `options` (a name that
points to a tree option, or an option object with `name`, `valueName`, `valueType`,
`required`, `repeatable`, a typed `default`, `possibleValues` and, where they apply,
`defaultNote`, `env`, `flagOnly`, `short`), `constraints`, `validators`, `errors`,
`outputs`, `input` and `examples`. A member equal to its default is absent: `required`,
`repeatable`, `flagOnly` false, a null `default`, `valueType` `string`, an empty list.
The `valueType` is `switch`, `count`, `string`, `integer`, `number`, `path`, `enum` or
`json`; an option that cannot be given in an `--input` document has `flagOnly: true`.
What every command accepts is not listed: `--json`; `--input` when the command has
`input`; `--fields` when an output has `fields`. The codes `USAGE` (with canon's finer
`*_INVALID` and `*_REQUIRED` argument codes), `INTERNAL`, `INPUT_INVALID`,
`INPUT_CONFLICT`, `INPUT_TOO_LARGE`, `BATCH_INCOMPLETE`, `PLAN_STALE` (with `--commit`)
and `CURSOR_INVALID` (with `--cursor`) are implied and not in `errors`. `--commit` and
`--plan-digest` are listed, by name, on exactly the commands that offer them (`purge`,
`artifacts move`, `artifacts prune`, `migrate`, `ledger compact`, `tier age`), so the document says
whether a bare run previews. Each output names its JSON Schema (`schemaRef`,
`#/schemas/<Name>`) and says `batch: true` for the report of an array or NDJSON
`--input`; `input` has `argumentsRef`, the schema of the arguments after the merge,
and one complete `example`. `examples` are complete calls that end with `--json` and
run as written. The schemas are not in the command document: `canon schema <command>
--schemas --json` answers `kind: "schemas"` with `command`, `schemas` (every schema the
document's refs name, and `Input`, the schema of one `--input` document: the keys it
accepts, no `required`) and `rejects` (one list per validator, in order, what that
validator refuses). `--schemas` needs a command path: without one, with a group, or
with `--errors`, `--error`, `--warnings` or `--warning` it is `USAGE` with `field`
`--schemas`.

**Read the guide from the binary.** `canon skills show canon` prints the
core guide; `canon skills show canon --full` adds every reference;
`canon skills show <name>` prints one reference (`role-reviewer`,
`canon-gate`, `brief-polish`, …). The `SKILL.md` that `canon skills install`
writes into a repo is only a stub that sends the agent here, so the guide
always matches the installed binary.

**`--json` envelope.** stdout is exactly one JSON document, nothing goes to
stderr: `{"ok": true, "data": …, "meta": …}` on success and
`{"ok": false, "error": …, "meta": …}` on failure (an exit 1 partial report
also carries `data`). The envelope follows atip/1. `meta` carries
`schemaVersion`, `tool` (`canon`), `toolVersion`, `contract` (`atip/1`),
`contractVersion` (`1.5`, on every envelope) and the
resolved `command`, plus `output` (the report name, for a command that
declares several), `context` (`{repo}`), `next`, `warnings`, `coverage`, `page`
and `x-canon` (canon-only extras) where they apply. A member with no value is
absent, never `null` and never `[]`. `--json` is accepted anywhere before `--`,
including at the root and on a group (`canon --json`, `canon finding --json`);
`--repo` and `--as` are accepted there too and do nothing on a group:
a group with only those options answers `COMMAND_REQUIRED`, not `USAGE`.
A reader keeps the members it knows and ignores the rest: a later canon adds
members, and a value of a closed set it has not seen is one item to leave out.

```json
{
  "ok": true,
  "data": { "unchanged": true, "…": "…" },
  "meta": {
    "schemaVersion": "1.0",
    "tool": "canon",
    "toolVersion": "0.34.0",
    "contract": "atip/1",
    "contractVersion": "1.5",
    "command": "evidence add",
    "context": { "repo": "." },
    "next": [
      {
        "command": "canon gate check --json",
        "argv": ["gate", "check", "--json"],
        "reason": "check the gate once every scenario has evidence",
        "x-canon": { "actor": "agent", "role": "reviewer" }
      }
    ]
  }
}
```

**Errors.** Every failure prints `canon: CODE: message` as the first stderr
line, then indented `field:`, `expected:` and `hint:` lines; in text mode
stdout stays empty. With `--json`, `error` is `{code, message, retryable}`,
plus `reason` (which of the situations registered under the code this is),
`hint` (one command line that starts with `canon`, the same with
`<PLACEHOLDER>`s, or one sentence), `field` (the option at fault), `expected` (its valid values),
`received` (what was given, `""` for an empty value) and `suggestions` when
canon can name them; `retryable` is always present, the rest are absent
otherwise. A `USAGE` that cannot name an argument has no `field` and its `hint` is
`canon schema <command> --json`. Codes are stable strings; `canon schema
--error <CODE>` explains one with its reasons, and a code that is only a
warning is explained by `canon schema --warning <CODE>`. A
command-line parse error is `USAGE`, an unknown command is `UNKNOWN_COMMAND`
(`expected` lists the valid words at that level), a call with no command at all
(`canon --json`, `canon finding --json`) is `COMMAND_REQUIRED`, and a panic in
JSON mode is `INTERNAL`. An old 0.27 spelling is a usage error whose hint names
the replacement. Only exits `0`, `1` and `2` exist, and each code's exit is the
one in its row of `canon schema --errors --json`: `2` means canon refused to
run because the invocation or its inputs are wrong and fixable (nothing was
written); `1` means it ran and the answer is negative or incomplete (an
operational failure, a blocking finding, an unverifiable check).

**`--input` for writes.** Every write command takes `--input`: its arguments
as one JSON object, inline, as a file path, or `-` for stdin. Keys are the
option names in camelCase, and `operands` is an array. A JSON array or NDJSON
is a batch: it is validated whole before anything is written, and the report
has one entry per element in `data.items[]` (`written`, `unchanged`, `failed`
or `skipped`); a batch where an element failed is `BATCH_INCOMPLETE` (exit 1).
An input canon cannot use is `INPUT_INVALID` with a `reason`:
`UNREADABLE` (a file that cannot be read), `STDIN_TTY` (`-` on a terminal), `EMPTY`,
`NOT_JSON`, `NOT_OBJECT`, `BATCH_UNSUPPORTED` (a batch the command does not
take), and for a document that breaks its schema (`field` is a pointer) `UNKNOWN_KEY`,
`FLAG_ONLY_KEY` or `INVALID_VALUE`; a source over the limits is `INPUT_TOO_LARGE`
with `TOO_MANY_BYTES` or `TOO_MANY_ITEMS`; `-` together with another stdin
reader is `USAGE` with `field` `--input`. `canon schema <command> --json` shows
the input example, and `canon schema <command> --schemas --json` the input schema (`Input`).

```text
canon evidence add --input <JSON|FILE|->
canon scenario new --input <JSON|FILE|->
canon finding add --input <JSON|FILE|->
```

**Revisions.** A command that records code takes `--rev` (any git revision,
default `HEAD`); the finding commands add `--resolution-rev` and
`--introduced-rev`. Uncommitted code is recorded too, with a `codeTree` and
`worktreeDirty`, and a review survives the commit when the code tree is the
same. Outside git, or with no commit, the command refuses with `COMMIT_REQUIRED`.

**Paging and fields.** `canon query`, `canon finding list`,
`canon divergence list` and `canon export` return at most `--limit`
records (default 100). `--all` returns everything; `--cursor <nextCursor>`
continues. `--json` adds `meta.page` = `{returned, total, nextCursor}`: a
`nextCursor` means more records follow, and `meta.next`
holds the call's explicit arguments plus `--cursor=<nextCursor>`. A cursor holds only for the
call that issued it, the value `CANON_ROLE` gave `--as` included: change `--limit`, `--all`, `--fields` or `--json` and nothing else,
or the call is `CURSOR_INVALID` with `error.reason` `ARGUMENTS_CHANGED`
(`FOREIGN`: not a cursor of this command, or one an older canon issued; `EXPIRED`: the record it points after
is gone). `--limit`, `--cursor`, `--all` and `--fields` are flags, never `--input` document keys (`FLAG_ONLY_KEY`). `canon query`, `canon finding list`, `canon divergence list`,
`canon export`, `canon status` and `canon context` also take `--fields a,b,c`
to project records: the paths `canon schema <command> --json` lists under
`outputs[].fields`, each spelled as the answer spells it (a path into a list is
`name[]`, a key that is not an identifier is `["the-key"]`). The answer's
`meta.fields` lists what was kept; an unknown path is `USAGE` with `field`
`--fields` and `expected` listing the selectable paths.

**Search and trace.** `canon search "<text>"` finds records, brief sections and
flow steps, and scenario text, and lists each hit with its neighbors in the
record graph (`data.hits[]`, `data.neighbors[]`, `data.edges[]`, `data.counts`,
`data.index`). `--kind` (repeatable) keeps hits of those kinds, `--expand <N>`
sets the hops (default 1) and `--limit <N>` the hits (default 20, no next page).
Korean is found from three characters; a shorter text is found as a part of a
node's text, in id order. The text is read as typed. An empty text is exit 2
(`SEARCH_QUERY_REQUIRED`); no match is exit 0 with empty `hits`. A reference no
committed source holds is a neighbor with `placeholder: true`, never an error.
`canon trace <finding key|review id|sha>` follows the review → finding → fix →
re-review → evidence chain of one loop in time order (`data.chain[]`: time, id,
kind, role, sha, edges), the archive's earlier versions included; an id no record
says, an ambiguous sha prefix or any other operand is exit 2 and the message
names the three shapes. Both read a derived index, `.canon/index/search.db`,
and first rebuild it in full when an input changed (records of the ledger and
this worktree's sqlite hot store, briefs, `.feature` files). It is gitignored
(`canon init` adds the line; until then the commands warn), never a source of
records, and deleting it changes nothing but `data.index.rebuilt`. Staged
records and those in postgres or an object store are not read; `data.index.unreadStores`
names the stores.

**`meta.next` after a write.** A write that succeeds names the next step
itself, so an agent does not call `canon status` just to find it: `--json`
adds `meta.next` (`[{command, argv, reason, x-canon}]`, at most five;
`data.nextOmitted` counts the rest). `argv` is the command without the
executable and carries `--json` when the call was in JSON mode; the `actor` and
`role` of a step sit in `x-canon`. Human output ends with one
`next: <command> — <reason>` line. These are `canon status`'s own steps,
narrowed to the subject the write touched; `x-canon.actor: human` marks a step
only a human takes. canon never runs a step.

**Retry safety.** Repeating `evidence add` or `review scenario` with identical
input returns the existing record with `data.unchanged: true` (a report that
is a stored record verbatim carries it as `meta.x-canon.unchanged`).

### Roles

An agent can declare a role: `planner`, `implementer`, `reviewer` or
`orchestrator`. Pass `--as <role>` or set `CANON_ROLE=<role>` (the flag wins);
an unknown value is `ROLE_INVALID`. A role is guidance, not enforcement:
`canon schema` lists the role's commands, `canon status` and `meta.next` keep
only the role's steps and count the rest in `data.waitingOn` (the orchestrator also
sees the human's steps), and `--role` on `evidence add` and `review scenario`
defaults to it. Unset, every command behaves as before. `CANON_ROLE` never
filters or fails `schema`, `context` or `skills show` (a bad value is only a
warning).

The guide is split the same way: a short shared core (`canon skills show
canon`) plus one reference per role (`canon skills show role-implementer`, and
likewise `role-planner`, `role-reviewer`, `role-orchestrator`). A spawned agent
with a role loads only its role reference; one agent doing everything follows
`canon status` and loads each role reference as its phase starts. The
orchestrator starts each role with `CANON_ROLE` set and runs the reviewer as a
separate process with its own session id. `--fields` (on `status`, `export`,
`divergence list`, `context`, `query`, `finding list`) keeps an agent's context
small.

`brief approve`, `policy approve`, `divergence accept` and `migrate --commit`,
which binds the `Approved:` line again, are a human's decision: an agent role is
refused with `retryable: false` unless it passes `--relayed-via <tool>`, and the
hint names the relay steps first (show the brief with `canon brief show <change>
--body`, ask through the harness's question tool, count only an explicit
approval, record it with `--relayed-via`) and then the command for the human to
type. A relayed record keeps the human's name and answer, the relaying agent's
role and actor, and the tool used to ask, and `approval: { relay: deny }` in
`canon.yaml` turns it off (then the refusal is `ACTOR_DENIED`). The only option
for going past a refusal is `--override-reason <TEXT>` (there is no `--force`);
the reason you pass is recorded and shown in `data.overrides[]` and `canon
status`.

### Destructive commands preview first

`purge`, `tier age`, `ledger compact`, `artifacts move`, `artifacts prune` and
`migrate` change or delete data. Run bare, each prints a report with `planDigest` and `effects[]`
and changes nothing. `--commit --plan-digest <planDigest>` acts only if the
plan recomputed now has the same digest (`PLAN_STALE`, exit `2`, otherwise).
`--dry-run` is gone from these six, and a document given to `--input` can
never carry `--commit` or `--plan-digest`.

```bash
canon purge --kind session --before 2026-01-01T00:00:00Z
canon purge --kind session --before 2026-01-01T00:00:00Z --commit --plan-digest 0123456789abcdef
```

**Done when:** the committed run reports `committed: true`; a following bare
run shows no remaining effects.

### Upgrading from 0.27

0.28 is a clean cutover of the grammar: no aliases, every write leaf takes
`--input`, commit options are `--rev`, and destructive leaves preview first.
The CHANGELOG's removed-spellings table (0.28.0 Upgrading) lists every old spelling with its
replacement, and canon prints the same replacement as the hint of the usage
error. To upgrade a repo:

```bash
canon migrate
canon migrate --commit --plan-digest 0123456789abcdef
canon skills install
```

The first command previews, the second applies the previewed plan (use the
digest it printed) and backs up each rewritten file under
`.canon/migrate-backup/`, and the third writes the stub guide.
`canon status`, `canon gate check` and `canon context` warn on a 0.27 repo and
put `canon migrate --json` first in `meta.next`.

**Done when:** `canon status` no longer warns and `canon gate check` runs
without a migration warning.
