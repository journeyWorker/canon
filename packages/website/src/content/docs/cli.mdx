`canon` is a single binary with one subcommand per capability. Run `canon
<command> --help` (or `canon <command> <subcommand> --help`) for the
authoritative flag list at any time — this page mirrors that output.

Most subcommands accept `--repo <dir>` (default `.`): the literal `.` default
walks `cwd`'s ancestors for the nearest `canon.yaml`; any other explicit path
is used as-is, no walk. Every command accepts `--json` for one
machine-readable document on stdout instead of the default human-readable
table/summary; see [Driving canon from an agent](#driving-canon-from-an-agent).

## Try it

A self-contained first-run demo — see a gate fail, add evidence, watch it pass.
No prior setup required.

| Command | What it does |
|---|---|
| `canon demo init [--repo <dir>]` | Scaffold a throwaway evidence loop: the real `canon init` config, a `reviewer`-requiring `policy.yaml`, and one seeded `dev` evidence record — leaving `canon gate check` red with `uncovered-cell auth.login.01`. Refuses to overwrite an existing `canon.yaml`. |
| `canon demo add [--repo <dir>]` | Record the missing independent-`reviewer` evidence for the demo scenario, turning the same `canon gate check` green. |

## Setup

Scaffold a repo's config, inspect what it resolves to, and materialize the
single provider-aware `canon` companion skill. Canon's CLI commands remain
explicit; the skill only routes an agent to lazy references.

| Command | Description |
|---|---|
| `canon init [--repo <dir>] [--no-agents-md] [--policy light\|standard\|strict \| --no-policy] [--providers <list>] [--language <tag>]` | Scaffold a fresh, working `canon.yaml` (`tiers:`/`routing:`, `specs:` with the default spec root `{id: root, root: .canon/specs}` holding `<root>/kind=feature/area=<area>/<surface>.feature`, a `plans:` section with `sources: []` preceded by comments — canon's own changes live in `.canon/changes/` and need no entry, and commented `openspec` (`root: .`) and `superpowers` (`root: docs/superpowers/plans`) examples show how to list external plans, which canon only reads; no `openspec/changes/` is created — and `write: { promote: auto }`, so staged writes promote themselves — see `canon gate promote`) at `<repo>/canon.yaml`, a starter `.canon/policy.yaml` at the `--policy` level (default `strict`: `spec_coverage` with `require_evidence`, `require_cases: [failure]`, `require_review: {}`; `standard` leaves out the review and `light` also the failure case, carrying them as commented lines to uncomment when raising the level; the first line `# canon policy level: <level>` names it — a human reviews it and approves it with `canon policy approve --by <who>`), and a canon block in `AGENTS.md` between `<!-- canon:begin -->`/`<!-- canon:end -->` (file created if absent; text outside the markers never touched; markers count only as standalone lines outside code fences, and anything but one begin/end pair is refused, exit `2`, before any write). `--no-agents-md`/`--no-policy` skip those two; an unknown level, or `--policy` with `--no-policy`, exits `2` before any write. A fresh init also adds any missing `.gitignore` line for `.canon/hot.db*`, `.canon/audit/` (the query/export/purge access log) and `.canon/ledger/kind=scenario/` (the derived scenario index; every reader rebuilds it); no line covers `.canon/specs`, which is authored and git-tracked. Never overwrites an existing `canon.yaml` or `policy.yaml`: a rerun only refreshes the `AGENTS.md` block (exit `0`; with `--no-agents-md` there is nothing to do and it refuses, exit `2`), so an existing repo's `canon.yaml` and `.gitignore` are unchanged; a rerun never asks for harnesses and does not apply `--providers`. A fresh init also picks the harnesses the canon skill is installed for (0.17): `--providers claude,codex` (any of `claude`, `codex`, `omp`, `pi`; `none` for none) answers; otherwise, on a terminal, it asks, with the harnesses whose `.claude`, `.codex`, `.omp` or `.pi` directory exists checked (`.agents` alone does not select Codex); otherwise it takes the detected ones. It records the answer as `skills: { providers: [...] }` in `canon.yaml` and installs the skill from the default source, as `canon skills install` does, printing `installed the canon skill for <list> (<dirs>)`. With no terminal, no flag and nothing detected it records only a commented example, installs nothing, and names `canon skills install --providers=<list>`. An unknown name is refused before anything is written (exit `2`); a missing skill source keeps the recorded choice and exits `2` naming the install to run. `--language <tag>` records `language:` in `canon.yaml`, the language briefs are written in (0.19): templates and prose rules ship for `en` and `ko`; any other tag gets `en` headings and the structure rules only. It is validated before anything is written and is not applied to an existing `canon.yaml`; `init --check-config` reports it. |
| `canon policy approve --by <who> [--note <text>] [--repo <dir>]` | Record that a human reviewed `.canon/policy.yaml`: writes `.canon/policy.approval.json` (pretty JSON with `policy_digest` — `sha256:<hex>` of the policy bytes — `approved_by`, `approved_at` in RFC3339 UTC, and `note` or `null`). Written directly; nothing to promote. The file is git-tracked, so commit it. Re-running replaces the record. Refused (exit `2`) when there is no `.canon/policy.yaml` or `--by` is empty. Until the record matches the current policy, `gate check` and `status` print an advisory; the exit code never changes. |
| `canon init --check-config [--repo <dir>]` | Read-only validate an existing `canon.yaml`, chaining the same strict loaders `inventory sync`/`ingest plans`/`tier age` use. The `write:` section reports `[PASS] write (promote: auto)` (or `manual`), `[not configured] write (promote: manual)` when absent, or `[FAIL] write: …` when malformed. The `skills:` section reports `[PASS] skills (providers: …)`, `[not configured] skills (…)` when absent, or `[FAIL] skills: …` for another shape or an unknown provider. |
| `canon migrate [--dry-run] [--repo <dir>]` | Move a repo that canon 0.16 or earlier set up onto the 0.17 layout. It prints the plan, then applies it; `--dry-run` stops after the plan. It is idempotent: a second run finds nothing to move. A spec root's `features/kind=feature/` moves to `<root>/kind=feature/` (`git mv` when tracked). A root at the repo-level `specs` moves to `.canon/specs`, and `canon.yaml` records `former_roots: [specs]`, so reviews pinned before the move still find their scenarios. Changes `canon change new` wrote under `openspec/changes/` move to `.canon/changes/<slug>/` (`proposal.md` → `brief.md`) and are re-imported under the same change id. A change counts only when it is still in that command's scaffold and its first stored version was adopted; every other change stays and is named. `canon init`'s `{ dialect: openspec, root: . }` source goes once nothing is left under it. An `Approved:` line in an external `proposal.md` is copied into a canon pointer `brief.md` with `Source:`, and the proposal is not edited. It also writes `skills.providers` from the install lock, adds missing canon `.gitignore` lines and rebuilds the scenario index. `canon.yaml` keeps every other byte, comments and CRLF included. Refused (exit `2`, nothing written) on uncommitted changes under a path it moves, an existing destination, or a `canon.yaml` edit it cannot make safely. A rerun of `canon init` on an existing repo also adds the missing `.gitignore` lines. |
| `canon context [--repo <dir>] [--json]` | Emit the resolved authoring surface: record kinds + envelope fields, enum domains, join-key grammars, partition layout, policy-derived requirements, capability version. A capability *query* — always exits 0, even when `fmt --check`/`gate` would report diagnostics. The human outline opens with a pointer to `canon status` and, when no `spec_coverage` policy is in force, a `warning:` line; `--json` is unchanged. |
| `canon status [--repo <dir>] [--json]` | Where the repo stands and what to run next: the canon version and the policy in force (or a warning that the gate enforces nothing), with its level — the policy's `# canon policy level:` line when it names `light`, `standard` or `strict`, else the level its `spec_coverage` section matches exactly, else `custom` (`policy.level` in `--json`, `null` without a policy); a `light` or `standard` level also says how to raise it — subjects grouped by status with their scenario, evidence, review and open-blocker counts and missing required cases, the scenarios no subject owns, and a `next:` list of at most five concrete commands. Counts come from the same joins `gate check` and `subject status` use, and status fails closed: a corpus kind routed off the `local` rung leaves only the routing repair, and an unusable `spec_coverage` section puts its repair first and withholds every move-on suggestion. With several spec roots, suggested `canon scenario new` commands carry `--project`. For each `building`, `verifying` or `shipped` subject, and each `proposed` subject whose newest adopted change has a brief, it shows whether the brief is approved (`brief: approved in <brief> — <words>` or `brief: not approved (…)`): an `Approved:` line, outside HTML comments and code fences, in `.canon/changes/<change>/brief.md` for the subject's newest adopted change, and only there (no record kind). A change from an external plan has its brief in that same canon file, holding a `Source: <path>` line that points at the external document; an `Approved:` line inside an external `proposal.md` is not read, and until the canon file exists an external openspec `proposal.md` under the plan sources still makes the brief one to answer. Fixes live as tasks in the approved change, so an older change's approval does not cover a newly adopted one. An unapproved brief makes the step addressed to a human the subject's only step, whatever its status (`human: stop and report the brief in <brief>; build and attest nothing for <id> until the human answers (one answer approves brief and policy)`, naming the canon `brief.md`, or the external proposal when no canon brief exists yet; `"actor": "human"` in `--json`): no `feature new`, `scenario new`, evidence, review or ship step before the human answers, and its reason says `canon evidence add` refuses the subject's scenarios and tasks until the `Approved:` line is recorded, and where to record it (for an external plan, the `brief.md` to create with its `Source:` line). Every other step is the agent's, including `canon subject status <id> --to shipped` once the ship guard would pass. When the policy has no approval record, or changed since it was approved, a `warning:` line says so (also in `--json` `warnings`). Each evidence record attested under a brief `--override-reason` (see `canon evidence add`) is listed as a `warning:` line naming what it attests, the actor, the time, the subject and the reason. A read — always exits 0 and writes nothing but a stale scenario index it rebuilds (one stderr line; see `canon inventory sync`). `--json` is a stable shape versioned by `statusVersion` (`3` since 0.17: subjects carry `brief`, `{approved, enforced, change?, brief?, briefExists, source?, approval?}`; its `proposal` field was removed and `brief`, `briefExists` and `source` were added. Version `2`, since 0.16, added `actor` to each `next` entry, whose `command` is a canon command only for `agent`, and the `brief` object). With `spec_coverage.require_audit` it shows an `audits` section (sampled, confirmed, owed, refuted) and suggests `canon evidence add --kind audit …`; recorded `--drop-attachment` drops list under `dropped bindings (N):` (`drops[]` in `--json`). |
| `canon context-pack new --manifest <repo-relative.json> [--repo <dir>] [--json]` | Create an immutable, content-addressed context snapshot from the explicitly selected files in a repository-local JSON manifest. Concise output prints only the pack id; `--json` prints manifest metadata and digests. |
| `canon context-pack show <id> [--repo <dir>] [--json]` | Verify and show a stored pack. `show` rechecks the manifest and every immutable content object before returning; concise output does not include captured bytes. |
| `canon context-pack verify <id> [--repo <dir>] [--json]` | Verify a pack without returning captured content. Exits nonzero when the pack is missing, stale, or tampered. |
| `canon adapter validate --response <path> [--repo <dir>] [--json]` | Read-only validation of a provider-neutral protocol-v1 response. Core fields are strict (`run_id`, provider/model, context-pack id, status, capabilities, safe evidence refs, and nonnegative ordered telemetry); provider data is opaque under `extensions`. JSON output is a redacted normalized summary with extension key names only. `--repo` optionally checks the context pack join; no provider is executed and capability declarations are not enforcement. |
| `canon prompt add --name <name> --version <version> --manifest <repo-relative.json> [--repo <dir>] [--json]` | Register a versioned prompt bundle from an explicit repository-local manifest in the immutable content registry. |
| `canon prompt show --name <name> --version <version> [--repo <dir>] [--json]` | Select and verify a registered prompt bundle version; default output is concise metadata, while `--json` includes snapshot metadata and digests. |
| `canon skills install [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi\|none]` | Project one canonical `canon` skill. Claude receives `.claude/skills/canon/SKILL.md`; Codex receives `.agents/skills/canon/SKILL.md` (the directory Codex scans for skills); OMP receives `.omp/skills/canon/SKILL.md`; and Pi receives `.pi/skills/canon/SKILL.md`. Every selected provider receives lazy `reference/**` and `scripts/**` sidecars. OMP/Pi are project-local passive bundles; their retrieve pre-dispatch script is a sidecar, not a native hook. Provider selection is deterministic: `--providers`, else `canon.yaml`'s `skills.providers`, else the providers the install lock records (a repo set up before 0.17), else the harnesses whose `.claude`, `.codex`, `.omp` or `.pi` directory exists (`.agents` alone does not select Codex). Nothing undetected is ever added: with nothing detected it installs nothing and names `--providers`. An explicit `--providers` also rewrites `skills.providers` in an existing `canon.yaml`, keeping every other byte, and never creates one. A legacy `.codex/skills/canon.md` + `.codex/skills/canon/**` projection from canon 0.13.0 or earlier is removed file by file when its bytes still match the install lock; edited or user files stay, and `.codex/skills` is removed only if it ends up empty. The install lock (`.canon/skills/.install-lock.json`) records `canon_version`, the canon that wrote it, and `source_commit`, the `HEAD` of the git checkout the source is in (omitted outside one); a rerun with an unchanged bundle and the same canon leaves it byte-identical. |
| `canon skills check [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Selects providers as `install` does and, without `--providers`, first prints `providers: <list> (<where they came from>)`. Read-only report of missing or stale canonical projections, the target-owned content manifest, any leftover legacy `.codex/skills` Codex projection (with its fix command), and an install lock another canon wrote: `<lock> — outdated (installed by canon X, this canon is Y — run canon skills install --providers=…)`, or "an unknown canon version" for a lock from before 0.16, which records none. Exits 1 on any of them. |
| `canon skills doctor [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Human-readable provider, drift, outdated-lock (`outdated:`) and legacy-remnant diagnostics across all four managed roots and the legacy `.codex/skills` root, naming the fix command. It also lists other skills in `.claude/skills`, `.agents/skills`, `.omp/skills` and `.pi/skills` whose frontmatter `description` claims build work (one sentence holds both a build verb — build, implement, create, make, scaffold, develop or code, in any form — and a build object — site, website, app, application, game, feature, frontend, ui, page, component, tool, library, service, api, cli, server, backend, project, prototype, product, program or script, singular or plural; so "Build websites and apps" claims build work and "Manage feature branches" does not) as `competing-skill:` lines warning that if an agent picks one for build work, canon's loop will not run. Those lines are advisory: they never make the projections unhealthy or change the exit code, and canon never edits another skill or deletes user files. It also adds a `stray:` line for each canon projection (`.claude/skills/canon`, `.agents/skills/canon`, `.omp/skills/canon`, `.pi/skills/canon`) whose provider is not selected, naming the `rm -r` that removes it and the install command that selects it; also advisory, and `check` ignores it. Without `--providers` its first line names where the providers came from, and with nothing selected or detected it prints `no-providers:` with the flag to pass instead of `status: healthy`. |

Canon contributors may use the legacy `canon skills install --source
canon/skills-dev --target .` materializer; it is not part of the consumer
installation flow.

## Subjects

Author and drive the durable product unit — canon's 13th record kind —
through its lifecycle, and adopt imported plan changes under it. See
[The Canon Concept](/concepts/canon/#subjects) for the subject-write-first
loop; "feature docs" always means Gherkin `.feature` files, a "subject"
is the management record.

| Command | Description |
|---|---|
| `canon subject new <id> --domain <d> --title <t> [--summary <s>] [--owner-role <r>] [--repo <dir>] [--json]` | Author a `Subject` (kebab-slug `<id>` is the durable `subject_id` join key). `--domain` is a vocabulary-defined kebab slug — base set `planning`/`design`/`dev`/`data`/`test`, extended per-repo via `.canon/vocab`. Starts at status `proposed`; `--owner-role` defaults to `implementer`. Envelope + policy validated at write. |
| `canon change new <slug> --subject <id> --title <t> [--kind feature\|chore] [--repo <dir>]` | Write canon's own change dir `.canon/changes/<slug>/`: `brief.md` (the PRD brief in `canon.yaml`'s `language:`: `# <title>`, then the sections Intent, Desired outcome, User flow, Step detail, Acceptance, Questions and assumptions and Out of scope, each behind a `<!-- canon:section <key> role=… -->` marker and holding a `canon:hint` comment until written, and a comment naming `canon brief approve` as where the human's answer is recorded; the Intent section's first paragraph is the title). It writes no `tasks.md`: a `tasks.md` is an optional work note nothing gates on, and an existing one is still read. `--kind chore` writes the short chore brief instead (Intent, Category `refactor\|dependency\|build\|ci\|infra`, Invariants, Checks, Out of scope; no flow): for work that changes how the subject is built or kept, never what it does. Read them with the native `canon` plan adapter `canon ingest plans` uses, and record the change adopted into the subject through the same write as `canon subject adopt` — no plans source and no `canon.yaml` edit needed. Prints `canon change new: wrote .canon/changes/<slug>/brief.md` and ``canon change new: recorded change `<slug>` adopted into subject `<id>` — …``; its records carry the actor `canon-plan-import-canon`. A failure before any record is written leaves nothing behind (the files are staged under `.canon/` and published only once they parse). The subject and change records cannot be written atomically: if the change record fails after the subject record, it exits `2`, keeps the change dir and the subject record, and prints the repair `canon ingest plans && canon subject adopt <slug> --subject <id>`, which is safe to rerun. Refuses (exit `2`, nothing written) an unknown subject, or a slug that already has a `.canon/changes/<slug>` dir (active or archived) or a change record. |
| `canon brief [--change <slug>] [--repo <dir>] [--json]` | Print a change's brief state (`draft`, `ready`, `approved`, `legacy`) and the next one to three steps (`shape`, `clarify`, `harden`, `align`, `polish`, `approve`), derived from the findings of `canon brief check`. Without `--change` it reads the repo's only live change. It never edits. |
| `canon brief check [--change <slug>] [--repo <dir>] [--json]` | Read the brief against the rules; read-only. Exit `0` clean (advisories allowed), `2` blocker findings, `1` an operational error with a stable string `error.code` (`NO_BRIEF`, `CHANGE_AMBIGUOUS`, `BRIEF_NOT_FOUND`, `BRIEF_UNREADABLE`, `CONFIG_UNREADABLE`, `SPEC_ROOTS_UNREADABLE`). Sections are found by their marker comment, never by heading text. Blockers (`brief.*`): a missing, duplicate or out-of-order section; a flow with no steps or a duplicate step id; step-detail subheadings that do not match the flow ids in order; leftover placeholders (a `canon:hint` comment, an empty section, `TODO`/`TBD`); once the subject is `building` or later, a flow step no scenario tagged `@flow:<change>.<F-id>` points at, or one with no `@case:failure` scenario; a malformed waiver. Advisories (`prose.*`, for `language:` `en` and `ko`, normative sections only): closed phrase lists, sentence and paragraph length, and a normative section without exactly one `==**key sentence**==`; a brief with no markers (every brief before 0.19) is `brief.legacy`. `<!-- canon:waive <rule-id> <section-key> "<reason>" -->` waives one rule in one section and is listed in the output. The ship guard of `canon subject status` runs the blocker rules; `canon status` shows the finding counts. |
| `canon brief approve --by <who> --note <words> [--change <slug>] [--repo <dir>] [--json]` | Record the human's answer to the brief in one call: writes `Approved: <who> <when> — "<words>" (brief sha256:<digest>)` into the brief (the digest covers the brief without its `Approved:` lines) and records the policy approval, as `canon policy approve` would. Refused (exit `2`) while `canon brief check` has structure blockers, and for an empty `--by` or `--note`; the coverage rules (`brief.flow-uncovered`, `brief.flow-no-failure`) gate shipping, never approval. A brief edited afterwards reads as not approved (`BRIEF_CHANGED_SINCE_APPROVAL`) in `status`, `evidence add` and the ship guard until a human answers again and the command runs again; an `Approved:` line with no digest (before 0.19) stays approved, with an advisory to re-approve. Run it only from the human's answer: canon cannot tell a human from an agent. |
| `canon subject adopt <change_id> --subject <id> [--repo <dir>] [--json]` | Link an imported plan `Change` (from `canon ingest plans`) to a `Subject`: appends the subject to `Change.subject_ids` and the change to the subject's `change_ids`. A change may belong to several subjects (0.18): adopting it under a second subject adds that subject, never re-points, and prints ``linked change `refactor-core` to subject `editing` as well; the change now belongs to `perception` and `editing` ``. A change written before 0.18 names one `subject_id`; it reads as a one-element `subject_ids`. Every reader (the gate's open-blocker rule, the status guard, `canon status`, the brief) joins a subject to its changes from both sides, so a blocker on a shared change gates every subject it belongs to. Writes only the side that lacks the link (a linked pair: nothing written, exit `0`). The subject is written first; if the change write then fails it exits `2` and prints `canon subject adopt <change_id> --subject <id>` to complete the link. |
| `canon subject status <id> --to <state> [--override-reason <text>] [--reason <text>] [--actor-id <id>] [--repo <dir>] [--json]` | Policy-gated transition along `proposed → specced → building → verifying → shipped` (plus `shipped → verifying` to reopen, and any → `retired`). `verifying → shipped` additionally requires the subject to own at least one scenario — one whose `@subject:<id>` tag `canon inventory sync` has indexed — and every owned scenario to carry a latest non-Divergent verdict; a violation prints by failure class, exits `1`, and leaves the record unchanged (fail closed). With `spec_coverage.require_review` set, it also prints on stderr which review checks it ran or skipped, and a move into a `require_review.scope` status with gaps (`unreviewed-promotion`, `open-blocker`) is refused the same way. `--override-reason "<one line>"` waives only those two classes — never ship-gate verdict or case gaps — and records `status_override` (`to`, `reason`, `waived`: the exact `{class, subject}` violations it let through, `actor` from `--actor-id`, default `canon`) on the new record. A gap it did not record, such as a blocker raised later, still fails the gate; a blank or multi-line reason exits `2`. The waiver clears on the subject's next status write. Without `require_review`, nothing changes. Moving to `shipped` also refuses `false-success` (a scenario whose latest audit is `refuted`) and, when `require_audit.scope` covers `shipped`, an owed sampled audit. **Reopen (0.18):** `shipped → verifying --reason "<one line>"` reopens a shipped subject for follow-up work and records `reopen` (`reason`, the approved `change` the work goes into, `actor`). It needs no human inside the approved scope (the newest adopted change's brief is approved, or there is none to answer); otherwise it exits `1` naming the brief to approve, and `--override-reason` does not waive it. `--reason` is required there and refused on any other transition (exit `2`). The review guard skips a reopen; shipping again runs every guard. `canon status` flags a shipped subject whose gate went red (`gate: red — …; reopen with …`) and names this command as its step. |

`verifying → shipped` also needs the subject's brief approved where a
brief exists, by the same check `canon status` uses for its `brief:` line:
the subject's newest adopted change must carry an `Approved:` line, outside
HTML comments and code fences, in its `.canon/changes/<change>/brief.md`,
written by `canon brief approve`, and a digest on that line must still match
the brief's text (a brief edited after its approval is refused as
`BRIEF_CHANGED_SINCE_APPROVAL`). It also needs `canon brief check` free of
blockers, which includes every flow step covered by a scenario with a
failure case. A brief exists when that canon `brief.md` does, or, for a
change from an external plan, when an openspec `proposal.md` under the plan
sources does (the canon `brief.md` is then still to be created, with a
`Source:` line pointing at that proposal; an `Approved:` line in the
proposal itself is not read). It runs with or without a policy. Without the
approval the move is refused as `unreviewed-promotion <subject>`, naming the
canon `brief.md` (and, for an external plan, the `Source:` line to write)
and saying a human must answer the brief; the agent records the answer with
`canon brief approve`, only from that answer.
`--override-reason` waives it like a review gap and records
`{class: unreviewed-promotion, subject: <subject>}` in the waiver. With no
adopted change, or a newest change with neither a canon `brief.md` nor an
external `proposal.md`, there is no brief to answer: the move prints an
advisory that the brief is not approved and is not refused, and `status`
shows the brief as an advisory with no human step
(`subjects[].brief.enforced: false`). A brief that says the
human ships changes who runs the move, not the check. This refusal is a
backstop: while the brief is unapproved, `canon evidence add` already
refuses the subject's scenarios and tasks, and the agent stops at the brief
before either fires.

## Corpus

Validate and grow a Gherkin `.feature` spec corpus.

| Command | Description |
|---|---|
| `canon format <ROOT> [--repo <dir>]` (alias `canon fmt`) | Validate a corpus root (e.g. `spec/`) against the artifact-family schemas + layout descriptors. Validating is the only mode, so `--check` is now the default and is accepted only for compatibility. A spec root still on the pre-0.17 layout (any `.feature` file under `<root>/features/`) is one `layout-grammar` violation at path `features`, naming `canon migrate`, which moves `features/kind=feature/` to `<root>/kind=feature/`. |
| `canon inventory sync [--repo <dir>] [--spec-root <dir>]` | Validate each configured `specs.roots[]` entry with `canon-fmt`, then materialize one `Scenario` ledger-index record per `(project_id, scenario_id)`. `--spec-root` overrides `canon.yaml` for one ad hoc root. The index is derived from the `.feature` files, so `gate check`, `status`, `subject status`, `review add` and `evidence add` rebuild a stale index themselves before reading it (a scenario with no record, or a record whose source digest differs from the file): same code, only the changed files materialized, validation still over the whole root. | `canon query --kind <kind> [--since <ts>] [--repo <dir>] [--canon-yaml <path>] [--json] [--plugin <id>] [--change-id <id>] [--domain <d>] [--status <s>] [--include-sensitive] [--limit <n> \| --all] [--cursor <c>] [--fields a,b,c]` | Fan out a record kind's read across every tier it may live in and merge by `at`; every invocation is recorded in `.canon/audit/access.jsonl` of the repository whose `canon.yaml` it read (`--repo` or `--canon-yaml`), never the current directory; with no `canon.yaml`, nothing is written. Returns at most `--limit` records (default 100; 0.20 changed this from "everything"): `--json` adds `meta: {returned, total, hasMore, nextCursor}`, human mode ends with the next cursor, and `--cursor <c>` continues (`INVALID_CURSOR` if the cursor is from another listing); `--all` returns the rest. `--fields` keeps only the named top-level fields in `--json` records (`UNKNOWN_FIELD` otherwise). `--include-sensitive` requires `.canon/policy.yaml` `query.allow_sensitive: true`. |
| `canon purge --kind <session\|run\|event\|trajectory> --before <RFC3339> (--plan \| --confirm <planDigest>) [--repo <dir>] [--json]` | Purge matching records from the routed rung and every aging destination, including historical versions. `--plan` prints what would be removed and a `planDigest` and deletes nothing; `--confirm <planDigest>` deletes only if the plan recomputed now has that digest, else `PLAN_CHANGED` (exit 2). A bare `purge` is refused (`PURGE_PLAN_REQUIRED`). It never deletes source transcripts or Git history. |
| `canon export --kind <kind> [--before <RFC3339>] [--after <RFC3339>] [--out <file>] [--repo <dir>] [--json] [--include-sensitive] [--limit <n> \| --all] [--cursor <c>]` | Write a versioned, redacted manifest with counts and content digests, one page of at most `--limit` records (default 100) at a time; the manifest's `meta` carries `returned`, `total`, `hasMore` and `nextCursor`. Sensitive bodies require explicit policy and flag; newly-created files are mode `0600`. |
| `canon plugin sync <PLUGIN_ID> [--repo <dir>] [--spec-root <dir>]` | Resolve `<plugin-id>`'s manifest-declared overlay(s), hand each to its registered source, write every candidate through the validate-then-write pipeline. |

## Driving canon from an agent

Every command shares one machine contract (0.20), so an agent never has to
scrape `--help` or human text.

**Discover with `canon schema`.** One call describes a command:

```bash
canon schema                      # every command, its effect, one line each
canon schema purge --json         # {data, meta}: arguments, options, exits, errorCodes
canon schema --errors --json      # every stable error code and its meaning
```

`data` carries `command`, `effect` (`read`, `write` or `destructive`),
`supportsJson`, `arguments`, `options` (`name`, `kind`, `valueName`,
`required`, `repeatable`, `possibleValues`, `default`), `exits` (`code`,
`meaning`) and `errorCodes`.

**`--json` output.** stdout is exactly one JSON document; narration goes to
stderr.

**Errors.** Every failure prints `canon <command>: CODE — message` and a
`hint:` line on stderr. With `--json`, stdout is instead
`{"error": {"code", "message", "hint", "retryable"}}`, plus `field` (the
option at fault) and `expected` (its valid values) when a usage error or an
input check can name them. Codes are stable
strings; a command-line parse error is `USAGE`. Exit `2` means the
invocation or its inputs are wrong and fixable (nothing was written); exit
`1` is an operational failure or a blocking finding the command reports.

**Paging and fields.** `canon query`, `canon finding list`,
`canon divergence status` and `canon export` return at most `--limit`
records (default 100). `--all` returns everything; `--cursor <nextCursor>`
continues. `--json` adds `meta: {returned, total, hasMore, nextCursor}`.
`canon query` and `canon finding list` also take `--fields a,b,c` to
project records; an unknown field is `UNKNOWN_FIELD` and the hint lists the
known ones.

**`meta.next` after a write.** A write that succeeds names the next step
itself, so an agent does not call `canon status` just to find it: `--json`
adds `meta.next` (`[{command, why, actor, role}]`, at most five, with
`meta.nextOmitted` counting the rest), and human output ends with one
`next: <command> — <why>` line. These are `canon status`'s own steps, narrowed
to the subject the write touched; `actor: human` marks a step only a human
takes. canon never runs a step.

**Deprecated names.** A renamed command (`context-pack create`, `prompt
register`, `divergence stage`, `demo attest`, and `subject status <id>
<state>`) still runs for one release, warns on stderr, and sets
`meta.deprecated: {use, removedIn}`.

**Retry safety.** Repeating `evidence add` or `review add` with identical
input returns the existing record with `meta.unchanged: true`.

### Roles

An agent can declare a role: `planner`, `implementer`, `reviewer` or
`orchestrator`. Set `CANON_ROLE=<role>` or pass `--as <role>` (the flag wins);
an unknown value is `UNKNOWN_ROLE`. A role is guidance, not enforcement:
`canon schema` lists the role's commands, `canon status` and `meta.next` keep
only the role's steps and count the rest in `waitingOn` (the orchestrator also
sees the human's steps), and `--role` on `evidence add` and `review add`
defaults to it. Unset, every command behaves as before.

The canon skill is split the same way: a short shared core plus
`reference/role-<role>.md`. A spawned agent with a role loads only its role
reference; one agent doing everything follows `canon status` and loads each
role reference as its phase starts. The orchestrator starts each role with
`CANON_ROLE` set and runs the reviewer as a separate process with its own
session id. `--fields` (on `status`, `export`, `divergence status`, `context`,
`query`, `finding list`) keeps an agent's context small.

**Destructive commands plan first.** `canon purge --plan` prints the removal
set and a `planDigest` and deletes nothing; `canon purge --confirm
<planDigest>` deletes only if the plan recomputed now has the same digest
(`PLAN_CHANGED` otherwise). There is no `--dry-run` on `purge`.
