`canon` is a single binary with one subcommand per capability. Run `canon
<command> --help` (or `canon <command> <subcommand> --help`) for the
authoritative flag list at any time — this page mirrors that output.

Most subcommands accept `--repo <dir>`. Absent or `.`, it is the nearest
ancestor of `cwd` with a `canon.yaml`; any other explicit path is that
directory as given, no walk. A command that needs canon state and finds no
`canon.yaml` there refuses with `CONFIG_MISSING` (exit `2`, `--repo` named,
the hint naming `canon init` and the directory searched) instead of reporting
an empty repo as clean. `init`, `migrate`, `demo`, `context`, `regime show`,
`schema`, `skills show`, `adapter`, `context-pack` and `prompt` run without one. Every command accepts `--json` for one
machine-readable document on stdout instead of the default human-readable
table/summary; see [Driving canon from an agent](#driving-canon-from-an-agent).

## Driving canon from an agent

Every command shares one machine contract, so an agent never has to scrape
`--help` or human text. The grammar is one spec, `docs/cli/canon.cli.json`;
the parser, `canon schema`, the tables above and the guide are generated from
it.

**Discover with `canon schema`.** One call describes a command:

```bash
canon schema                      # every command, its effect, one line each
canon schema purge --json         # arguments, options, exits, errorCodes
canon schema evidence add --json  # the --input schema and an example
canon schema --errors --json      # every stable error code and its meaning
```

`data` carries `command`, `effect` (`read`, `write` or `destructive`),
`supportsJson`, `arguments`, `options` (`name`, `kind`, `valueName`,
`required`, `repeatable`, `possibleValues`, `default`), `exits` (`code`,
`meaning`) and `errorCodes`.

**Read the guide from the binary.** `canon skills show canon` prints the
core guide; `canon skills show canon --full` adds every reference;
`canon skills show <name>` prints one reference (`role-reviewer`,
`canon-gate`, `brief-polish`, …). The `SKILL.md` that `canon skills install`
writes into a repo is only a stub that sends the agent here, so the guide
always matches the installed binary.

**`--json` envelope.** stdout is exactly one JSON document, nothing goes to
stderr: `{"ok": true, "data": …, "meta": …}` on success and
`{"ok": false, "error": …, "meta": …}` on failure. `meta` carries `command`,
`schemaVersion` and `canonVersion`, plus `next` and `unchanged` where they
apply.

**Errors.** Every failure prints `canon <command>: CODE — message` and a
`hint:` line. With `--json`, `error` is `{code, message, hint, retryable}`,
plus `field` (the option at fault) and `expected` (its valid values) when a
usage error or an input check can name them. Codes are stable strings; a
command-line parse error is `USAGE`, and an old 0.27 spelling is a usage error
whose hint names the replacement. Exit `2` means the invocation or its inputs
are wrong and fixable (nothing was written); exit `1` is an operational
failure or a blocking finding the command reports.

**`--input` for writes.** Every write command takes `--input`: its arguments
as one JSON object, inline, as a file path, or `-` for stdin. Keys are the
option names in camelCase, and `operands` is an array. A JSON array or NDJSON
is a batch: it is validated whole before anything is written, and the report
has one entry per element in `data.items[]` (`written`, `unchanged`, `failed`
or `skipped`). `canon schema <command> --json` shows the input schema.

```text
canon evidence add --input <JSON|FILE|->
canon scenario new --input <JSON|FILE|->
canon finding add --input <JSON|FILE|->
```

**Revisions.** A command that records code takes `--rev` (any git revision,
default `HEAD`); the finding commands add `--resolution-rev` and
`--introduced-rev`. Uncommitted code is recorded too, with a `codeTree` and
`worktreeDirty`, and a review survives the commit when the code tree is the
same. Outside git, or with no commit, the command refuses with `NO_COMMIT`.

**Paging and fields.** `canon query`, `canon finding list`,
`canon divergence list` and `canon export` return at most `--limit`
records (default 100). `--all` returns everything; `--cursor <nextCursor>`
continues. `--json` adds `meta: {returned, total, hasMore, nextCursor}`.
`canon query` and `canon finding list` also take `--fields a,b,c` to
project records; an unknown field is `UNKNOWN_FIELD` and the hint lists the
known ones.

**`meta.next` after a write.** A write that succeeds names the next step
itself, so an agent does not call `canon status` just to find it: `--json`
adds `meta.next` (`[{command, why, actor, role}]`, at most five, with
`meta.nextOmitted` counting the rest), and human output ends with one
`next: <command> — <why>` line. These are `canon status`'s own steps, narrowed
to the subject the write touched; `actor: human` marks a step only a human
takes. canon never runs a step.

**Retry safety.** Repeating `evidence add` or `review scenario` with identical
input returns the existing record with `meta.unchanged: true`.

### Roles

An agent can declare a role: `planner`, `implementer`, `reviewer` or
`orchestrator`. Pass `--as <role>` or set `CANON_ROLE=<role>` (the flag wins);
an unknown value is `UNKNOWN_ROLE`. A role is guidance, not enforcement:
`canon schema` lists the role's commands, `canon status` and `meta.next` keep
only the role's steps and count the rest in `waitingOn` (the orchestrator also
sees the human's steps), and `--role` on `evidence add` and `review scenario`
defaults to it. Unset, every command behaves as before.

The guide is split the same way: a short shared core (`canon skills show
canon`) plus one reference per role (`canon skills show role-implementer`, and
likewise `role-planner`, `role-reviewer`, `role-orchestrator`). A spawned agent
with a role loads only its role reference; one agent doing everything follows
`canon status` and loads each role reference as its phase starts. The
orchestrator starts each role with `CANON_ROLE` set and runs the reviewer as a
separate process with its own session id. `--fields` (on `status`, `export`,
`divergence list`, `context`, `query`, `finding list`) keeps an agent's context
small.

### Destructive commands preview first

`purge`, `tier age`, `ledger compact`, `artifacts move` and `migrate` change or
delete data. Run bare, each prints a report with `planDigest` and `effects[]`
and changes nothing. `--commit --plan-digest <planDigest>` acts only if the
plan recomputed now has the same digest (`PLAN_CHANGED`, exit `2`, otherwise).
`--dry-run` is gone from these five, and a document given to `--input` can
never carry `--commit` or `--plan-digest`.

```bash
canon purge --kind session --before 2026-01-01T00:00:00Z
canon purge --kind session --before 2026-01-01T00:00:00Z --commit --plan-digest 0123456789abcdef
```

**Done when:** the committed run reports `committed: true`; a following bare
run shows no remaining effects.

### Upgrading from 0.27

0.28 is a clean cutover of the grammar: no aliases, every write leaf takes
`--input`, commit options are `--rev`, and destructive leaves preview first.
The README's removed-spellings table lists every old spelling with its
replacement, and canon prints the same replacement as the hint of the usage
error. To upgrade a repo:

```bash
canon migrate
canon migrate --commit --plan-digest 0123456789abcdef
canon skills install
```

The first command previews, the second applies the previewed plan (use the
digest it printed) and backs up each rewritten file under
`.canon/migrate-backup/`, and the third writes the stub guide.
`canon status`, `canon gate check` and `canon context` warn on a 0.27 repo and
put `canon migrate --json` first in `meta.next`.

**Done when:** `canon status` no longer warns and `canon gate check` runs
without a migration warning.
