`canon` is a single binary with one subcommand per capability. Run `canon
<command> --help` (or `canon <command> <subcommand> --help`) for the
authoritative flag list at any time — this page mirrors that output.

Most subcommands accept `--repo <dir>` (default `.`): the literal `.` default
walks `cwd`'s ancestors for the nearest `canon.yaml`; any other explicit path
is used as-is, no walk. Several also accept `--json` for machine-readable
output instead of the default human-readable table/summary.

## Try it

A self-contained first-run demo — see a gate fail, add evidence, watch it pass.
No prior setup required.

| Command | What it does |
|---|---|
| `canon demo init [--repo <dir>]` | Scaffold a throwaway evidence loop: the real `canon init` config, a `reviewer`-requiring `policy.yaml`, and one seeded `dev` evidence record — leaving `canon gate check` red with `uncovered-cell auth.login.01`. Refuses to overwrite an existing `canon.yaml`. |
| `canon demo attest [--repo <dir>]` | Record the missing independent-`reviewer` evidence for the demo scenario, turning the same `canon gate check` green. |

## Setup

Scaffold a repo's config, inspect what it resolves to, and materialize the
single provider-aware `canon` companion skill. Canon's CLI commands remain
explicit; the skill only routes an agent to lazy references.

| Command | Description |
|---|---|
| `canon init [--repo <dir>] [--no-agents-md] [--policy light\|standard\|strict \| --no-policy]` | Scaffold a fresh, working `canon.yaml` (`tiers:`/`routing:`/`specs:`, a `plans:` source `{dialect: openspec, root: .}` with an empty `openspec/changes/`, and `write: { promote: auto }`, so staged writes promote themselves — see `canon gate promote`) at `<repo>/canon.yaml`, a starter `.canon/policy.yaml` at the `--policy` level (default `strict`: `spec_coverage` with `require_evidence`, `require_cases: [failure]`, `require_review: {}`; `standard` leaves out the review and `light` also the failure case, carrying them as commented lines to uncomment when raising the level; the first line `# canon policy level: <level>` names it — a human reviews it and approves it with `canon policy approve --by <who>`), and a canon block in `AGENTS.md` between `<!-- canon:begin -->`/`<!-- canon:end -->` (file created if absent; text outside the markers never touched; markers count only as standalone lines outside code fences, and anything but one begin/end pair is refused, exit `2`, before any write). `--no-agents-md`/`--no-policy` skip those two; an unknown level, or `--policy` with `--no-policy`, exits `2` before any write. A fresh init also adds any missing `.gitignore` line for `.canon/hot.db*`, `.canon/audit/` (the query/export/purge access log) and `.canon/ledger/kind=scenario/` (the derived scenario index; every reader rebuilds it). Never overwrites an existing `canon.yaml` or `policy.yaml`: a rerun only refreshes the `AGENTS.md` block (exit `0`; with `--no-agents-md` there is nothing to do and it refuses, exit `2`), so an existing repo's `canon.yaml` and `.gitignore` are unchanged. Prints `canon skills install` as the next step. |
| `canon policy approve --by <who> [--note <text>] [--repo <dir>]` | Record that a human reviewed `.canon/policy.yaml`: writes `.canon/policy.approval.json` (pretty JSON with `policy_digest` — `sha256:<hex>` of the policy bytes — `approved_by`, `approved_at` in RFC3339 UTC, and `note` or `null`). Written directly; nothing to promote. The file is git-tracked, so commit it. Re-running replaces the record. Refused (exit `2`) when there is no `.canon/policy.yaml` or `--by` is empty. Until the record matches the current policy, `gate check` and `status` print an advisory; the exit code never changes. |
| `canon init --check-config [--repo <dir>]` | Read-only validate an existing `canon.yaml`, chaining the same strict loaders `inventory sync`/`ingest plans`/`tier age` use. The `write:` section reports `[PASS] write (promote: auto)` (or `manual`), `[not configured] write (promote: manual)` when absent, or `[FAIL] write: …` when malformed. |
| `canon context [--repo <dir>] [--json]` | Emit the resolved authoring surface: record kinds + envelope fields, enum domains, join-key grammars, partition layout, policy-derived requirements, capability version. A capability *query* — always exits 0, even when `fmt --check`/`gate` would report diagnostics. The human outline opens with a pointer to `canon status` and, when no `spec_coverage` policy is in force, a `warning:` line; `--json` is unchanged. |
| `canon status [--repo <dir>] [--json]` | Where the repo stands and what to run next: the canon version and the policy in force (or a warning that the gate enforces nothing), with its level — the policy's `# canon policy level:` line when it names `light`, `standard` or `strict`, else the level its `spec_coverage` section matches exactly, else `custom` (`policy.level` in `--json`, `null` without a policy); a `light` or `standard` level also says how to raise it — subjects grouped by status with their scenario, evidence, review and open-blocker counts and missing required cases, the scenarios no subject owns, and a `next:` list of at most five concrete commands. Counts come from the same joins `gate check` and `subject status` use, and status fails closed: a corpus kind routed off the `local` rung leaves only the routing repair, and an unusable `spec_coverage` section puts its repair first and withholds every move-on suggestion. With several spec roots, suggested `canon scenario new` commands carry `--project`. For each `building`, `verifying` or `shipped` subject it shows whether the brief is approved: an `Approved:` line, outside HTML comments and code fences, in the `proposal.md` of the subject's newest adopted change, read under the `openspec` plan sources (no record kind). Fixes live as tasks in the approved change, so an older change's approval does not cover a newly adopted one. An unapproved brief adds the only step addressed to a human (`human: get the brief approved (one human answer covers brief and policy)`; `"actor": "human"` in `--json`) and withholds the subject's move-on; every other step is the agent's, including `canon subject status <id> shipped` once the ship guard would pass. When the policy has no approval record, or changed since it was approved, a `warning:` line says so (also in `--json` `warnings`). A read — always exits 0 and writes nothing but a stale scenario index it rebuilds (one stderr line; see `canon inventory sync`). `--json` is a stable shape versioned by `statusVersion` (`2` since 0.16: each `next` entry carries `actor`, and its `command` is a canon command only for `agent`; subjects carry `brief`). With `spec_coverage.require_audit` it shows an `audits` section (sampled, confirmed, owed, refuted) and suggests `canon evidence add --kind audit …`; recorded `--drop-attachment` drops list under `dropped bindings (N):` (`drops[]` in `--json`). |
| `canon context-pack create --manifest <repo-relative.json> [--repo <dir>] [--json]` | Create an immutable, content-addressed context snapshot from the explicitly selected files in a repository-local JSON manifest. Concise output prints only the pack id; `--json` prints manifest metadata and digests. |
| `canon context-pack show <id> [--repo <dir>] [--json]` | Verify and show a stored pack. `show` rechecks the manifest and every immutable content object before returning; concise output does not include captured bytes. |
| `canon context-pack verify <id> [--repo <dir>] [--json]` | Verify a pack without returning captured content. Exits nonzero when the pack is missing, stale, or tampered. |
| `canon adapter validate --response <path> [--repo <dir>] [--json]` | Read-only validation of a provider-neutral protocol-v1 response. Core fields are strict (`run_id`, provider/model, context-pack id, status, capabilities, safe evidence refs, and nonnegative ordered telemetry); provider data is opaque under `extensions`. JSON output is a redacted normalized summary with extension key names only. `--repo` optionally checks the context pack join; no provider is executed and capability declarations are not enforcement. |
| `canon prompt register --name <name> --version <version> --manifest <repo-relative.json> [--repo <dir>] [--json]` | Register a versioned prompt bundle from an explicit repository-local manifest in the immutable content registry. |
| `canon prompt show --name <name> --version <version> [--repo <dir>] [--json]` | Select and verify a registered prompt bundle version; default output is concise metadata, while `--json` includes snapshot metadata and digests. |
| `canon skills install [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Project one canonical `canon` skill. Claude receives `.claude/skills/canon/SKILL.md`; Codex receives `.agents/skills/canon/SKILL.md` (the directory Codex scans for skills); OMP receives `.omp/skills/canon/SKILL.md`; and Pi receives `.pi/skills/canon/SKILL.md`. Every selected provider receives lazy `reference/**` and `scripts/**` sidecars. OMP/Pi are project-local passive bundles; their retrieve pre-dispatch script is a sidecar, not a native hook. Provider selection is deterministic; absent selection detects `.claude`, `.agents` or `.codex` (Codex), `.omp`, and `.pi`, and defaults to Claude+Codex when none exists. A legacy `.codex/skills/canon.md` + `.codex/skills/canon/**` projection from canon 0.13.0 or earlier is removed file by file when its bytes still match the install lock; edited or user files stay, and `.codex/skills` is removed only if it ends up empty. The install lock (`.canon/skills/.install-lock.json`) records `canon_version`, the canon that wrote it, and `source_commit`, the `HEAD` of the git checkout the source is in (omitted outside one); a rerun with an unchanged bundle and the same canon leaves it byte-identical. |
| `canon skills check [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Read-only report of missing or stale canonical projections, the target-owned content manifest, any leftover legacy `.codex/skills` Codex projection (with its fix command), and an install lock another canon wrote: `<lock> — outdated (installed by canon X, this canon is Y — run canon skills install --providers=…)`, or "an unknown canon version" for a lock from before 0.16, which records none. Exits 1 on any of them. |
| `canon skills doctor [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | Human-readable provider, drift, outdated-lock (`outdated:`) and legacy-remnant diagnostics across all four managed roots and the legacy `.codex/skills` root, naming the fix command. It also lists other skills in `.claude/skills`, `.agents/skills`, `.omp/skills` and `.pi/skills` whose frontmatter `description` claims build work (one sentence holds both a build verb — build, implement, create, make, scaffold, develop or code, in any form — and a build object — site, website, app, application, game, feature, frontend, ui, page, component, tool, library, service, api, cli, server, backend, project, prototype, product, program or script, singular or plural; so "Build websites and apps" claims build work and "Manage feature branches" does not) as `competing-skill:` lines warning that if an agent picks one for build work, canon's loop will not run. Those lines are advisory: they never make the projections unhealthy or change the exit code, and canon never edits another skill or deletes user files. |

Canon contributors may use the legacy `canon skills install --source
canon/skills-dev --target .` materializer; it is not part of the consumer
installation flow.

## Subjects

Author and drive the durable product unit — canon's 13th record kind —
through its lifecycle, and adopt imported plan changes under it. See
[The Canon Concept](/concepts/canon/#subjects) for the subject-write-first
loop; "feature docs" always means Gherkin `.feature` files, a "subject"
is the management record.

| Command | Description |
|---|---|
| `canon subject new <id> --domain <d> --title <t> [--summary <s>] [--owner-role <r>] [--repo <dir>] [--json]` | Author a `Subject` (kebab-slug `<id>` is the durable `subject_id` join key). `--domain` is a vocabulary-defined kebab slug — base set `planning`/`design`/`dev`/`data`/`test`, extended per-repo via `.canon/vocab`. Starts at status `proposed`; `--owner-role` defaults to `implementer`. Envelope + policy validated at write. |
| `canon change new <slug> --subject <id> --title <t> [--repo <dir>]` | Scaffold `openspec/changes/<slug>/proposal.md` (the title as its `## Why`) and an empty `tasks.md` under the repo's `openspec` plans source, read them with the `openspec` adapter `canon ingest plans` uses, and record the change adopted into the subject through the same write as `canon subject adopt` — no `canon.yaml` edit. A failure before any record is written leaves nothing behind (the files are staged under `.canon/` and published only once they parse). The subject and change records cannot be written atomically: if the change record fails after the subject record, it exits `2`, keeps the change dir and the subject record, and prints the repair `canon ingest plans && canon subject adopt <slug> --subject <id>`, which is safe to rerun. Refuses (exit `2`, nothing written) an unknown subject, an existing slug, or a repo with no `openspec` plans source. |
| `canon subject adopt <change_id> --subject <id> [--repo <dir>] [--json]` | Link an imported plan `Change` (from `canon ingest plans`) to a `Subject`: stamps `Change.subject_id` and appends to the subject's `change_ids`. Writes only the side that lacks the link (a linked pair: nothing written, exit `0`). The subject is written first, since the gate reads adopted changes from its `change_ids`; if the change write then fails it exits `2` and prints `canon subject adopt <change_id> --subject <id>` to complete the link. |
| `canon subject status <id> <state> [--override-reason <text>] [--actor-id <id>] [--repo <dir>] [--json]` | Policy-gated transition along `proposed → specced → building → verifying → shipped` (plus any → `retired`). `verifying → shipped` additionally requires the subject to own at least one scenario — one whose `@subject:<id>` tag `canon inventory sync` has indexed — and every owned scenario to carry a latest non-Divergent verdict; a violation prints by failure class, exits `1`, and leaves the record unchanged (fail closed). With `spec_coverage.require_review` set, it also prints on stderr which review checks it ran or skipped, and a move into a `require_review.scope` status with gaps (`unreviewed-promotion`, `open-blocker`) is refused the same way. `--override-reason "<one line>"` waives only those two classes — never ship-gate verdict or case gaps — and records `status_override` (`to`, `reason`, `waived`: the exact `{class, subject}` violations it let through, `actor` from `--actor-id`, default `canon`) on the new record. A gap it did not record, such as a blocker raised later, still fails the gate; a blank or multi-line reason exits `2`. The waiver clears on the subject's next status write. Without `require_review`, nothing changes. Moving to `shipped` also refuses `false-success` (a scenario whose latest audit is `refuted`) and, when `require_audit.scope` covers `shipped`, an owed sampled audit. |

`verifying → shipped` also needs the subject's brief approved, by the same
check `canon status` uses for its `brief:` line: the `proposal.md` of the
subject's newest adopted change must carry an `Approved:` line outside HTML
comments and code fences. It runs with or without a policy. Without the line
the move is refused as `unreviewed-promotion <subject>`, naming that
`proposal.md` and saying a human must answer the brief; the agent writes the
line only from that answer. `--override-reason` waives it like a review gap
and records `{class: unreviewed-promotion, subject: <subject>}` in the
waiver. A brief that says the human ships changes who runs the move, not the
check.

## Corpus

Validate and grow a Gherkin `.feature` spec corpus.

| Command | Description |
|---|---|
| `canon format <ROOT> [--repo <dir>]` (alias `canon fmt`) | Validate a corpus root (e.g. `spec/`) against the artifact-family schemas + layout descriptors. Validating is the only mode, so `--check` is now the default and is accepted only for compatibility. |
| `canon inventory sync [--repo <dir>] [--spec-root <dir>]` | Validate each configured `specs.roots[]` entry with `canon-fmt`, then materialize one `Scenario` ledger-index record per `(project_id, scenario_id)`. `--spec-root` overrides `canon.yaml` for one ad hoc root. The index is derived from the `.feature` files, so `gate check`, `status`, `subject status`, `review add` and `evidence add` rebuild a stale index themselves before reading it (a scenario with no record, or a record whose source digest differs from the file): same code, only the changed files materialized, validation still over the whole root. They print one stderr line — `canon status: refreshed the scenario index from 1 changed feature file(s) (…): 1 record(s) written` — and nothing when the index is fresh; a root that fails to sync is named as `NOT refreshed` with a pointer back here, and the command still runs. Nothing is written in a directory without `canon.yaml`. Run `inventory sync` to index explicitly and to list the violations. |
| `canon scenario new <TAG> --title <label> [--subject <id>] [--lane <v>] [--case <v>] [--actor <id>] [--feature <path>] [--repo <dir>]` | Append (creating if absent) a `.feature` stub for a `<area>.<surface>.<nn>` tag: a `# canon:` provenance line directly above the tags, then `@subject:<id>` / `@lane:<v>` / `@case:<v>` if given, then the id tag and header. `--actor` (or `CANON_ACTOR`) names the provenance actor, default `canon-scaffold`; `--lane` and `--case` are checked against the repo's `lane`/`case` vocabularies. Writes no ledger record. |
| `canon feature new <SURFACE> --title <label> [--actor <id>] [--repo <dir>]` | Scaffold a fresh, zero-scenario `.feature` file for a not-yet-started `<area>.<surface>`. Fails loud rather than overwriting an existing file. |

## Ingest

Fold agent-CLI sessions, evidence artifacts, and foreign plan dialects into
tiered storage.

| Command | Description |
|---|---|
| `canon ingest sessions [--watch] [--interval-secs <n>] [--home <dir>] [--canon-yaml <path>] [--full] [--all-workspaces]` | Scan every registered session-store adapter (`omp`/`pi`, Claude Code, Codex, Hermes), normalize into `Session`/`Run`/`Event` records — including `user_directive` events captured from user turns — persist through canon-store. Defaults to THIS PROJECT's sessions (main worktree + every linked `git worktree` root); `--all-workspaces` restores the machine-wide scan. `--watch` polls (default 30s) with a per-FILE watermark so only changed transcripts reparse; `--full` ignores the watermark. |
| `canon ingest artifacts [--watch] [--interval-secs <n>] [--repo <dir>] [--json]` | Run the artifact/verdict half of the join spine: ledger/divergence/openspec-task path adapters plus the handoff records-source, derive verdicts, fold into regime-keyed trajectories, persist via canon-learn. Unlike `sessions`, a repeated `--watch` pass is not yet write-idempotent. |
| `canon ingest plans [--dialect <name> --source <dir>] [--repo <dir>] [--json]` | Import one plan dialect — `openspec` change dirs, or `superpowers` writing-plans-shaped docs (s30: `# <title>`/`**Goal:**`/`### Task N:` sections, a task done iff every checkbox in its section is checked) — into canon-model's Change/Task records, both keyed `task_id = <change_id>#<n>` through the same join. No `--watch` — plans are operator-pulled. `--dialect`/`--source` bypass `canon.yaml`'s `plans:` section for a one-shot import; both are required together. |

## Trust

The trust-spine gate, plus the native `Review`/`Divergence` verdict
producers it reads.

| Command | Description |
|---|---|
| `canon gate check [--repo <dir>] [--release]` | Run the coverage/ledger/staleness/spec-coverage/bound-artifact/trust-ladder check set, printing violations by failure class (ten: `uncovered-cell`, `unreviewed-promotion`, `trust-below-required`, `stale-evidence`, `malformed-evidence`, `flagged`, `unevidenced-flip`, `fabricated-evidence`, `open-blocker`, `false-success`). With the opt-in `spec_coverage.require_review`, in-scope scenarios without an independent `Review` are `unreviewed-promotion` and open `blocker` findings on adopted changes are `open-blocker`; gaps waived by `canon subject status --override-reason` print afterwards as `review waivers:` advisories without failing. When the indexed spec corpus has scenarios but `.canon/policy.yaml` has no `spec_coverage` section, one stdout line `advisory: spec_coverage is off — N scenario(s) are not checked for evidence; see .canon/policy.yaml` follows the result; the exit code is unchanged. Exit `0` clean, `1` gate-red, `2` usage/load failure. `--release` additionally engages the release-scoped trust check. A file bound to a latest evidence record must still be provable: from its stored blob, or (records from before 0.14) from a working-tree file with the recorded digest, which prints an `evidence artifacts:` advisory naming `canon evidence vault`; otherwise it is `stale-evidence`. With `spec_coverage.require_audit: {rate, seed, scope}`, a deterministically sampled in-scope scenario whose latest audit is missing or `indeterminate` is `uncovered-cell`; a scenario whose latest audit is `refuted` is always `false-success`, whatever the policy, overriding any declared faithful verdict until a newer audit clears it. When `.canon/policy.yaml` exists but has no approval record, changed since approval, or the record is unreadable, an `advisory: policy not approved: …` / `advisory: policy changed since approval: …` / `advisory: policy approval unreadable: …` line follows the result, naming `canon policy approve --by <who>`; the exit code never changes. |
| `canon gate task <TASK_ID> [--repo <dir>]` | Evidence-gated checkbox flip for one plan `task_id` (`<change_id>#<n>`). Fails closed — the row stays unflipped — on missing, malformed, or fabricated evidence. The row's note sums up every record bound to the task (`2 evidence records (2 faithful); latest: <summary>`), and the plan source is re-ingested so `canon query --kind task` agrees. The flip still happens, but a warning goes to stderr when no evidence record for the task binds a file (`--artifact`/`--report`) and one of them cites a canon command as its `--ref` (for example `canon gate check`): bind the artifact or report that proves the task. |
| `canon gate promote [--repo <dir>] [--dry-run]` | Promote `_staging/` evidence records to the committed ledger, assigning a monotonic per-(role, surface) `run_seq`. `--dry-run` prints the plan without writing. `evidence add` and `finding add`/`close` stage for it. Under `canon.yaml`'s `write: { promote: auto }` (what `canon init` writes) or with `--promote`, they promote the one record they just staged in the same run — the same validation and `run_seq` assignment as this command, printing that record's promote line — and say `— staged and promoted in this run; nothing to promote`, so a separate `gate promote` is unnecessary for it. A record another run staged stays staged; only `gate promote` commits everything staged. It stays idempotent (with nothing staged it prints `nothing staged`, exit `0`). Under `write: { promote: manual }` (also the default when `write:` is absent) or with `--no-promote` they say ``— run `canon gate promote` to commit it``. When the promotion refuses the command's own record, it stays staged, the line says ``— run `canon gate promote` to commit it``, and the command exits `1`. `--promote` with `--no-promote` is exit `2`; with neither flag, a malformed `write:` section refuses the write (exit `2`) before anything is staged. Every other write command says `— written directly; nothing to promote`. |
| `canon gate install-hooks [--repo <dir>] [--event <name>] [--matcher <m>] [--command <cmd>] [--timeout <secs>]` | Idempotent, diff-only hook-seam install into `.claude/settings.json`/`.codex/hooks.json`, plus a generic pre-commit script. Defaults: `--event PreToolUse`, `--command "canon gate task"`, `--timeout 30`. |
| `canon gate selftest` | Run the shipped fixture corpus: every `FAILURE_CLASSES` string (all ten, including `false-success`) proven to fire, exact-set-match against `expected_failures.txt`. Takes no `--repo`. |
| `canon evidence add --task <id> --kind <k> --ref <r> --role <role> [--session-id <id>] [--surface-ref <path-or-effect>] [--verdict <v>] [--summary <s>] [--command-result <out>] [--scenario-id <id>] [--run-id <ulid>] [--artifact <path>] [--report <junit\|cucumber>:<path>] [--report-case <name>]... [--max-artifact-mib <n>] [--promote\|--no-promote] [--repo <dir>]` | Stage one attributed `EvidenceRecord` for a plan task, commit it — in the same run under `write: { promote: auto }` (what `canon init` writes) or with `--promote`, otherwise with `canon gate promote` (see there) — and spend it with `canon gate task`. A stale scenario index is rebuilt first (see `canon inventory sync`). `--surface-ref` persists a validated path or `effect:<kebab-slug>` risk binding, but remains attestation input rather than proof of changed paths. `--summary` is allowed with or without `--task` and scanned for fabrication markers; a task's flipped row shows the latest one; a line break in it is refused, because one would forge a second checked row. Risk approvals count only with a detached SSH signature verified against policy-pinned `approval.allowed_signers` and `--approval-role human`; `CANON_ACTOR`, caller text, and agent roles are not counted. **Experimental:** `--artifact` binds any repository file by sha256 and `--report` parses a JUnit/Cucumber report, recording the scenario's matched case and outcome (a `faithful` verdict over a failed case is refused); canon never runs the test. `--scenario-id` alone (with `--project-id`) attests a scenario instead of a task; a record with both answers both. Every report case carrying the scenario id is bound, `--report-case` (repeatable) adds more, and any failed bound case refuses `faithful`. Bound files are copied into `.canon/artifacts/sha256/<hex>` (tracked; commit them); a file over 25 MiB is refused unless `--max-artifact-mib` raises the limit. `--kind audit` records an external evaluator's audit — canon never generates or runs one: it requires `--evaluator-id`, `--evaluator-version`, `--evaluator-digest` (sha256, 64 lowercase hex), `--audit-result confirmed\|refuted\|indeterminate`, `--scenario-id` and `--project-id`, refuses `--task`, `--verdict`, `--surface-ref` and `--approval-*`, binds optional `--report`/`--artifact` counterexamples, and derives the verdict (confirmed → faithful, refuted → divergent, indeterminate → not-applicable); audits fold apart and never become the scenario's latest declared verdict. For a scenario, a record that stops binding a file the current latest record of its fold (staged or committed) binds is refused (exit `2`) unless it re-binds the path or names it with `--drop-attachment <path>` (repeatable) plus one single-line `--drop-reason <text>`, recorded as `attachment_drop: {paths, reason}`. |
| `canon evidence vault [--max-artifact-mib <n>] [--repo <dir>]` | Store the bound files of existing evidence records (written before 0.14) in `.canon/artifacts/sha256/`: each file whose working-tree bytes still match the recorded digest is copied in, everything else is listed as not stored with both digests. Exit `0` when it ran, `2` on a ledger read or write failure. |
| `canon finding add --change-id <id> --round <n> --seq <n> --severity <s> --reviewer <name> --summary <s> [--disposition <d>] [--reviewed-sha <sha>] [--resolution-sha <sha>] [--introduced-by <sha>] [--file-ref <path:lines>] [--session-id <id>] [--promote\|--no-promote] [--repo <dir>]` | Stage one code-review finding as a durable record, so a release note's count is read rather than remembered. Under `write: { promote: auto }` or with `--promote` it is promoted in the same run; otherwise `canon gate promote` commits it (see there). A defect the author found in its own work is recorded the same way, with `--reviewer` set to the author; `--introduced-by` names the introducing commit, so `--introduced-by self` is refused. `--seq` is required and a collision is refused. `fixed` requires `--resolution-sha`, and only `fixed` may carry one. `--reviewed-sha`/`--resolution-sha`/`--introduced-by` take a full 40-char sha or a short one (4–40 lowercase hex); a short sha is resolved with `git rev-parse` and the record stores the full sha. Refused (exit `2`) when it names no commit, is ambiguous, resolves only through a tag, or the directory is not a git repo. |
| `canon finding close --change-id <id> --round <n> --seq <n> --disposition <d> [--resolution-sha <sha>] [--session-id <id>] [--promote\|--no-promote] [--repo <dir>]` | Move an already-committed finding's disposition. Append-only: this writes a superseding record rather than editing history, so the round it was raised in is preserved. Reopening is a real transition. `--resolution-sha` takes a full or short sha, resolved through git as in `finding add`. Staged and promoted like `finding add`. |
| `canon review add --project-id <id> --scenario-id <id> --reviewer <name> --pin <pin> --role <role> --upstream-ref <ref>` (or `--original-spec-ref <ref>`) `[--actor-id <id>] [--session-id <id>] [--outcome signed\|indeterminate\|unavailable] [--reviewer-provider <p>] [--reviewer-model <m>] [--reviewer-harness <h>] [--artifact <path>]... [--max-artifact-mib <MiB>] [--repo <dir>]` | Write one native, attributed `Review` record directly to the ledger; there is nothing to promote. Exactly one of `--upstream-ref`/`--original-spec-ref` is required — both or neither refuses the write. The review pins what it saw, computed from the corpus: the scenario's source digest and its latest evidence records (`key`, ledger file digest); a scenario with no record is refused with exit `2`. Under `require_review` a pinned review counts only while both are unchanged; otherwise it is a stale `unreviewed-promotion`. `--outcome` (default `signed`) records an `indeterminate` or `unavailable` reviewer run as a gap, never an approval; the latest review per reviewer wins. `--reviewer-provider`/`--reviewer-model`/`--reviewer-harness` record the reviewer runtime. `--session-id` fills `actor.session_id`: under `require_review.distinct_actor`, a review from a session that attested the scenario's evidence does not count. `--artifact` (repeatable) binds a screenshot or recording the reviewer looked at, exactly as `evidence add --artifact` does: inside the repo, within `--max-artifact-mib` (default 25), stored in `.canon/artifacts/sha256/` and recorded as `{path, sha256}`; a refusal exits `2` and writes nothing. `canon gate check` re-hashes the stored blobs of every in-effect review, and a missing or altered one is `stale-evidence` naming the review. Canon never compares images. |
| `canon divergence stage --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --role <role> [--status <status>] [--reason <r>] [--expiry <e>] [--round <n>] [--detail <d>] [--promote\|--no-promote] [--repo <dir>]` | Write one unordered staging candidate carrying no `run_seq`; `--status` accepts `open`, `still-divergent`, `resolved`, or `deferred` (`deferred` additionally requires `--reason`/`--expiry`). `canon divergence promote` assigns `run_seq` later — or this same run does for this one candidate, under `write: { promote: auto }` or with `--promote`, ending `— staged and promoted in this run; nothing to promote`; other staged candidates stay staged. A candidate the promotion refuses stays staged, the line says ``— run `canon divergence promote` to commit it``, and the command exits `1`; flags and `write:` work as for `canon gate promote`. |
| `canon divergence promote [--repo <dir>] [--dry-run]` | Batch-promote every currently-staged `Divergence` candidate, assigning each a monotonic `run_seq` within its `(project_id, role, surface)` partition. |
| `canon divergence resolve --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --role <role> [--round <n>] [--detail <d>] [--repo <dir>]` | Direct-commit a `Resolved` candidate — never touches the staging directory. |
| `canon divergence defer --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --reason <r> --expiry <e> --role <role> [--round <n>] [--repo <dir>]` | Direct-commit a `Deferred { reason, expiry }` candidate — never touches the staging directory. |
| `canon divergence status [--repo <dir>] [--as-of <date>]` | The current-state divergence burn-down view. `--as-of` governs `Deferred` expiry evaluation; defaults to now. |

A review written before 0.15 carries no pins, only `--pin`, the commit it
reviewed. `gate check`, `status` and `subject status` read the scenario at
that commit through `git` and decide the same way: **current** when its
per-scenario digest there equals today's and no declared evidence is newer
than the review (it counts); **stale** when the spec changed since the pin
or the evidence is newer (`unreviewed-promotion`, like a stale pinned review);
**undecidable** when the commit or the scenario at it is not in this clone
(it still counts, as in 0.15). One advisory line counts the three, counts a
stale one as superseded when its scenario already has another current
review, and names only the scenarios still owed a review. In CI, check out
full history (`fetch-depth: 0`) for the gate job, or every such review is
undecidable.

## Memory

Distilled strategies, role+regime-scoped retrieval, and the dispatch-time
write seam.

| Command | Description |
|---|---|
| `canon learn promote <STRATEGY_ID> [--repo <dir>] [--evaluation <path> --approval <path>] [--signature <path>] [--dry-run]` | Activate one **quarantined** `StrategyItem` into `.canon/strategies/<role>/<id>.md`. The configured `occurrence`/paired-`crn` gate is only eligibility; activation also requires a valid paired `PromotionEvaluation` and an approval declared `human`, signed with an SSH detached signature. The evaluation requires non-empty paired baseline/candidate result digests, finite `pairs`/positive `uplift`/zero `regressions`, matching integrity/provenance, and a passing decision. The verifier uses policy-pinned `approval.allowed_signers` with `ssh-keygen -Y verify`; `--evaluation` and `--approval` are required together, and there is no `--force`. `--dry-run` does not activate. |
| `canon learn approve <STRATEGY_ID> --evaluation <path> --principal <id> [--repo <dir>] [--json]` | Validate the quarantined candidate/evaluation and print an unsigned, domain-separated `canon-learning-approval-v1` payload (`strategy:<id>`, evaluation digest, RFC3339 timestamp, `payload_hex`) for an external SSH signer. It never reads a private key or sets `verified`. |
| `canon learn request <STRATEGY_ID> --evaluation <path> --principal <id> [--repo <dir>] [--json]` | Exact alias of `learn approve`; emits the same unsigned approval payload. |
| `canon learn rollback <STRATEGY_ID> --reason <text> --actor <id> --signature-file <path> --approved-at <RFC3339> [--contradicting-trajectory-id <id>] [--repo <dir>]` | Authenticated operator rollback, distinct from ordinary contradiction demotion. Verifies an armored SSH signature over the rollback-bound payload against policy-pinned `approval.allowed_signers`, records provenance, and sets lifecycle `rolled_back`. |
| `canon retrieve --role <role> (--regime <regime_key> \| --domain <d> [--subject <id>]) [--k <n>] [--repo <dir>] [--json]` | Role+regime-scoped strategy retrieval. Give `--regime` directly, or derive it from `--domain`/`--subject` — retrieval tries area candidates `<domain>-<subject_id>` then `<domain>` in that fallback order. `--role` must equal the regime's leading segment (exit `2` on mismatch). Fail-soft: always exits `0` once that holds; a store outage degrades to an empty list. Quarantined/rejected/rolled-back/demoted rows are excluded; legacy `lifecycle: null` rows remain readable but carry no current paired-evaluation or SSH-approval provenance and are not measured-uplift evidence. |
| `canon dispatch begin --role <role> --regime <regime_key> [--context-manifest <repo-relative.json>] [--prompt-bundle <name@version>] [--agent-id <id>] [--repo <dir>] [--json]` | Mint a `Run` (status `Running`), retrieve guidance for `--role`/`--regime`, and record an immutable ContextPack lineage. An explicit context manifest selects the exact docs/tools/prompts captured; `--prompt-bundle` selects and verifies a registered immutable prompt bundle. Missing, unsafe, or tampered selections are rejected before any run id or manifest is written. |
| `canon regime-key --role <r> --repo <r> --area <a> --hash <h>` | Serialize + validate one canonical `regime_key` (`<role>/<repo>/<area>/<hash>`) from raw segments — the shell-facing counterpart to the Rust serializer every write/read path shares. Prints the key and exits `0`; exits `2` on a malformed result. |

## Surface

Read the current state: reports, the dashboard, ad hoc queries, tier
maintenance, plugin overlays, and self-checks.

| Command | Description |
|---|---|
| `canon report [--repo <dir>] [--check] [--snapshot <dir>]` | Generate the markdown status report (default), byte-diff it against the committed copy (`--check`, exit `1` on drift), or export panel marts to Parquet + `manifest.json` (`--snapshot`, wins if both given). |
| `canon dashboard [--repo <dir>] [--snapshot <dir>] [--port <n>]` | Serve the built dashboard app locally against a snapshot. Default port `4173`; an omitted `--snapshot` regenerates fresh at `.canon/dashboard-snapshot` on every run. |

| `canon purge --kind &lt;session|run|event|trajectory&gt; --before &lt;RFC3339&gt; [--repo &lt;dir&gt;] [--dry-run] [--json]` | Purge matching records from the routed rung and every aging destination, including historical versions. Apply mode preflights all destinations; dry-run is non-destructive. It never deletes source transcripts or Git history. |
