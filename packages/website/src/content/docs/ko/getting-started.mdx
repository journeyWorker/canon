canon은 **npm 런처 뒤에 있는 하나의 Rust 코어**로 배포됩니다: 미리
빌드된 플랫폼 바이너리가 npm `optionalDependencies`이고, 얇은 JS
쉼(shim)이 맞는 것을 골라 씁니다. [Bun](https://bun.sh)이 있다면
이미 필요한 모든 것이 갖춰진 셈입니다. npm 패키지 이름은
`@journeykit/canon`이며, 설치되는 바이너리 이름은 여전히 `canon`이므로
`bun add -g @journeykit/canon` 후 그냥 `canon <cmd>`로 실행해도 됩니다.

```bash
bunx @journeykit/canon --help
```

**미리 빌드됨:** macOS arm64 · Linux x64 (glibc) · Windows x64. 그 외
플랫폼(Intel Mac, musl/arm64 Linux, Windows arm64)은 로컬 Rust 툴체인으로
소스에서 빌드합니다
(`cargo build --release -p canon-cli`).

## 5분 만에 보기: gate가 막고, 통과하기

canon을 실제 레포에 연결하기 전에, 일회용 데모로 trust spine이 어떻게
동작하는지 먼저 봅니다. `canon demo`는 작은 evidence loop를 스캐폴드합니다
— 사전 개념 학습이 필요 없습니다.

```bash
mkdir canon-demo && cd canon-demo

bunx @journeykit/canon demo init      # 일회용 evidence loop 스캐폴드
bunx @journeykit/canon gate check     # RED  — gate가 거부
bunx @journeykit/canon demo review    # reviewer의 evidence 기록
bunx @journeykit/canon gate check     # GREEN — gate 통과
```

첫 `gate check`는 실패하며, 빠진 evidence를 정확히 지목합니다:

```output
canon gate check: 1 violation(s)

uncovered-cell (1):
  uncovered-cell auth.login.01 — policy-required cell 'reviewer' has no matching-role evidence record
```

`dev` voice가 scenario `auth.login.01`에 evidence를 남겼지만, `policy.yaml`은
독립적인 `reviewer`를 요구합니다. reviewer evidence가 없으니 → 이 cell은
uncovered → gate가 red입니다. `demo review`가 그 evidence를 기록하면 같은
check가 green으로 바뀝니다:

```output
canon gate check: clean (0 violations)
```

이 red → green 전환이 곧 canon입니다: 완료는 자가 보고가 아니라, 존재하고
귀속되며 최신인(fresh) evidence로 게이트됩니다. 전체 failure-class 표는
[Trust spine](/ko/concepts/trust-spine/)을 참고하세요.

**Done when:** 둘째 `canon gate check`가 `clean (0 violations)`을 출력하고 exit `0`으로
끝나면 데모는 끝입니다. 결과는 `gate check`의 출력(`--json`이면 `data`)에서 읽습니다.

## 하나의 문법, 하나의 명세

canon의 모든 명령은 명세 하나(`docs/cli/canon.cli.json`)에서 생성된 하나의 문법을
따릅니다. `--help`, [CLI 레퍼런스](/ko/cli/)의 표, 에이전트 가이드가 모두 같은
명세에서 나오고, 옵션 이름은 `canon schema <command>`로 확인합니다. 외워 둘 것은
몇 가지뿐입니다:

- **`--json`은 봉투 하나**를 냅니다: `{ok, data, meta}`. 쓰기 명령은 `meta.next`로 다음
  단계를, 같은 입력의 반복은 `meta.unchanged`로 "이미 있음"을 알립니다.
- **쓰기 명령은 모두 `--input`**(인라인 JSON, 파일, `-`로 stdin)을 받습니다. 배열은
  배치이고 첫 쓰기 전에 전부 검증됩니다. `canon schema <command> --json`이 입력
  스키마와 예시를 보여 줍니다.
- **코드에 묶이는 기록은 `--rev`**(git revision, 기본 `HEAD`)를 받습니다. 커밋하지
  않은 코드도 기록할 수 있으며 `codeTree`가 함께 남습니다.
- **파괴적 명령은 미리보기가 기본**입니다. `--commit --plan-digest <digest>`를 줘야
  실행됩니다.

## 레포 설정하기

<Steps>

1. **설정 파일 스캐폴드.** 레포 루트에서:

   ```bash
   bunx @journeykit/canon init
   ```

   바로 동작하는 `canon.yaml` 스켈레톤을 씁니다 — 스토리지
   `tiers:`, 레코드 `routing:`, 기본 root `.canon/specs`를 가진
   `specs:`(`.feature` 파일은
   `<root>/kind=feature/area=<area>/<surface>.feature`에 두며, 직접
   작성하고 git으로 추적합니다), 그리고 `sources: []`인 `plans:` 섹션까지.
   canon 자체의 change는 `.canon/changes/`에 있어 여기에 항목이 필요 없고,
   주석은 직접 준비한 외부 plan을 나열하는 법을 보여 줍니다(주석 처리된
   `openspec`, `superpowers` 예시). canon은 외부 plan을 읽기만 합니다.
   함께 쓰는 것은 다음과 같습니다:

   - **`.canon/policy.yaml`**: `spec_coverage`를 켜는 시작 정책입니다.
     모든 시나리오에 evidence가, 모든 feature surface에 `@case:failure`
     시나리오가, 완료를 주장한 subject의 작업에는 독립 리뷰가
     필요합니다. 이것이 기본 `strict` 수준입니다. `--policy standard`는
     리뷰를, `--policy light`는 failure 케이스까지 빼고, 수준을 올릴 때
     주석을 풀면 되도록 주석 줄로 남겨 둡니다. 첫 줄
     `# canon policy level: <level>`이 수준을 밝히고 `canon status`가
     보여 줍니다. gate가 이 정책으로 작업을 채점하므로 사람이 승인합니다.
     서브젝트의 brief를 승인하는 같은 답변으로 함께 승인하며, 에이전트가
     그 답변을 `canon brief approve --approver <human> --note "<their words>"`
     한 번으로 기록합니다(둘 다 기록됩니다). `brief approve`와 `policy approve`는
     사람만 할 수 있는 단계라 에이전트 역할로는 거부됩니다. 그 전까지
     `canon gate check`와 `canon status`가 advisory를 출력합니다.
   - **`AGENTS.md`의 canon 블록**: `<!-- canon:begin -->`과
     `<!-- canon:end -->` 사이에 씁니다. 어떤 에이전트에게든 기능을
     canon으로 관리한다는 것, 작업 루프, `canon status`와 canon 스킬을
     알려 줍니다. 루프는 범위마다 한 번만 사람을 기다립니다: 새
     서브젝트나 승인된 서브젝트의 범위 변경에는 brief와 정책을 함께
     승인하는 답변 하나가 필요합니다. 승인된 범위 안에서는 에이전트가
     멈추지 않고 수정·후속 작업을 하고, 변경마다 독립 리뷰를 받고,
     ship까지 진행합니다. 파일이 없으면 만들고, 있으면 마커 사이의
     텍스트만 canon이 관리합니다. 마커는 코드 펜스 밖의 단독 줄일 때만
     인정되며, 중복되거나 짝이 맞지 않는 마커는 거부하고 아무것도 쓰지
     않습니다.
   - **고른 하네스용 canon 스킬 스텁**: 터미널에서는 `init`이 어느 하네스에
     설치할지 묻고, `.claude`·`.codex`·`.omp`·`.pi` 디렉터리가 있는
     하네스를 미리 체크해 둡니다. `--providers claude,codex`(또는
     `none`)를 주면 묻지 않습니다. 터미널도 플래그도 없으면 감지된
     하네스에만 설치하고, 감지된 것이 없으면 아무것도 설치하지 않은 채
     `canon skills install --providers=<list>`를 안내합니다. 답은
     `canon.yaml`에 `skills: { providers: [...] }`로 기록됩니다.
     `.agents`만으로는 Codex를 선택하지 않습니다. 설치되는 `SKILL.md`는 짧은
     스텁이며 에이전트를 `canon skills show canon`으로 보냅니다.

   `--no-agents-md`와 `--no-policy`로 둘을 건너뜁니다. `init`은 기존
   `canon.yaml`과 `policy.yaml`을 절대 덮어쓰지 않으며, 다시 실행하면
   `AGENTS.md` 블록만 갱신합니다. 기존 설정은 언제든 다음으로 검증할
   수 있습니다:

   ```bash
   bunx @journeykit/canon init --check
   ```

   설정을 손으로 고치지 않고 subject 아래에 change를 시작합니다:

   ```bash
   bunx @journeykit/canon subject new auth --domain dev --title "Auth"
   bunx @journeykit/canon change new add-login --subject-id auth --title "Add login"
   ```

   `change new`는 `.canon/changes/add-login/brief.md`를 쓰고 change를
   subject에 adopt합니다. `tasks.md`는 쓰지 않습니다(아무것도 gate하지 않는
   선택적 작업 메모입니다). brief는 요청의 언어로 쓴 PRD
   골격입니다(`canon init --language ko`가 기록하는 `canon.yaml`의 `language:`가 `canon brief check`의 감지보다 우선합니다): 의도, 원하는 결과,
   `F1`, `F2`, … 단계로 된 사용자 흐름, 단계 상세, 인수 조건, 질문과 가정,
   범위 밖. 에이전트가 이를 채우고 blocker가 없고 prose advisory가 모두 고쳐지거나 이유와 함께 면제될 때까지
   `canon brief check`를 실행한 뒤, 멈추고 사람에게 그 언어로 보고합니다. 사람이 승인하면 에이전트가
   `canon brief approve add-login --approver <human> --note "<their words>"`로
   답을 기록하며, 이 명령이 brief 본문에 묶인 `Approved:` 줄과 정책 승인을 함께
   씁니다. 이후 brief를 고치면 사람이 다시 답하기 전까지 승인되지 않은 것으로
   읽힙니다. 각 시나리오는 자신이 증명하는 단계를 가리키고
   (`canon scenario new --flow F1`), `canon status`는 단계마다 시나리오를
   보여 주며 시나리오나 실패 케이스가 없는 단계를 표시합니다. 또
   `canon status`는 서브젝트가 관할하는 change(시나리오가 태그한 것, 승인 줄이 있는 것, chore)마다
   승인을 읽어 `briefs`에 보여 주고, 승인이 없을 때만 사람에게 요청하라고 안내합니다.
   사용자에게 보이는 것이 바뀌지 않는 작업(의존성, 빌드, 리팩터링)은
   `canon change new <slug> --change-kind chore`로 하며, 짧은 brief에 새 시나리오가 없습니다.
   외부 plan(`plans.sources`에 나열한 openspec `proposal.md`)에서 온 change도
   `.canon/changes/<change>/brief.md`에 brief를 두며, 그 파일의
   `Source: <path>` 줄이 plan을 가리킵니다. canon은 plan을 고치지 않습니다.
   수정과 후속 작업은 승인된 change 안에 머뭅니다. 새 `canon change new`는 새
   범위이므로 사람의 승인이 필요합니다.

2. **저작 표면(authoring surface) 확인.** canon 아티팩트를 작성하기
   전에, 이 레포가 어떤 어휘와 스키마로 해석되는지 먼저 물어봅니다:

   ```bash
   bunx @journeykit/canon context
   ```

   이것은 검증이 아니라 역량 *조회*(query)입니다 — 항상 exit 0으로
   종료하며 레코드 종류, enum domain, join-key 문법, 정책 기반
   요구사항을 출력합니다. 머신이 읽을 수 있는 형태가 필요하면
   `--json`을 추가하세요. 특정 명령의 옵션과 입력 형태는
   `canon schema <command>`가 알려 줍니다.

3. **시나리오 작성과 인덱싱.** 레포가 설정된 `specs.roots[]` 항목 아래에
   Gherkin `.feature` 스펙을 보관한다면, 시나리오를 추가하고 코퍼스를
   검증한 뒤 인덱스를 구체화합니다. 시나리오가 여럿이면 `--input` 배열
   하나로 한 번에 씁니다(전부 검증된 뒤에야 쓰기 시작합니다):

   ```bash
   bunx @journeykit/canon scenario new auth.login.01 --title "Sign in" --feature .canon/specs/kind=feature/area=auth/login.feature
   bunx @journeykit/canon format          # 먼저 코퍼스를 검증
   bunx @journeykit/canon inventory sync  # 시나리오 레저 인덱스를 구체화
   ```

4. **에이전트 세션 적재.** Claude Code, Codex 등 등록된 에이전트
   CLI의 트랜스크립트를 티어드 스토리지로 접어 넣습니다 — 소스별
   워터마크를 통해 증분(incremental) 방식으로:

   ```bash
   bunx @journeykit/canon ingest sessions
   bunx @journeykit/canon ingest sessions --watch   # 계속 폴링
   ```

5. **evidence 기록과 작업 게이트 통과.** 시나리오마다 evidence를 남기고(리뷰는
   독립된 reviewer가 `review scenario`로) gate를 실행합니다. 트러스트
   스파인이 coverage, verdict ledger, staleness를 검사합니다 — 완료는 절대
   자가 보고되지 않고 항상 증거로 게이트됩니다. 기록은 `--rev`(기본 `HEAD`)에
   묶이며, 커밋하지 않은 코드에 대한 기록도 허용됩니다:

   ```bash
   bunx @journeykit/canon evidence add --scenario-id auth.login.01 --class test-run --ref "npm test" --role implementer
   bunx @journeykit/canon review scenario auth.login.01 --actor-id reviewer-1 --role reviewer --original-spec-ref docs/prd.md
   bunx @journeykit/canon gate check
   ```

   각 쓰기의 출력 끝에 `next:` 줄(`--json`이면 `meta.next`)이 다음 명령을 알려
   줍니다.

6. **현재 상황 읽기.** 레포 상태 리포트를 생성하거나(생성된
   파일이며 절대 손으로 편집하지 않음) 로컬 대시보드를 엽니다:

   ```bash
   bunx @journeykit/canon report build
   bunx @journeykit/canon dashboard
   ```

</Steps>

**Done when:** `canon gate check`가 `clean (0 violations)`(exit `0`)이고
`canon subject show auth`에서 서브젝트가 ship 가능한 상태로 보이면 끝입니다.
무엇이 남았는지는 `canon status`가 서브젝트별 gap과 다음 명령으로 보여 줍니다.

## 에이전트 하네스를 위한 설정

레포에서 코딩 에이전트를 실행한다면, 선택한 provider의 레포 로컬 위치에 canon
스킬 **스텁**을 설치합니다. Claude에는 `.claude/skills/canon/SKILL.md`, Codex에는
`.agents/skills/canon/SKILL.md`(Codex는 `.codex/skills`가 아니라 `.agents/skills`를
탐색합니다), OMP에는 `.omp/skills/canon/SKILL.md`, Pi에는
`.pi/skills/canon/SKILL.md`가 생성됩니다. 스텁은 canon이 무엇인지, 다섯 줄짜리
루프, 그리고 "전체 가이드는 `canon skills show canon`, 옵션은 추측하지 말고
`canon schema <command>`"만 담습니다. 가이드 본문은 바이너리에 들어 있으므로
레포에 reference 파일이 투영되지 않고, canon을 올리면 가이드도 같이 올라갑니다.
`canon init`이 고른 하네스에 이미 설치해 둡니다. `skills install`, `check`,
`doctor`는 `canon.yaml`의 `skills.providers`를 따릅니다. 그 키가 없는 레포(0.17
이전에 설정한 레포)는 설치 lock에 기록된 provider를, 그것도 없으면 감지된
`.claude`·`.codex`·`.omp`·`.pi` 디렉터리를 씁니다. 감지되지 않은 하네스를 기본으로
더하는 일은 없습니다. 목록을 바꾸려면 `--providers`를 주세요. install이
`canon.yaml`에 기록합니다:

```bash
# 네 provider에 canon 스킬 스텁을 설치하고 목록을 기록
bunx @journeykit/canon skills install --providers=claude,codex,omp,pi

# 쓰기 없이 설치 상태 확인
bunx @journeykit/canon skills check
bunx @journeykit/canon skills doctor

# 에이전트가 읽는 가이드: 바이너리에서 출력
bunx @journeykit/canon skills show canon
bunx @journeykit/canon skills show role-implementer

# 태스크 시작 전에 역할별 전략 메모리를 노출
bunx @journeykit/canon retrieve --for-role dev --regime "$(bunx @journeykit/canon regime show --role-segment dev --repo-name my-repo --area core --hash abcdef012345)"
```

`skills show <NAME>`은 `canon`(핵심 가이드)이나 reference 이름(`role-implementer`,
`role-reviewer`, `canon-gate` 등)을 받고, `--full`은 요약 대신 전문을 냅니다.
각 워크플로는 끝에 **Done when:** 줄로 완료 기준을 밝힙니다.

`skills check`와 `skills doctor`는 읽기 전용입니다. `check`는 누락되거나
오래된 스텁을 보고하고, `doctor`는 네 관리 root 전체의 provider·drift·legacy
잔재를 진단하며 사용자 파일을 삭제하지 않습니다. 설치 잠금 파일은 자신을 쓴
canon 버전을 기록하므로, canon을 올린 뒤에는 다시 설치할 때까지 둘 다
"installed by canon X, this canon is Y — run `canon skills install`"이라고
알려 줍니다. `doctor`는 더 이상 선택되지 않은 하네스에 남은 canon 설치도 `stray:`
줄로 알려 주며 지우는 `rm -r` 명령을 함께 보여 줍니다. 또 같은 provider root에서
설명(description)의 한 문장에 빌드 동사(build·create 등)와 빌드 대상(site·app·game·
feature·tool·service 등)이 함께 있는 다른 스킬도 알려 줍니다. 에이전트가 빌드 작업에
그 스킬을 고르면 canon 루프가 돌지 않기 때문입니다. 알려 주기만 하고 고치지는
않습니다.

**Done when:** `canon skills check`가 exit `0`이면 스텁이 이 canon 버전과 맞는
것입니다. 결과는 그 출력에서 읽습니다.

## 0.27에서 올리기

0.28은 CLI 문법을 바꿨고 옛 철자의 별칭을 두지 않았습니다(대응표는 README의
removed spellings 표). 기존 레포는 이 순서로 올립니다:

```bash
bunx @journeykit/canon migrate
bunx @journeykit/canon migrate --commit --plan-digest 0123456789abcdef
bunx @journeykit/canon skills install
```

첫 줄은 미리보기(`planDigest`와 `effects`)이고, 둘째 줄의 digest는 그 출력의 값을
넣습니다. 마지막 줄이 옛 전체 스킬을 스텁으로 바꿉니다. 0.27 레포에서
`canon status`, `canon gate check`, `canon context`는 경고를 내고 `meta.next`의 첫
항목으로 `canon migrate --json`을 안내합니다. 자세한 내용은 [CLI 레퍼런스](/ko/cli/)의
0.27에서 올리기를 참고하세요.

**Done when:** `canon status`에 0.27 경고가 없고 `canon gate check`가 exit `0`이면
끝입니다.

전략은 팀 자신의 판정(verdict)에서 증류되며 기본적으로 quarantine됩니다.
paired evaluation과 policy-pinned SSH approval 이후에만 활성화됩니다 —
전체 플라이휠은 [전략 메모리](/ko/concepts/strategy-memory/)를
참고하세요. 이 repository에는 측정된 uplift 결과가 공개되어 있지
않습니다.

## 옵트아웃

canon 데이터는 레포 루트의 `canon.yaml`과 함께 단일 `.canon/` 디렉토리에
보관됩니다. 프로젝트 로컬 skill 스텁은 선택한 provider root
(`.claude`, `.agents`, `.omp`, `.pi`)에도 생성됩니다. 완전히 되돌리려면
`canon.yaml`, `.canon/`, 더 이상 필요하지 않은 skill root를 지우면 됩니다
— 이것이 프로젝트 로컬 footprint의 전부입니다.
