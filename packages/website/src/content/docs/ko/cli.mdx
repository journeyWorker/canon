---

`canon`은 기능마다 하나의 서브커맨드를 갖는 단일 바이너리입니다. 언제든
`canon <command> --help` (또는 `canon <command> <subcommand> --help`)를
실행하면 정확한 플래그 목록을 확인할 수 있습니다 — 이 페이지는 그 출력을
그대로 반영합니다.

대부분의 서브커맨드는 `--repo <dir>` (기본값 `.`)를 받습니다: 리터럴
`.` 기본값은 `cwd`의 조상 디렉터리를 거슬러 올라가며 가장 가까운
`canon.yaml`을 찾고, 다른 명시적 경로는 그대로 사용되며 탐색을 하지
않습니다. 모든 명령은 기본 사람이 읽기 좋은 표/요약 대신 stdout에 기계가
읽을 수 있는 문서 하나를 내는 `--json`을 받습니다. [에이전트로 canon
구동하기](#에이전트로-canon-구동하기)를 참고하세요.

## Try it

사전 설정 없이 바로 실행하는 데모 — gate가 막히고, evidence를 추가하면
통과하는 과정을 봅니다.

| Command | Description |
|---|---|
| `canon demo init [--repo <dir>]` | 일회용 evidence loop를 스캐폴드합니다: 실제 `canon init` 설정, `reviewer`를 요구하는 `policy.yaml`, 그리고 seed된 `dev` evidence 레코드 하나 — 그 결과 `canon gate check`는 `uncovered-cell auth.login.01`로 red 상태가 됩니다. 기존 `canon.yaml`은 덮어쓰지 않고 거부합니다. |
| `canon demo add [--repo <dir>]` | 데모 scenario에 빠진 독립 `reviewer` evidence를 기록하여, 같은 `canon gate check`를 green으로 바꿉니다. |

## Setup

레포 설정을 스캐폴딩하고, 해석 결과를 확인하고, provider-aware 단일
`canon` 동반 스킬을 구체화합니다. 스킬은 명시적인 CLI 명령을 대신하지
않고 필요한 참조 문서만 지연 로드하도록 안내합니다.

| Command | Description |
|---|---|
| `canon init [--repo <dir>] [--no-agents-md] [--policy light\|standard\|strict \| --no-policy] [--providers <list>] [--language <tag>]` | `<repo>/canon.yaml`에 동작하는 새 `canon.yaml`(`tiers:`/`routing:`, `<root>/kind=feature/area=<area>/<surface>.feature`를 담는 기본 스펙 루트 `{id: root, root: .canon/specs}`를 가진 `specs:`, 주석이 앞에 붙은 `sources: []` `plans:` 섹션 — canon 자체의 change는 `.canon/changes/`에 있어 항목이 필요 없고, 주석 처리된 `openspec`(`root: .`)과 `superpowers`(`root: docs/superpowers/plans`) 예시가 canon이 읽기만 하는 외부 plan을 나열하는 법을 보여 줍니다. `openspec/changes/`는 만들지 않습니다 — 그리고 스테이징 쓰기가 스스로 promote하도록 하는 `write: { promote: auto }` — `canon gate promote` 참고), `--policy` 수준의 시작 정책 `.canon/policy.yaml`(기본 `strict`: `require_evidence`, `require_cases: [failure]`, `require_review: {}`를 담은 `spec_coverage`. `standard`는 리뷰를, `light`는 failure 케이스까지 빼고 수준을 올릴 때 풀 주석 줄로 남깁니다. 첫 줄 `# canon policy level: <level>`이 수준을 밝힙니다 — 사람이 검토하고 `canon policy approve --by <who>`로 승인합니다), `AGENTS.md`의 `<!-- canon:begin -->`/`<!-- canon:end -->` 사이 canon 블록(파일이 없으면 만들고, 마커 밖 텍스트는 건드리지 않음. 마커는 코드 펜스 밖의 단독 줄만 인정하며, 시작/끝 한 쌍이 아니면 쓰기 전에 거부, exit `2`)을 생성합니다. `--no-agents-md`/`--no-policy`로 뒤의 둘을 건너뜁니다. 알 수 없는 수준이나 `--policy`와 `--no-policy`를 함께 주면 쓰기 전에 exit `2`로 거부합니다. 새로 init할 때는 `.gitignore`에 `.canon/hot.db*`, `.canon/audit/`(query/export/purge 접근 로그), `.canon/ledger/kind=scenario/`(파생된 시나리오 인덱스. 읽는 명령마다 다시 만듭니다) 중 없는 줄도 추가합니다. `.canon/specs`는 직접 작성하고 git으로 추적하므로 이를 가리키는 줄은 없습니다. 기존 `canon.yaml`과 `policy.yaml`은 덮어쓰지 않습니다: 다시 실행하면 `AGENTS.md` 블록만 갱신하므로(exit `0`; `--no-agents-md`이면 할 일이 없어 거부, exit `2`) 기존 레포의 `canon.yaml`과 `.gitignore`는 그대로입니다. 다시 실행할 때는 하네스를 묻지 않고 `--providers`도 적용하지 않습니다. 새로 init할 때는 canon 스킬을 설치할 하네스도 고릅니다(0.17): `--providers claude,codex`(`claude`·`codex`·`omp`·`pi` 중 아무 조합, 없으면 `none`)가 답이 되고, 아니면 터미널에서 `.claude`·`.codex`·`.omp`·`.pi` 디렉터리가 있는 하네스를 미리 체크한 채 묻습니다(`.agents`만으로는 Codex를 선택하지 않습니다). 터미널이 아니면 감지된 하네스를 씁니다. 답은 `canon.yaml`에 `skills: { providers: [...] }`로 기록하고 `canon skills install`처럼 기본 소스에서 스킬을 설치한 뒤 `installed the canon skill for <list> (<dirs>)`를 출력합니다. 터미널도 플래그도 없고 감지된 것도 없으면 주석 예시만 남기고 아무것도 설치하지 않으며 `canon skills install --providers=<list>`를 안내합니다. 알 수 없는 이름은 쓰기 전에 거부하고(exit `2`), 스킬 소스가 없으면 기록한 선택은 남긴 채 실행할 설치 명령을 알려 주고 exit `2`로 끝납니다. `--language <tag>`는 브리프를 쓰는 언어를 `canon.yaml`의 `language:`에 기록합니다(0.19). 템플릿과 문장 규칙은 `en`과 `ko`용으로 제공하고, 다른 태그는 `en` 제목과 구조 규칙만 받습니다. 아무것도 쓰기 전에 검증하며 이미 있는 `canon.yaml`에는 적용하지 않습니다. `init --check-config`가 이 값을 보고합니다. |
| `canon policy approve --by <who> [--note <text>] [--repo <dir>]` | 사람이 `.canon/policy.yaml`을 검토했음을 기록합니다: `.canon/policy.approval.json`(정책 바이트의 `sha256:<hex>`인 `policy_digest`, `approved_by`, RFC3339 UTC `approved_at`, `note` 또는 `null`을 담은 pretty JSON)을 씁니다. 바로 쓰므로 promote할 것이 없습니다. git으로 추적하는 파일이니 커밋하세요. 다시 실행하면 기록을 교체합니다. `.canon/policy.yaml`이 없거나 `--by`가 비어 있으면 거부합니다(exit `2`). 정책을 한 번도 승인하지 않았다면 `gate check`와 `status`가 advisory를 출력하고 종료 코드는 바뀌지 않습니다. 승인 뒤에 정책이 바뀌었거나 승인 파일을 읽을 수 없으면 fail-closed입니다(`canon policy show` 참고). |
| `canon policy show [--repo <dir>] [--json]` | 정책의 경로와 현재 digest, 그리고 승인 상태를 출력합니다: `approved`, `changed`(바이트가 승인된 digest와 다름), `unreadable`(승인 파일을 해석할 수 없음), `unapproved`. 승인자, 시각, 승인된 digest를 함께 보여 주며, `changed`와 `unreadable`이면 `gate: fails closed (…)`와 해결 방법을 덧붙입니다. **Fail-closed:** 이때 `gate check`는 `1`로 종료하고, `canon subject status`(ship 가드와 reopen)는 `POLICY_CHANGED_SINCE_APPROVAL`(또는 `POLICY_APPROVAL_UNREADABLE`)로 거부하며 `--override-reason`으로도 면제되지 않습니다. 사람이 `canon policy approve`로 현재 정책을 다시 승인하거나 승인된 파일을 git에서 복원합니다. 에이전트는 gate를 통과시키려고 정책을 고치지 않습니다. 읽기 전용입니다. |
| `canon init --check-config [--repo <dir>]` | 기존 `canon.yaml`을 읽기 전용으로 검증합니다. `inventory sync`/`ingest plans`/`tier age`가 쓰는 것과 동일한 strict loader를 그대로 체이닝합니다. `write:` 섹션은 `[PASS] write (promote: auto)`(또는 `manual`), 없으면 `[not configured] write (promote: manual)`, 형식이 잘못되면 `[FAIL] write: …`로 보고합니다. `skills:` 섹션은 `[PASS] skills (providers: …)`, 없으면 `[not configured] skills (…)`, 형식이 다르거나 모르는 provider를 적으면 `[FAIL] skills: …`로 보고합니다. |
| `canon migrate [--dry-run] [--repo <dir>]` | canon 0.16 이하로 설정한 레포를 0.17 레이아웃으로 옮깁니다. 계획을 출력한 뒤 적용하며, `--dry-run`은 계획만 출력합니다. 멱등이라 두 번째 실행에서는 옮길 것이 없습니다. 스펙 루트의 `features/kind=feature/`는 `<root>/kind=feature/`로 옮깁니다(추적 중인 파일이면 `git mv`). 레포 최상위 `specs` 루트는 `.canon/specs`로 옮기고, `canon.yaml`에 `former_roots: [specs]`를 기록합니다. 그래서 이동 전에 고정된 리뷰도 시나리오를 계속 찾습니다. `canon change new`가 `openspec/changes/` 아래에 쓴 change는 `.canon/changes/<slug>/`로 옮기고(`proposal.md` → `brief.md`) 같은 change id로 다시 가져옵니다. 이런 change로 보는 것은 그 명령의 스캐폴드가 그대로 남아 있고 처음 저장된 버전이 이미 서브젝트에 채택된 경우뿐입니다. 나머지 change는 그대로 두고 이름을 알려 줍니다. `canon init`이 쓴 `{ dialect: openspec, root: . }` 소스는 그 아래에 남은 change가 없을 때만 지웁니다. 외부 `proposal.md`의 `Approved:` 줄은 `Source:` 줄과 함께 canon 포인터 `brief.md`로 복사하며, 외부 proposal은 고치지 않습니다. 설치 lock의 provider로 `skills.providers`를 쓰고, 빠진 canon `.gitignore` 줄을 추가하고, 시나리오 인덱스를 다시 만듭니다. `canon.yaml`은 주석과 CRLF를 포함해 나머지 바이트를 그대로 둡니다. 옮길 경로에 커밋하지 않은 변경이 있거나, 대상이 이미 있거나, `canon.yaml`을 안전하게 고칠 수 없으면 거부합니다(exit `2`, 아무것도 쓰지 않음). 기존 레포에서 `canon init`을 다시 실행해도 빠진 `.gitignore` 줄을 추가합니다. |
| `canon context-pack new --manifest <repo-relative.json> [--repo <dir>] [--json]` | 레포 내부의 명시적 JSON 매니페스트가 선택한 파일로 불변 content-addressed context snapshot을 생성합니다. 간결한 출력은 pack id만 출력하며 `--json`은 매니페스트 메타데이터와 digest를 출력합니다. |
| `canon context-pack show <id> [--repo <dir>] [--json]` | 저장된 pack을 검증한 뒤 표시합니다. `show`는 반환 전에 매니페스트와 모든 불변 content object를 다시 검사하며, 간결한 출력에는 캡처된 바이트가 포함되지 않습니다. |
| `canon context-pack verify <id> [--repo <dir>] [--json]` | 캡처된 내용을 반환하지 않고 pack을 검증합니다. pack이 없거나 오래되었거나 변조되었으면 nonzero로 종료합니다. |
| `canon adapter validate --response <path> [--repo <dir>] [--json]` | provider-neutral protocol-v1 응답을 읽기 전용으로 검증합니다. 핵심 필드(`run_id`, provider/model, context-pack id, status, capability, 안전한 evidence ref, 순서가 맞는 nonnegative telemetry)는 strict하게 검사하고, provider 전용 데이터는 `extensions` 아래의 불투명 JSON으로 둡니다. JSON 출력은 정규화된 핵심 요약과 extension 키 이름만 포함하며 payload는 노출하지 않습니다. `--repo`는 context pack 조인을 선택적으로 확인합니다. provider를 실행하지 않으며 capability 선언 자체가 sandbox enforcement는 아닙니다. |
| `canon prompt add --name <name> --version <version> --manifest <repo-relative.json> [--repo <dir>] [--json]` | 명시적 레포 내부 매니페스트에서 버전이 지정된 prompt bundle을 불변 content registry에 등록합니다. |
| `canon prompt show --name <name> --version <version> [--repo <dir>] [--json]` | 등록된 prompt bundle 버전을 선택하고 검증합니다. 기본 출력은 간결한 메타데이터이며 `--json`은 snapshot 메타데이터와 digest를 포함합니다. |
| `canon context [--repo <dir>] [--json]` | 해석된 저작 표면을 출력합니다: 레코드 종류 + envelope 필드, enum 도메인, 조인 키 문법, 파티션 레이아웃, 정책 기반 요구사항, capability 버전. capability *쿼리*입니다 — `fmt --check`/`gate`가 같은 레포에서 진단을 보고하더라도 항상 0으로 종료합니다. 사람용 개요는 `canon status` 안내로 시작하고, `spec_coverage` 정책이 적용되지 않으면 `warning:` 줄을 덧붙입니다. `--json` 출력은 바뀌지 않습니다. |
| `canon status [--repo <dir>] [--json]` | 레포가 지금 어디까지 왔고 다음에 무엇을 실행할지 보여 줍니다: canon 버전과 적용 중인 정책(없으면 gate가 아무것도 강제하지 않는다는 경고)과 그 수준(정책의 `# canon policy level:` 줄이 `light`·`standard`·`strict`를 가리키면 그 수준, 아니면 `spec_coverage` 섹션이 정확히 일치하는 수준, 그것도 아니면 `custom`. `--json`에서는 `policy.level`이며 정책이 없으면 `null`입니다. `light`·`standard`이면 수준을 올리는 방법도 알려 줍니다), 상태별로 묶은 서브젝트와 각 서브젝트의 시나리오·증거·리뷰·열린 blocker 수와 빠진 필수 케이스, 어느 서브젝트에도 속하지 않은 시나리오, 그리고 구체적인 명령을 최대 다섯 개 담은 `next:` 목록. 모든 수치는 `gate check`와 `subject status`가 쓰는 조인을 그대로 쓰며, gate가 거부할 진행은 제안하지 않습니다: 코퍼스 종류가 `local` rung 밖으로 라우팅되면 라우팅 수리 단계만 보여 주고, `spec_coverage` 섹션을 쓸 수 없으면 그 수리를 맨 앞에 두고 다음 상태로 옮기라는 제안을 모두 보류합니다. spec root가 여러 개면 제안하는 `canon scenario new` 명령에 `--project-id`를 붙입니다. `building`, `verifying`, `shipped` 서브젝트와, 가장 최근에 adopt한 change에 brief가 있는 `proposed` 서브젝트마다 brief가 승인됐는지 보여 줍니다(`brief: approved in <brief> — <words>` 또는 `brief: not approved (…)`): 서브젝트가 가장 최근에 adopt한 change의 `.canon/changes/<change>/brief.md`에서만 HTML 주석과 코드 펜스 밖에 있는 `Approved:` 줄을 읽습니다(레코드 종류는 없습니다). 외부 plan에서 온 change도 같은 canon 파일에 brief를 두며, 그 파일의 `Source: <path>` 줄이 외부 문서를 가리킵니다. 외부 `proposal.md` 안의 `Approved:` 줄은 읽지 않으며, canon 파일이 아직 없어도 plan 소스 아래의 외부 openspec `proposal.md`가 있으면 답할 brief가 있는 것으로 봅니다. 수정은 승인된 change 안의 task로 들어가므로, 이전 change의 승인은 새로 adopt한 change를 덮지 않습니다. `canon brief check`에 blocker가 남아 있는 동안은 planner의 단계(`write the brief: canon brief check --change-id <slug> lists N blockers`)가 나오고, brief가 깨끗해진 뒤 승인되지 않았으면 서브젝트의 상태와 상관없이 사람에게 향하는 단계(`human: stop and report the brief in <brief>; | `canon skills install [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi\|none]` | canonical `canon` 스킬 하나를 투영합니다. Claude는 `.claude/skills/canon/SKILL.md`, Codex는 `.agents/skills/canon/SKILL.md`(Codex가 스킬을 찾는 디렉토리), OMP는 `.omp/skills/canon/SKILL.md`, Pi는 `.pi/skills/canon/SKILL.md`를 받습니다. 선택된 모든 provider가 `reference/**`와 `scripts/**` sidecar를 받습니다. OMP/Pi는 레포 로컬의 passive bundle이며 retrieve pre-dispatch 스크립트는 sidecar일 뿐 native hook이 아닙니다. provider는 `--providers`, 없으면 `canon.yaml`의 `skills.providers`, 그것도 없으면 설치 lock에 기록된 provider(0.17 이전에 설정한 레포), 그것도 없으면 `.claude`·`.codex`·`.omp`·`.pi` 디렉터리가 있는 하네스 순으로 정합니다(`.agents`만으로는 Codex를 선택하지 않습니다). 감지되지 않은 하네스를 기본으로 더하지 않으므로, 감지된 것이 없으면 아무것도 설치하지 않고 `--providers`를 안내합니다. `--providers`를 명시하면 기존 `canon.yaml`의 `skills.providers`도 다시 쓰며(다른 바이트는 그대로), `canon.yaml`을 새로 만들지는 않습니다. canon 0.13.0 이하가 만든 legacy `.codex/skills/canon.md` + `.codex/skills/canon/**` 투영은 설치 lock의 해시와 바이트가 일치하는 파일만 하나씩 제거합니다. 수정된 파일과 사용자 파일은 남기며, `.codex/skills`는 비었을 때만 제거합니다. 설치 lock(`.canon/skills/.install-lock.json`)은 자신을 쓴 canon 버전 `canon_version`과, 소스가 git 체크아웃 안에 있으면 그 `HEAD`인 `source_commit`을 기록합니다. 번들과 canon이 그대로면 다시 실행해도 lock은 바이트 단위로 같습니다. 번들이 더 이상 제공하지 않는 투영 파일은 바이트가 lock과 같을 때 정리(prune)하고, 수정된 파일은 남겨 `kept:`로 보고합니다. |
| `canon skills check [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | `install`과 같은 방식으로 provider를 고르며, `--providers`가 없으면 첫 줄에 `providers: <list> (<출처>)`를 출력합니다. 쓰기 없이 canonical 투영의 누락·오래됨, target 소유 content manifest, 남아 있는 legacy `.codex/skills` Codex 투영(수정 명령 포함), 다른 canon이 쓴 설치 lock(`<lock> — outdated (installed by canon X, this canon is Y — run canon skills install --providers=…)`, 버전을 기록하지 않은 0.16 이전 lock이면 "an unknown canon version")을 확인하며, 하나라도 있으면 1로 종료합니다. 번들이 더 이상 제공하지 않는 투영 파일은 orphan이며, `check`는 각각을 이름으로 알리고 종료 코드 1(`SKILLS_DRIFT`)을 냅니다. |
| `canon skills doctor [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | 네 개의 관리 root와 legacy `.codex/skills` root 전체에서 provider, drift, 오래된 lock(`outdated:`), legacy 잔재를 사람이 읽을 수 있게 진단하고 수정 명령을 함께 알려 줍니다. `.claude/skills`, `.agents/skills`, `.omp/skills`, `.pi/skills`에서 frontmatter `description`이 빌드 작업을 주장하는(한 문장 안에 build·implement·create·make·scaffold·develop·code 같은 빌드 동사(활용형 포함)와 site·website·app·application·game·feature·frontend·ui·page·component·tool·library·service·api·cli·server·backend·project·prototype·product·program·script(단수·복수) 같은 빌드 대상이 함께 있는. 예를 들어 "Build websites and apps"는 해당하고 "Manage feature branches"는 해당하지 않습니다) 다른 스킬도 `competing-skill:` 줄로 알리며, 에이전트가 빌드 작업에 그 스킬을 고르면 canon 루프가 돌지 않는다고 경고합니다. 이 줄은 권고일 뿐이라 투영 상태나 종료 코드를 바꾸지 않으며, canon은 다른 스킬을 고치거나 사용자 파일을 삭제하지 않습니다. 선택되지 않은 provider의 canon 투영(`.claude/skills/canon`, `.agents/skills/canon`, `.omp/skills/canon`, `.pi/skills/canon`)이 남아 있으면 지우는 `rm -r`과 선택하는 install 명령을 담은 `stray:` 줄도 더합니다. 이 줄도 권고이며 `check`는 무시합니다. `--providers`가 없으면 첫 줄에 provider의 출처를 밝히고, 선택되거나 감지된 것이 없으면 `status: healthy` 대신 플래그를 안내하는 `no-providers:` 줄을 출력합니다. orphan은 `orphan:` 줄로 출력됩니다. |

Canon 기여자는 legacy `canon skills install --source
canon/skills-dev --target .` materializer를 사용할 수 있습니다. 이는
일반 사용자 설치 흐름에 포함되지 않습니다.


## Subjects

canon의 13번째 레코드 종류인 durable product unit(서브젝트)을 저작하고
라이프사이클을 통해 구동하며, import된 plan change를 그 아래로 adopt합니다.
subject-write-first 루프는 [캐논 개념](/ko/concepts/canon/#서브젝트)을
참고하세요. "feature docs"는 항상 Gherkin `.feature` 파일을, "subject"는
관리 레코드를 뜻합니다.

| Command | Description |
|---|---|
| `canon subject new <id> --domain <d> --title <t> [--summary <s>] [--owner-role <r>] [--repo <dir>] [--json]` | `Subject`을 저작합니다(kebab-slug `<id>`가 durable `subject_id` 조인 키). `--domain`은 vocabulary로 정의된 kebab slug입니다 — 기본 집합 `planning`/`design`/`dev`/`data`/`test`, `.canon/vocab`로 레포별 확장. 상태 `proposed`로 시작하며, `--owner-role`은 생략 시 `implementer`가 기본값입니다. 쓰기 시 envelope + 정책을 검증합니다. |
| `canon change new <slug> --subject-id <id> --title <t> [--kind feature\|chore] [--repo <dir>]` | canon 자체의 change 디렉터리 `.canon/changes/<slug>/`에 `brief.md`(`canon.yaml`의 `language:`로 쓴 PRD 브리프: `# <title>` 다음에 의도, 원하는 결과, 사용자 흐름, 단계 상세, 인수 조건, 질문과 가정, 범위 밖 섹션이 각각 `<!-- canon:section <key> role=… -->` 마커 뒤에 오고, 쓰기 전까지 `canon:hint` 주석이 들어 있으며, 사람의 답을 `canon brief approve`로 기록한다고 알려 주는 주석이 붙습니다. 의도 섹션의 첫 문단이 제목입니다)만 쓰고 `tasks.md`는 쓰지 않습니다. `tasks.md`는 아무것도 gate하지 않는 선택적 작업 메모이며, 이미 있는 파일은 계속 읽습니다. `--kind chore`는 짧은 chore 브리프를 대신 씁니다(의도, 분류 `refactor\|dependency\|build\|ci\|infra`, 불변 조건, 검증, 범위 밖이며 흐름은 없음): subject가 무엇을 하는지가 아니라 어떻게 만들어지고 유지되는지만 바꾸는 작업용입니다. 그리고 `canon ingest plans`와 같은 네이티브 `canon` plan 어댑터로 읽은 뒤 `canon subject adopt`와 같은 쓰기로 subject에 adopt된 change를 기록합니다 — plans 소스도, `canon.yaml` 수정도 필요 없습니다. `canon change new: wrote .canon/changes/<slug>/brief.md`, ``canon change new: recorded change `<slug>` adopted into subject `<id>` — …``를 출력하며, 레코드의 actor는 `canon-plan-import-canon`입니다. 레코드를 하나도 쓰기 전의 실패는 아무것도 남기지 않습니다(파일은 `.canon/` 아래에서 먼저 준비되고 파싱된 뒤에만 제자리로 옮겨집니다). subject와 change 두 레코드는 원자적으로 쓸 수 없습니다: subject 레코드를 쓴 뒤 change 레코드가 실패하면 exit `2`로 끝나고, change 디렉터리와 subject 레코드를 남긴 채 복구 명령 `canon ingest plans && canon subject adopt <slug> --subject-id <id>`를 출력합니다. 이 명령은 다시 실행해도 안전합니다. 없는 subject, 또는 `.canon/changes/<slug>` 디렉터리(활성 또는 보관)나 change 레코드가 이미 있는 slug는 거부합니다(exit `2`, 아무것도 쓰지 않음). `building`, `verifying`, `shipped` subject에서는 브리프가 승인될 때까지 경고하며(stderr와 JSON `meta.warnings`), 기존 시나리오의 증거는 막히지 않습니다. 시나리오는 `@flow:<change>.<F-id>` 태그가 가리키는 change의 승인에 따릅니다. |
| `canon brief [--change-id <slug>] [--repo <dir>] [--json]` | change 브리프의 상태(`draft`, `ready`, `approved`, `legacy`)와 다음 한 개에서 세 개의 단계(`shape`, `clarify`, `harden`, `align`, `polish`, `approve`)를 출력합니다. 단계는 `canon brief check`의 finding에서 도출합니다. prose advisory가 남아 있으면 `polish`가 `approve`보다 먼저 옵니다. `--change-id`가 없으면 레포의 유일한 진행 중 change를 읽습니다. 아무것도 수정하지 않습니다. |
| `canon brief check [--change-id <slug>] [--repo <dir>] [--json]` | 브리프를 규칙에 대어 읽습니다(읽기 전용). 종료 코드 `0`은 깨끗함(advisory는 허용), `2`는 blocker finding, `1`은 운영 오류이며 고정된 문자열 `error.code`(`NO_BRIEF`, `CHANGE_AMBIGUOUS`, `BRIEF_NOT_FOUND`, `BRIEF_UNREADABLE`, `CONFIG_UNREADABLE`, `SPEC_ROOTS_UNREADABLE`)를 냅니다. 섹션은 제목 글자가 아니라 마커 주석으로 찾습니다. blocker(`brief.*`): 빠졌거나 중복되었거나 순서가 틀린 섹션, 단계가 없는 흐름이나 중복된 단계 id, 흐름 id와 순서가 맞지 않는 단계 상세 소제목, 남아 있는 자리표시자(`canon:hint` 주석, 빈 섹션, `TODO`/`TBD`), subject가 `building` 이후일 때 `@flow:<change>.<F-id>` 태그 시나리오가 없는 흐름 단계나 `@case:failure` 시나리오가 없는 단계, 형식이 잘못된 waiver입니다. advisory(`prose.*`, `en`·`ko`. 언어는 본문 글자로 감지하며 `canon.yaml`의 `language:`가 있으면 그것이 우선합니다. 출력에는 `language: ko (detected)` 한 줄이 있고, `--json`에는 `language`, `languageSource`, 그리고 본문이 설정과 다른 언어로 보이면 `languageNote`가 있습니다): 닫힌 표현 목록(`evaluative`, `connective`, `contrast`, `colloquial`, `degree`), `ai-vocabulary`, `code-citation`, `parenthetical`, `decision-history`, `ko-ending`은 normative 섹션, 의도, 질문에서(`decision-history`는 질문 제외), `sentence-length`, `paragraph-length`, 핵심 문장 `==**…**==`이 정확히 하나가 아닌 normative 섹션은 normative 섹션에서만, `length`는 섹션별과 브리프 전체의 글자 수 예산입니다(전체 예산 면제는 섹션 키 `brief`). 마커가 없는 브리프(0.19 이전의 모든 브리프)는 `brief.legacy`입니다. `<!-- canon:waive <rule-id> <section-key> "<reason>" -->`는 한 섹션의 한 규칙을 면제하며(`match="<text>"`를 붙이면 일치한 글자에 그 텍스트가 들어 있는 finding만 면제합니다) 출력에 나열됩니다. `canon subject status`의 ship 가드가 blocker 규칙을 실행하고, `canon status`가 finding 개수를 보여 줍니다. |
| `canon brief approve --by <who> --note <words> [--change-id <slug>] [--repo <dir>] [--json]` | 사람이 브리프에 한 답을 한 번의 호출로 기록합니다: `Approved: <who> <when> — "<words>" (brief sha256:<digest>)` 줄을 브리프에 쓰고(digest는 `Approved:` 줄을 뺀 브리프 전체에 대한 것입니다) `canon policy approve`와 같은 정책 승인도 함께 기록합니다. `canon brief check`에 구조 blocker가 있으면 거부하고(exit `2`), 빈 `--by`나 `--note`도 거부합니다. coverage 규칙(`brief.flow-uncovered`, `brief.flow-no-failure`)은 ship만 gate하며 승인은 막지 않습니다. 이후 브리프를 고치면 사람이 다시 답하고 이 명령을 다시 실행할 때까지 `status`, `evidence add`, ship 가드가 승인되지 않은 것으로 읽으며(`BRIEF_CHANGED_SINCE_APPROVAL`), digest 없는 `Approved:` 줄(0.19 이전)은 승인으로 남고 다시 승인하라는 advisory가 붙습니다. 사람의 답이 있을 때만 실행하세요: canon은 사람과 에이전트를 구별할 수 없습니다. |
| `canon subject adopt <change_id> --subject-id <id> [--repo <dir>] [--json]` | import된 plan `Change`(`canon ingest plans` 결과)를 `Subject`에 연결합니다: subject를 `Change.subject_ids`에, change를 subject의 `change_ids`에 추가합니다. 한 change는 여러 subject에 속할 수 있습니다(0.18): 두 번째 subject로 adopt하면 그 subject를 더하고 다시 가리키지(re-point) 않으며, ``linked change `refactor-core` to subject `editing` as well; the change now belongs to `perception` and `editing` ``를 출력합니다. 0.18 이전에 쓴 change는 `subject_id` 하나를 담고 있으며 원소 하나인 `subject_ids`로 읽힙니다. gate의 open-blocker 규칙, 상태 가드, `canon status`, 브리프는 모두 subject와 change를 양쪽에서 조인하므로, 공유된 change의 blocker는 그 change가 속한 모든 subject를 막습니다. 연결이 없는 쪽만 씁니다(이미 연결된 쌍이면 아무것도 쓰지 않고 exit `0`). subject를 먼저 쓰며, 그 뒤 change 쓰기가 실패하면 exit `2`로 끝나고 연결을 마무리할 `canon subject adopt <change_id> --subject-id <id>`를 출력합니다. subject가 `building`, `verifying`, `shipped`이고 change의 브리프가 승인되지 않았다면 경고합니다(stderr와 JSON `meta.warnings`). |
| `canon subject unadopt <change_id> --subject-id <id> [--repo <dir>] [--json]` | change를 subject에서 다시 뺍니다: 두 레코드의 링크를 지우고 change와 브리프는 남기므로, 초안을 다른 곳(예: `proposed` 보관용 subject)에 adopt할 수 있습니다. 브리프에 `Approved:` 줄이 있는 change는 `SUBJECT_UNADOPT_REFUSED`로 거절되고, 이미 연결이 없으면 아무 일도 하지 않습니다. |
| `canon subject status <id> --to <state> [--override-reason <text>] [--reason <text>] [--actor-id <id>] [--repo <dir>] [--json]` | `proposed → specced → building → verifying → shipped`(및 다시 열기 `shipped → verifying`, any → `retired`)를 따르는 정책 게이팅 전이입니다. `verifying → shipped`는 subject가 시나리오를 하나 이상 소유하고(`canon inventory sync`가 인덱싱한 `@subject:<id>` 태그 기준), 소유한 모든 scenario가 최신 non-Divergent 판정을 가질 것을 추가로 요구합니다. 위반 시 failure class별로 출력하고 `1`로 종료하며 레코드는 변경되지 않습니다(fail closed). `spec_coverage.require_review`가 설정되어 있으면 어떤 리뷰 검사를 실행했고 건너뛰었는지 stderr에 출력하며, `require_review.scope` 상태로 옮길 때 빈틈(`unreviewed-promotion`, `open-blocker`)이 있으면 같은 방식으로 거부합니다. `--override-reason "<한 줄>"`은 이 두 클래스만 면제하고 — ship 게이트의 판정·case 빈틈은 절대 면제하지 않습니다 — 새 레코드에 `status_override`(`to`, `reason`, 넘겨준 위반을 정확히 `{class, subject}`로 적은 `waived`, `--actor-id`에서 온 `actor`, 기본 `canon`)를 남깁니다. 나중에 올라온 blocker처럼 기록되지 않은 빈틈은 여전히 게이트를 실패시킵니다. 사유가 비었거나 여러 줄이면 `2`로 종료합니다. 면제는 subject의 다음 상태 쓰기에서 지워집니다. `require_review`가 없으면 아무것도 바뀌지 않습니다. `shipped`로의 전이는 `false-success`(최신 audit이 `refuted`인 시나리오)도 거부하며, `require_audit.scope`가 `shipped`를 포함하면 아직 받지 않은 샘플 audit도 거부합니다. 다시 열기와 `--reason`은 아래를 보세요. |

`verifying → shipped`는 브리프가 있는 곳에서 서브젝트의 브리프 승인도
요구합니다. `canon status`가 `brief:` 줄에 쓰는 것과 같은 검사로, 서브젝트가
가장 최근에 adopt한 change의 `.canon/changes/<change>/brief.md`에 HTML 주석과
코드 펜스 밖의 `Approved:` 줄이 있어야 하고(`canon brief approve`가 씁니다),
그 줄의 digest가 브리프 본문과 아직 일치해야 합니다(승인 뒤에 고친 브리프는
`BRIEF_CHANGED_SINCE_APPROVAL`로 거부됩니다). `canon brief check`에 blocker가
없어야 하며, 모든 흐름 단계에 실패 케이스를 가진 시나리오가 있어야 한다는 조건도
여기에 포함됩니다. 그 canon `brief.md`가 있거나,
외부 plan에서 온 change라면 plan source 아래에 openspec `proposal.md`가 있을
때 브리프가 있는 것입니다(이때 canon `brief.md`는 그 proposal을 가리키는
`Source:` 줄과 함께 앞으로 만들 파일이며, proposal 안의 `Approved:` 줄은 읽지
않습니다). 정책이 있든 없든 실행됩니다. 승인이 없으면
`unreviewed-promotion <subject>`로 거부하면서 canon `brief.md`(외부 plan이면
써야 할 `Source:` 줄까지)를 가리키고 사람이 브리프에 답해야 한다고 알립니다.
에이전트는 그 답이 있을 때만 `canon brief approve`로 기록합니다. `--override-reason`은 리뷰 빈틈처럼
이를 면제하고, 면제 기록에 `{class: unreviewed-promotion, subject: <subject>}`를
남깁니다. adopt한 change가 없거나, 가장 최근 change에 canon `brief.md`도 외부
`proposal.md`도 없으면 답할 브리프가 없으므로, 브리프가 승인되지 않았다는
advisory만 출력하고 거부하지 않습니다. `status`도
브리프를 advisory로 보여 주고 human 단계를 내지 않습니다
(`subjects[].brief.enforced: false`). 브리프에 사람이 ship한다고 적혀 있으면
누가 전이를 실행하는지만 달라지고, 검사는 같습니다. 이 거부는 마지막
안전장치입니다: 브리프가 승인되지 않은 동안 `canon evidence add`가 이미 그
서브젝트의 시나리오와 task를 거부하며, 에이전트는 둘 중 어느 것이 발동하기
전에 브리프에서 멈춥니다.

**다시 열기(0.18).** `canon subject status <id> --to verifying --reason "<한 줄>"
[--actor-id <id>]`는 출하된(`shipped`) 서브젝트를 후속 작업을 위해 다시 엽니다.
새 레코드에 `reopen`(`reason`, 작업이 들어갈 승인된 `change`, `actor`)을
남기며, 다음 상태 쓰기에서 지워집니다. 승인된 범위 안(가장 최근 adopt한
change의 브리프가 승인됐거나 답할 브리프가 없음)이면 사람이 필요 없고, 아니면
승인할 브리프를 밝히며 `1`로 거부합니다. `--override-reason`은 이를 면제하지
않습니다. `--reason`은 이 전이에서 필수이고, 다른 전이에서는 선택이며 `status_reason`(`reason`,
`actor`)으로 기록됩니다. 다시 열 때는 리뷰 가드를 건너뛰며, 다시 출하할 때 모든 가드가 다시
실행됩니다. `canon status`는 게이트가 빨갛게 된 출하 서브젝트를
``gate: red — …; reopen with `canon subject status <id> --to verifying --reason …` ``로
표시하고 이 명령을 그 서브젝트의 단계로 제시합니다.

## Corpus

Gherkin `.feature` 스펙 코퍼스를 검증하고 확장합니다.

| Command | Description |
|---|---|

| `canon inventory sync [--repo <dir>] [--spec-root <dir>]` | 설정된 `specs.roots[]` 항목마다 `canon-fmt`로 검증한 뒤, `(project_id, scenario_id)`당 하나의 `Scenario` ledger-index 레코드를 생성합니다. `--spec-root`는 하나의 ad hoc 루트로 `canon.yaml`을 완전히 오버라이드합니다. 인덱스는 `.feature` 파일에서 파생되므로, `gate check`, `status`, `subject status`, `review add`, `evidence add`는 읽기 전에 낡은 인덱스(레코드가 없는 시나리오, 또는 source digest가 파일과 다른 레코드)를 스스로 다시 만듭니다: 같은 코드로 바뀐 파일만 생성하고, 검증은 여전히 루트 전체에 대해 합니다. stderr에 한 줄 — `canon status: refreshed the scenario index from 1 changed feature file(s) (…): 1 record(s) written` — 을 출력하고, 인덱스가 최신이면 아무것도 출력하지 않습니다. 동기화에 실패한 루트는 `NOT refreshed`로 이름을 밝히고 이 명령을 안내하며, 명령은 그대로 실행됩니다. 다만 `gate check`는 `uncovered-cell <root>`로 실패하고, `subject status … shipped`도 같은 위반으로 거부되며, `status`는 이 sync만 다음 단계로 보여 줍니다. 0.17 이전 레이아웃의 루트(`<root>/features/` 아래에 `.feature` 파일이 있는 루트)는 여기서 중단되고(exit `1`, 0건 기록), 읽는 명령의 갱신은 tombstone을 쓰지 않고 그 루트를 건너뛰며 대신 `canon migrate`를 안내합니다. `canon.yaml`이 없는 디렉터리에는 아무것도 쓰지 않습니다. 명시적으로 인덱싱하고 위반 목록을 보려면 `inventory sync`를 실행하세요. |

| `canon scenario new --from <file\|-> [--actor-id <id>] [--repo <dir>]` | 한 번에 여러 시나리오(0.21): `--from`은 한 줄에 JSON 객체 하나인 NDJSON을 읽습니다(`-`는 stdin, 빈 줄과 `#` 주석은 건너뜁니다). 각 줄은 단일 형태의 필드를 긴 플래그 이름 그대로 가집니다: `{"id":"auth.login.02","title":"Sign out","subject-id":"demo","flow":"F1","case":"failure"}`(`id`, `title`, `subject-id`, `lane`, `case`, `flow`, `change-id`, `feature`, `project-id`). `<TAG>`와 단일 형태의 플래그와는 함께 쓸 수 없습니다. 모든 줄을 먼저 단일 형태와 같은 검사로 확인하고, 배치 안에서 반복된 id도 거부합니다. 전부 아니면 전무입니다: 잘못된 줄이 하나라도 있으면 종료 코드 `2`로 아무것도 쓰지 않고, 잘못된 줄마다 하나씩 `data.items: [{line, id, error: {code, message, field?}}]`를 담은 `error`를 돌려줍니다. 모두 유효하면 단일 호출 N번과 같은 파일을 하나의 provenance 시각으로 쓰고 `data.items: [{line, id, path}]`와 `meta.next` 하나를 돌려줍니다. |
| `canon feature new <SURFACE> --title <label> [--actor-id <id>] [--repo <dir>]` | 아직 시작되지 않은 `<area>.<surface>`를 위한 시나리오 없는 새 `.feature` 파일을 스캐폴딩합니다. 기존 파일이 있으면 덮어쓰지 않고 실패합니다. 스펙 루트가 0.17 이전 레이아웃이면 아무것도 쓰지 않고 거부합니다(exit `2`). 먼저 `canon migrate`를 실행하세요. |

**재검증.** 최신 disposition이 `fixed`인 blocker와 승인된 chore change는, 증거가 있는 모든 시나리오에 close나 승인 이후의 증거가 기록될 때까지 subject의 ship을 막습니다. 거부 메시지는 해당 시나리오와 명령 `canon evidence add --project-id <root-id> --all-scenarios --report <format>:<path> …`를 알려 줍니다. 리뷰는 증거의 판정과 체크의 정체를 pin할 뿐 어느 레코드인지는 pin하지 않으므로, 같은 케이스에서 같은 판정으로 스위트를 다시 기록하면 리뷰는 현재 상태로 남습니다. chore는 대신 chore 자체에 대한 change 수준 리뷰 하나(`canon review add --change-id <slug> …`)가 필요합니다. shipped subject에 `canon change new`를 하면 reopen 명령(`canon subject status <id> --to verifying --reason "<why>"`)을 출력합니다. 모든 거부는 다음 길을 알려 주는 `hint`를 가집니다.

0.23 이전에 쓴 리뷰는 gate가 더는 비교하지 않는 것을 pin합니다. 0.15–0.22 리뷰는
증거 레코드 파일을 pin하고, 0.15 이전 리뷰는 pin 없이 리뷰한 커밋(`--pin`)만 있습니다.
이런 리뷰는 `canon migrate`가 증거가 말하는 것으로 다시 쓰기 전까지 인정되지 않습니다.
마이그레이션은 쓰일 당시 규칙으로 current였던 리뷰(0.15 이전 리뷰는 `git`으로 읽은 그
커밋의 시나리오 digest와 대조)를 pin하고, 이미 stale이던 리뷰는 stale로 두며, 커밋이나
시나리오가 이 클론에 없는 리뷰는 시나리오의 현재 상태로 pin합니다. `gate check`,
`status`, `subject status`는 아직 기다리는 시나리오 수를 밝히는 advisory 한 줄을
출력합니다. CI에서는 `canon migrate`를 돌리는 job을 전체 히스토리(`fetch-depth: 0`)로
체크아웃하세요.

## 에이전트로 canon 구동하기

모든 명령은 하나의 머신 계약(0.20)을 공유하므로, 에이전트가 `--help`나 사람용
텍스트를 긁어 읽을 필요가 없습니다.

**`canon schema`로 파악합니다.** 한 번의 호출로 명령 하나를 설명합니다:

```bash
canon schema                      # 모든 명령과 effect, 한 줄씩
canon schema purge --json         # {data, meta}: arguments, options, exits, errorCodes
canon schema --errors --json      # 고정된 모든 오류 코드와 의미
```

`data`에는 `command`, `effect`(`read`, `write`, `destructive`),
`supportsJson`, `arguments`, `options`(`name`, `kind`, `valueName`,
`required`, `repeatable`, `possibleValues`, `default`), `exits`(`code`,
`meaning`), `errorCodes`가 담깁니다.

**`--json` 출력.** stdout에는 JSON 문서가 정확히 하나만 나오고, 안내 문구는
stderr로 갑니다.

**오류.** 실패하면 stderr에 `canon <command>: CODE — message`와 `hint:` 줄을
냅니다. `--json`이면 stdout에 대신
`{"error": {"code", "message", "hint", "retryable"}}`가 나오고, 사용 오류나 입력
검사가 지목할 수 있으면 `field`(문제의 옵션)와 `expected`(유효한 값)가 더해집니다. 코드는 고정된
문자열이며, 커맨드라인 파싱 오류는 `USAGE`입니다. 종료 코드 `2`는 호출이나
입력이 잘못되어 고칠 수 있다는 뜻(아무것도 쓰지 않음)이고, `1`은 운영 실패
또는 명령이 보고하는 blocking finding입니다.

**페이징과 필드.** `canon query`, `canon finding list`,
`canon divergence status`, `canon export`는 최대 `--limit`개(기본 100)만
반환합니다. `--all`은 전부, `--cursor <nextCursor>`는 이어서 가져옵니다.
`--json`은 `meta: {returned, total, hasMore, nextCursor}`를 더합니다.
`canon query`와 `canon finding list`는 `--fields a,b,c`로 레코드를 투영할 수
있으며, 모르는 필드는 `UNKNOWN_FIELD`이고 hint가 알려진 필드를 나열합니다.

**쓰기 뒤의 `meta.next`.** 성공한 쓰기 명령은 다음 단계를 직접 알려 주므로,
에이전트가 그것만 알아내려고 `canon status`를 부를 필요가 없습니다. `--json`은
`meta.next`(`[{command, why, actor, role}]`, 최대 다섯 개, 나머지 수는
`meta.nextOmitted`)를 더하고, 사람용 출력은 `next: <command> — <why>` 한 줄로
끝납니다. 이 단계들은 `canon status`의 단계와 같고 쓰기가 건드린 subject로
좁혀집니다. `actor: human`은 사람만 할 수 있는 단계입니다. canon은 단계를 직접
실행하지 않습니다.

**재시도 안전.** `evidence add`나 `review add`를 같은 입력으로 반복하면 기존
레코드를 `meta.unchanged: true`와 함께 돌려줍니다.

### 역할

에이전트는 역할을 선언할 수 있습니다: `planner`, `implementer`, `reviewer`,
`orchestrator`. `CANON_ROLE=<role>`을 설정하거나 `--as <role>`을 넘기며(플래그가
우선), 모르는 값은 `UNKNOWN_ROLE`입니다. 역할은 강제가 아니라 안내입니다.
`canon schema`는 그 역할의 명령을 나열하고, `canon status`와 `meta.next`는 그
역할의 단계만 남기며 나머지는 `waitingOn`에 개수로 셉니다(orchestrator는 사람의
단계도 봅니다). `evidence add`와 `review add`의 `--role` 기본값도 이 역할입니다.
설정하지 않으면 모든 명령이 전과 같이 동작합니다.

canon 스킬도 같은 식으로 나뉩니다: 짧은 공용 코어와 `reference/role-<role>.md`.
역할을 받아 생성된 에이전트는 자기 역할의 reference만 읽고, 혼자 다 하는
에이전트는 `canon status`를 따르며 각 단계가 시작될 때 해당 역할 reference를
읽습니다. orchestrator는 각 역할을 `CANON_ROLE`을 설정해 띄우고, reviewer는 고유
세션 id를 가진 별도 프로세스로 실행합니다. `--fields`(`status`, `export`,
`divergence status`, `context`, `query`, `finding list`)는 에이전트의 컨텍스트를
작게 유지합니다.

**파괴적 명령은 계획이 먼저입니다.** `canon purge --plan`은 제거 대상과
`planDigest`를 출력하고 아무것도 지우지 않습니다. `canon purge --confirm
<planDigest>`는 지금 다시 계산한 plan의 digest가 같을 때만 지우며, 아니면
`PLAN_CHANGED`입니다. `purge`에 `--dry-run`은 없습니다.
