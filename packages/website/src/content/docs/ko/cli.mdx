---

`canon`은 기능마다 하나의 서브커맨드를 갖는 단일 바이너리입니다. 문법은 하나이고
명세 하나(`docs/cli/canon.cli.json`)에서 생성됩니다: `--help`, 아래 표, 에이전트
가이드, `canon schema`가 모두 같은 명세를 읽으므로 서로 어긋나지 않습니다.
언제든 `canon <command> --help` (또는 `canon <command> <subcommand> --help`)로
정확한 옵션 목록을, `canon schema <command> --json`으로 같은 내용을 기계가 읽는
형태로 확인할 수 있습니다.

대부분의 서브커맨드는 `--repo <dir>`를 받습니다. 생략하거나 `.`이면 `cwd`의
조상 중 `canon.yaml`이 있는 가장 가까운 디렉터리이고, 다른 명시적 경로는 그
디렉터리를 그대로 사용하며 탐색하지 않습니다. canon 상태가 필요한 명령이 거기서
`canon.yaml`을 찾지 못하면 빈 레포를 깨끗하다고 보고하는 대신 `CONFIG_MISSING`
(exit `2`, `--repo` 명시, `canon init`과 찾아본 디렉터리를 알리는 힌트)으로
거부합니다. `init`, `migrate`, `demo`, `context`, `regime`, `adapter`,
`context-pack`, `prompt`는 없어도 실행됩니다. 모든 명령은 사람이 읽기 좋은 표/요약 대신 stdout에 기계가
읽을 수 있는 문서 하나를 내는 `--json`을 받습니다. [에이전트로 canon
구동하기](#에이전트로-canon-구동하기)를 참고하세요.

## 에이전트로 canon 구동하기

모든 명령은 하나의 머신 계약을 공유하므로, 에이전트가 `--help`나 사람용
텍스트를 긁어 읽을 필요가 없습니다.

**`canon schema`로 파악합니다.** 한 번의 호출로 명령 하나를 설명합니다. 옵션 이름을 추측하지 말고 여기서 확인하세요:

```bash
canon schema                      # 모든 명령과 effect, 한 줄씩
canon schema purge --json         # {ok, data, meta}: arguments, options, exits, errorCodes, input 스키마와 예시
canon schema --errors --json      # 고정된 모든 오류 코드와 의미
```

`data`에는 `command`, `effect`(`read`, `write`, `destructive`),
`supportsJson`, `arguments`, `options`(`name`, `kind`, `valueName`,
`required`, `repeatable`, `possibleValues`, `default`), `exits`(`code`,
`meaning`), `errorCodes`가 담깁니다.

**`--json` 봉투(envelope).** `--json`이면 stdout에 JSON 문서가 정확히 하나만 나오고
(안내 문구는 stderr), 성공과 실패 모두 같은 모양입니다: `{ok, data, meta}`.
exit 1의 부분 보고서는 실패 봉투에 `data`도 함께 담습니다. 봉투는 atip/1을
따릅니다. `meta`에는 `schemaVersion`, `tool`(`canon`), `toolVersion`,
`contract`(`atip/1`), 해석된 `command`가 들어 있고, 해당할 때 `output`(명령이
보고서를 여럿 선언하면 그 이름), `context`(`{repo}`), `next`, `warnings`,
`coverage`, `page`, `x-canon`(canon 전용 추가 정보)이 더해집니다. 값이 없는
멤버는 `null`도 `[]`도 아니라 아예 빠집니다. `--json`은 `--` 앞이면 어디에든 올 수
있어 루트와 그룹에도 붙습니다(`canon --json`, `canon finding --json`).
텍스트가 곧 산출물인 몇 개 명령(`skills show`의 가이드, `export`와
`approval-payload`의 바이트, 셸 완성 스크립트)은 텍스트 모드에서만 봉투로
감싸지 않습니다.

```json
{
  "ok": true,
  "data": { "unchanged": true, "…": "…" },
  "meta": {
    "schemaVersion": "1.0",
    "tool": "canon",
    "toolVersion": "0.33.0",
    "contract": "atip/1",
    "command": "evidence add",
    "context": { "repo": "." },
    "next": [
      {
        "command": "canon gate check --json",
        "argv": ["gate", "check", "--json"],
        "reason": "모든 시나리오에 증거가 생겼으니 게이트를 확인합니다",
        "x-canon": { "actor": "agent", "role": "reviewer" }
      }
    ]
  }
}
```

**오류.** 실패하면 stderr 첫 줄에 `canon: CODE: message`를 내고, 이어서 들여쓴
`field:`, `expected:`, `hint:` 줄을 냅니다. 텍스트 모드에서 stdout은 비어 있습니다.
`--json`이면 봉투의 `error`가 `{"code", "message", "retryable"}`를 담고, canon이
지목할 수 있으면 `hint`, `field`(문제의 옵션), `expected`(유효한 값), `received`,
`suggestions`가 더해집니다. `retryable`은 항상 있고 나머지는 값이 없으면
빠집니다. 코드는 고정된 문자열입니다. 커맨드라인 파싱 오류는 `USAGE`, 모르는
명령은 `UNKNOWN_COMMAND`(`expected`가 그 단계의 유효한 단어를 나열), 명령이 아예
없는 호출(`canon --json`, `canon finding --json`)은 `COMMAND_REQUIRED`,
JSON 모드의 패닉은 `INTERNAL`입니다. 종료 코드는 `0`, `1`, `2`뿐이며 각 코드의
종료 코드는 `canon schema --errors --json`의 해당 행이 정합니다. `2`는 호출이나
입력이 잘못되어 고칠 수 있으므로 canon이 실행을 거부했다는 뜻(아무것도 쓰지
않음)이고, `1`은 실행했지만 답이 부정적이거나 불완전하다는 뜻(운영 실패, blocking
finding, `unverifiable`)입니다. 검사가 아무것도 살펴보지 못했다면 `clean`이 아니라
`unverifiable`(exit `1`)이고 `meta.coverage`가 무엇을 살펴봤는지 알려 줍니다.

**`--input`: JSON으로 인자를 넘깁니다.** 쓰기 명령은 모두 `--input <JSON|FILE|->`을
받습니다. 값이 `{`나 `[`로 시작하면 인라인 JSON, `-`이면 stdin, 그 외에는 파일
경로입니다. 키는
옵션 이름의 camelCase(`scenario`, `project`, …)이고 피연산자는 `operands`
배열에 둡니다. 모르는 키, 잘못된 타입, 읽을 수 없는 파일, 터미널에서의 `-`처럼
쓸 수 없는 입력은 조용히 버려지지 않고 `INPUT_INVALID`로 거부되며 구분은
`message`와 `field`에 남습니다(`-`를 다른 stdin 입력과 함께 쓰면 `field`가
`--input`인 `USAGE`입니다). 객체는 호출 한 번이고, 배열(또는 파일/stdin의 NDJSON)은 **배치**입니다:
모든 원소를 첫 쓰기 전에 검증하므로 검증이 실패하면 아무것도 쓰지 않고 `error.field`가
`/items/<i>/<key>`로 지목합니다. 원소 일부가 실패한 배치는 `BATCH_INCOMPLETE`(exit 1)입니다.
같은 배치를 다시 실행해도 안전합니다(이미 있는
동일한 레코드는 `unchanged`). `scenario new`, `evidence add`, `finding add`처럼
레코드를 많이 쓰는 명령에 씁니다. `scenario new --from`은 사라졌습니다.
`canon schema <command> --json`이 그 명령의 입력 스키마와 예시를 보여 줍니다.

```text
canon scenario new --input '[{"operands":["auth.login.02"],"title":"Sign out"},{"operands":["auth.login.03"],"title":"Session expiry"}]'
```

**커밋 옵션은 `--rev`입니다.** 코드에 묶이는 명령(`evidence add`, `review scenario`,
`finding add` 등)은 `--rev <git revision>`을 받고 기본값은 `HEAD`입니다.
`finding`의 `--resolution-rev`와 `--introduced-rev`가 같은 규칙을 따릅니다.
커밋하지 않은 코드에 대한 기록도 허용되며 `codeTree`/`worktreeDirty`를 함께 담습니다.
코드 트리가 같다면 커밋 뒤에도 리뷰는 유효합니다. git 밖이거나 커밋이 아직 없으면
`NO_COMMIT`입니다.

**페이징과 필드.** `canon query`, `canon finding list`,
`canon divergence list`, `canon export`는 최대 `--limit`개(기본 100)만
반환합니다. `--all`은 전부, `--cursor <nextCursor>`는 이어서 가져옵니다.
`--json`은 `meta.page`(`{returned, total, nextCursor}`)를 더합니다. `nextCursor`가
있으면 더 있다는 뜻이고 `meta.next`가 같은 호출에
`--cursor <nextCursor>`를 붙여 알려 줍니다. 잘못된 커서는 `CURSOR_INVALID`입니다.
`canon query`와 `canon finding list`는 `--fields a,b,c`로 레코드를 투영할 수
있으며, 모르는 필드는 `field`가 `--fields`인 `USAGE`이고 `expected`가 고를 수 있는
필드를 나열합니다.

**검색과 추적.** `canon search "<텍스트>"`는 레코드, brief 섹션과 flow 단계, 시나리오
본문에서 텍스트를 찾고 걸린 노드마다 레코드 그래프의 이웃을 함께 냅니다
(`data.hits[]`, `data.neighbors[]`, `data.edges[]`, `data.counts`, `data.index`).
`--kind`(반복)는 그 종류의 hit만 남기고, `--expand <N>`은 홉 수(기본 1), `--limit <N>`은
hit 수(기본 20, 다음 페이지 없음)입니다. 한국어는 세 글자부터 찾고, 그보다 짧은 질의는
노드 본문의 부분 문자열로 id순으로 찾습니다. 질의는 쓴 그대로 읽습니다. 빈 질의는
exit 2(`SEARCH_QUERY_EMPTY`), 일치가 없으면 exit 0과 빈 `hits`입니다. 원본이 없는 참조는
`placeholder: true`인 이웃이며 오류가 아닙니다.
`canon trace <finding 키|리뷰 id|sha>`는 한 고리의 리뷰 → finding → 수정 → 재리뷰 →
evidence 사슬을 시간순으로 냅니다(`data.chain[]`: 시각, id, kind, 역할, sha, 엣지). archive의
옛 버전도 들어 있습니다. 어떤 레코드도 말하지 않는 id, 모호한 sha 앞부분, 그 밖의 모양은
exit 2이고 메시지가 받는 모양 셋을 적습니다. 둘 다 파생 색인 `.canon/index/search.db`를 읽고,
입력(레저 레코드와 이 worktree의 sqlite hot 저장소, brief, `.feature`)이 바뀌었으면 먼저
전체를 다시 만듭니다. 색인은 gitignore되고(`canon init`이 줄을 넣고, 그 전에는 명령이
경고합니다) 레코드의 원본이 아니며, 지워도 `data.index.rebuilt`만 달라집니다. staged 레코드와
postgres, 객체 저장소의 레코드는 읽지 않고 `data.index.unreadStores`가 그 저장소를 적습니다.

**쓰기 뒤의 `meta.next`.** 성공한 쓰기 명령은 다음 단계를 직접 알려 주므로,
에이전트가 그것만 알아내려고 `canon status`를 부를 필요가 없습니다. `--json`은
`meta.next`(`[{command, argv, reason, x-canon}]`, 최대 다섯 개, 나머지 수는
`data.nextOmitted`)를 더합니다. `argv`는 실행 파일을 뺀 인자이고 JSON 모드였으면
`--json`이 붙어 있으며, 단계의 `actor`와 `role`은 `x-canon`에 있습니다. 사람용
출력은 `next: <command> — <reason>` 한 줄로
끝납니다. 이 단계들은 `canon status`의 단계와 같고 쓰기가 건드린 subject로
좁혀집니다. `x-canon.actor: human`은 사람만 할 수 있는 단계입니다. canon은 단계를 직접
실행하지 않습니다.

**재시도 안전(`data.unchanged`).** `evidence add`나 `review scenario`를 같은 입력으로
반복하면 기존 레코드를 `data.unchanged: true`와 함께 돌려줍니다(저장된 레코드를 그대로
돌려주는 보고서는 `meta.x-canon.unchanged`입니다). `finding close`도
이미 닫힌 finding에 대해 같고, 쓰기 명령마다 명세가 멱등성을 선언합니다.

### 역할

에이전트는 역할을 선언할 수 있습니다: `planner`, `implementer`, `reviewer`,
`orchestrator`. `CANON_ROLE=<role>`을 설정하거나 `--as <role>`을 넘기며(플래그가
우선), 모르는 값은 `UNKNOWN_ROLE`입니다. 역할은 강제가 아니라 안내입니다.
`canon schema`는 그 역할의 명령을 나열하고, `canon status`와 `meta.next`는 그
역할의 단계만 남기며 나머지는 `data.waitingOn`에 개수로 셉니다(orchestrator는 사람의
단계도 봅니다). `evidence add`와 `review scenario`의 `--role` 기본값도 이 역할입니다.
설정하지 않으면 모든 명령이 전과 같이 동작합니다. `CANON_ROLE`은 `schema`, `context`,
`skills show`를 거르거나 실패시키지 않습니다(잘못된 값은 경고일 뿐입니다).

`brief approve`, `policy approve`, `divergence accept`와 `Approved:` 줄을 다시 묶는
`migrate --commit`은 사람의 결정입니다: 에이전트 역할은 `--relayed-via <도구>` 없이는
`retryable: false`로 거부되고, hint가 먼저 대리 절차(`canon brief show <change> --body`로
보여 주기, 하네스의 질문 도구로 묻기, 명시적 승인만 세기, `--relayed-via`로 기록하기)를,
다음에 사람이 직접 칠 명령을 알려 줍니다. 대리 기록은 사람의 이름과 답, 대리한 에이전트의
역할과 actor, 질문에 쓴 도구를 남기며, `canon.yaml`의 `approval: { relay: deny }`로 끌 수
있습니다(끄면 `HUMAN_ONLY`). 거부를 넘어서 진행해야 할 때의 유일한 옵션은
`--override-reason <TEXT>`이며(`--force`는 없습니다) 넘긴 사유는 기록에 남고
`data.overrides[]`와 `canon status`에 보입니다.

### 가이드는 바이너리에서 나옵니다

가이드는 레포에 파일로 투영되지 않습니다. `canon skills show <NAME> [--full]`이
이 바이너리에 들어 있는 버전이 일치하는 가이드를 출력합니다: `canon`은 핵심
가이드이고 역할과 주제별 reference는 이름(`role-implementer`, `canon-gate`,
`brief-polish` 등)으로 읽습니다. 설치되는 `SKILL.md`는 canon이 무엇인지, 루프
요약, "전체 가이드는 `canon skills show canon`, 옵션은 추측하지 말고
`canon schema <command>`"만 담은 짧은 스텁이라 스킬이 바이너리와 어긋날 수
없습니다.

```bash
canon skills show canon
canon skills show role-implementer
```

역할을 받아 생성된 에이전트는 자기 역할의 reference만 읽고, 혼자 다 하는
에이전트는 `canon status`를 따르며 각 단계가 시작될 때 해당 역할 reference를
읽습니다. orchestrator는 각 역할을 `CANON_ROLE`을 설정해 띄우고, reviewer는 고유
세션 id를 가진 별도 프로세스로 실행합니다. `--fields`(`status`, `export`,
`divergence list`, `context`, `query`, `finding list`)는 에이전트의 컨텍스트를
작게 유지합니다. 가이드의 각 워크플로는 **Done when:** 줄로 끝나, 어떤
`canon gate check` 또는 `canon subject show <id>` 결과가 끝을 뜻하는지 밝힙니다.

### 파괴적 명령은 계획이 먼저입니다

삭제하거나 기존 데이터를 다시 쓰는 `purge`, `tier age`, `ledger compact`,
`artifacts move`, `migrate`는 **미리보기가 기본**입니다. `--commit` 없이 실행하면
`planDigest`와 `effects`를 출력하고 아무것도 바꾸지 않으며 exit `0`입니다.
실제로 실행하려면 `--commit --plan-digest <planDigest>`를 줍니다. 지금 다시 계산한
plan의 digest가 같을 때만 실행하고, 아니면 `PLAN_STALE`입니다. 이 명령들에
`--dry-run`은 없습니다(미리보기가 곧 dry run입니다). `init`, `skills install`,
`inventory sync`, `ingest *`처럼 미리보기가 도움이 되는 다른 쓰기 명령은
`--dry-run`을 받습니다.

```bash
canon purge --kind session --before 2020-01-01T00:00:00Z
canon purge --kind session --before 2020-01-01T00:00:00Z --commit --plan-digest 0123456789abcdef
```

**Done when:** 미리보기의 `planDigest`로 `--commit --plan-digest`를 실행해 exit `0`이
나오면 끝이고, 결과는 그 실행의 `data`에서 읽습니다.

### 0.27에서 올리기

0.28에서 문법이 바뀌었고 별칭은 남기지 않았습니다. 옛 철자(`demo add`,
`regime-key`, `review add`, `--pin`, `--sha`, `--reviewed-sha`, `--resolution-sha`,
`--introduced-by`, `scenario new --from` 등)는 모두 새 철자로 대체되었으며 대응표는
CHANGELOG의 제거된 철자(removed spellings) 표(0.28.0 Upgrading)와 명세의 `removed` 목록에 있습니다.
레포는 다음 순서로 올립니다:

```bash
canon migrate
canon migrate --commit --plan-digest 0123456789abcdef
canon skills install
```

첫 줄이 미리보기이고 둘째 줄의 digest는 그 출력의 `planDigest`입니다. 마지막
줄이 옛 전체 스킬을 스텁으로 바꿉니다. 0.27 레포에서는 `canon status`,
`canon gate check`, `canon context`가 경고를 내고 `meta.next`의 첫 항목으로
`canon migrate --json`을 안내합니다.

**Done when:** `canon status`에 0.27 경고가 더 나오지 않고 `canon gate check`가
깨끗하게(exit `0`) 끝나면 끝입니다.
