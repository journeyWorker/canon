title: CLI 레퍼런스
description: canon --help 출력을 기준으로 목적별로 묶은 전체 서브커맨드.
---

`canon`은 기능마다 하나의 서브커맨드를 갖는 단일 바이너리입니다. 언제든
`canon <command> --help` (또는 `canon <command> <subcommand> --help`)를
실행하면 정확한 플래그 목록을 확인할 수 있습니다 — 이 페이지는 그 출력을
그대로 반영합니다.

대부분의 서브커맨드는 `--repo <dir>` (기본값 `.`)를 받습니다: 리터럴
`.` 기본값은 `cwd`의 조상 디렉터리를 거슬러 올라가며 가장 가까운
`canon.yaml`을 찾고, 다른 명시적 경로는 그대로 사용되며 탐색을 하지
않습니다. 일부는 기본 사람이 읽기 좋은 표/요약 대신 기계가 읽을 수 있는
출력을 위한 `--json`도 받습니다.

## Try it

사전 설정 없이 바로 실행하는 데모 — gate가 막히고, evidence를 추가하면
통과하는 과정을 봅니다.

| Command | Description |
|---|---|
| `canon demo init [--repo <dir>]` | 일회용 evidence loop를 스캐폴드합니다: 실제 `canon init` 설정, `reviewer`를 요구하는 `policy.yaml`, 그리고 seed된 `dev` evidence 레코드 하나 — 그 결과 `canon gate check`는 `uncovered-cell auth.login.01`로 red 상태가 됩니다. 기존 `canon.yaml`은 덮어쓰지 않고 거부합니다. |
| `canon demo attest [--repo <dir>]` | 데모 scenario에 빠진 독립 `reviewer` evidence를 기록하여, 같은 `canon gate check`를 green으로 바꿉니다. |

## Setup

레포 설정을 스캐폴딩하고, 해석 결과를 확인하고, provider-aware 단일
`canon` 동반 스킬을 구체화합니다. 스킬은 명시적인 CLI 명령을 대신하지
않고 필요한 참조 문서만 지연 로드하도록 안내합니다.

| Command | Description |
|---|---|
| `canon init [--repo <dir>]` | `<repo>/canon.yaml`에 동작하는 새 `canon.yaml` (`tiers:`/`routing:`/`specs:`/`plans:`)을 생성합니다. 기존 파일이 있으면 덮어쓰지 않습니다. 다음 단계로 `canon skills install`을 안내합니다. |
| `canon init --check-config [--repo <dir>]` | 기존 `canon.yaml`을 읽기 전용으로 검증합니다. `inventory sync`/`ingest plans`/`tier age`가 쓰는 것과 동일한 strict loader를 그대로 체이닝합니다. |
| `canon context-pack create --manifest <repo-relative.json> [--repo <dir>] [--json]` | 레포 내부의 명시적 JSON 매니페스트가 선택한 파일로 불변 content-addressed context snapshot을 생성합니다. 간결한 출력은 pack id만 출력하며 `--json`은 매니페스트 메타데이터와 digest를 출력합니다. |
| `canon context-pack show <id> [--repo <dir>] [--json]` | 저장된 pack을 검증한 뒤 표시합니다. `show`는 반환 전에 매니페스트와 모든 불변 content object를 다시 검사하며, 간결한 출력에는 캡처된 바이트가 포함되지 않습니다. |
| `canon context-pack verify <id> [--repo <dir>] [--json]` | 캡처된 내용을 반환하지 않고 pack을 검증합니다. pack이 없거나 오래되었거나 변조되었으면 nonzero로 종료합니다. |
| `canon adapter validate --response <path> [--repo <dir>] [--json]` | provider-neutral protocol-v1 응답을 읽기 전용으로 검증합니다. 핵심 필드(`run_id`, provider/model, context-pack id, status, capability, 안전한 evidence ref, 순서가 맞는 nonnegative telemetry)는 strict하게 검사하고, provider 전용 데이터는 `extensions` 아래의 불투명 JSON으로 둡니다. JSON 출력은 정규화된 핵심 요약과 extension 키 이름만 포함하며 payload는 노출하지 않습니다. `--repo`는 context pack 조인을 선택적으로 확인합니다. provider를 실행하지 않으며 capability 선언 자체가 sandbox enforcement는 아닙니다. |
| `canon prompt register --name <name> --version <version> --manifest <repo-relative.json> [--repo <dir>] [--json]` | 명시적 레포 내부 매니페스트에서 버전이 지정된 prompt bundle을 불변 content registry에 등록합니다. |
| `canon prompt show --name <name> --version <version> [--repo <dir>] [--json]` | 등록된 prompt bundle 버전을 선택하고 검증합니다. 기본 출력은 간결한 메타데이터이며 `--json`은 snapshot 메타데이터와 digest를 포함합니다. |
| `canon context [--repo <dir>] [--json]` | 해석된 저작 표면을 출력합니다: 레코드 종류 + envelope 필드, enum 도메인, 조인 키 문법, 파티션 레이아웃, 정책 기반 요구사항, capability 버전. capability *쿼리*입니다 — `fmt --check`/`gate`가 같은 레포에서 진단을 보고하더라도 항상 0으로 종료합니다. |
| `canon skills install [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | canonical `canon` 스킬 하나를 투영합니다. Claude는 `.claude/skills/canon/SKILL.md`, Codex는 `.agents/skills/canon/SKILL.md`(Codex가 스킬을 찾는 디렉토리), OMP는 `.omp/skills/canon/SKILL.md`, Pi는 `.pi/skills/canon/SKILL.md`를 받습니다. 선택된 모든 provider가 `reference/**`와 `scripts/**` sidecar를 받습니다. OMP/Pi는 레포 로컬의 passive bundle이며 retrieve pre-dispatch 스크립트는 sidecar일 뿐 native hook이 아닙니다. 선택하지 않으면 `.claude`, `.agents` 또는 `.codex`(Codex), `.omp`, `.pi`를 감지하고, 아무 root도 없을 때는 Claude+Codex를 기본 선택합니다. canon 0.13.0 이하가 만든 legacy `.codex/skills/canon.md` + `.codex/skills/canon/**` 투영은 설치 lock의 해시와 바이트가 일치하는 파일만 하나씩 제거합니다. 수정된 파일과 사용자 파일은 남기며, `.codex/skills`는 비었을 때만 제거합니다. |
| `canon skills check [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | 쓰기 없이 canonical 투영의 누락·오래됨, target 소유 content manifest, 남아 있는 legacy `.codex/skills` Codex 투영(수정 명령 포함)을 확인하며, 하나라도 있으면 1로 종료합니다. |
| `canon skills doctor [--source <dir>] [--target <dir>] [--providers=claude,codex,omp,pi]` | 네 개의 관리 root와 legacy `.codex/skills` root 전체에서 provider, drift, legacy 잔재를 사람이 읽을 수 있게 진단하고, legacy Codex 투영에는 수정 명령을 함께 알려 주며 사용자 파일을 삭제하지 않습니다. |

Canon 기여자는 legacy `canon skills install --source
canon/skills-dev --target .` materializer를 사용할 수 있습니다. 이는
일반 사용자 설치 흐름에 포함되지 않습니다.


## Subjects

canon의 13번째 레코드 종류인 durable product unit(서브젝트)을 저작하고
라이프사이클을 통해 구동하며, import된 plan change를 그 아래로 adopt합니다.
subject-write-first 루프는 [캐논 개념](/ko/concepts/canon/#서브젝트)을
참고하세요. "feature docs"는 항상 Gherkin `.feature` 파일을, "subject"는
관리 레코드를 뜻합니다.

| Command | Description |
|---|---|
| `canon subject new <id> --domain <d> --title <t> [--summary <s>] [--owner-role <r>] [--repo <dir>] [--json]` | `Subject`을 저작합니다(kebab-slug `<id>`가 durable `subject_id` 조인 키). `--domain`은 vocabulary로 정의된 kebab slug입니다 — 기본 집합 `planning`/`design`/`dev`/`data`/`test`, `.canon/vocab`로 레포별 확장. 상태 `proposed`로 시작하며, `--owner-role`은 생략 시 `implementer`가 기본값입니다. 쓰기 시 envelope + 정책을 검증합니다. |
| `canon subject adopt <change_id> --subject <id> [--repo <dir>] [--json]` | import된 plan `Change`(`canon ingest plans` 결과)를 `Subject`에 연결합니다: `Change.subject_id`를 찍고 subject의 `change_ids`에 추가합니다. |
| `canon subject status <id> <state> [--override-reason <text>] [--actor-id <id>] [--repo <dir>] [--json]` | `proposed → specced → building → verifying → shipped`(및 any → `retired`)를 따르는 정책 게이팅 전이입니다. `verifying → shipped`는 subject가 시나리오를 하나 이상 소유하고(`canon inventory sync`가 인덱싱한 `@subject:<id>` 태그 기준), 소유한 모든 scenario가 최신 non-Divergent 판정을 가질 것을 추가로 요구합니다. 위반 시 failure class별로 출력하고 `1`로 종료하며 레코드는 변경되지 않습니다(fail closed). `spec_coverage.require_review`가 설정되어 있으면 어떤 리뷰 검사를 실행했고 건너뛰었는지 stderr에 출력하며, `require_review.scope` 상태로 옮길 때 빈틈(`unreviewed-promotion`, `open-blocker`)이 있으면 같은 방식으로 거부합니다. `--override-reason "<한 줄>"`은 이 두 클래스만 면제하고 — ship 게이트의 판정·case 빈틈은 절대 면제하지 않습니다 — 새 레코드에 `status_override`(`to`, `reason`, 넘겨준 위반을 정확히 `{class, subject}`로 적은 `waived`, `--actor-id`에서 온 `actor`, 기본 `canon`)를 남깁니다. 나중에 올라온 blocker처럼 기록되지 않은 빈틈은 여전히 게이트를 실패시킵니다. 사유가 비었거나 여러 줄이면 `2`로 종료합니다. 면제는 subject의 다음 상태 쓰기에서 지워집니다. `require_review`가 없으면 아무것도 바뀌지 않습니다. |

## Corpus

Gherkin `.feature` 스펙 코퍼스를 검증하고 확장합니다.

| Command | Description |
|---|---|
| `canon format <ROOT> [--repo <dir>]` (별칭 `canon fmt`) | 코퍼스 루트(예: `spec/`)를 아티팩트 패밀리 스키마 + 레이아웃 디스크립터에 대해 검증합니다. 검증이 유일한 모드이므로 `--check`는 이제 기본값이며 호환을 위해서만 받아들여집니다. |
| `canon inventory sync [--repo <dir>] [--spec-root <dir>]` | 설정된 `specs.roots[]` 항목마다 `canon-fmt`로 검증한 뒤, `(project_id, scenario_id)`당 하나의 `Scenario` ledger-index 레코드를 생성합니다. `--spec-root`는 하나의 ad hoc 루트로 `canon.yaml`을 완전히 오버라이드합니다. |
| `canon scenario new <TAG> --title <label> [--subject <id>] [--lane <v>] [--case <v>] [--actor <id>] [--feature <path>] [--repo <dir>]` | `<area>.<surface>.<nn>` 태그에 대한 `.feature` 스텁을 추가합니다(없으면 생성): 태그 바로 위의 `# canon:` provenance 줄, 지정 시 `@subject:<id>` / `@lane:<v>` / `@case:<v>`, 그 다음 id 태그와 헤더. `--actor`(또는 `CANON_ACTOR`)가 provenance의 actor를 정하며 기본값은 `canon-scaffold`, `--lane`과 `--case`는 레포의 `lane`/`case` vocabulary에 대해 검사됩니다. ledger 레코드는 쓰지 않습니다. |
| `canon feature new <SURFACE> --title <label> [--actor <id>] [--repo <dir>]` | 아직 시작되지 않은 `<area>.<surface>`를 위한 시나리오 없는 새 `.feature` 파일을 스캐폴딩합니다. 기존 파일이 있으면 덮어쓰지 않고 실패합니다. |

## Ingest

에이전트 CLI 세션, 증거 아티팩트, 외부 plan dialect를 티어드 스토리지로
적재합니다.

| Command | Description |
|---|---|
| `canon ingest sessions [--watch] [--interval-secs <n>] [--home <dir>] [--canon-yaml <path>] [--full] [--all-workspaces]` | 등록된 모든 세션 스토어 어댑터(`omp`/`pi`, Claude Code, Codex, Hermes)를 스캔하고, `Session`/`Run`/`Event` 레코드로 정규화한 뒤(사용자 턴에서 캡처한 `user_directive` 이벤트 포함) canon-store로 저장합니다. 기본값은 현재 프로젝트의 세션만 대상으로 합니다(메인 워크트리 + 연결된 모든 `git worktree` 루트); `--all-workspaces`는 머신 전체 스캔으로 되돌립니다. `--watch`는 파일 단위 워터마크와 함께 폴링합니다(기본 30초) — 변경된 트랜스크립트만 다시 파싱합니다. `--full`은 워터마크를 무시합니다. |
| `canon ingest artifacts [--watch] [--interval-secs <n>] [--repo <dir>] [--json]` | 조인 스파인의 아티팩트/판정 절반을 실행합니다: ledger/divergence/openspec-task 경로 어댑터와 handoff 레코드 소스 어댑터로 판정을 도출하고, regime 키가 매겨진 trajectory로 접어 canon-learn을 통해 저장합니다. `sessions`와 달리 반복된 `--watch` 패스는 아직 write-idempotent하지 않습니다. |
| `canon ingest plans [--dialect <name> --source <dir>] [--repo <dir>] [--json]` | 하나의 plan dialect — `openspec` change 디렉터리, 또는 `superpowers`의 writing-plans 형식 문서(s30: `# <title>`/`**Goal:**`/`### Task N:` 섹션, 섹션 안의 체크박스가 모두 체크되어야 해당 task가 done) — 를 canon-model의 Change/Task 레코드로 가져옵니다. 둘 다 같은 조인을 거쳐 `task_id = <change_id>#<n>`로 키가 매겨집니다. `--watch`는 없습니다 — plan은 operator가 직접 pull합니다. `--dialect`/`--source`는 `canon.yaml`의 `plans:` 섹션을 우회하는 일회성 import이며 둘 다 함께 필요합니다. |

## Trust

트러스트 스파인 gate와, 그것이 읽는 네이티브 `Review`/`Divergence` 판정
프로듀서입니다.

| Command | Description |
|---|---|
| `canon gate check [--repo <dir>] [--release]` | coverage/ledger/staleness/spec-coverage/bound-artifact/trust-ladder 체크 셋을 실행하고 위반 사항을 failure class별로 출력합니다(9개: `uncovered-cell`, `unreviewed-promotion`, `trust-below-required`, `stale-evidence`, `malformed-evidence`, `flagged`, `unevidenced-flip`, `fabricated-evidence`, `open-blocker`). 옵트인 `spec_coverage.require_review`가 켜지면 독립 `Review`가 없는 범위 안 시나리오는 `unreviewed-promotion`, adopt된 change의 열린 `blocker` finding은 `open-blocker`가 됩니다. `canon subject status --override-reason`으로 면제된 빈틈은 실패시키지 않고 뒤에 `review waivers:` advisory로 출력됩니다. 종료 코드: `0` 클린, `1` gate-red, `2` 사용/로드 실패. `--release`는 release-scoped 트러스트 체크를 추가로 적용합니다. 최신 증거 레코드에 묶인 파일은 계속 증명 가능해야 합니다. 저장된 blob으로, 또는 (0.14 이전 레코드라면) 기록된 digest와 같은 작업 트리 파일로 증명하며, 후자는 `canon evidence vault`를 안내하는 `evidence artifacts:` advisory를 출력합니다. 둘 다 안 되면 `stale-evidence`입니다. |
| `canon gate task <TASK_ID> [--repo <dir>]` | plan `task_id` (`<change_id>#<n>`) 하나에 대한 증거 게이팅된 체크박스 플립입니다. 증거가 없거나 형식이 잘못되었거나 조작된 경우 fail closed — 행은 플립되지 않은 채로 남습니다. 행의 노트는 태스크에 묶인 모든 레코드를 요약하며(`2 evidence records (2 faithful); latest: <summary>`), plan 소스를 다시 수집하므로 `canon query --kind task`도 같은 상태를 보여줍니다. |
| `canon gate promote [--repo <dir>] [--dry-run]` | `_staging/` 증거 레코드를 커밋된 ledger로 승급시키고, (role, surface)별로 단조 증가하는 `run_seq`를 부여합니다. `--dry-run`은 쓰지 않고 계획만 출력합니다. |
| `canon gate install-hooks [--repo <dir>] [--event <name>] [--matcher <m>] [--command <cmd>] [--timeout <secs>]` | `.claude/settings.json`/`.codex/hooks.json`에 멱등적인 diff-only hook-seam을 설치하고, 범용 pre-commit 스크립트도 함께 설치합니다. 기본값: `--event PreToolUse`, `--command "canon gate task"`, `--timeout 30`. |
| `canon gate selftest` | 번들된 fixture 코퍼스를 실행합니다: 발동이 증명된 모든 `FAILURE_CLASSES` 문자열(`open-blocker`를 포함한 9개)을 `expected_failures.txt`와 정확히 일치시킵니다. `--repo`를 받지 않습니다. |
| `canon evidence add --task <id> --kind <k> --ref <r> --role <role> [--surface-ref <path-or-effect>] [--verdict <v>] [--summary <s>] [--command-result <out>] [--scenario-id <id>] [--run-id <ulid>] [--artifact <path>] [--report <junit\|cucumber>:<path>] [--report-case <name>]... [--max-artifact-mib <n>] [--repo <dir>]` | 플랜 태스크에 대한 귀속된 `EvidenceRecord` 하나를 스테이징합니다. `--surface-ref`는 검증된 경로 또는 `effect:<kebab-slug>` 위험 바인딩을 저장하지만 변경 경로의 증명은 아닙니다. 위험 승인은 policy에 고정된 `approval.allowed_signers`로 검증되는 detached SSH 서명과 `--approval-role human`이 있을 때만 계산되며, `CANON_ACTOR`·호출자 문자열·agent 역할은 계산되지 않습니다. **실험 기능:** `--artifact`는 저장소 안의 파일을 sha256으로 묶고, `--report`는 JUnit/Cucumber 리포트를 파싱해 시나리오와 매칭된 케이스와 결과를 기록합니다(실패한 케이스에 `faithful` 판정은 거부). canon은 테스트를 실행하지 않습니다. 이후 `canon gate promote`로 커밋하고 `canon gate task`로 사용합니다. `--summary`는 `--task` 없이도 쓸 수 있으며 조작 마커 검사를 받고, 태스크 행을 플립할 때는 가장 최근 summary가 붙습니다. `--project-id`와 함께 `--scenario-id`만 주면 태스크 대신 시나리오를 신고하며, 둘 다 주면 한 레코드가 양쪽을 모두 증명합니다. 시나리오 id를 담은 리포트 케이스는 모두 묶이고 `--report-case`(반복 가능)로 더할 수 있으며, 묶인 케이스 중 하나라도 실패하면 `faithful`은 거부됩니다. 묶인 파일은 `.canon/artifacts/sha256/<hex>`에 복사되며(git 추적, 함께 커밋), 25 MiB를 넘는 파일은 `--max-artifact-mib`로 한도를 올리지 않으면 거부됩니다. |
| `canon evidence vault [--max-artifact-mib <n>] [--repo <dir>]` | 0.14 이전에 쓰인 증거 레코드의 묶인 파일을 `.canon/artifacts/sha256/`에 저장합니다. 작업 트리 바이트가 기록된 digest와 같은 파일은 복사하고, 나머지는 두 digest와 함께 저장하지 못한 목록으로 보여줍니다. 실행되면 `0`, 레저 읽기나 쓰기 실패면 `2`로 종료합니다. |
| `canon finding add --change-id <id> --round <n> --seq <n> --severity <s> --reviewer <name> --summary <s> [--disposition <d>] [--reviewed-sha <sha>] [--resolution-sha <sha>] [--introduced-by <sha>] [--file-ref <path:lines>] [--repo <dir>]` | 코드 리뷰 findings 하나를 durable 레코드로 스테이징합니다. 릴리즈 노트의 개수를 기억이 아니라 조회로 얻게 하기 위함입니다. `--seq`는 필수이며 충돌은 거부됩니다. `fixed`는 `--resolution-sha`를 요구하고, `fixed`만 그것을 가질 수 있습니다. |
| `canon finding close --change-id <id> --round <n> --seq <n> --disposition <d> [--resolution-sha <sha>] [--repo <dir>]` | 이미 커밋된 finding의 처분(disposition)을 옮깁니다. append-only입니다: 이력을 수정하는 대신 이를 대체하는 레코드를 쓰므로, 그것이 제기된 라운드가 보존됩니다. 재오픈도 실제 전이입니다. |
| `canon review add --project-id <id> --scenario-id <id> --reviewer <name> --pin <pin> --role <role> --upstream-ref <ref>` (또는 `--original-spec-ref <ref>`) `[--actor-id <id>] [--repo <dir>]` | 네이티브하고 귀속된 `Review` 레코드 하나를 씁니다. `--upstream-ref`/`--original-spec-ref` 중 정확히 하나가 필요합니다 — 둘 다 또는 둘 다 아니면 쓰기를 거부합니다. |
| `canon divergence stage --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --role <role> [--status <status>] [--reason <r>] [--expiry <e>] [--round <n>] [--detail <d>] [--repo <dir>]` | `run_seq`가 없는 순서 없는 staging candidate 하나를 씁니다. `--status`는 `open`, `still-divergent`, `resolved`, `deferred` 중 하나를 받으며(`deferred`는 `--reason`/`--expiry`를 추가로 요구합니다), `run_seq`는 이후 `canon divergence promote`가 부여합니다. |
| `canon divergence promote [--repo <dir>] [--dry-run]` | 현재 staged된 모든 `Divergence` candidate를 일괄 승급시키고, `(project_id, role, surface)` 파티션 내에서 각각 단조 증가하는 `run_seq`를 부여합니다. |
| `canon divergence resolve --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --role <role> [--round <n>] [--detail <d>] [--repo <dir>]` | `Resolved` candidate를 직접 커밋합니다 — staging 디렉터리를 건드리지 않습니다. |
| `canon divergence defer --project-id <id> --scenario-id <id> --sha <sha> --reviewer <name> --reason <r> --expiry <e> --role <role> [--round <n>] [--repo <dir>]` | `Deferred { reason, expiry }` candidate를 직접 커밋합니다 — staging 디렉터리를 건드리지 않습니다. |
| `canon divergence status [--repo <dir>] [--as-of <date>]` | divergence 번다운의 현재 상태 뷰입니다. `--as-of`는 `Deferred` 만료 평가 기준 시점을 지정하며, 생략하면 지금입니다. |

## Memory

증류된 전략, 역할+regime 범위의 retrieval, 그리고 dispatch 시점의 쓰기
경로입니다.

| Command | Description |
|---|---|
| `canon learn promote <STRATEGY_ID> [--repo <dir>] [--evaluation <path> --approval <path>] [--signature <path>] [--dry-run]` | **quarantine**된 `StrategyItem` 하나를 `.canon/strategies/<role>/<id>.md`로 활성화합니다. 설정된 `occurrence`/paired-`crn` 게이트는 자격일 뿐이며, 유효한 paired `PromotionEvaluation`과 `human으로 선언된 approval`의 SSH detached signature가 추가로 필요합니다. evaluation은 비어 있지 않은 paired baseline/candidate result digest, 유한한 `pairs`/양수 `uplift`/0인 `regressions`, 일치하는 integrity/provenance, 통과 decision을 요구합니다. verifier는 policy-pinned `approval.allowed_signers`에 대해 `ssh-keygen -Y verify`를 사용하며 `--evaluation`과 `--approval`은 함께 필요합니다. `--force`는 없고 `--dry-run`은 활성화하지 않습니다. |
| `canon learn approve <STRATEGY_ID> --evaluation <path> --principal <id> [--repo <dir>] [--json]` | quarantine candidate/evaluation을 검증하고 외부 SSH signer가 사용할 서명되지 않은 domain-separated `canon-learning-approval-v1` payload(`strategy:<id>`, evaluation digest, RFC3339 timestamp, `payload_hex`)를 출력합니다. private key를 읽거나 `verified`를 설정하지 않습니다. |
| `canon learn request <STRATEGY_ID> --evaluation <path> --principal <id> [--repo <dir>] [--json]` | `learn approve`의 정확한 alias이며 동일한 서명되지 않은 approval payload를 출력합니다. |
| `canon learn rollback <STRATEGY_ID> --reason <text> --actor <id> --signature-file <path> --approved-at <RFC3339> [--contradicting-trajectory-id <id>] [--repo <dir>]` | 일반적인 contradiction demotion과 구별되는 인증된 operator rollback입니다. policy-pinned `approval.allowed_signers`에 대해 rollback-bound payload의 armored SSH signature를 검증하고 provenance를 기록하며 lifecycle을 `rolled_back`로 설정합니다. |
| `canon retrieve --role <role> (--regime <regime_key> \| --domain <d> [--subject <id>]) [--k <n>] [--repo <dir>] [--json]` | 역할+regime 범위의 전략 retrieval입니다. `--regime`을 직접 주거나 `--domain`/`--subject`로부터 도출합니다 — retrieval은 area 후보를 `<domain>-<subject_id>` 다음 `<domain>` 순서(폴백)로 시도합니다. `--role`은 `--regime`의 선행 세그먼트와 같아야 합니다(불일치 시 종료 코드 `2`). fail-soft: 그 전제조건이 성립하면 항상 `0`으로 종료하며, 스토어 장애는 빈 목록으로 저하됩니다. quarantine/rejected/rolled_back/demoted 로우는 제외되며, legacy `lifecycle: null` 로우는 읽을 수 있지만 현재 paired-evaluation 또는 SSH-approval provenance가 없으므로 measured-uplift 증거가 아닙니다. |
| `canon dispatch begin --role <role> --regime <regime_key> [--context-manifest <repo-relative.json>] [--prompt-bundle <name@version>] [--agent-id <id>] [--repo <dir>] [--json]` | `Run`(status `Running`)을 발급하고, `--role`/`--regime` guidance를 retrieve하여 불변 ContextPack lineage를 기록합니다. 명시적 context 매니페스트는 캡처할 문서·도구·prompt를 정확히 선택하며, `--prompt-bundle`은 등록된 불변 prompt bundle을 선택하고 검증합니다. 누락·위험·변조된 선택은 RunId나 매니페스트를 쓰기 전에 거부됩니다. |
| `canon regime-key --role <r> --repo <r> --area <a> --hash <h>` | 원본 세그먼트로부터 하나의 정규 `regime_key` (`<role>/<repo>/<area>/<hash>`)를 직렬화 + 검증합니다 — 모든 write/read 경로가 공유하는 Rust 직렬화기의 셸 대응물입니다. 키를 출력하고 `0`으로 종료하며, 형식이 잘못되면 `2`로 종료합니다. |

## Surface

현재 상태를 읽습니다: 리포트, 대시보드, ad hoc 쿼리, 티어 유지보수,
플러그인 오버레이, 셀프 체크입니다.

| Command | Description |
|---|---|
| `canon report [--repo <dir>] [--check] [--snapshot <dir>]` | markdown 상태 리포트를 생성하거나(기본값), 커밋된 사본과 byte-diff하거나(`--check`, drift 시 종료 코드 `1`), panel mart를 Parquet + `manifest.json`으로 export합니다(`--snapshot`, 둘 다 주어지면 우선). |
| `canon dashboard [--repo <dir>] [--snapshot <dir>] [--port <n>]` | 로컬에서 빌드된 대시보드 앱을 스냅샷 기준으로 서빙합니다. 기본 포트는 `4173`이며, `--snapshot`을 생략하면 매 실행마다 `.canon/dashboard-snapshot`에 새로 생성됩니다. |
| `canon query --kind <kind> [--since <ts>] [--repo <dir>] [--canon-yaml <path>] [--json] [--plugin <id>] [--change-id <id>] [--domain <d>] [--status <s>]` | 레코드 종류의 읽기를 그것이 있을 수 있는 모든 티어에 걸쳐 팬아웃하고 `at` 기준으로 병합합니다. `--plugin`은 해석된 플러그인의 오버레이 필드를 각 레코드에 투영하며, 미해석 플러그인이나 종류 불일치 시 fail-soft합니다. `--change-id`는 `--kind change`/`--kind task`에, `--domain`/`--status`는 `--kind subject`(도메인별 관리 뷰)에 범위를 제한하며, `--status`는 `--kind change`/`--kind task`에도 적용됩니다. |
| `canon purge --kind &lt;session|run|event|trajectory&gt; --before &lt;RFC3339&gt; [--repo &lt;dir&gt;] [--dry-run] [--json]` | 일치하는 레코드를 라우팅된 rung과 모든 aging 대상에서 과거 버전을 포함해 제거합니다. 적용 모드는 모든 대상을 사전 점검하며, dry-run은 변경하지 않습니다. 원본 transcript나 Git history는 삭제하지 않습니다. |
| `canon tier age [--dry-run] [--repo <dir>] [--canon-yaml <path>]` | 모든 `canon.yaml` `aging:` 규칙을 한 번 적용해, 임계값을 넘은 레코드를 설정된 대상 티어로 이동시킵니다. `--dry-run`은 쓰지 않고 미리보기만 합니다. |
| `canon plugin sync <PLUGIN_ID> [--repo <dir>] [--spec-root <dir>]` | `<plugin-id>`의 매니페스트에 선언된 오버레이를 해석하고, 각각을 등록된 소스로 넘긴 뒤, 모든 candidate를 validate-then-write 파이프라인으로 씁니다. |
| `canon selftest [--json]` | 등록된 모든 크레이트의 fixture 코퍼스 셀프 테스트를 실행하고 EXPECTED oracle과 비교합니다. `canon gate selftest`와 별도로 추가됩니다. |
