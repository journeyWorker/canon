`canon-gate`는 canon의 트러스트 스파인입니다: `EvidenceRecord` 형태의
코퍼스 위에서 동작하는 2계층 증거 게이트입니다. 아티팩트마다 **서로 다른**
두 질문에 답하며, 이를 절대 하나의 "완료" 불리언으로 뭉뚱그리지 않습니다:

- **커버리지** — 정책상 요구되는 증거가 이 아티팩트에 대해 *존재*하는가?
- **판정 레저** — 그 증거가 *통과*했는가, 누가 했는가, 얼마나 오래됐는가?

`Divergent` 판정도 커버리지는 만족합니다 — 커버리지는 "테스트가
존재한다"이지, 결코 "테스트가 통과했다"가 아닙니다.

두 질문 모두 증거에서 출발하므로, 아무도 증명한 적 없는 스펙은 어느
쪽에도 보이지 않습니다. [스펙 커버리지](#스펙-커버리지-해야-할-일-목록)는
대신 스펙 코퍼스에서 출발하는, 옵트인 방식의 세 번째 질문입니다.

## 9개의 실패 클래스

`canon gate`가 보고하는 모든 위반은 아래의 안정적이고 grep 가능한 문자열
중 하나를 가집니다. 조율된 픽스처+훅 마이그레이션 없이는 이름을 절대
바꾸지 않습니다:

| 클래스 | 의미 |
|---|---|
| `uncovered-cell` | 정책상 요구되는 증거 셀(역할 × 아티팩트)에 대응하는 레코드가 아예 없음 — 또는 `spec_coverage`가 켜진 경우, 스펙 코퍼스의 시나리오 중 어떤 증거도 없거나, 열린 divergence를 갖거나, 최신 판정이 `Divergent`인 것. 어느 쪽인지는 detail 문자열이 밝힙니다. |
| `unreviewed-promotion` | 아티팩트의 `reviewed` 라이프사이클 태그에 대응하는 레저 리뷰-레코드가 없음 — 또는 `spec_coverage.require_review`가 켜진 경우, 범위 안 시나리오에 유효한 `Review`가 없음(아예 없거나, 그 시나리오의 증거를 남긴 액터 본인의 리뷰뿐임). |
| `trust-below-required` | 아티팩트의 트러스트 레벨이 `policy.yaml`의 `trust_required`보다 낮음 — release 스코프 전용(`canon gate check --release`). |
| `stale-evidence` | 통과했던 레코드가 stale로 저하됨: `evidence_sha` 이후 선언된 표면이 변경됐거나, HEAD가 `staleness.max_commits_behind`를 넘어섬. 이미 green인 레코드만 저하시킴. |
| `malformed-evidence` | 후보 레코드가 파싱되지 않거나, 잘못된 위치에 있거나, 파싱 불가능한 임시 태그를 가짐. 잘못된 형식의 증거는 증거가 아님. |
| `flagged` | 사람만 설정 가능한 `flagged` 오버레이가 켜짐 — 어떤 통과 증거가 있어도 절대 green이 되지 않음. |
| `unevidenced-flip` | `canon gate task <task_id>`가 대응하는 non-`Divergent` `EvidenceRecord` 없이 체크박스 플립을 요청받음. |
| `fabricated-evidence` | 플립에 첨부된 증거 노트에 차단 대상 마커(`"would pass"`, `"TBD"`, `"n/a"`)가 있거나, 첨부된 커맨드 결과 없이 `verified`만 주장함. |
| `open-blocker` | `spec_coverage.require_review`가 켜진 경우, 범위 안 subject가 adopt한 change에 최신 버전 기준 severity `blocker`, disposition `open`인 리뷰 finding이 있음. subject 문자열은 `<change_id>#<round>.<seq>`입니다. |

## 스펙 커버리지: 해야 할 일 목록

커버리지와 판정 레저는 둘 다 증거에서 출발해 열거하므로, 스펙만 써두고
아무도 손대지 않은 `.feature` 시나리오는 두 검사 모두에게 보이지
않습니다 — 묶을 레코드 자체가 없기 때문입니다. 스펙 주도 도구가 가장
잡아야 할 경우가 바로 그것이라, `spec_coverage`는 방향을 뒤집습니다:
`canon inventory sync`가 인덱싱한 Scenario 코퍼스에서 출발해 증거를
left join합니다. 그 결과가 곧 해야 할 일 목록입니다. **미구현 스펙과
미스매치 스펙은 둘 다 작업 항목**이며, 둘 다 `uncovered-cell`로
보고되고 어느 쪽인지는 detail이 밝힙니다.

**옵트인하지 않으면 꺼져 있습니다.** 스펙 주도 팀은 구현보다 스펙을
먼저 쓰므로, 기본값이 켜짐이면 그 방식대로 일하기 시작하는 순간 게이트가
빨개집니다. 섹션이 없으면 위반은 0건입니다:

```yaml
# .canon/policy.yaml
spec_coverage:
  require_evidence: true
  scope: [building, verifying]
  exclude_lanes: [process]
  require_cases: [failure]
```

`scope`는 무엇이 *차단할 수 있는지*를, Gherkin `@subject:<id>` 태그로
Subject에 연결된 시나리오 중 해당 [라이프사이클
상태](/ko/concepts/canon/)에 있는 것으로 좁힙니다. `building`이나
`verifying` 상태의 Subject가 없는 영역은 아무것도 차단하지 않으며, 이것이
부분적으로만 스펙이 있는 리포를 정직하게 유지합니다 — 스펙이 없는 부분은
조용히 green이 되는 대신 눈에 띄게 비어 있습니다. `scope`를 생략하면 모든
시나리오가 대상입니다.

`exclude_lanes`는 `scope` 다음에 적용되는 두 번째 독립 필터입니다.
시나리오의 **lane** — `@lane:<value>` 태그로, 인덱싱된 `Scenario`
레코드에 실립니다 — 은 그 요구사항이 어떤 종류인지 말합니다: `behavior`
(제품이 무엇을 하는가), `design`(어떻게 보이고 움직이는가),
`architecture`(코드가 어떻게 생겼는가), `process`(팀이 어떻게 일하는가 —
리뷰 보고서가 무엇을 주장해도 되는지, 인수를 어떻게 진행하는지). 기본
집합은 `canon.core`의 것이며, 레포는 자체 `lane` vocabulary enum으로
교체합니다. `process` 규칙은 코드 표면이 없어 테스트로 `faithful`이 될 수
없으므로, 여기에 올려두면 실제 규칙이 오염시킬 뿐인 숫자 밖에 머무릅니다.
생략하면 아무것도 제외되지 않습니다.

`require_cases`는 증거 존재 여부로는 보이지 않는 빈틈을 막습니다: 모든
시나리오에 증거가 붙어 있지만 전부 골든패스만 설명하는 표면입니다.
시나리오의 **case** — `@case:<value>` 태그 — 는 그 시나리오가 동작의 어느
경로를 명세하는지 말합니다: `happy`, `failure`(거부·오류·차단된 동작),
`edge`(빈 집합·한계·중복 같은 경계). 범위 안 시나리오가 있는 모든 기능
표면(`<area>.<surface>`)은 나열된 case마다 시나리오를 하나 이상 가져야
하며, 없으면 그 표면이 `uncovered-cell`로 보고되고 `canon subject status
<id> shipped`도 같은 규칙으로 거부됩니다. 태그 없는 시나리오는 어떤 case도
채우지 않으므로, 분류되지 않은 코퍼스는 통과하지 않고 모든 표면이
보고됩니다. 생략하면 아무것도 요구하지 않습니다.

섹션이 있는데 형식이 잘못된 경우는 섹션이 없는 것과 결코 같지
않습니다 — 보고된 뒤 검사를 실패시키므로, 오타(또는 slug가 아닌 lane,
형식이 잘못된 `require_review`)가 게이트를 조용히 꺼버릴 수 없습니다.

### 독립 리뷰

증거는 테스트가 있다는 것을 말할 뿐, 작성자 아닌 누군가가 그 작업을
들여다봤다는 것은 말하지 않습니다. `require_review`(기본값은 없음 — 레포가
설정하기 전까지는 아무것도 바뀌지 않습니다)는 subject를 완료라고 주장하기
전에 그 두 번째 확인을 요구합니다:

```yaml
spec_coverage:
  require_evidence: true
  require_review:                 # `{}`이면 전부 기본값
    scope: [verifying, shipped]   # 기본값; [] = 모든 시나리오
    distinct_actor: true          # 기본값
    block_on_findings: true       # 기본값
```

subject가 `require_review.scope`에 있는 모든 시나리오(`spec_coverage.scope`와는
독립적이며, `exclude_lanes`는 여기서도 제외합니다)는 `Review` 레코드가
필요합니다 — `canon review add --project-id <root> --scenario-id <id>
--reviewer <who> --role reviewer --pin <sha> --upstream-ref <ref>` 후
`canon gate promote`. `distinct_actor`이면 리뷰의 `reviewer`와 액터가 둘 다
그 시나리오 증거의 모든 액터와 달라야 하므로, 에이전트가 자기 작업을 스스로
리뷰할 수 없습니다. 리뷰가 없거나 본인 리뷰뿐이면 `unreviewed-promotion`입니다.
리뷰에는 판정이 없으며, 판정은 여전히 ship 게이트가 확인합니다.

`block_on_findings`이면 리뷰 finding(`canon finding add --severity
blocker|should-fix|note`)은 `(change_id, round, seq)`별 최신 버전으로
읽힙니다. 범위 안 subject가 adopt한 change에 열린 `blocker`가 있으면, 닫힐
때까지 — `--resolution-sha <sha>`와 함께 `fixed`, 또는 `rejected`나
`deferred` — `open-blocker`입니다:

```
open-blocker c-demo#1.1 — open blocker finding by `reviewer-2` on change `c-demo` (subject `demo-subject`): unbounded subprocess wait; fix it and `canon finding close --disposition fixed --resolution-sha <sha>`, or close it as rejected or deferred
```

`should-fix`와 `note` finding은 절대 차단하지 않습니다.

`canon subject status --override-reason`으로 이 검사를 넘긴 subject는
([CLI 레퍼런스](/ko/cli/) 참고) 게이트를 실패시키지 않고, 위반 목록 뒤에
advisory로 빈틈을 계속 보여줍니다:

```
review waivers: 1 advisory(ies) — not failing the gate:
  waived unreviewed-promotion world.demo.01 — no review record ... [waiver: subject `demo-subject` moved to verifying by `lead`: reviewer out until Monday]
```

`canon context`는 finding severity, disposition, Review 필드, 현재
`require_review` 설정을 나열합니다.

## 실험 기능: 증거 바인딩

증거 기록은 신고입니다 — canon은 `--ref`를 실행하지 않으며, 팀이 쓰는 모든
언어와 에이전트 기반 QA 도구를 실행할 수도 없습니다. 바인딩(기본 off)은
팀의 러너나 에이전트가 이미 만든 파일을 기록이 가리키게 합니다:

```bash
# 어떤 파일이든 — trace, 스크린샷, 에이전트 QA 로그 — sha256으로 묶음
canon evidence add ... --artifact test-results/cart-trace.zip
# JUnit XML / Cucumber JSON 리포트: 매칭된 케이스와 결과까지 기록
canon evidence add ... --report junit:target/nextest/default/junit.xml
```

리포트 케이스는 이름이나 태그에 들어 있는 시나리오 id로 찾으며
(`--report-case`로 직접 지정 가능), 실패한 케이스에 `faithful` 판정을
붙이면 거부됩니다. 게이트가 이를 볼지는 policy 스위치로 정합니다:

```yaml
experimental:
  evidence_binding:
    mode: warn          # off(기본) | warn | require
    strength: artifact  # artifact(묶인 파일) | report(통과한 케이스)
    case: [failure]     # 선택: 이 시나리오만 대상
```

`warn`은 `strength`에 못 미치는 시나리오를 게이트 결과 뒤에 나열하지만
실패시키지 않고, `require`는 각각을 `uncovered-cell`로 보고합니다. 묶인
테스트가 정말 그 시나리오를 검증하는지는 여전히 canon이 알 수 없습니다 —
바인딩은 신뢰의 빈틈을 좁힐 뿐 메우지는 않습니다.

## 트러스트 래더

아티팩트는 **draft → reviewed**(에이전트 + 리뷰-레코드) **→ ratified**(사람)
순으로 올라갑니다. 대응하는 리뷰-레코드 없는 단순 승급은
`unreviewed-promotion`입니다. `flagged`는 사람만 설정 가능하며 절대
green이 되지 않고, 사람이 귀속된 clear-record로만 해제됩니다 — 한 방향
래칫입니다.

## 레포 검사

```bash
canon gate check --repo .            # 일반 평가
canon gate check --repo . --release  # + trust-below-required
```

`canon gate check`는 디스패처입니다: 커버리지 + 레저 + staleness +
스펙 커버리지 + 항상 켜져 있는 트러스트 래더 검사를 모아 실행하고, 모든 위반을 실패 클래스별로
묶어 출력합니다. `--release`는 release 스코프의 `trust-below-required`
검사를 추가로 켭니다 — `--release`가 전달되어도 트러스트 래더 검사는
절대 빠지지 않습니다. 종료 코드: 깨끗하면 `0`, 게이트 red(위반 존재)면
`1`, 사용법/로드 실패(읽을 수 없는 레저, 손상된 `canon.yaml`)면 `2`입니다.

## 태스크 체크박스 플립 게이팅

```bash
canon gate task s5-trust-spine-gate#5.2 --repo .
```

`canon gate task <task_id>`는 change의 plan 문서에서 체크박스 행 하나를
증거 기반으로 플립합니다. `<task_id>`(`<change_id>#<n>`)는 `canon.yaml`의
`plans:` 소스를 통해 해석됩니다 — 설정된 dialect 중 해당 태스크를 먼저
찾아낸 쪽이 이기므로 플립은 plan-dialect에 중립적입니다(`openspec` change
디렉터리, `superpowers` plan 문서). `plans:` 섹션이 없는 레포는 호환
기본값 `[{ dialect: openspec, root: <repo> }]`로 폴백합니다.
레저에서 대응하는 non-`Divergent` `EvidenceRecord`를 요구하며, 검사가
깨끗할 때에만 `- [ ]` → `- [x]`로 플립하면서 증거 노트를 덧붙입니다.
증거가 없거나, `Divergent` 판정이거나, 조작된 증거 노트인 경우 해당 행은
바이트 단위로 변경되지 않고 `1`로 종료하며 차단 위반을 stderr에
출력합니다. 이미 `[x]`인 행은 멱등 no-op입니다. 알 수 없는 `task_id`는
보고되며, 절대 조용히 무시되지 않습니다.

## 스테이징 → 승급

```bash
canon gate promote --repo .              # 스테이징된 모든 후보를 반영
canon gate promote --repo . --dry-run    # 미리보기만
```

`.canon/ledger/_staging/` 아래의 잘 정형화된 모든 레코드는 게이트와 동일한
검사로 재검증되고, (역할, 표면)별 단조 증가하는 `run_seq`를 부여받은 뒤 —
한 번의 호출 내에서 빈틈없이, 커밋된 티어 자체의 최댓값에서 이어서 —
커밋된 레저로 옮겨집니다. 잘못된 형식이거나 파티션 불가능한 후보는
거부됩니다: `1`로 종료하고, `run_seq`가 소비되지 않으며, 스테이징 파일은
리뷰어가 고칠 수 있도록 그대로 남습니다. `--dry-run`은 아무것도 쓰거나
지우지 않고 계획만 출력합니다.

## 훅 심(seam) 설치

```bash
canon gate install-hooks --repo .
```

멱등적이고 diff 전용입니다: `.claude/settings.json`과
`.codex/hooks.json` 양쪽에 훅 항목을 병합하며, 추가만 하고 같은 matcher
그룹 안의 기존 항목은 절대 건드리지 않습니다. 수동 편집 없이 두 번
실행하면 "no diff"를 보고하고 아무것도 쓰지 않습니다. 두 파일 모두
`canon gate`를 호출하는 항목이 없을 때는 `.canon/scripts/canon-gate-pre-commit.sh`도
함께 생성합니다(기본은 advisory; 게이트 실패 시 커밋을 막으려면
`CANON_GATE_ADVISORY=0`을 설정).

## 게이트 자체를 검증하기

```bash
canon gate selftest
```

내장된 픽스처 코퍼스를 실행합니다 — 실패 클래스마다 하나씩(`open-blocker`를
포함한 9개), 의도적으로
깨진 코퍼스로 해당 클래스만 발동함을 증명합니다. 게이트 자체의 코드를
건드린 뒤, 다른 `canon gate check` 실행의 green을 신뢰하기 전에
실행하십시오.

## 위반 읽기

모든 출력 줄은 `<failure-class> <subject> — <detail>` 형태입니다.
`<subject>`는 아티팩트 자신의 조인 스파인 식별자입니다(`task_id` 우선,
다음 `scenario_id`, 다음 `run_id`) — 이것으로 레저나 `tasks.md`를 직접
grep 하십시오, 절대 추측하지 마십시오.
