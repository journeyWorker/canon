canon의 전략 메모리(S6/S7/S8)는 누적된 verdict trajectory를 검색 가능하고
승급 가능한 인사이트로 바꿉니다 — 역할별로 네임스페이스가 나뉩니다:
`planning`, `design`, `dev`, `test`, `review` 등이 하나의 백본을
공유하면서도 각자 따로 진화합니다.

canon의 입장은 이렇습니다: 전략 메모리는 그 텍스트가 모델 외부의
아티팩트에 근거할 때에만 검색할 가치가 있습니다 — 그렇지 않으면
retrieval 루프는 모델 자신의 출력을 다시 되먹이는 데 그칩니다.

## 플라이휠

```
    → distill: 성공 → quarantine 전략, review 지적 → guardrail
    → 자격 게이트 (occurrence 또는 paired CRN)
    → paired evaluation + policy-pinned SSH approval
    → git 티어에서 활성화 (버전 관리, PR 리뷰)
    → 태스크 시작 전 retrieve (역할 + regime 스코프, 어드바이저리)
    → 이후 에이전트 실행 (uplift는 아직 측정되지 않음) ↻
```

## 두 개의 티어, 두 개의 스토어

- **웜 — trajectory (Parquet).** `<repo>/.canon/learn/trajectories/`
  아래의 `ParquetTrajectoryStore`: ingest가 기록한 verdict-키 로우.
  로컬, 재빌드 가능, `.gitignore` 대상 — 절대 수동 커밋되지
  않습니다.
- **더러블 — 전략 (git).** `ParquetStrategyStore`와 git으로 추적되는
  `<repo>/.canon/strategies/<role>/<id>.md` 파일: promotion이 쓰고
  demotion이 소프트 플래그를 다는, 증류된 PR 리뷰 가능한
  `StrategyItem`.

trajectory는 자신이 파생된 구체적 아티팩트 — scenario, handoff,
task — 를 제목에 지목하고, 그 근거가 된 evidence 레코드가 실제로 들고
있는 산문을 그대로 실어 나릅니다: 리뷰어의 pin, divergence 지적의
서술, 태스크의 증거 노트. 그래서 증류된 전략은 canon 자신의 ingest를
요약한 문장이 아니라 실제 증거를 인용합니다:

```
# before — the trajectory described the adapters that produced it
2 verdict(s) derived from canon-ingest artifact adapters for regime test/canon/platformer/41fdd8c50ee6

# now — the title names the artifact, the content quotes the evidence
platformer.session.04: resolved divergence
resolved divergence: Fixed and independently re-verified+attested at 505a668efedaed6dfb5e125a0d927f118b2dfad1 (dev-fix wave 8d3c1506..505a668e; movement.03/session.03 at ea77374)
```

산문 필드가 없다는 건 한계가 아닙니다. canon의 조인 스파인은 레코드가
자기에 관한 모든 사실을 직접 들고 있지 않아도 되게 하려고 존재합니다.
이벤트 자신에게 없는 텍스트를 두 개의 조인이 공급합니다.

- **선행 findings.** verdict를 가진 이벤트는, 같은 아티팩트에서 그보다
  앞선 산문 있는 non-verdict 이벤트들과 함께 증류됩니다. 그래서
  `resolved` divergence는 자신이 닫은 `open` ship-blocker를 함께
  담습니다 — 함정과 그 함정이 실제로 어떻게 고쳐졌는지가 한 아이템에
  들어오는, 전략이 취할 수 있는 가장 유용한 형태입니다. open finding은
  여전히 non-verdict입니다: 자기만의 verdict나 리워드, trajectory를
  만들지 않습니다.
- **시나리오 타이틀.** 아티팩트가 시나리오인 trajectory는 그 시나리오를
  사람이 읽는 문장으로 지목하므로, attestation이 무엇을 검증했는지
  말해줍니다.

```
platformer.session.04: resolved divergence — Idle and resize sessions stay error-free
    resolved divergence: Fixed and independently re-verified+attested at 505a668e...
    preceded on this artifact by:
      - open divergence: SHIP-BLOCKER src/render/PixiStage.tsx:28-32 assigns app before
        awaiting loadTextures ... Centralize teardown behind an idempotent owner.
      - open divergence: SHIP-BLOCKER src/App.tsx:45-46 calls sim.setPaused() inside a
        React updater ... Compute the next pause state outside the updater.
```

<Aside type="note">
  `records::Review`에는 정말로 산문이 없습니다 — `reviewer`, `pin`,
  `provenance_ref`뿐입니다. 그럼에도 attestation이 증거로 읽히는 이유는
  레코드에 필드가 생겼기 때문이 아니라, 검증 대상 시나리오와 그 시나리오에
  제기된 findings에 조인되기 때문입니다. 선행 findings는 `(at, line)`으로
  정렬·중복 제거·상한 적용되므로 이 텍스트는 결정적으로 유지됩니다.
</Aside>

전략 메모리는 **한 번 계산되고 끝나는 게 아니라 재빌드**됩니다: `canon
ingest artifacts`는 실행할 때마다 현재 trajectory 집합으로부터 증류된
전략을 다시 파생시킵니다(`rebuild_namespace`). 이 재파생은
결정적입니다 — 같은 아티팩트를 두 번 ingest하면 바이트 단위로 동일한
trajectory 콘텐츠가 파생되므로, 재빌드가 의존하는 중복 스킵이 그대로
동작하고 반복 실행이 내용을 흔들지 않습니다. 이 재빌드는
비파괴적(non-destructive)입니다 — 원시 trajectory 로우가 건드리지
않는 전략은 절대 삭제되지 않으므로, 재빌드가 수동으로 승급한 전략을
조용히 지우는 일은 없습니다. 독립된 `canon learn` 재빌드 명령은
없으며, `canon learn`의 유일한 서브커맨드는 `promote`입니다.

## trajectory에 보상 매기기

역할마다 자기만의 보상 함수가 있습니다 — 하나의 공식을 획일적으로
적용하지 않습니다. `dev`의 보상은 가중 합성입니다(`pr-merged 0.4 +
ci-pass 0.3 + no-rollback 0.3`, 롤백이나 CI 실패 시 `0.1`로 바닥,
사람 승인이 있으면 `1.0`으로 즉시 확정). 다른 빌트인 역할들은 실제
역할별 데이터가 쌓여 자기만의 공식을 정당화하기 전까지 잠정 기본값
(성공 `0.9` / 실패 `0.3` / 대기 `0.5`)을 공유합니다.

trajectory는 정확히 한 번 커버링 verdict가 매겨집니다 — `Pending`
상태를 벗어나는 것은 단방향 전이이며, 알 수 없는 trajectory id는
조용히 no-op하지 않고 즉시 실패합니다.

## 승급 자격과 활성화: `crn` vs `occurrence`

역할의 승급 자격 게이트는 컴파일 타임이 아니라 `canon.yaml`의
`learn:` 설정으로 선택합니다:

```yaml
learn:
  promotion:
    dev:
      mode: occurrence
      n_min: 8 # 선택 — 기본값 5
      window_days: 14 # 선택 — 기본값 30
    sim:
      mode: crn
  demotion:
    hard_delete: false # 선택 — 기본은 소프트 플래그
    strategies_root: .canon/strategies
```

새로 증류된 전략은 **기본적으로 quarantine**됩니다. 자격 게이트를
통과하는 것만으로는 충분하지 않습니다. 활성화에는 정직한 paired
evaluation과 `human`으로 선언된 approval이 필요하며, signature는
policy에 pin된 principal을 인증할 뿐 그 사람이 실제 인간인지 또는
policy 밖의 권한이 있는지 증명하지 않습니다.

- **`occurrence`** — 결정적 replay를 지원하지 않는 역할용(대부분의
  `dev`/`content`/`design`/`review`)입니다. trailing window 안에서 같은
  regime의 해소된 `Success` trajectory가 최소 `n_min`개이고
  `Failure`/`RolledBack` trajectory가 없어야 합니다. 모순 하나가
  카운트를 리셋하며 평균으로 희석되지 않습니다.
- **`crn`** — 결정적 simulator를 실행할 수 있는 역할용입니다. 비교하는
  설정들이 동일한 `crn:config=<label>` 및 `crn:panel=<index>` 패널을
  사용하는 paired common-random-number 자격 게이트입니다. 패널이
  부족하거나 설명되지 않는 noise가 크면 통과가 아닙니다.

명시적인 `promotion.<role>`이 없는 역할은 `occurrence`, `n_min: 5`,
`window_days: 30`으로 해석됩니다. 두 모드 모두 raw verdict row가
아니라 해소된 trajectory outcome을 읽으므로 먼저
`canon ingest artifacts`를 실행해야 합니다. 어느 모드도 품질 향상을
단독으로 증명하지 않습니다.

## 승급, 승인, 롤백

```bash
canon ingest artifacts
canon learn approve 01J...ULID --evaluation evaluation.json \
  --principal alice --repo .
# `request`는 `approve`의 정확한 alias입니다
canon learn promote 01J...ULID --repo . \
  --evaluation evaluation.json --approval approval.json
```

`PromotionEvaluation`은 외부의 정직한 evaluator adapter가 만드는 JSON
bundle입니다. quarantine 상태의 candidate, 전략 및 source-trajectory
digest, paired baseline/candidate result digest, 그리고 비어 있지 않은
corpus/evaluator/context/policy/model/tool provenance에 바인딩되어야
합니다. 유한한 `paired_metrics`에는 `pairs`, `uplift`, `regressions`가
반드시 있어야 하며, pairs는 result 개수와 같고 uplift는 양수,
regressions는 0이어야 합니다. 누락되었거나 unknown인 metric, 중복되거나
서로 공유되는 result digest, 잘못된 integrity digest, 통과가 아닌
decision은 거부됩니다. Canon은 evaluator를 실행하지 않으며, 이
repository에는 현재 **측정된 uplift 결과가 공개되어 있지 않습니다**.

`canon learn approve`/`request`는 서명하지 않은 payload를 출력합니다:
namespace `canon-learning-approval-v1`, subject `strategy:<id>`,
evaluation digest, RFC3339 `approved_at`, `payload_hex`입니다. private
key를 읽거나 `verified`를 설정하지 않습니다. 정확히 그 bytes를
decode한 뒤 외부에서
`ssh-keygen -Y sign -n canon-learning-approval-v1`으로 서명합니다.
Armored detached signature를 `PromotionApproval.signature`에 넣고
`signer_key`를 principal과 같게 하며 `approver_role: human`을 사용합니다.
서명되는 canonical JSON은 다음과 같습니다:

```json
{"namespace":"canon-learning-approval-v1","subject":"strategy:<id>","project":null,"artifact_sha":"<evaluation_digest>","run_id":null,"surface":[],"effects":[],"actor":"<principal>","timestamp":"<RFC3339 nanosecond timestamp>"}
```

rollback에서는 subject와 `artifact_sha`가
`strategy:<id>:rollback:<sha256(reason)>` 및 해당 reason digest를 사용합니다.
signature는 policy에 pin된 principal만 인증하며 실제 인간인지 또는
policy 밖의 권한이 있는지는 증명하지 않습니다. Repository policy의
verifier는 다음처럼 pin해야 합니다:

```yaml
approval:
  allowed_signers: .canon/allowed_signers
```

승급은 이 policy-pinned 파일과 `ssh-keygen -Y verify`로 signature를
검증합니다. `--evaluation`과 `--approval`은 함께 필요하며
`--signature <path>`로 armored signature를 approval JSON에 붙일 수
있습니다. 유효한 paired evidence와 이 signature가 없으면 quarantine
candidate는 계속 quarantine 상태입니다. `--force`는 없습니다.

일반적인 모순 trajectory는 이미 active인 전략을 demote합니다. 기본은
기존 git 파일에 `status: demoted`와 `reason:`을 소프트 플래그하며,
`demotion.hard_delete: true`이면 파일을 삭제합니다. 이것은 인증된
rollback이 아니며 rollback record도 만들지 않습니다. 명시적 rollback은
별도 작업입니다:

```bash
canon learn rollback 01J...ULID --reason "regression" --actor alice \
  --signature-file rollback.sig --approved-at 2026-10-02T12:00:00Z \
  --contradicting-trajectory-id 01J...TRAJECTORY --repo .
```

rollback signature는 `canon-learning-approval-v1` namespace에서
`strategy:<id>:rollback:<sha256(reason)>`, actor, timestamp에 바인딩됩니다.
actor는 policy-pinned `approval.allowed_signers`에 있어야 하며, 성공한
rollback은 provenance를 기록하고 lifecycle을 `rolled_back`로 설정합니다.

## 태스크 전에 retrieve하기

```bash
canon retrieve --role dev --regime dev/canon/join-spine/9c93d024b1a2
canon retrieve --role dev --regime dev/canon/join-spine/9c93d024b1a2 --k 3 --json
```

`--regime`은 전체 `regime_key` 문자열, `<role>/<repo>/<area>/<hash>`
입니다 — 쓰기 쪽이 만드는 것과 동일한 정규 직렬화입니다. 두 번째로
갈라질 수 있는 별도 파생 대신 하나의 시리얼라이저로 조립하세요:

```bash
canon regime-key --role dev --repo canon --area join-spine --hash abc123
```

`--role`은 `--regime`의 선두 세그먼트와 반드시 일치해야 합니다 —
불일치는 깔끔한 사용법 오류(exit `2`)입니다. role과 regime이 일치하고
나면, retrieval은 **fail-soft이며 항상 exit `0`**입니다 — 스토어
장애, 빈 스토어, 손상된 로우 모두 빈 가이던스 목록으로 저하될 뿐,
호출자가 처리해야 하는 nonzero exit로 드러나지 않습니다.

<Aside type="note">
  디스패치된 실행은 `canon retrieve`가 반환한 값을 라이브 스토어를
  가리키는 대신 자신의 매니페스트(`Run.injected_guidance`)에
  스냅샷으로 저장합니다 — 이후 원본 전략이 편집되거나 강등되어도 이미
  기록된 매니페스트를 소급해서 바꿀 수 없습니다. 실행을 리플레이하면
  새로 retrieve하지 않고 이 스냅샷을 읽습니다.
</Aside>
