## Verdicts on canon 0.19 proposals

### 1. PRD-shaped brief: intent → outcome → numbered user flow → detail → acceptance mapped to scenario IDs → questions/assumptions → out of scope

**Supported, with a narrower precedent than “PRD.”** Spec Kit's mandatory spec already combines prioritized user journeys, independent tests, Given/When/Then acceptance scenarios, edge cases, requirements, measurable outcomes, assumptions, and entity context. ([Spec Kit template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)) AI-DLC separately produces intent, scope, user flows, requirements, user stories/acceptance IDs, and out-of-scope/assumption sections; its stable IDs and `traceability.json` are a particularly strong precedent for mapping acceptance to downstream work. ([AI-DLC artifacts](https://github.com/awslabs/aidlc-workflows/blob/main/docs/guide/14-artifacts-reference.md), [requirements stage](https://github.com/awslabs/aidlc-workflows/blob/main/core/aidlc-common/stages/inception/requirements-analysis.md#step-10-generate-requirements), [user stories stage](https://github.com/awslabs/aidlc-workflows/blob/main/core/aidlc-common/stages/inception/user-stories.md#step-8-execute-plan--generate-stories-and-personas-via-the-mob)) **Copy:** stable IDs and machine-readable coverage/traceability from AI-DLC; independently testable journeys and measurable outcomes from Spec Kit. **Challenge:** neither source mandates canon's exact “see → do → becomes” prose shape or a single all-in-one PRD. Keep the brief terse and make the numbered flow an authoring convenience, not another unverified artifact.

### 2. Canon-owned feature changes drop `tasks.md`; retain it only for imported external plans

**Challenged / no direct precedent.** Spec Kit's core feature workflow explicitly generates and consumes `tasks.md`, and `/speckit.converge` appends missing tasks to it. ([Agentic SDD](https://github.github.io/spec-kit/reference/agentic-sdd.html#speckittasks), [tasks template](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md)) AI-DLC has no file named `tasks.md`, but it still has generated units, Bolts, per-unit code-generation checkboxes, and traceability; it does not eliminate actionable planning. ([AI-DLC artifacts](https://github.com/awslabs/aidlc-workflows/blob/main/docs/guide/14-artifacts-reference.md), [Code Generation](https://github.com/awslabs/aidlc-workflows/blob/main/core/aidlc-common/stages/construction/code-generation.md#step-2-part-1--planning)) OpenHands/SWE-agent are runtimes and do not establish a required task artifact either. The evidence does support **scenario-driven behavior coverage**, but not deleting an execution worklist: canon should either retain a generated task/checklist artifact or explicitly replace it with scenario-to-change implementation steps. **Copy:** Spec Kit's user-story grouping/parallel marker and AI-DLC's requirement/story/unit traceability, while ensuring the ship guard trusts evidence rather than checkbox state.

### 3. `canon change new --kind chore` for refactor/dependency/build/CI/infra with intent, category, invariants, checks; no new scenarios; existing suite + category checks + independent review

**Supported; strongest precedent is AI-DLC.** AI-DLC has first-class `refactor`, `infra`, `bugfix`, and `security-patch` profiles, with explicit phase skipping and behavior-preservation wording for refactor; this directly validates a separate path instead of pretending every maintenance change is a user feature. ([Workflow Profiles](https://github.com/awslabs/aidlc-workflows/blob/main/docs/guide/workflow-profiles.md)) OpenHands' QA process classifies refactor/config/bugfix/feature and produces evidence with commands, outputs, screenshots, and PASS/FAIL/PARTIAL; dependency-upgrade guidance requires tests and compatibility/regression checks. ([Automated QA](https://docs.openhands.dev/openhands/usage/use-cases/qa-changes.md#customization), [Dependency Upgrades](https://docs.openhands.dev/openhands/usage/use-cases/dependency-upgrades.md#testing-and-validation-examples)) Spec Kit's bug path is a useful separate diagnosis/fix/test precedent, though core docs do not prescribe chores. ([Bugfix guide](https://github.github.io/spec-kit/guides/bugfix.html)) **Copy:** AI-DLC's profile-specific route and human-authorized verification command/receipt; OpenHands' category-aware evidence report; Spec Kit's “original reproduction must be exercised” rule. **Constraint:** “no new scenarios” must be conditional on an explicit behavior-preserving invariant; any externally observable behavior change must use the feature/fix path. Existing suite rerun alone is evidence, not proof of complete coverage.

### 4. `canon.yaml language:` for briefs and human-facing reports

**No precedent found in these four.** The reviewed Spec Kit, AI-DLC, and SWE-agent sources do not document a generated-artifact language key; OpenHands mentions application language preferences but does not document a generated-report locale key. ([Spec Kit README](https://github.com/github/spec-kit/blob/main/README.md), [AI-DLC README](https://github.com/awslabs/aidlc-workflows/blob/main/README.md), [OpenHands application settings](https://docs.openhands.dev/openhands/usage/settings/application-settings.md), [SWE config](https://swe-agent.com/latest/reference/agent_config/)) This proposal is therefore **no precedent**, but it is not contradicted: a repo-level language setting is a reasonable canon-specific feature. Define scope carefully (human-facing prose only; IDs, commands, paths, code, and machine-readable fields remain stable), inheritance/override, and default; treat locale as policy/config rather than an LLM prompt convention.
