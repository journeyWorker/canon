# Who depends on canon's CLI names and JSON shapes (canon 0.25.0, e347991f)

Method: read every consumer; ran every one of the 70 leaf commands with `--json` in a scratch repo (installed `canon` 0.25.0, `json_contract.rs` argument logic); regex-counted option/command mentions per consumer. Counts are regex counts, so treat them as approximate sizes. The full tables are in `local://cli-audit-callers-options.tsv` and `local://cli-audit-callers-commands.tsv` (rows: option or command; columns: consumer). Scratch dir deleted; repo untouched (`git status` clean; I never ran `status`/`gate`/`query` inside it).

## 0. The headline facts

1. **There is no single envelope today.** Of 70 leaf commands (dashboard skipped), `--json` success shapes are:
   - `{data, meta:{command[,next,…]}}`: about 45 commands. `meta.command` is the command id.
   - **Own top-level fields, no `data`:** `status` (`statusVersion,canonVersion,policy,warnings,subjects,unowned,next,nextOmitted[,audits,waitingOn]`), `context` (`capabilityVersion,cel,enums,joinKeys,kinds,policy,review,vocab`), `query` (`count,kind,meta{returned,total,hasMore,nextCursor},records,since,violations`), `finding list` (`change_id,findings,meta`), `dispatch diff` (`counts,declared,edges,notes,observed`), `selftest` (`clean,suites`; failing adds `error`), `brief check` (`approved,brief,change,counts,findings,language,legacy,phase,waivers`; blockers add `error`).
   - **Bare or raw:** `retrieve --json` is a **bare JSON array** (`retrieve.rs:347-354`, "stays backward compatible"). `context-pack new|show` and `prompt show` print the raw record. `context-pack verify` prints `{id,verified}`. `adapter validate` prints a raw summary. `adapter authorize` prints a raw result, plus `error` when refused.
   - **Error:** `{error:{code,message,hint,retryable[,field,expected]}}`, with no `meta`, `command`, `ok` or `schemaVersion`. `gate check` and `format` are `{data, error, meta}` (data and error together, exit 1).
   - There is **no `ok`, no `schemaVersion`, and `command` lives in `meta.command`**. `statusVersion` and `capabilityVersion` are the only in-payload versions.
2. Option names, command names and JSON keys are also **typed back by canon itself**. `meta.next[].command` and `status.next[].command` are full command lines that agents execute; `hint` and `why` strings embed flags too. About 1978 option mentions sit in `crates/canon-cli/src` (help, hints, next steps). This is the largest self-consumer. A rename that misses one string means an agent is told to type a refused spelling.
3. **No test checks docs, skill text, `next` strings or hints against the clap tree.** I ran that check ad hoc and it is cheap:
   - Skill: 602 `canon <cmd> … --opt` mentions, 1 off-command (`query --scenario-id`).
   - Website en: 410 checked, 0 off.
   - `init.rs` AGENTS block: 27 checked, 0 off.
   - README: 10 off, all intentional "removed spelling" upgrade notes.
   - So today the docs are in sync, but only by discipline. A doc-lint test over `canon schema` is the missing enforcement and would also be the migration safety net.
4. **Silent-break hazard:** `canon/skills/scripts/canon-retrieve-pre-dispatch.sh:116-125` parses `retrieve --json` as a bare array (`jq 'length'`, `map(.title/.content)`), with `2>/dev/null || true` and `exit 0` on empty. Wrapping the array in `{data,meta}` fails this way:
   - `jq length` returns 2, so the script continues.
   - `map("- " + .title…)` errors with `cannot index [...] with "title"`.
   - The error is swallowed, so no guidance is injected and nothing fails.
   - I verified this with jq. The script is copied into users' repos by `canon skills install`, so stale copies outlive the binary upgrade.
5. **Skill text already drifts on the shape:** `SKILL.src.md:173` says "`canon status --json`, then follow `meta.next`", but `status` has top-level `next` and no `meta`. `role-orchestrator.md:12` correctly uses `--fields next,waitingOn`. A unified envelope removes this trap; the text needs one rewrite either way.

**(a) Unified envelope `{command, schemaVersion, ok, data, meta}`.** Key point: `data` and `meta` are already the majority shape, so adding top-level `command/schemaVersion/ok` to enveloped commands is additive. The expensive part is wrapping the stragglers.

## 3. How the 0.21 and 0.24 deprecations were done

**0.21 (`fb66be6b`, `ad13b52d`; removed in 0.22 `c00b31b9`):** a 69-line `deprecation.rs` with a `DEPRECATED` table of `{old,new}` command paths. Each old command stayed as a hidden clap subcommand routed to the canonical handler and called `warn_path(old)`. That printed `canon <old>: deprecated — use canon <new>` on stderr and added `meta.deprecated:{use,removedIn}` through `json_out::envelope`. `canon schema --all` listed them. A drift test kept the table and the clap tree in step. The release after deleted the table, the hidden variants, `meta.deprecated` and the schema field. Removed forms became plain clap usage errors; `usage-removed-deprecated-forms` was the conformance case.

**0.24 (`ff700f70`, 319-line `deprecation.rs`, 35 files; removed 0.25 `7ce0d7cb`):**
- `FLAGS: [FlagRename{commands, old, new}]` plus `KIND_VALUES`. `apply()` registered `old` as a hidden clap alias (`mut_arg(.alias)`); the `*_record` kind values stayed accepted.
- `scan(root, argv)` re-read argv against the clap tree to see which deprecated spellings were *used*. It skipped option values and anything after `--`, and handled `--old=value`.
- `warn()` printed one stderr line per spelling. `meta()` fed `meta.deprecated:[{used,use,removedIn}]` into `json_out::envelope`.
- `tag_document()` added `meta.deprecated` to non-envelope documents (`brief check`, `query`) by creating a `meta` key.
- `canon schema` listed `deprecatedAliases`/`deprecatedValues`; help hid them. `warn_input_name` covered `scenario new --from` batch keys.
- Same commit (checklist reused in 0.25): migrate every caller in the tree (skill, website, AGENTS block, hints, `next`), `tests/one_name.rs` (checker as a pure function over `(path, flags, kind values)` so it can be fed a synthetic split), conformance case `usage-deprecated-spellings`, `trace_check.py` naming/deprecated counters (`27ae2b01`), and README "Upgrading".
- **0.25 removal (`removed.rs`, 215 lines):** the aliases and table are gone. `removed::find(root, argv)` runs only after clap refuses a line and re-reads argv with the same skip rules. It returns a usage error `"<old> was removed in 0.25.0"` with hint `"<old> was renamed <new> in 0.24.0; use <new>"`, plus `field`. The `FLAGS` table survives only to write that hint (`main.rs:1786`, `scaffold.rs:519`). Conformance: `usage-removed-spellings`.

**Limits of the mechanism:**
- It is **input-driven**. `scan()` knows a caller typed `--change` and can warn that caller. It has no signal about which keys a caller *reads* from output, so output-shape deprecation cannot be targeted. Any `meta.deprecated` note on a shape change would fire for every `--json` caller, including ones already reading the new shape.
- It was **never used for a JSON shape change**. 0.20 S3 (`14adc0b0`) and 0.21 t5 (`561f480e`) changed shapes (dispatch, learn, purge, export, ingest from raw → `{data,meta}`; status and others gained `meta.next`) as **hard breaks** announced in README plus tests, with no dual emission.
- `meta.deprecated` is already **gone** (0.22, 0.25). Reusing it means re-adding `json_out`'s hook; the ACTIVE registry design (a `Mutex<Vec<Used>>` read by `envelope()`) is reusable as is.
- Staleness of installed consumers is detectable: `canon skills check` reports `stale`/outdated lock (the lock records `canon_version`, `skills.rs:1693`), and `init` reports the AGENTS block "already current". Neither detects a stale *hook script's parsing*.

## 4. Can deprecation cover JSON shape changes? Least-bad option

Rejected:
- **Env var or flag opt-in** (for example `CANON_JSON=2`): the cli-interface-design skill forbids an environment variable changing output, and a per-flag opt-in is a spelling every command and every skill line must carry. Harnesses will not set it. Two shapes under one command line is the exact "same command line, different output" defect.
- **Dual keys for the own-field reports** (legacy top-level keys plus `data`): doubles the payload. `context --json` is 21,907 bytes in a near-empty repo (about 44 KB doubled); `status` grows with subjects. For agents, token cost is the metric, and compact JSON is the skill's stated preference.
- **A `meta.deprecated` banner on output shape**: fires for every caller (see limits above).

Least-bad, a two-step plan with consumer-first tolerance, and sized to what really breaks:
1. **Release N (additive only).**
   - Add `command`, `schemaVersion`, `ok` top-level to every enveloped command and error, **keeping `meta.command`** (documented as mirrored, removed in N+1).
   - Fix the retrieve hook script to accept both (`(.data // .)`) and ship it **before** retrieve's shape changes, because installed copies update only on `canon skills install`.
   - Add the `schemaVersion` discriminator to `schema` so a reader can switch on it. Existing `statusVersion` and `capabilityVersion` are the precedent for in-payload versions.
   - Add the doc-lint test (skill/website/README/AGENTS block/`next`/hints against `canon schema`) before any rename.
2. **For the 7 own-field reports and bare outputs**, make the shape decision once and take it in **one hard cut with the same discipline as 0.21 t5**, with no dual emission:
   - Wrap them in `data`, because `{data,meta}` already covers about 45 commands (dashboard client, 102 test `["data"]` reads, website docs, skill) and flattening everything to the skill's Lute-style flat shape would break far more consumers. `query`'s `records`/`meta` page, `status`'s `next`, and `context`'s keys move under `data`.
   - Release notes list old key → new key per command (README "Upgrading", as in 0.25), and conformance re-blesses with a reviewed diff.
   - Give the three consumers outside the repo's control a one-release tolerant read first (N): the retrieve hook, `trace_check` (already independent), and the skill text.
3. **Renamed options** reuse the 0.24 → 0.25 two-step exactly: N adds `deprecation::apply/scan/warn` (alias plus stderr line plus `meta.deprecated` plus `schema deprecatedAliases`), N+1 moves to `removed.rs`. That mechanism fits (input-detected, one minor). Reuse the 0.24 commit checklist. `removed.rs` hints must keep the sentence `was renamed … in <rel>; use …` so `trace_check.RENAMED` and agents keep recognising it. **Do not combine** a shape cut and a rename in the same release for the same command: conformance diffs become unreviewable, and a consumer cannot tell which change broke it.

If a full dual-shape window is demanded anyway, the only affordable place is the 4 small reports (`finding list`, `dispatch diff`, `context-pack verify`, `selftest`: all under 1 KB); do not do it for `status`, `context` and `query`.
