- **Branch:** `steelhead` (integration). Slices on their own branches and worktrees (`feat/0.25-brief-scope`, `feat/0.25-finding-reason`, `feat/0.25-skills-prune`, `feat/0.25-dashboard`, `feat/0.25-names`, then `feat/0.25-skill-text`), merged in order. One PR to `main`.
- **Base:** `main` at 68e075e0 (0.24.1 plus the agent-skill-pack research, #101).
- **Version:** 0.25.0 (minor).
- **Status:** IN PROGRESS.
- **Issues:** #96, #102, #103, #98, #99, #100.

## Principle

The one step only a human takes, approving a brief, should cost the human
one page, and should hold back only the work it approves. Planning the next
change must not freeze the evidence of behavior that is already approved, and
the dashboard that shows the human what is pending must run wherever canon
runs.

## Why (measured)

|---|---|

The brief rule reads the subject's newest adopted change for every scenario (`brief::attested_briefs` → `brief_of(changes.last())`); nothing warns at adoption and nothing undoes it. |

| A rejected finding records no why (#98) | `Finding` stores the disposition but no rationale; a rejected or deferred blocker leaves nothing to audit. |

## Decisions

- **D1: brief approval is scoped to the scenarios a change adds or modifies (#96).**
  - A change adds or modifies the scenarios tagged `@flow:<change>.<F-id>` (written by `scenario new --flow`). Evidence for a scenario needs the approval of each change its `@flow:` tags name.
  - A scenario with no `@flow:` tag answers to the subject's newest adopted change whose brief was approved at some point (carries an `Approved:` line, current or edited since). When no adopted change was ever approved, a scenario that already has evidence needs no brief (behavior evidenced before any approved scope, e.g. a subject older than briefs adopting its first change), and one with none answers to the newest adopted change, as before. Evidence for a task needs the approval of the task's own change.
  - Adopting a change whose brief is not approved into a `building`, `verifying` or `shipped` subject (`change new --subject-id`, `subject adopt`) prints a warning on stderr and in JSON `meta.warnings`: which scenarios now wait for the approval, that the subject cannot ship until then, and the command that undoes it.
  - `canon subject unadopt <change> --subject-id <id>` removes the link on both sides; refused for a change whose brief carries an `Approved:` line (it is the subject's approved scope). The change and its brief stay; it can be adopted elsewhere, for example into a `proposed` holding subject. One name per concept (0.24 D1): `--subject-id`, positional change as in `subject adopt`.
- **D2: the dashboard ships in the binary (#102).**
  - The release build embeds the built app, gzip-compressed, through a `build.rs` that reads `CANON_DASHBOARD_DIST` at build time; the release workflows build the app once and hand it to each platform row. A build without it embeds nothing.
  - App resolution: `packages/dashboard/dist` under the repo when its `package.json` is canon's dashboard (`@canon-dev/dashboard`; development override), else the embedded app, else `DASHBOARD_NOT_BUILT` with a hint that names the release install and the development build.
  - Served gzip-encoded when the browser accepts it, decompressed otherwise. The embedded app does not carry the demo fixture snapshot; a repo whose snapshot could not be generated (no `duckdb` on PATH, for example) still gets the server and the briefs page, and the panels page says why there is no snapshot and how to get one. It never shows demo data.
  - Failures get their own codes and hints: `DASHBOARD_PORT_IN_USE` (pass `--port`), `DASHBOARD_NOT_BUILT`, `DASHBOARD_CONFIG_INVALID`; `DASHBOARD_FAILED` stays for the rest with a hint that does not guess the port.
- **D3: approve briefs from the dashboard (#103).**
  - A briefs page lists the changes whose brief awaits the human (the set `canon status` asks the human about): rendered intent, outcome, flow steps, acceptance, questions and assumptions; the `brief check` blockers and advisories; and an approve form (name and note, typed, nothing prefilled).
  - Approving records exactly what `canon brief approve --change-id <id> --by <name> --note <text>` records: the CLI and the server call one function. It is bound to the bytes shown: the request carries the sha256 of the brief file the page rendered, and the server refuses (`BRIEF_CHANGED_SINCE_PAGE_LOAD`) when the file differs, and while the brief has blockers (`BRIEF_HAS_BLOCKERS`).
  - The server binds 127.0.0.1 only. The write endpoint accepts only `POST` with `Content-Type: application/json`, a `Host` of the bound address, and an `Origin` equal to the page's own; anything else is refused before the brief is read.
- **D4: finding close records why (#98).** Optional `reason` on `Finding` (absent on old records, which read unchanged). `finding close --reason <text>`: required for `rejected` and `deferred` (`FINDING_REASON_REQUIRED`), optional for `fixed`. The disposition transition carries the reason, so promote accepts the close. Shown in `finding list` and JSON.
- **D5: skills install prunes what a bundle no longer ships (#99).** Install deletes projected files the previous lock lists, the new bundle does not, and whose bytes still match the lock hash; a modified one is kept and reported. `skills check` and `skills doctor` name each orphan with a hint. An unselected provider is untouched.
- **D6: the deprecated spellings are removed (0.24 D2).** `--change`, `--project`, `--subject`, `--actor`, `--run` and `--kind <kind>_record` become usage errors whose hint names the new spelling; `meta.deprecated` and `deprecatedAliases` go.
- **D7: skill text (#100, after D5).** Bundle A of the adoption brief, folded into the existing references; plus the 0.25 surfaces (`subject unadopt`, `finding close --reason`, the dashboard briefs page). One reference per concern, no reference deleted without D5.
- **D8: acceptance.**
  - (a) Workspace tests pass; conformance re-blessed where outputs change, plus cases for each new refusal.
  - (b) Canon's own repo: new scenarios evidenced by an implementer unit and reviewed by an independent reviewer session (its own process and session id); `canon gate check` clean.
  - (c) Dogfood eval 13 on a consumer game repo with pending briefs, running the 0.25 build: `canon dashboard` serves from that repo with no `packages/dashboard`; briefs approved from the page produce the same records as `canon brief approve`; adopting a draft change into a live subject leaves evidence for its existing scenarios recordable; screenshots of the dashboard pages.
