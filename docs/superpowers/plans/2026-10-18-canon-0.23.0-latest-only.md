## Principle

Only the current decision needs to be in the working set. A record that has been superseded is history: it moves to an archive, is never dragged into new records, and is read only when history is asked for. Rules that exist only to patch an earlier rule go; one freshness rule replaces several.

## Why (measured on dogfood eval 10's repo and on canon)

| Finding | Measurement |
|---|---|
| Evidence carry-forward (0.21) re-lists every earlier attachment in each new record | records grew 0.7 KB → 5.4 KB; avg 20.6 attachments, max 33; stale reports from other changes attached; agents could not find how to drop them (#80) |
| Superseded versions stay in the working set and every read scans them before folding | evidence_record: 541 of 641 files superseded (84%); subject 96%; finding 75%. `GitTier::read` scans every file, fold comes after |
| Artifact bytes are committed to git | content-addressed (no duplicate bytes), but every new screenshot is in history forever |
| A write computes the whole state twice | guards load the corpus, then `meta.next` reruns the status engine; `gate check` 3.4 s on eval 10's repo |
| Re-recording a suite stales every review | eval 10 re-reviewed 82 unchanged scenarios after a feature and 100 after a behavior-preserving chore; reviews pin evidence record ids, not what the evidence says |
| Overlapping freshness rules | review pins, 0.22 re-verification triggers, accepted-divergence pins each implement pinning/staleness separately |
| Staging has three shapes; divergence bypasses it | default `write: promote: auto` makes staging a pass-through for most writes |
| Legacy compatibility paths | pre-0.15 reviews use a second freshness algorithm (348 such reviews measured in 0.16) |
| Derived index work | `brief check` reparses every .feature instead of reading the scenario index |

## Decisions

- **D1: no carry-forward (#80).** An evidence record binds exactly the files its own write names. The dropped-attachment guard and `--drop-attachment`/`--drop-reason` are removed. History keeps old records (D2), so nothing is hidden; a new record is re-reviewed (D5) on its own files.
- **D2: latest-only working set with an archive.**
  - Every append to a natural-keyed kind moves the key's previous versions from `.canon/ledger/kind=<k>/` to the archive (default `.canon/archive/kind=<k>/`, git-tracked; or a configured tier). The ledger directory then holds one file per key.
  - Default reads (status, gate, guards, query) read the ledger only. `canon query --history` (and any rule that truly needs history) reads the archive explicitly. Inventory every rule that reads non-latest versions today (finding first-record/close times, subject transitions and reopen, approval history, accepted divergence by time, run_seq folds, learn) and either carry the needed field on the latest record or read the archive explicitly; no rule silently loses data.
  - `canon ledger compact [--dry-run]` moves existing superseded versions to the archive once (idempotent); `canon migrate` runs it.
  - The archive is append-only and never read by the gate unless a rule names it.
- **D3: artifact bytes off git.**
  - `canon.yaml` `artifacts:` selects the artifact store backend: `local` (today's `.canon/artifacts/sha256`, git-tracked, the default so a repo works with no credentials) or an object store (`r2`/`s3`, reusing the tier backends and credentials, with its own bucket or prefix, e.g. `prefix: artifacts/`). Records keep only digests; the gate verifies a digest against the configured store.
  - `canon artifacts migrate --to <backend>` copies every blob to the object store, verifies digests, and removes the local copies (`.gitignore` gains `.canon/artifacts/` when the backend is not local).
  - Artifacts referenced only by archived records stay retrievable from the store; nothing is deleted by compaction.
- **D4: compute once.** One process loads the gate context once; a write's guard result and its `meta.next` come from the same loaded state (no second status run). `brief check` reads flow coverage from the scenario index. Read commands do not refresh the index unless it is stale (keep the existing staleness check, measure it). Target: halve `gate check` and write latency on eval 10's repo (measure before/after).
- **D5: reviews bind what the evidence says.** A review pins the scenario digest and, per scenario, the latest evidence's verdict and the identity of its bound checks (report format + matched case names, or the artifact digests for artifact-only evidence) instead of the evidence record id. A new evidence record with the same verdict from the same checks keeps the review current; a different verdict, different checks, or a changed scenario stales it.
  - Chore (0.22 D2): re-recording the suite after a chore no longer stales unchanged scenarios' reviews; instead the chore change itself needs one change-level review (`canon review add --change <slug> …`, reviewer signs the chore's invariants and checks against the diff) before `--to shipped`.
  - Fixed blocker: still needs evidence newer than the close; scenario reviews stay current when verdicts and checks are unchanged; the finding close is the reviewer's step.
- **D6: one freshness rule; simpler staging; no legacy paths.**
  - Review pins, accepted divergence and re-verification share one "pinned to what, stale when" module in canon-gate.
  - Staging: one shape for every staged kind (evidence, finding, divergence), no bypass; keep `--no-promote` for manual promotion.
  - `canon migrate` pins pre-0.15 reviews (current ones get today's pins; stale ones stay stale) and the legacy freshness algorithm is deleted. Other compat paths left only for unmigrated repos are removed with a migrate step.
- **D7: acceptance.**
  - (a) Contract tests for each decision; existing gate/guard outcomes unchanged except where a decision changes them (listed in the README migration).
  - (b) `canon migrate` on a copy of eval 10's repo: ledger keeps one file per key, archive holds the rest, `gate check` result identical before/after, sizes and timings before/after recorded.
  - (c) Dogfood eval 11 on omp, orchestrated roles: a feature then a chore. Pass: no carried attachments; the chore needs one change-level review instead of re-reviewing every scenario; calls per scenario and wall time compared with eval 10.
