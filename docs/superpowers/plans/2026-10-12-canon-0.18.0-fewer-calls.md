## Decisions

- **D1: one report, many scenarios (#27, #33, #24③, #26).**
  - `evidence add --report <fmt:path> --all-scenarios` writes one record per indexed scenario that has a case in the report, using the existing `owns_scenario` rule. Each record's verdict comes from its own cases. A scenario that is not indexed is named and skipped. One refusal (for example a failed case under a faithful claim) refuses the whole batch, and nothing is written.
  - `review add` takes `--scenario-id` repeated, or `--scenario-ids-from <file|->`, with one reviewer, pin and set of artifacts. It writes one review per scenario, all-or-nothing. This is the batch re-pin.
  - `--task --report` with no scenario id binds every case in the report. A faithful verdict needs all of them to pass.
  - `--report swift-testing:<path>` parses the Swift Testing event stream (JSON lines from `swift test --experimental-event-stream-output`). It reads `displayName` for the scenario id and the test result for the outcome. `ReportFormat` gains a variant (a generated schema regen, not a new record kind).
- **D2: the write that breaks a pin says so (#24①).** When `evidence add` (single or batch) supersedes evidence that a current pinned review saw, it prints one line per review now stale: the reviewer, the scenario, and the exact `canon review add … --pin <sha>` re-pin command. The decision is the gate's own `review_gap`.
- **D3: reopening a shipped subject (#31).**
  - `canon subject status <id> verifying` from `shipped` is allowed. Inside an approved scope it needs no human: the subject's newest change is approved and unchanged. It records who and why (`--reason`, required).
  - Shipping again runs every guard again.
  - `status` flags a `shipped` subject whose gate is red, naming the reopen command.
  - The skill's follow-up step uses it: reopen, add tasks to the approved change, scenario, evidence, review, ship.
- **D4: a change belongs to several subjects (#28).**
  - `Change.subject_id: Option<SubjectId>` becomes `subject_ids: Vec<SubjectId>`. This is a canon-model change: regenerate JOIN_SPINE and the schemas, and update the state-model docs.
  - Deserialization reads the old field into a one-element list. The ledger is append-only, so old records must still read.
  - A second `adopt` adds the subject and says so. Readers (the gate, status, report marts, query) join from both sides the same way.
  - Per-task subject is out of scope.
- **D5: gate correctness (#32, #36).**
  - Fabrication markers match whole words only: never inside a path, a file name or a longer word. The refusal reads "refused" and exits like the other evidence refusals.
  - Review attachments are re-checked by the evidence rule. Only current (in-effect) reviews are checked, and a missing blob whose working-tree file still matches is a vault advisory, not a violation.
- **D6: consumer-repo hygiene and reads (#25, #29, #34, #37).**
  - `skills install` and `doctor` print the glob list of canon-owned paths to exclude from formatters and linters.
  - `doctor` tells "a formatter rewrote this" (same content after whitespace or format normalization) apart from real drift, and names the ignore entry to add.
  - `canon report` reads the sqlite hot tier, which is local and needs no credential, so task columns fill under init's default routing.
  - `canon finding list --change-id <id> [--open] [--json]` prints round, seq, severity, disposition and summary.
  - Skill wording: a review runs in a session that can run the checks it signs off. A bound report is kept in `.canon/artifacts`, so the working-tree copy may be gitignored.
- **D7: the example's real evidence (#30).** Give `examples/platformer` vitest tests over the game state, one per scenario (named with the id). Bind them with `--report junit:… --all-scenarios` (the first real use of D1), and have every platformer scenario re-reviewed by an independent reviewer. This clears the 5 stale and 8 undecidable legacy platformer reviews in canon's advisory.
- **D8: acceptance.**
  - (a) Eval 5 on omp, same prompt plus a turn-3 follow-up in the same repo. The follow-up reopens the shipped subject (D3), and the batch attestation (D1) is used. Pass when: one human stop before shipped; the follow-up reaches re-ship without a human; there are fewer `evidence add`/`review add` calls than scenarios; gate clean.
  - (b) A Swift Testing event stream bound with `--all-scenarios`. Use Lifeshot's real tests on a /tmp copy if Swift builds there, otherwise a checked-in fixture captured from `swift test` on a tiny package.
  - (c) canon's own advisory: platformer legacy reviews no longer stale or undecidable (D7).
