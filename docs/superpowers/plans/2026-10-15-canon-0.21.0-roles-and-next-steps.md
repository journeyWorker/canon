# Canon 0.21.0: one grammar, role-aware guidance, next steps after writes

- **Branch:** `feat/0.21` (worktree `~/external/canon/0.21`). Each slice gets its own worktree under `~/external/canon/` off `feat/0.21`, merged back in order. One PR to `main`.
- **Base:** `main` after 0.20.0 (#59).
- **Version:** 0.21.0 (minor).
- **Status:** RELEASED (PR to main).
- **Issue:** #60.

## Why

0.20 made every command machine-readable but left three gaps an agent pays for in calls and context:

- **Names.** `canon schema` lists 64 commands. Most follow `<resource> <verb>`, but four verbs are synonyms of the shared ones: `context-pack create` (new), `prompt register`, `divergence stage`, `demo attest` (add). `subject status <id> <state>` takes two positionals of different meaning. The report's checklist asks for one grammar with no synonyms (`deep-research-report.md:998-999`).
- **Next steps.** `canon status` returns `next[]` (0.16), bare `canon brief` recommends a pass (0.19), and refusals carry `hint` (0.20). Successful writes mostly return nothing about what comes next (`change new`, `brief approve`, `scenario new`, `review add`, `finding add|close`, `subject status`, `gate check`, `gate promote`), so the agent calls `status` again: eval 8 made 4 `status` and 5 `gate` calls for one feature. Impeccable leads with 2–3 next commands derived from project state and never runs them itself.
- **Roles.** One skill and one command list serve every agent. A reviewer loads the PRD-writing passes it never uses. A role-specific view needs only a declared role: canon cannot detect a role, just as it cannot detect a session id (#14).
- **Smaller gaps** from the 0.20 audit: `--fields` only on `query` and `finding list`; errors lack `field`/`expected`; `schema` has no examples; retrying a write was not checked for duplicates; a few undocumented exit-code exceptions; `learn promote`'s demotion failure has no code; `schema` marks `subject status` and `format` as `read`.

## Decisions

- **D1: one verb grammar, with deprecation.**
  - Shared verbs: `new` creates a resource, `add` appends a ledger record, `list` lists, `show` shows one. Domain verbs with their own meaning stay (`approve`, `promote`, `resolve`, `defer`, `close`, `check`, `sync`, `install`, `verify`, `validate`, `authorize`, `begin`, `end`, `adopt`, `vault`, `age`, `rollback`).
  - Renames: `context-pack create` → `context-pack new`, `prompt register` → `prompt add`, `divergence stage` → `divergence add`, `demo attest` → `demo add`. `subject status <id> <state>` → `subject status <id> --to <state>` (`subject status <id>` alone shows the subject).
  - The old forms are **deprecated, not aliased**. For one release they still run, print `canon <old>: deprecated — use canon <new>` on stderr, and in JSON mode add `meta.deprecated: { "use": "<new>", "removedIn": "0.22.0" }`. `canon schema` lists them with `deprecated: { use, removedIn }` and hides them from the bare listing unless `--all`. 0.22 removes them.
  - `schema` effect fixes: `subject status` is `write` (with `--to`), `format` is `write` (without `--check`).
- **D2: `meta.next` after successful writes.**
  - Every successful write command returns `meta.next: [{command, why, actor}]` in JSON mode, the same shape as `status`'s `next[]`, computed by the same engine from the state after the write (for the subject or change the write touched). Human mode ends with one `next: <command> — <why>` line (and `+N more`).
  - Never executed by canon. `actor: human` marks the steps only a human takes (brief approval).
  - Read commands do not carry it; `status` and bare `brief` keep their own.
- **D3: roles.**
  - Roles: `planner`, `implementer`, `reviewer`, `orchestrator`. Declared with `CANON_ROLE` or the global `--as <role>` (flag wins). An unknown role is `UNKNOWN_ROLE`.
  - Unset: today's behavior everywhere.
  - Set: `status` and `meta.next` keep that role's steps and summarize the rest as counts per role (`waiting on reviewer: 2`). `schema` gives every command `roles: [...]`; bare `schema` lists the role's commands (`--all` lists all). `--role` on `evidence add` / `review add` defaults to the declared role when it is `implementer` / `reviewer`.
  - Guidance, not enforcement: the role is self-declared. Session separation between implementer and reviewer stays ledger-based.
  - Step ownership: planner — `subject new`, brief writing, `brief check`, `change new`; implementer — `feature new`, `scenario new` (single and `--from`), code, `evidence add`, `gate promote`; reviewer — `review add`, `finding add|close`, `brief check` (read); orchestrator — `status`, dispatch, `subject status` transitions, spawning roles; human — brief approval.
- **D4: skill by role.** `SKILL.src.md` becomes a shared core (the loop, `status`/`schema`/`meta.next`, how to know your role) plus `reference/role-{planner,implementer,reviewer,orchestrator}.md`. The core tells an agent with a declared role to load only its role reference. The brief passes (`brief-*.md`) are linked from the planner reference only. The reviewer reference reads a PRD with `canon brief check` and checks scenarios against its flow. The orchestrator reference says how to spawn each role with `CANON_ROLE` set and a separate session for review (#39). An agent with no role (one agent doing everything) loads the core and follows `status`.
- **D5: smaller contract items.**
  - `--fields` on `status`, `export`, `divergence status`, `context` (same projection rules and `UNKNOWN_FIELD`).
  - `CliError` gains optional `field` and `expected`; usage errors and input validation set them (`--to` with a bad state: `field: "--to"`, `expected: ["specced", …]`).
  - `schema <command>` returns `example`: one minimal invocation that the contract test runs.
  - Retry safety: repeating `evidence add` / `review add` with identical input returns the existing record (`meta.unchanged: true`) instead of writing a duplicate, if today it duplicates (verify first).
  - Exit-code exceptions are either justified in `schema`'s exit meanings or aligned; `learn promote`'s demotion failure gets a code.
- **D6: acceptance.**
  - (a) Contract tests: every write returns `meta.next` that `status` agrees with; deprecated forms run with the warning and `meta.deprecated`; every `schema` example runs; `CANON_ROLE=reviewer canon status --json` shows only reviewer steps plus counts.
  - (b) Dogfood eval 9 on omp: an orchestrator agent spawns a planner, an implementer and a reviewer subagent with `CANON_ROLE` set. Pass: same loop as eval 8; each subagent loads only its role reference (trace); canon calls per new scenario at or below eval 8's 2.1; no `status` call made only to find the next step after a write.
