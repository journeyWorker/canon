# Canon 0.12.0 — conformance corpus and release packet

- **Branch:** `feat/0.12-conformance` (worktree `../canon-0.12`), merged by PR.
- **Base:** `main` at `601f5c85` (0.11.0).
- **Version:** 0.12.0 (minor). The conformance corpus adds no CLI or record
  shape change. The 2026-10-09 amendment below adds the opt-in review
  requirement for issue #2 and the website redesign to the same release.
- **Status:** READY FOR MERGE.

## Why

Three defects in the last week reached users through canon's *external*
contracts while every unit test passed:

| Release | Defect | Contract it broke | Found by |
|---|---|---|---|
| 0.8.0–0.9.0 | npm launcher exited 0 on every refusal | CLI exit codes | Kino |
| 0.8.0 | `Subject.scenario_ids` never written; ship gate passed on an empty set | record ↔ report ↔ gate join | Kino |
| 0.8.0–0.10.0 | docs said approvals verify against `CANON_ACTOR` | documented behavior | self, by accident |

Lute (the sibling toolchain) prevents this class with a frozen conformance
corpus that external consumers replay byte-for-byte
(`lute/conformance/README.md`, `lute/crates/lute-cli/tests/conformance.rs`)
and with a release packet: decision log, sliced plan, review gate per
slice, final review (`lute/docs/superpowers/plans/2026-10-07-lute-0.37.0-surface.md`).
0.12.0 adopts both for canon.

## Decisions

- **D1 — What "conformance" means for canon.** A case is a frozen
  repository fixture plus an ordered list of `canon` invocations, each
  with its expected exit code, stdout, and stderr. Consumers of canon
  (scripts, CI, hooks, other repos such as Kino) rely on exactly these:
  exit codes, the gate's violation lines, refusal messages, and JSON
  output. The corpus pins them.
- **D2 — Byte-exact after normalization only.** Outputs carry values that
  are legitimately non-deterministic: the temp repo path, ULIDs, RFC3339
  timestamps, and digests of time-stamped records. The runner replaces
  those with stable placeholders (`<repo>`, `<ulid>`, `<ts>`,
  `<digest12>`) by a fixed, documented, ordered list of rules. No other
  normalization: anything a consumer could parse is compared exactly.
- **D3 — The runner is a cargo integration test** in `canon-cli`, so
  `cargo test --workspace` (already in CI on push to main and on PRs)
  enforces it. No new workflow.
- **D4 — Discovery, never a list.** The runner discovers every
  `conformance/cases/*/case.yaml`. Zero discovered cases is a failure,
  so a moved directory cannot silently pass.
- **D5 — One regeneration entry point.** `conformance/regenerate.sh`
  re-blesses expected outputs (`CANON_CONFORMANCE_BLESS=1`). A bless that
  changes an existing expectation is a contract change: it must be named
  in the release notes. Hand-built refusal fixtures (malformed records,
  broken policy) are never regenerated from code.
- **D6 — Live stamp invariant.** One case pins `canon --version` to the
  workspace version, so a release bump without a re-bless fails — the
  corpus is always stamped with the version it describes.
- **D7 — Scope.** The first corpus covers the contracts named in "Why"
  plus the gates added in 0.9–0.11. It is not a replacement for unit
  tests and does not exercise network tiers (Postgres/R2).

## Case format

```
conformance/
  README.md            # contract, normalization rules, how to add/bless
  regenerate.sh        # the only bless entry point
  cases/<name>/
    case.yaml          # description, env, steps
    repo/              # the fixture repository, copied to a temp dir
    expected/<n>.out   # normalized stdout of step n
    expected/<n>.err   # normalized stderr of step n
```

`case.yaml`:

```yaml
description: one sentence naming the contract this case pins
env: { CANON_ACTOR: canon }       # merged over a fixed base env
steps:
  - args: [gate, check]
    exit: 1
```

The runner copies `repo/` to a fresh temp dir, `git init`s it (canon
reads Git), runs each step's `args` against the built `canon` binary with
the case env and a cleared, fixed base env (no inherited `CANON_*`), and
compares exit code and normalized output. On mismatch it prints a unified
diff and the bless command.

## Review gate

After each slice, before the next: a reviewer reads the diff and every
new expected output, and checks — (1) the case pins a contract a
consumer actually relies on, not incidental wording; (2) the expected
output was derived from the real binary, never hand-typed to match a
guess; (3) normalization did not hide a value a consumer parses.
Findings are fixed in the same slice.

## Amendment (2026-10-09) — issue #2 and the website

The user asked for the canon operator's issue
[#2](https://github.com/journeyWorker/canon/issues/2) and the website
redesign to ship in 0.12.0 too.

Issue #2: in a consumer repo, subjects reached `verifying`/`shipped` with
only implementer-attested `test-run` evidence and no review. `gate check`
(even `--release`) stayed clean and every status transition succeeded.
`trust_required: {review: agent}` cannot express the requirement: it keys on
an EvidenceRecord's `class`, and `TrustLadderCheck` only demands a Review for
records whose lifecycle tag is `reviewed`. Nothing enumerates scenarios
lacking review, and gate checks never read Finding.

### Decisions

- **R1 — Opt-in policy, own scope.** A new
  `spec_coverage.require_review` section:
  `{ scope: [verifying, shipped], distinct_actor: true, block_on_findings: true }`.
  Every field is optional, and the defaults are the ones shown. When the
  section is absent, nothing changes byte-for-byte; the existing
  opt-in-stability tests prove that. A malformed section poisons
  `spec_coverage` the same way `require_cases` does: reported invalid,
  never silently off. `scope` is independent of `spec_coverage.scope`,
  because evidence is wanted while building and review once claimed done.
- **R2 — What counts as a qualifying review.** A `Review` record for the
  scenario's `(project_id, scenario_id)`. With `distinct_actor`, both its
  `reviewer` and its `actor.agent_id` must differ from every `agent_id` on
  that scenario's EvidenceRecords. Review has no verdict field, so the
  issue's `verdicts: [faithful]` is not adopted: the existing ship guard
  already refuses `divergent` and missing verdicts, and that stays the
  verdict rule.
- **R3 — Gate classes.** A scenario in scope without a qualifying review
  is `unreviewed-promotion`, which already means "promoted as reviewed
  without a review record"; the detail says which rule failed. An open
  `blocker` Finding on a change listed in an in-scope Subject's
  `change_ids` is a new ninth class, `open-blocker`. Findings fold
  latest-by-natural-key first (open → fixed/rejected/deferred), with the
  same semantics as the report's `finding_latest`. Adding the class
  touches `ALL`/`FAILURE_CLASSES`, the generated schemas, and the
  selftest fixtures, in one change.
- **R4 — Status guard.** With `require_review` active,
  `canon subject status <s> <to>` refuses (exit 1, as the ship guard does)
  when `<to>` is in `require_review.scope` and any owned scenario lacks a
  qualifying review, or when an open blocker exists on the subject's
  changes. `--override-reason <text>` lets the transition through. The
  reason and the overridden checks are recorded on the new Subject
  record, attributed to the actor. `gate check` then reports that
  subject's review gaps as advisories that name the waiver, not as
  violations. A waiver is accountable, never silent. The guard prints
  which checks it ran and which it skipped.
- **R5 — Discoverability.** `canon context` (text and `--json`) lists the
  finding severities and dispositions, the Review fields, and the
  `require_review` settings. These are static vocabulary, not corpus
  reads. The skill gains a "Finish a subject" route and a
  `canon-review` reference: evidence, then an independent review
  (`finding add` per issue, fix, `finding close --resolution-sha`), then
  `review add` per scenario, then the transition. `canon-gate.md` and
  `canon-subject.md` link to it.
- **R6 — Canon's own policy.** It stays without `require_review` in 0.12.
  Canon's 246 scenarios have 26 reviews, so turning it on is a separate,
  deliberate dogfooding change, not a side effect of this release.
