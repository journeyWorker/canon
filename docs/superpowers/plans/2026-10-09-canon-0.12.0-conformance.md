# Canon 0.12.0 — conformance corpus and release packet

- **Branch:** `feat/0.12-conformance` (worktree `../canon-0.12`), merged by PR.
- **Base:** `main` at `601f5c85` (0.11.0).
- **Version:** 0.12.0 (minor: a new CI-enforced contract; no CLI or record
  shape change is intended — any change a slice discovers is a finding
  for the final review, not a silent fix).
- **Status:** IN PROGRESS.

## Why

Three defects in the last week reached users through canon's *external*
contracts while every unit test passed:

| Release | Defect | Contract it broke | Found by |
|---|---|---|---|
| 0.8.0–0.9.0 | npm launcher exited 0 on every refusal | CLI exit codes | Kino |
| 0.8.0 | `Subject.scenario_ids` never written; ship gate passed on an empty set | record ↔ report ↔ gate join | Kino |
| 0.8.0–0.10.0 | docs said approvals verify against `CANON_ACTOR` | documented behavior | self, by accident |

Lute (the sibling toolchain) prevents this class with a frozen conformance
corpus that external consumers replay byte-for-byte
(`lute/conformance/README.md`, `lute/crates/lute-cli/tests/conformance.rs`)
and with a release packet: decision log, sliced plan, review gate per
slice, final review (`lute/docs/superpowers/plans/2026-10-07-lute-0.37.0-surface.md`).
0.12.0 adopts both for canon.

## Decisions

- **D1 — What "conformance" means for canon.** A case is a frozen
  repository fixture plus an ordered list of `canon` invocations, each
  with its expected exit code, stdout, and stderr. Consumers of canon
  (scripts, CI, hooks, other repos such as Kino) rely on exactly these:
  exit codes, the gate's violation lines, refusal messages, and JSON
  output. The corpus pins them.
- **D2 — Byte-exact after normalization only.** Outputs carry values that
  are legitimately non-deterministic: the temp repo path, ULIDs, RFC3339
  timestamps, and digests of time-stamped records. The runner replaces
  those with stable placeholders (`<repo>`, `<ulid>`, `<ts>`,
  `<digest12>`) by a fixed, documented, ordered list of rules. No other
  normalization: anything a consumer could parse is compared exactly.
- **D3 — The runner is a cargo integration test** in `canon-cli`, so
  `cargo test --workspace` (already in CI on push to main and on PRs)
  enforces it. No new workflow.
- **D4 — Discovery, never a list.** The runner discovers every
  `conformance/cases/*/case.yaml`. Zero discovered cases is a failure,
  so a moved directory cannot silently pass.
- **D5 — One regeneration entry point.** `conformance/regenerate.sh`
  re-blesses expected outputs (`CANON_CONFORMANCE_BLESS=1`). A bless that
  changes an existing expectation is a contract change: it must be named
  in the release notes. Hand-built refusal fixtures (malformed records,
  broken policy) are never regenerated from code.
- **D6 — Live stamp invariant.** One case pins `canon --version` to the
  workspace version, so a release bump without a re-bless fails — the
  corpus is always stamped with the version it describes.
- **D7 — Scope.** The first corpus covers the contracts named in "Why"
  plus the gates added in 0.9–0.11. It is not a replacement for unit
  tests and does not exercise network tiers (Postgres/R2).

## Case format

```
conformance/
  README.md            # contract, normalization rules, how to add/bless
  regenerate.sh        # the only bless entry point
  cases/<name>/
    case.yaml          # description, env, steps
    repo/              # the fixture repository, copied to a temp dir
    expected/<n>.out   # normalized stdout of step n
    expected/<n>.err   # normalized stderr of step n
```

`case.yaml`:

```yaml
description: one sentence naming the contract this case pins
env: { CANON_ACTOR: canon }       # merged over a fixed base env
steps:
  - args: [gate, check]
    exit: 1
```

The runner copies `repo/` to a fresh temp dir, `git init`s it (canon
reads Git), runs each step's `args` against the built `canon` binary with
the case env and a cleared, fixed base env (no inherited `CANON_*`), and
compares exit code and normalized output. On mismatch it prints a unified
diff and the bless command.

## Slices

Each slice is one commit `feat(0.12) S<n>: …`, leaves `cargo test
--workspace` green, and is reviewed (see Review gate) before the next
starts.

| Slice | Content | Done when |
|---|---|---|
| S1 | Runner (`crates/canon-cli/tests/conformance.rs`), normalization rules, discovery + zero-case guard, bless mode, `conformance/README.md`, `regenerate.sh`, and the D6 version case | the version case passes; deleting `cases/` fails the run; a deliberately wrong expectation fails with a readable diff |
| S2 | Exit-code + gate contract cases: clean (0), red (1), usage error (2, unreadable `canon.yaml`), malformed evidence record, `spec_coverage` unevidenced, `require_cases` golden-path-only surface | each case's expected output reviewed line by line against the code that produces it |
| S3 | Subject lifecycle cases: `verifying → shipped` refused on zero tagged scenarios, on a missing verdict, on a `require_cases` gap; allowed once satisfied; off-chain transition (2) | as S2 |
| S4 | Evidence cases: `evidence add` refusals (no subject key, newline injection, report contradiction 1, file outside repo 2, no matching case 2), binding `off`/`warn`/`require` gate output, malformed `experimental` section | as S2 |
| S5 | Read-surface cases: `canon context --json` policy summary, `canon inventory sync` diagnostics (invalid `@case`/`@lane`, unknown namespace), `canon query --kind subject --json` | as S2 |
| S6 | Release: docs (README 0.12.0 note, `canon-gate`/`ARCHITECTURE.md` pointer to the corpus), version bump to 0.12.0, re-bless the D6 case, lockfiles | `cargo test --workspace`, release checks, website build green |

## Review gate

After each slice, before the next: a reviewer reads the diff and every
new expected output, and checks — (1) the case pins a contract a
consumer actually relies on, not incidental wording; (2) the expected
output was derived from the real binary, never hand-typed to match a
guess; (3) normalization did not hide a value a consumer parses.
Findings are fixed in the same slice.
