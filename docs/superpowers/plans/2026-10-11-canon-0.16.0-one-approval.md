# Canon 0.16.0: one approval, then the agent drives

- **Branch:** `feat/0.16` (worktree `../canon-0.16`). Each slice gets its own
  worktree off `feat/0.16`, merged back in order. One PR to `main`.
- **Base:** `main` at `28b85153` (0.15.0).
- **Version:** 0.16.0 (minor).
- **Status:** DONE (merged via PR #38).

## Why

The maintainer's rule (2026-10-11): an agent reviewing another agent is cheap;
a human blocking the work is expensive. After one approval, the agent should
run on its own. Independent review on every change stays.

What eval 2 measured (`~/Workspace/canon-dogfood/FINDINGS-2.md`):

- **Human stops: two.** The agent stopped at the brief and asked for brief and
  policy approval (16:50). After 68 minutes of autonomous work it stopped again,
  leaving `shipped` for the human, because the skill doesn't say who ships.
- **canon refusals: none.** Of 116 canon calls, none were refused.
- **Bookkeeping: about a fifth of calls.** 16 `gate promote`, 5 `format`, 4
  `inventory sync`.

The skill applies the human-approved brief to *every* request that changes a
feature (`canon/skills/SKILL.src.md:15-31`), including a one-line fix inside a
subject that is already approved.

Backlog items folded in: #21, #22, #23 (autonomy), #8, #9, #10, #11 (next),
#12 (re-review canon's legacy reviews). #13 (Codex eval) is deferred, as the
maintainer asked.

## Decisions

- **D1: one approval per scope (#21).**
  - **What needs the human.** Only a new subject, or a change to an approved
    subject's scope. The human's one answer covers both the brief and the
    policy. The agent records the approval right away. The brief gets an
    `Approved:` line in the change's `proposal.md` (who, when, the human's
    words). The policy is approved with
    `canon policy approve --by <the human> --note "<their words>"`, run by the
    agent on the human's behalf. The agent never approves without a human
    answer.
  - **Inside an approved scope, the agent never stops for a human.** Fixes,
    follow-ups, review rounds and re-reviews go straight to: scenario (add or
    extend) → implement → evidence → independent review.
  - **The agent moves the subject to `shipped` itself** once the ship guard
    passes. The exception is a brief that says the human ships. When no human
    can answer, the existing rule still applies: write the assumption into the
    brief and proceed.
  - **Who carries the rule.** The skill, the AGENTS.md block from
    `canon init`, and `canon status`. Status says whether the subject's brief
    is approved; when the guard passes it says `ship`, not "ask".
  - **M7 amendment (2026-10-12).** Eval 3b regressed on criterion (a). The
    agent wrote the brief, and `canon status` showed the human step, but the
    agent kept building for 2 hours with no approval. Two causes. It read the
    rule above ("when no human can answer, write the assumption into the
    brief and proceed") as covering the approval. And step 8 of the skill
    presented brief approval as a ship gate only ("Approval is only needed to
    ship"), so it read that only `verifying -> shipped` is refused. The
    maintainer decided:
    - The approval is the one thing never assumed. Write the brief, then stop
      and report it. Build nothing for that scope before the human answers,
      even when the human said they cannot answer until you report: the
      brief is that report. "Proceed on assumptions" applies to the brief's
      questions and to work inside an approved scope.
    - canon enforces it. `canon evidence add` is refused for a scenario or
      task whose subject's brief is enforced and not approved. Subjects with
      no brief to answer (no adopted change, or the newest change has no
      `proposal.md`) are unaffected. An explicit `--override-reason` is
      allowed and recorded.
- **D2: fewer bookkeeping calls (#22).**
  - **Promote on write.** Staged write commands accept `--promote`.
    `canon.yaml` `write: { promote: auto }` makes it the default. `canon init`
    writes `auto` for new repos, and existing repos keep today's behavior.
  - **Fresh index without a sync step.** Commands that read the scenario index
    (gate check, status, subject status, review add, evidence add) refresh it
    from the spec files when it is stale, instead of telling the agent to run
    `inventory sync`. The refresh is the same idempotent sync, scoped to
    changed files. `inventory sync` stays available as a command.
- **D3: starter policy levels (#23).** Adds `canon init --policy light|standard|strict`.
  - light: evidence.
  - standard: + a failure case per feature.
  - strict: + independent review.

  The default stays `strict`, per the maintainer: review is cheap. The level
  is noted in `policy.yaml` and shown by `canon status`.
- **D4: small next items.**
  - **#8:** init's gitignore and canon's own ignore `.canon/audit/`.
  - **#9:** the skills install lock records the canon version (and source
    commit). `skills check`/`doctor` name a projection installed by an older
    canon and give the install command.
  - **#10:** `skills doctor` lists co-installed skills, in the same provider
    roots, whose description claims build/site/app/game work, and warns that
    canon's loop won't run if one is chosen. It only reports and never edits
    them.
- **D5: the reviewer can attach what it looked at (#11).**
  - `review add --artifact <path>` (repeatable) stores the bytes like
    evidence and pins their digests.
  - The skill tells reviewers of user-visible behavior to attach screenshots
    or recordings, and tells authors to bind them to visual scenarios.
- **D6: a legacy review is checked against its own pin, and only the drifted ones get re-reviewed (#12).**
  Reviews written before 0.15 carry no digests, but every one carries `pin`,
  the commit it reviewed. That pin is enough to tell whether the review still
  describes the current scenario.
  - **Rule.** A legacy review stays current when two things hold. First, the
    scenario's digest at the pinned commit equals its current digest: the same
    per-scenario normalization as 0.15, computed from `git show <pin>:<feature
    file>`. Second, none of the scenario's declared evidence is newer than the
    review. Otherwise the review is stale, the same as a pinned review. Results
    are cached per (pin, file).
  - **When the pin is unreadable.** If the commit isn't available (shallow
    clone, rewritten history), keep the 0.15 behavior: the review counts, and
    an advisory names the count and suggests `fetch-depth: 0`. A missing commit
    never turns a review into a violation.
  - **canon's own CI** checks out full history for the gate job, so the rule
    is enforced there.
  - **Measured on canon (2026-10-11).** Of 348 legacy reviews:
    - 285 are unchanged and stay current with no new review;
    - 26 belong to scenarios that no longer exist and are ignored;
    - 37 have drifted: 30 by spec, 3 by evidence, 4 by both.

    So only about 37 scenarios need re-review, not 340. Kino's 103 legacy
    reviews get the same check for free.
  - **Re-review.** Independent reviewer sessions re-review exactly the
    scenarios the gate reports as stale. The new reviews pin. Findings are
    fixed and re-reviewed.
- **D7: acceptance is eval 3 (omp).** Use the same one-line prompt in a fresh
  repo initialized with the 0.16 build. Answer the brief once with
  "승인. 네 가정대로 진행". Then, in the same repo, send one follow-up fix
  request with no new approval.

  Pass when:
  - (a) exactly one human stop happens before `shipped`;
  - (b) the follow-up fix goes to review without stopping;
  - (c) bookkeeping calls (promote/sync/format) are under 5% of canon calls;
  - (d) every scenario is independently reviewed and the gate is clean.
