# Canon 0.14.0 — the working loop: init, status, evidence integrity, unit identity, skill

- **Branch:** `feat/0.14` (worktree `../canon-0.14`). Slices run in their own
  worktrees off `feat/0.14` and are merged back in order. One PR to `main`.
- **Base:** `main` at `5376dbb0` (0.13.1).
- **Version:** 0.14.0 (minor). `canon init` writes more files, bound evidence
  artifacts are checked by the gate, `canon context` prints a short header,
  and there is a new `canon status` command and a new `canon change new` command.
- **Status:** READY FOR MERGE (acceptance rerun pending).

## Why

Dogfood eval 1 (`~/Workspace/canon-dogfood/FINDINGS.md`, F1–F17) gave two
harnesses the one-line request "make a cat-themed Vampire-Survivors-like" in a
fresh canon repo. canon's guardrails worked once an agent turned them on. What
canon did not do was tell the agent *how to work*: the skill is a CLI manual,
`init` leaves no AGENTS.md and no policy (so the gate is clean on zero
evidence and the implementer writes its own grading policy), bound evidence is
never re-checked, delegated units leave no trace, and `canon context` never
says what state the repo is in or what to do next.

Codex-specific follow-up (re-running the eval on Codex) is deferred by the
user; F1 shipped in 0.13.1.

## Decisions

- **D1 — Skill is a working loop (K6; F2, F3, F6, F12, F17).** `SKILL.md`'s
  description claims build/implement/change-a-feature work in any repo that
  has `canon.yaml`, ahead of generic site/app builders. The body starts with
  the loop:
  1. brief (record the request and assumptions);
  2. subject;
  3. features and scenarios, including failure paths — add a new failure
     scenario, never retag an existing one;
  4. split into units, one actor id and session per unit;
  5. implement, with tests named by scenario id;
  6. evidence;
  7. independent review in a different session, with findings for every
     defect, including ones the author found; every bug fix adds or extends a
     scenario;
  8. status transition.

  The loop names the stop points: human approval of the brief and the policy.
  The command reference moves below the loop. Written last, so it describes
  the commands as they ship.
- **D2 — `canon init` sets up the loop (K2; F4, F5, F7).** `init` writes, next
  to `canon.yaml`:
  - **A starter `.canon/policy.yaml`:** `spec_coverage` with
    `require_evidence`, `require_cases: [failure]` and `require_review: {}`.
  - **An AGENTS.md block:** delimited by `<!-- canon:begin -->` /
    `<!-- canon:end -->`, created when AGENTS.md is absent and merged when it
    is present. It is idempotent and never touches text outside the markers.
    The block says that features are managed with canon, names the loop, and
    points to the skill.
  - **A default plans source,** so changes and tasks have a home.

  `--no-agents-md` and `--no-policy` opt out. A second `init` on an existing
  repo refreshes the AGENTS.md block and leaves everything else alone.
  `canon change new <slug> --subject <id> --title …` scaffolds an openspec
  change (proposal + tasks), adopts it into the subject, and needs no hand
  edits to `canon.yaml`.
- **D3 — The gate says when it is not enforcing (K2; F5).** When the spec
  corpus has scenarios and `spec_coverage` is absent, `canon gate check`
  prints one advisory line naming the scenario count and how to turn coverage
  on. The exit code is unchanged: an advisory, not a violation.
- **D4 — Bound evidence stays provable (K3; F9).**
  - **Storing the bytes.** `evidence add --artifact/--report` copies the
    bytes into a content-addressed store, `.canon/artifacts/sha256/<hex>`,
    which is tracked in git.
  - **What the gate checks.** For every attachment on an in-scope latest
    evidence record, the gate checks the stored blob. When the blob is
    missing, the working-tree path must still hash to the recorded digest;
    this is the back-compat path for 0.11–0.13 records, and the gate prints
    an advisory naming `canon evidence vault` to store it. Anything else is a
    `stale-evidence` violation that names the path and both digests.
  - **Size limit.** Stored files have a documented limit; a larger file is
    refused with an override flag named in the message.
- **D5 — Evidence is not shaped by tasks (K3; F8, F14, F15).**
  - **Summaries.** `--summary` is allowed on scenario-only evidence.
  - **Report cases.** `--report-case` is repeatable, and every report case
    whose name carries the scenario id is bound. Any failed bound case
    refuses a `faithful` verdict.
  - **Tasks.** The summary on a flipped task row aggregates every evidence
    record bound to the task. `gate task` leaves the task's stored status
    agreeing with the flipped checkbox, so `canon query --kind task` matches
    `tasks.md`.
- **D6 — Units and reviews carry a session (K4; F10, F11, F12, F16).**
  - **Session ids.** `--session-id` on `evidence add`, `review add` and
    `finding add` fills `actor.session_id`; the field already exists on the
    envelope.
  - **Distinct actor.** `require_review.distinct_actor` also rejects a review
    whose session id equals any evidence session id on that scenario, when
    both are set.
  - **Self-found defects.** An author can record a defect in its own work:
    `finding add --reviewer <me> --actor-id <me>`. The author's own open
    blocker still blocks under `require_review`. *Amended during K4:* the
    original wording, `--introduced-by self`, is not adopted.
    `introduced_by` is the SHA of the commit that introduced the defect,
    and the fix-of-fix count reads it, so a `self` value would corrupt
    that count. `self` is refused with a pointer to `--reviewer`. What F12
    actually lacked was guidance, not a flag; K6's skill tells authors to
    record every defect they find, their own included.
  - **Write mode.** Every write command says in its output whether it staged
    (then `gate promote`) or committed directly.
- **D7 — `canon status` answers "where are we, what next" (K5; F13).**
  - **What it prints.** `canon status [--json]` lists subjects by status. For
    each it gives the scenario, evidence and review counts, its gaps, and the
    policy warnings. It ends with a short `next:` list of concrete commands,
    produced by deterministic rules over the same joins the gate uses.
  - **Pointer from context.** `canon context` prints a three-line header
    first: a pointer to `canon status` and any policy-absent warning. The
    schema follows unchanged. JSON output is unchanged apart from a
    `capabilityVersion` bump if the header adds a field.
- **D8 — Acceptance is a dogfood rerun (K7).** The same prompt as eval 1, run
  in a fresh repo initialized with the 0.14 build, using omp only (Codex is
  deferred). Every F-item is marked resolved, partly resolved or open, with
  transcript evidence. The release notes cite the result.

Every slice:
- adds Gherkin scenarios (with `@case`) for its consumer-visible rules and
  attests them;
- gets an independent review whose reviews and findings are recorded in
  canon's own ledger (canon has `require_review` on);
- fixes its findings before the next merge.
