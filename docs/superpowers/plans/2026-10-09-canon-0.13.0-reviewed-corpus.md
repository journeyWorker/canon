# Canon 0.13.0 — reviewed corpus, parseable context, strict policy keys, website v2

- **Branch:** `feat/0.13` (worktree `../canon-0.13`), website on
  `feat/0.13-website` (worktree `../canon-0.13-web`), merged by PR.
- **Base:** `main` at `b556ab75` (0.12.0).
- **Version:** 0.13.0 (minor): `canon context --json` changes shape and
  unknown `policy.yaml` keys stop being silently accepted.
- **Status:** IN PROGRESS.

## Why

The items 0.12.0 left open, which the user asked to close:

1. Canon does not pass its own review requirement. 21 subjects are in
   `verifying` with ~250 scenarios, and almost none have an independent
   review. The user chose real reviews over waivers.
2. `canon context --json` gives `spec_coverage` and `evidence_binding`
   as human summary strings (`scope=verifying, shipped require_cases=failure`).
   A consumer cannot parse them reliably.
3. An unknown top-level `policy.yaml` key (`bogus_key: 1`) is accepted
   silently. A typo in a policy section name turns that policy off without
   saying so — the same class as the 0.12 invalid-`canon.yaml` fix.
4. The website redesign was rejected: the grid hairlines hurt
   readability, and the comparison has to be a real table. The user picked
   the Checks Panel (PR checks) direction instead.

## Decisions

- **D1 — Real reviews, independent actors.** Six reviewer agents, one per
  subject group, read every scenario, its proving test, and the code under
  test. Each uses actor id `canon-reviewer-g<n>`, never `canon`, the
  evidence actor. A scenario gets a Review only if its test genuinely
  verifies the Given/When/Then. Anything short of that becomes a Finding
  on change `canon-0.13-review`, round 1, with the reviewer's severity.
  Reviewers do not write records themselves; one integrator records them
  in order, so concurrent `gate promote` runs can't race.
- **D2 — Fix, then re-review.** Every blocker and should-fix is fixed on
  this branch with a test, and closed `fixed --resolution-sha`. A scenario
  withheld in round 1 is re-reviewed after its fix, by a reviewer that
  did not make the fix. Notes may be closed `rejected` or `deferred`, with
  the reason in the summary.
- **D3 — Then turn it on.** `.canon/policy.yaml` gets
  `spec_coverage.require_review: {}` only once `canon gate check` is clean
  with it on. CI then enforces it on every push.
- **D4 — Structured context.** In `canon context --json`, the policy
  summary gives `spec_coverage` and `evidence_binding` as JSON objects
  (typed fields, arrays for lists). An invalid section becomes
  `{ "invalid": "<detail>" }`. The text output is unchanged.
  `capabilityVersion` goes to 5.
- **D5 — Unknown policy keys fail loud.** An unknown top-level key in
  `.canon/policy.yaml` becomes a policy diagnostic. The gate reports it the
  same way as an invalid section, naming the key and the known keys, and
  `canon gate check` fails. Known-key parsing is unchanged.
- **D6 — Website v2.** Comp-led Impeccable build of the approved Checks
  Panel comp. The comparison is an HTML table at every width, with every
  non-canon cell sourced. There are no grid hairlines. Fig. 1 and its data
  pipeline are deleted.
