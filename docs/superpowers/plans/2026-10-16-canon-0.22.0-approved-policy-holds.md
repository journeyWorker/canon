# Canon 0.22.0: the policy the gate grades against is the one a human approved

- **Branch:** `feat/0.22`. Each slice gets its own worktree off `feat/0.22`, merged back in order. One PR to `main`.
- **Base:** `main` after 0.21.1 (#65) and the forca chores (#66–#69).
- **Version:** 0.22.0 (minor; one exit-code contract change, named below).
- **Status:** IN PROGRESS.
- **Issues:** #71, #70. The deprecations 0.21 scheduled for removal in 0.22.

## Why

Input: the 2026-10-16 research briefing, checked against its primary sources (`docs/research/2026-10-16-canon-bard-weekly-briefing.md`).

- **#71: an edited policy still passes.** GitHub's managed settings now fail closed when a client cannot confirm the current policy ([changelog](https://github.blog/changelog/2026-10-13-enterprise-managed-settings-enforcement-updates/)). canon records the approved policy digest (`.canon/policy.approval.json`, 0.15) but only advises. Reproduced on 0.21.1: approve a policy with `require_review`, delete that key, and `subject status --to shipped` ships with no review while `gate check` exits 0 with one advisory line. The skill says never to edit the policy to make the gate pass; nothing enforces it.
- **Observability of the approval.** The briefing's agent-interface paper ([arXiv:2610.15765](https://arxiv.org/abs/2610.15765)) names observability: a write should have a read that returns the state it changed. `policy approve` has none. The state shows up only as advisory prose in `status` and `gate check`.
- **#70: `status` points at the human while the brief is a skeleton.** The transition condition for "stop for the human" is "the brief is approvable". Today it is "the brief is not approved".
- **Deprecations.** 0.21 printed `removedIn: "0.22.0"` for `context-pack create`, `prompt register`, `divergence stage`, `demo attest` and `subject status <id> <state>`.

## Decisions

- **D1: a changed policy fails closed (#71).**
  - `policy_approval::approval_state` is unchanged. Its consumers change:
    - `Changed` (the bytes differ from the approved digest) and `Unreadable` (the approval file exists but does not parse) are a gate violation. The new `canon_gate::FailureClass` variant is `UnapprovedPolicy`, wire `unapproved-policy`. The detail names the policy path, both digests (or the parse error), the approver and the time, and says a human reviews the change and approves it (`canon policy approve --by <who>`, or `canon brief approve`, which records both).
    - `canon gate check` reports it as a violation and exits 1. It is repo-wide, so it has no scenario.
    - Every `canon subject status` transition that runs the gate's guards refuses on it: building → verifying, verifying → shipped, and the reopen shipped → verifying. JSON error codes are `POLICY_CHANGED_SINCE_APPROVAL` and `POLICY_APPROVAL_UNREADABLE`. `--override-reason` does not waive it, matching the reopen brief gap (0.18). A waiver of the policy that grades the waiver would be circular.
    - `canon status` turns the advisory into a step with `actor: human`: review the policy change and approve it. Nothing else is suggested for transitions until then. `status` still exits 0.
  - `Unapproved` (a policy exists and was never approved) stays an advisory. There is no approved digest to be stale against, and every repo initialised before 0.15 is in this state. `NoPolicy` stays silent.
  - `canon evidence add` and `canon review add` are unchanged. A record is graded when the gate runs, not when it is written.
- **D2: `canon policy show` (read).**
  - Output: the policy path, the current digest, `state` (`approved | unapproved | changed | unreadable | none`), and the approval (`approvedBy`, `approvedAt`, `note`, `policyDigest`) when one exists. JSON follows the 0.20 contract. Always exits 0. Roles: all.
  - `policy approve`'s `meta.next` and the D1 refusals name `canon policy show` as the read-back.
- **D3: the brief's next step follows its check state (#70).**
  - For an enforced, unapproved brief, `status`/`meta.next` derive the step from `canon brief check`. With blockers, the step is the planner's (`actor: agent`, `role: planner`): write the brief, naming the command and the blocker count. With no blockers, it is the human stop as today. `--as planner` then shows the planner its step, and `waitingOn.human` drops to 0 until the brief is clean.
  - `change new`'s output follows the same rule (no `waiting on human` for a skeleton).
- **D4: remove the deprecated forms.**
  - `context-pack create`, `prompt register`, `divergence stage`, `demo attest` and the two-positional `subject status <id> <state>` stop parsing. They now get the normal `USAGE` refusal. `canon schema` no longer lists them.
  - Any code that existed only to serve them goes too (the deprecation registry, `meta.deprecated`, `schema`'s `deprecated` field) unless something else still uses it. A clean cutover, with no aliases left behind.
- **D5: acceptance.**
  - Conformance cases (new): `gate check` exits 1 with `unapproved-policy` after a change; the ship guard refuses with `POLICY_CHANGED_SINCE_APPROVAL` and an override does not waive it; re-approval lifts both; an unreadable approval refuses with `POLICY_APPROVAL_UNREADABLE`; never-approved stays an advisory with exit 0; `policy show` in each state; `status` gives the planner step for a skeleton brief and the human step for a clean one; each removed form gets `USAGE`.
  - Contract change, named in the release notes: `policy-approve-changed-advisory` (and any other case whose policy changed after approval) now exits 1 where it exited 0.
  - canon's own corpus: `policy.expressions.32` ("the gate's exit code is the same in all three runs") is rewritten for D1. New scenarios cover D1–D3 with `@case:failure` paths. Tests are named by scenario id, evidence is recorded with `canon evidence add`, and the scenarios are reviewed in a separate session. `canon gate check` on this repo stays clean.
  - Smoke: the #71 reproduction on the release build refuses at the ship step and fails `gate check`.
