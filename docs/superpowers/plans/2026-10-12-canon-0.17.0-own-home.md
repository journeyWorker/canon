# Canon 0.17.0: canon's own home

- **Branch:** `feat/0.17` (worktree `../canon-0.17`). Each slice gets its own worktree off `feat/0.17`, merged back in order. One PR to `main`.
- **Base:** `main` at 98120cea (0.16.0).
- **Version:** 0.17.0 (minor; the layout changes come with a migration command).
- **Status:** IN PROGRESS.

## Why

The maintainer's rules (2026-10-12):

1. **Canon keeps what it writes in `.canon/`.** Today the spec corpus sits outside it, in `specs/features/kind=feature/area=<area>/<surface>.feature`. That path is also redundant: the root name `features` and the `kind=feature` segment say the same thing (`canon-model/src/family/mod.rs:294-301`).
2. **Canon reads external plans and never writes into them.** Openspec changes, superpowers plans, ADRs and other plan docs are inputs a user prepares. Today `canon init` creates `openspec/changes/` and makes it the default plans source (`canon-cli/src/init.rs:130-135,175`). `canon change new` scaffolds its brief there (`change.rs:48-59`). 0.16 also writes the human's `Approved:` line into that external `proposal.md` (`brief.rs:9-14`).
3. **Canon asks which harnesses to install for.** Today `canon skills install` picks providers from directory markers (`.claude`, `.agents`/`.codex`, `.omp`, `.pi`). When it finds none, it installs Claude and Codex (`skills.rs:87-111,488-504`). It never asks, and `.agents` is a generic name other tools use too.

Consumers on 0.16 must be able to move with one command. Ledger joins (scenario ids, change ids, review pins) must survive the move. This release migrates canon's own repo. Kino and Lifeshot move later, by the maintainer's call; this release only proves the migration on throwaway copies of them.

## Decisions

- **D1: spec layout.**
  - The `Feature` family drops its `features/` root dir. A spec root holds `kind=feature/area=<area>/<surface>.feature` directly. `kind=` stays at the top so other kinds (for example `kind=content`) can sit beside it later.
  - A new repo's default root is `.canon/specs` (`id: root`). `specs.roots` still takes any path.
  - `canon feature new`, `scenario new`, `format`, `inventory sync`, the reader refresh, the legacy-pin lookup and every doc follow the new layout.
  - The old layout is refused with a message that names `canon migrate`. There is no dual-layout reading (clean cutover).
  - The other families (ledger, divergences, inventory) are unchanged. No repo uses them as spec roots.
- **D2: canon's own changes.**
  - `canon change new <slug>` writes `.canon/changes/<slug>/brief.md` and `.canon/changes/<slug>/tasks.md`. The brief uses the same sections the openspec proposal had, and the task grammar is the openspec row grammar.
  - `.canon/changes` is canon's native plan source. Every reader (`ingest plans`, `gate task`, `evidence add --task`, status, the brief check) always reads it without any `plans:` entry.
  - `plans.sources` lists only external inputs. `canon init` no longer creates `openspec/` and writes no default source. Its `plans:` block shows commented openspec and superpowers examples.
- **D3: the approval lives in canon's file.**
  - The `Approved:` line (who, when, the human's words; the same parse that ignores comments and fences) is read only from `.canon/changes/<change>/brief.md`.
  - A change imported from an external plan gets its brief as a canon file too: `.canon/changes/<change>/brief.md`. It holds a `Source: <path>` pointer to the external doc and, once the human answers, the `Approved:` line. Canon never edits the external doc.
  - When a brief is enforced (as in 0.16 M7, the newest adopted change has a brief to answer):
    - A canon `brief.md` counts as a brief.
    - An external openspec `proposal.md` with no canon `brief.md` also counts. In that case status, the evidence refusal and the ship guard name the canon file to create (with the `Source:` pointer) and the approval to record.
  - `--override-reason` stays.
- **D4: external task rows.** `canon gate task` keeps flipping the checkbox in an external plan's `tasks.md`, as today. Those rows are the plan's own execution status. That is the one place canon writes into an external plan, and the README says so. (Open for the maintainer: record external flips only in the ledger instead.)
- **D5: harness choice.**
  - `canon.yaml` gains `skills: { providers: [claude, codex, omp, pi] }` (any subset).
  - `canon init` asks which harnesses to install the canon skill for, on a terminal. The detected ones are pre-checked; a detection marker is a directory: `.claude`, `.codex`, `.omp` or `.pi`. `.agents` alone no longer selects Codex, because other tools use it. Init writes the answer and installs. `--providers a,b` answers without a prompt.
  - With no terminal and no flag, init installs for the detected ones only. With none detected it installs nothing and says how to choose (`canon skills install --providers …`).
  - `skills install`, `check` and `doctor` follow `skills.providers`. An explicit `--providers` on install also rewrites that list.
  - No undetected harness is ever added by default. The Claude+Codex fallback goes away.
  - `skills doctor` names any projection directory canon owns that is not in the list, and says how to remove it.
- **D6: `canon migrate`.** One idempotent command, with `--dry-run` printing the plan.
  - **Spec roots.** For each spec root in the old layout, move `<root>/features/kind=feature/**` to `<root>/kind=feature/**`. A root at the repo-level `specs` default moves to `.canon/specs`. Other roots (e.g. `examples/platformer/specs`) stay where they are and only drop the `features/` level. Rewrite `canon.yaml` `specs.roots`.
  - **Canon-written changes.** Changes that `canon change new` wrote under openspec move into `.canon/changes/<slug>/`, as `proposal.md` → `brief.md` with `tasks.md` alongside. The openspec plans source entry that init added goes too, when nothing else is left under it. How a canon-written change is told apart is decided by evidence (provenance in the Change record or the scaffold, or recorded by `change new`). Never guess: an ambiguous change is left in place and named.
  - **Approvals.** An `Approved:` line canon wrote into an external `proposal.md` that stays external is copied into a canon `brief.md` with a `Source:` pointer. The external file is not edited; the leftover line is named in the output.
  - **Skills.** `skills.providers` is written from the install lock's providers.
  - **Gitignore.** Missing canon gitignore lines are added (hot db, audit, scenario index, index lock, artifact-store lock; closes #35). Re-running `canon init` on an existing repo also adds them.
  - **Index.** The scenario index is rebuilt at the end.
  - **Acceptance.** Before and after, `canon gate check` and `canon status` print the same violations, counts and legacy advisory. A pure move keeps every pinned review current: pins are content digests, and the legacy lookup finds a scenario in another file at the pin. Verify this; don't assume it.
- **D7: acceptance.**
  - **(a) Self-migration.** canon's own repo is migrated by the release build inside this PR. `gate check` stays clean with the same counts.
  - **(b) Copy migrations.** Throwaway `/tmp` copies of Kino and Lifeshot migrate with the same before/after equality. The originals are never touched.
  - **(c) Eval 4 (Codex, #13).** The one-line game prompt runs in a fresh repo initialized by the release build with `--providers codex`.
    - Pass when: the agent stops once at the brief; after one answer it reaches `shipped`; specs land under `.canon/specs/kind=feature/`; the brief and approval are in `.canon/changes/`; no `openspec/` directory is created; only `.agents/skills/canon` is projected; `gate check` is clean.
    - If Codex cannot run (auth), use omp and say so.

Shared rules for every slice:
- `@case`-tagged scenarios with tests, evidence attested with the slice's `--session-id`.
- Independent review in another session, with reviews and findings recorded in canon's ledger, pinned.
- Findings fixed before merge.
- README notes, EN/KO website cli pages, the skill and references, and re-projected skills.
- Conformance re-blessed and reviewed.
- Before commit: `cargo xtask check-generated`, `cargo test --workspace`, conformance, check-knowledge, `git diff --check`.
