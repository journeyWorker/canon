# context-pack의 비밀 검사는 토큰 모양만 거절하고, 깨끗한 저장소는 dirty가 아니다

Source: 결함 D6과 D9의 곁가지(0.37.0 디버그 바이너리로 재현, `docs/research/vendor-audits/00-cross-vendor-patterns-rust-2026-11.md` 재검증 절), 이 저장소의 `.md`를 0.38 규칙으로 센 값

## Intent

`canon context-pack add`는 담기 전에 아홉 개 문자열을 소문자 본문에서 부분 문자열로 찾는다. 단어의 일부여도 걸린다. `risk-high`, `task-list`, `disk-usage`, `mask-all`, `Akiashi`를 한 줄씩 담은 파일은 모두 `CONTEXT_INPUT_INVALID`(종료 값 2)로 거절됐고 비밀은 없었다. 이 저장소의 `.md` 176개 중 26개가 거절 대상이다. 거절하면 안 되는 글의 시험은 없다.

팩이 적는 저장소 상태에도 결함이 있다. 팩 저장소 경로를 뺀 `git status -z`가 비어도 결과는 NUL 한 바이트다. 깨끗한 저장소의 팩이 `dirty` 참이고, 깨끗함을 뜻하는 갈래는 닿지 않는다.

## Desired outcome

- 비밀 모양이 없는 글은 `risk-`, `task-`, `akia`가 단어 안에 있어도 팩이 된다.
- ==**검사는 접두어, 글자 종류, 최소 길이, 왼쪽 경계가 맞는 토큰과 비공개 키 머리줄, 키 이름이 붙은 값만 비밀로 읽는다.**==
- 비밀의 위치와 종류를 돌려주는 함수가 잎 크레이트에 하나 있고 context-pack이 그것을 부른다.
- 거절은 이유와 종료 값이 그대로이고 메시지가 줄과 규칙 이름을 말한다. 값은 말하지 않는다.
- 깨끗한 저장소의 팩은 `dirty`가 거짓이다.

## User flow

1. F1 에이전트는 비밀이 없는 문서를 담아 `canon context-pack add`를 돌린다 → 팩이 만들어진다 → 아이디를 받는다.
2. F2 에이전트는 비밀 모양이 든 파일을 담는다 → 거절된다 → ==**메시지가 파일, 줄, 규칙 이름을 말하고 아무것도 저장되지 않는다.**==
3. F3 오케스트레이터는 주입 지침이 든 `dispatch begin`을 돌린다 → 지침 글이 같은 규칙으로 검사된다 → 같은 판정을 받는다.
4. F4 구현자는 다른 기능에서 비밀 위치가 필요하다 → 같은 함수를 부른다 → context-pack과 같은 판정을 얻는다.
5. F5 에이전트는 깨끗한 저장소에서 팩을 만들고 읽는다 → `dirty`가 거짓이다 → 파일을 고치면 참이다.
6. F6 사람은 CHANGELOG를 읽는다 → 거절이 줄고 몇 가지가 새로 거절되며 같은 입력의 팩 아이디가 바뀐다 → 알림을 읽는다.

## Step detail

### F1 평범한 글

- 거절하면 안 되는 줄의 표가 모두 팩이 된다: `risk-high`, `RISK-HIGH`, `task-list`, `disk-usage`, `mask-all`, `ask-user`, `Akiashi`, `AKIATSU`, `sk-live-123456`, `sk-documentation-for-onboarding-flow`, `ghp_`와 `github_pat_` 한 단어, `-----BEGIN CERTIFICATE-----`, `-----BEGIN PUBLIC KEY-----`, `api_key=` 뒤가 비었거나 `<your key>`, `${API_KEY}`, `YOUR_API_KEY`, `api_key: string`, `max_api_key_len = 4`.
- 이 저장소의 `canon/`, `docs/`, `.canon/` 아래 `.md`는 하나도 거절되지 않는다.

### F2 비밀 모양

대소문자를 구분하고(키 이름만 무시) 여섯 규칙으로만 맞춘다. 왼쪽 경계는 앞 글자가 없거나 영문자, 숫자, `_`가 아닌 것이다.

| 규칙 | 맞는 모양 |
|---|---|
| AWS 액세스 키 아이디 | 왼쪽 경계, `AKIA`, 대문자와 숫자 16글자, 오른쪽 경계 |
| GitHub 개인 토큰 | 왼쪽 경계, `ghp_`, 영문자와 숫자 36글자 이상 |
| GitHub 세분 토큰 | 왼쪽 경계, `github_pat_`, 영문자, 숫자, `_` 22글자 이상 |
| API 비밀 키 | 왼쪽 경계, `sk-`, 영문자, 숫자, `_`, `-` 20글자 이상이고 숫자가 하나 이상(`sk-proj-` 꼴 포함) |
| 비공개 키 | `-----BEGIN `, 대문자와 공백의 머리 낱말에 `PRIVATE KEY`가 든 `-----` 머리줄(`RSA`, `OPENSSH`, `ENCRYPTED`, `PGP … BLOCK` 포함) |
| 키 이름이 붙은 값 | `api_key`, `apikey`, `access_token`, `secret_key`(대소문자 무시, 앞이 영문자나 숫자가 아님), 닫는 따옴표, 공백, `=` 또는 `:`, 공백, 여는 따옴표, `[A-Za-z0-9._~+/=-]` 8글자 이상. `:`는 따옴표 값일 때만. 전부 대문자와 `_`인 값은 자리표시자다 |

- 위치는 바이트 범위와 종류다. 비공개 키는 머리줄부터 `-----END …-----` 끝까지(없으면 머리줄만), 키 이름이 붙은 값은 값만이다. 겹치면 하나로 합치고 앞의 종류를 쓴다. 시작 순으로 나온다.
- 각 규칙은 후보에서 최대 512바이트(머리줄은 80바이트)만 읽는다. 입력이 길어도 선형이다.
- 파일은 UTF-8로 바꿔(잘못된 바이트는 대체 문자) 한 번 읽는다. 소문자로 바꾸지 않는다.
- 메시지는 `selected context input contains plaintext secret material: <파일> (line <N>, <규칙 이름>)`이다. 코드, `reason`, 안내문, 종료 값, 코드 표 문구는 그대로다.

### F3 주입 지침

- 지침마다 제목과 본문을 쓰인 그대로 검사한다. 직렬화한 JSON을 검사하지 않는다. 직렬화가 만드는 `\n`과 `\"`가 규칙의 경계와 따옴표 읽기를 바꾸기 때문이다.
- 메시지의 파일 자리에는 `injected guidance`와 그 지침의 `strategyId`가 선다.

### F4 공유

- 검사 함수는 `canon-model`의 새 모듈 `secret_scan`에 있다. 글을 받아 위치 목록을 돌려주는 순수 함수이고 새 의존성이 없다. 손으로 짠 스캐너다.
- ==**`context_pack.rs`에는 자체 접두어 목록이나 판정이 남지 않는다.**== 파일과 지침 모두 이 함수를 부른다.
- `canon-ingest`는 별개의 변경이 0.39에서 없앤다. `normalize.rs`의 `redact_directive`는 건드리지도 복사하지도 않는다. 새 모듈은 그 위치 모델만 따른다.

### F5 깨끗함

- 팩 저장소 경로를 뺀 상태 목록에서 빈 항목을 버린다. 남은 항목과 `git diff HEAD`가 모두 비면 `dirty`는 거짓이고 `stateDigest`는 깨끗함의 다이제스트다.
- 하나라도 있으면 참이다. 상태가 있는 저장소의 `stateDigest`는 끝 NUL이 하나 줄어서 달라진다.
- 방금 만든 팩이 팩 저장소 경로에 남긴 파일은 더럽히지 않는다. 팩 저장소 경로 밖의 변경은 더럽힌다.
- git 저장소가 아니거나 커밋이 없을 때 `commit`이 없는 것과, git이 상태를 못 주면 변경이 없다고 읽는 것은 그대로다. 이때 `dirty`가 거짓이 된다.
- 이미 만든 팩은 저장된 바이트로 검증되므로 `verify`와 `show`의 답이 바뀌지 않는다.

### F6 변경 기록

- Fixed에 줄어든 거절과 `dirty`를 싣는다.
- Changed에 새로 거절되는 입력(공백이 낀 대입, JSON 따옴표 값, `-`가 든 긴 `sk-` 키)과 팩 아이디 변화를 싣는다.

## Acceptance

- F1:
  - 표의 줄마다 `context-pack add`가 팩을 만들고 `canon-model` 함수에는 위치가 없다. 이 저장소의 `canon/`, `docs/`, `.canon/` 아래 `.md` 전부에서 위치가 없다.
  - 실패 경로: 한 줄이라도 거절되면 시험이 실패한다. `sk-live-123456`과 숫자 없는 긴 `sk-` 낱말열이 표에 있다.
- F2:
  - 규칙마다 긍정 한 줄과 최소 길이 바로 위와 아래의 경계 한 쌍이 있다. 경계 아래는 통과, 위는 거절이다. 키 이름 규칙에는 공백이 낀 대입, 환경 변수 접두어, JSON 따옴표 값이 있다. 기존 두 시험이 그대로 통과한다.
  - 실패 경로: ==**거절은 팩 저장소에 아무것도 남기지 않고, 메시지는 파일, 줄, 규칙 이름을 말하며 비밀 값을 담지 않는다.**== 코드, `reason`, 종료 값은 0.38과 같다.
- F3:
  - 본문에 AWS 키 모양이 든 지침은 거절되고 `risk-high`만 든 지침은 팩이 된다. 따옴표 값은 직렬화된 `\"`가 있어도 거절된다.
  - 실패 경로: 같은 글을 파일로 담을 때와 지침으로 담을 때 판정이 다르면 시험이 실패한다.
- F4:
  - `canon-model` 시험이 위치의 시작, 끝, 종류, 합침, 시작 순을 확인한다. 4 MiB의 `sk-`, `AKIA`, `-----BEGIN ` 반복 입력이 끝난다.
  - 실패 경로: `canon-cli` 시험이 표의 모든 줄에서 함수와 `context-pack add`의 판정을 견주고, 어긋나는 줄에서 실패한다.
- F5:
  - 깨끗한 git 저장소의 팩은 `dirty`가 거짓이고 상태 다이제스트가 깨끗함의 다이제스트다. 방금 만든 팩이 남긴 파일이 있어도 같다.
  - 실패 경로: 추적하는 파일을 바꾸거나 팩 저장소 경로 밖에 추적하지 않는 파일을 두면 `dirty`가 참이다. 상태가 있는 저장소의 상태 다이제스트는 항목마다 NUL이 하나씩만 붙은 값이다.
- F6:
  - CHANGELOG 항목이 있다.
  - 실패 경로: 항목이 없으면 릴리스 확인 시험이 실패한다.
- `cargo test --workspace`와 `canon gate check`가 통과한다.

## Questions and assumptions

- 결정: 모듈은 `canon-model`에 둔다. 새 크레이트는 작업공간과 CI 행과 배포 목록을 늘리는데 필요한 것은 순수 함수 하나다. `canon-store`와 `canon-cli`가 이미 `canon-model`을 쓰므로 앞으로 첨부 검사가 불러도 새 간선이 없다.
- 결정: 정규식을 쓰지 않는다. 잠금 파일의 `regex`는 간접 의존이고 작업공간의 어느 크레이트도 직접 쓰지 않는다. 규칙이 접두어, 글자 종류, 길이, 경계라서 손으로 짠 스캐너로 충분하다.
- 결정: 키 이름 규칙은 기존 이름 넷만 둔다. 값은 8글자 이상이고, 전부 대문자와 `_`인 값은 뺀다. `:`는 따옴표 값일 때만 읽어서 문서의 `api_key: string`을 거절하지 않는다. 따옴표 없는 YAML 값은 놓친다. 이 놓침은 알고 받아들인다.
- 결정: `sk-` 규칙은 `_`와 `-`도 읽고 숫자를 요구한다. 요즘 키(`sk-proj-…`)에는 하이픈이 들어서 영문자와 숫자만 읽으면 0.38이 잡던 것을 놓친다. 하이픈으로 이은 영어 낱말열은 숫자가 없다. 시험표 두 줄이 이를 고정한다.
- 결정: 비공개 키는 머리줄만 보고 맞춘다. 본문이 한 줄로 이어졌거나 끝줄이 잘려도 놓치지 않는다.
- 결정: 거절 메시지에 줄과 규칙 이름을 넣는다. 거짓 거절이 이 결함의 해악이므로 사람이 왜 걸렸는지 바로 알아야 한다. 값은 넣지 않는다.
- 결정: 위치 모델만 만들고 가려 쓰는 함수는 만들지 않는다. 부를 곳이 없다. 세션 수집은 사라지고 첨부 검사는 거절과 끔만 한다.
- 결정: 세션 수집의 가림 함수와 합치지 않는다. 그 규칙(`token`, `secret`, `password`, `Bearer`, 이메일)은 대화록을 가리는 분류기라서 거절에 쓰면 문서의 `token:`까지 걸린다. 그 파일은 세션 수집을 없애는 변경이 지운다.
- 결정: 지침은 직렬화하지 않고 글로 검사한다.
- 결정: `dirty` 수정은 상태 목록의 빈 항목을 버리는 한 곳이다. 팩 아이디가 상태 다이제스트를 담으므로 같은 입력의 새 아이디는 0.38과 다르다. 옛 계산에 맞추는 호환 경로는 만들지 않는다.
- 버린 설계: (1) 정규식 직접 의존. (2) 접두어 목록에 단어 경계만 붙이기. 길이와 글자 종류가 없으면 단어 첫머리의 `sk-`가 남는다. (3) 엔트로피로 거르기. 임계값을 정하기 어렵고 접두어와 길이로 이미 닫힌다. (4) 가려서 담기. 팩은 바이트 그대로 저장하는 재생 증거라서 가린 사본은 원본이 아니다.
- 실패 방식: 규칙이 좁아 놓치는 비밀이 생긴다. 이 변경은 0.38이 거절하지 않던 입력도 거절하고(공백이 낀 대입, JSON 따옴표 값), 짧은 `sk-`와 짧은 키 값은 더는 거절하지 않는다. 새 규칙은 표의 한 행과 시험 한 줄이다.

## Out of scope

- 세션 수집의 결함 D1-D5, D20과 `redact_directive`. 별개의 변경이 0.39에서 세션 수집을 없앤다.
- 증거 첨부 검사(`--secret-scan`, D18)와 새 거절 코드. 새 모듈이 그 자리지만 첨부 시점에는 부르지 않는다.
- 새 규칙: `Bearer`, `password`, `secret`, `token` 키, `glpat-`, `xox`, `sk_live_`, `ASIA`, `gho_`, `api-key` 철자.
- `redact()`, 가려 쓰기, `Secret<T>`, `S3Connection`의 `Debug`.
- 팩의 git 호출이 외부 `GIT_*` 환경 변수를 비우는 일(D9의 본 줄기). 같은 함수를 보지만 이 변경은 빈 항목만 고친다.
- 이미 저장된 팩의 다시 검사.
