# 대체표와 업그레이드 노트로 오류 코드 이름 바꾸기를 닫는다

Source: https://github.com/journeyWorker/atip tag v1.4.2 approaches/migration.md §8, spec 15.3, 계약 저자의 1.3.0 최종 규칙 댓글, canon issue #135

## Intent

코드 이름 바꾸기는 호출자 표면을 깨는 변경이고, 계약 15.3은 한 릴리스에서 모든 호출자를 옮기고 옛 이름과 새 이름을 변경 기록에 나열하며 별칭을 두지 않게 한다. 앞선 다섯 변경은 각자 자기 코드의 표와 소비자 이동을 맡았다. 이 변경은 그것을 하나의 완전한 대체표와 업그레이드 노트로 묶고, 옛 이름이 어디에도 남지 않았음을 한 번에 증명한다. 이 변경이 닫히기 전에는 코드 이름 바꾸기가 끝났다고 말할 수 없다.

## Desired outcome

- CHANGELOG의 0.36 항목이 0.35 레지스트리의 179개 코드를 모두 한 행씩 갖는다. 행은 옛 이름, 새 이름, 이유, 종료 값 변화, 재시도 값 변화를 말한다. 유지된 이름과 없어진 이름이 모두 들어 있다.
- ==**어느 옛 이름도 안내, 웹사이트, 대시보드, 평가, conformance, 시나리오, 소스, 설계 문서에 남지 않는다.**== 표를 제외한 곳이다.
- 레지스트리의 모든 코드가 core 코드이거나 `<SUBJECT>_<CONDITION>` 규칙을 통과한다. 첫 변경이 둔 "아직 옛 이름" 목록은 비어 있다.
- 업그레이드 노트가 호출자의 할 일을 말한다. 대상은 코드 이름 분기, 종료 값이 바뀐 코드, 합쳐진 코드와 이유, 없어진 `STOPPED_MIDWAY`, 거절이 `data` 대신 `details`를 싣는 것이다.
- 고친 시나리오의 리뷰가 모두 현재이고 `canon gate check`가 깨끗하다.

## User flow

1. F1 스크립트 작성자는 CHANGELOG의 대체표를 읽는다 → 자기가 분기하던 코드의 새 이름과 종료 값 변화가 있다 → ==**표대로 스크립트를 고친다.**==
2. F2 에이전트는 레지스트리를 읽는다 → 모든 코드가 이름 규칙을 따른다 → 처음 보는 코드도 조건으로 읽는다.
3. F3 사람은 안내와 웹사이트를 읽는다 → 새 이름만 보인다 → 그대로 따른다.
4. F4 게이트를 돌리는 사람은 `canon gate check`를 한다 → 고친 시나리오의 리뷰가 현재이다 → 깨끗하다.
5. F5 릴리스 담당은 변경 기록을 확인한다 → 표, 종료 값 표, 업그레이드 노트가 있다 → 릴리스한다.

## Step detail

### F1 대체표

- ==**표는 0.35 레지스트리의 179개 이름을 모두 싣는다.**== 행마다 옛 이름, 새 이름(여러 개이면 모두), 이유, 종료 값 변화(`1 → 2`), 재시도 값 변화이다. 유지된 이름은 "유지"로, 없어진 이름은 "없어짐"으로 적는다.
- 표 아래에 네 목록을 따로 모은다. 종료 값이 1에서 2로 바뀐 코드, 한 코드로 합쳐진 옛 이름들, 가르는 옛 코드와 그 새 코드들, 없어진 코드이다.
- 표는 기계가 읽는 형식이다. 시험이 옛 이름 179개를 시험 자료로 갖고 표와 맞춘다. 자료는 0.35 레지스트리에서 한 번 뽑은 것이다.
- 새 이름 중 canon이 전에 다른 뜻으로 쓴 것이 없음을 이 변경이 마지막으로 확인한다. 이전 CHANGELOG의 대체표와 `removed` 목록을 읽는다.

### F2 규칙 통과

- 레지스트리 시험이 core 코드를 뺀 모든 행에 `atip::condition::code_name_problem`을 돌려 통과를 확인한다.
- 첫 변경이 둔 "아직 옛 이름" 목록은 비어 있어야 한다. 이 변경이 그 목록과 목록을 읽는 시험 부분을 지운다.

### F3 소비자

- 옛 이름을 찾는 시험은 스킬 안내와 참조 문서, 웹사이트의 영어와 한국어 쪽, 대시보드의 소스와 시험을 본다. 평가 스크립트와 시험 자료, 설계 문서, conformance 케이스, 시나리오 문장, 소스의 힌트도 본다. 변경 기록의 표, `.canon/changes`의 과거 브리프, 장부, 날짜가 붙은 조사 문서는 제외한다.
- 시험이 찾는 이름은 옛 이름 179개 중 레지스트리에서 사라진 것 전부이다. 새 이름이 옛 이름과 같은 코드(유지된 것)는 찾지 않는다.
- 안내 문장이 종료 값 1을 "게이트가 거절했다"는 뜻으로 말하는 곳이 있으면 고친다. 이제 종료 값 2가 거절이다.

### F4 시나리오와 리뷰

- 이름이 바뀐 코드를 말하는 시나리오 문장이 모두 새 이름이다. 모든 변경을 합쳐 약 122개이다. 변경마다 낸 차이표를 모아 하나의 표로 CHANGELOG 밖 evidence에 둔다.
- 고친 시나리오의 리뷰는 stale이다. 구현자와 다른 행위자가 차이표를 보고 시나리오마다 다시 리뷰한다. 이름만 바뀐 시나리오와 뜻이 바뀐 시나리오를 차이표에서 구별한다.

### F5 업그레이드 노트

- 호출자별로 쓴다. 스크립트(코드와 종료 값), 사람이 쓰는 훅, 에이전트 안내, 대시보드를 쓰는 곳이 그 대상이다.
- 거절 봉투의 `data.violations`, `data.refused`가 `error.details[]`로 간 것을 `canon gate promote`, `subject move`, `task done`, `brief approve`별로 적는다.
- 별칭은 없다. 옛 이름으로 분기하던 스크립트는 표로 고친다고 적는다.

## Acceptance

- F1:
  - 시험이 CHANGELOG 표를 읽어 옛 이름 179개가 정확히 한 번씩 있음을 확인한다. 표의 새 이름이 모두 레지스트리에 있고, 레지스트리의 코드가 모두 새 이름이나 유지된 이름으로 표에 있다.
  - ==**종료 값이 바뀐 코드의 표와 레지스트리의 비교에서 어긋나는 행이 없다.**==
  - 실패 경로: 표에서 한 행을 지우거나 새 이름 하나를 틀리게 쓰면 시험이 실패한다.
- F2:
  - core를 뺀 레지스트리의 모든 행이 규칙을 통과한다. 목록 파일이 없고 시험이 그것을 참조하지 않는다.
  - 실패 경로: 규칙에 어긋난 코드를 하나 더하면 시험이 실패한다.
- F3:
  - 옛 이름 시험이 모든 범위에서 통과한다. 사라진 이름 하나를 안내에 되살리면 실패한다.
  - 실패 경로: 새 이름을 틀리게 쓴 안내(레지스트리에 없는 코드)는 시험이 실패한다. 웹사이트 영어와 한국어 쪽이 같은 코드를 말한다.
- F4:
  - `canon gate check`가 깨끗하고 고친 시나리오 중 stale 리뷰가 없다. 차이표의 행 수가 고친 시나리오 수와 같다.
- F5:
  - 업그레이드 노트가 호출자 네 종류를 모두 다루고, 종료 값이 바뀐 모든 코드와 `data`가 `details`로 간 모든 명령을 싣는다.
- `just conformance`의 차이가 이전 변경들이 낸 것과 같고 새 차이가 없다. `cargo test --workspace`, 생성 문서 drift 시험이 통과한다.

## Questions and assumptions

- 가정: 앞선 다섯 변경과 `canon-0-36-code-reasons`가 모두 끝나야 시작한다. 중간에 코드가 한 변경에서 다른 변경으로 옮겨졌으면 표가 최종 상태를 말한다.
- 가정: 옛 이름 시험 자료(0.35 코드 179개)는 시험 파일 안에 둔다. 레지스트리를 읽어 만들면 옛 이름이 사라진 뒤에는 만들 수 없다.
- 정책 질문: 시나리오 리뷰를 다시 하는 범위(약 122개)와 방식이다. 리뷰어가 차이표를 보고 하나씩 다시 하는 것을 가정한다. 이름만 바뀐 시나리오를 한 번에 다시 정하는 정책이 필요하면 사람이 정한다.
- 정책 질문: 외부 스크립트가 종료 값 1을 기다리는 경우의 안내 범위이다. 업그레이드 노트에 한 줄로 두는 것을 가정한다.

## Out of scope

- 새 코드와 새 이유를 더하는 일. 앞선 변경이 끝낸다.
- 경고 코드의 이름 바꾸기.
- 옛 이름의 별칭이나 이전 안내를 내는 일.
- 1.4 선언(`canon-0-36-claim-1-4`).
