# 승인된 chore는 코드 범위가 바뀐 시나리오에만 새 증거를 요구한다

Source: canon 이슈 #130의 첫 본문(0.37이 닫은 것은 그 댓글 사례), canon-0-37-approval-evidence, canon-0-28 D11

## Intent

승인된 chore는 코드를 일부 바꾸고, 출하는 승인 뒤에 기록된 증거를 시나리오마다 요구한다. 마지막 증거가 지금 코드 트리에 있는 시나리오만 면제되고, 트리는 저장소 전체에서 하나다. chore가 앱 쪽 파일 몇 개만 바꿔도 코어 시나리오 33개까지 새 증거를 요구받았고, 시나리오 77개가 걸렸다. 화면 조작으로 얻은 증거는 보고서로 다시 묶을 수 없어 `--override-reason`으로 덮게 된다.

## Desired outcome

- 정책이 시나리오의 영역이나 표면마다 코드 경로 범위를 선언할 수 있다. 선언은 선택이다.
- ==**범위가 선언된 시나리오는 마지막 증거의 트리와 지금 트리 사이에서 바뀐 경로가 그 범위에 없으면 chore 때문에 새 증거를 요구받지 않는다.**==
- 범위가 없는 시나리오와 트리 차이를 구할 수 없는 경우는 0.37과 같다.
- 거절은 요구받는 시나리오마다 범위 안에서 바뀐 경로를 말한다.
- `canon subject move`, `canon status`, `canon gate check`가 같은 답을 낸다.

## User flow

1. F1 사람은 정책에 영역 이름과 경로 패턴을 적고 정책을 승인한다 → 범위가 선다 → 승인 전에는 서지 않는다.
2. F2 에이전트는 승인된 chore가 코드 일부를 바꾼 주제를 출하한다 → 범위 안이 바뀐 시나리오와 범위 없는 시나리오만 요구받는다 → ==**요구는 바뀐 경로와 배치 명령 하나를 낸다.**==
3. F3 에이전트는 `canon status`와 `canon gate check`를 읽는다 → 출하와 같은 요구와 면제를 말한다 → 같은 다음 단계를 따른다.
4. F4 에이전트는 범위가 없거나 트리 차이를 못 구하는 시나리오를 만난다 → 0.37의 규칙이 선다 → 지금처럼 증거를 기록한다.
5. F5 사람은 범위가 잘못 쓰인 정책을 본다 → 어느 패턴이 아무 파일에도 맞지 않는지 안다 → 정책을 고쳐 다시 승인한다.
6. F6 사람은 CHANGELOG를 읽는다 → 새 정책 키와 게이트가 덜 요구하는 경우가 있다 → 알림을 읽는다.

## Step detail

### F1 범위 선언

- 정책에 키 `code_scopes`가 생긴다. 키는 시나리오 아이디의 영역(`core`)이나 표면(`app.bulkread`)이고 값은 경로 패턴 목록이다. 패턴은 `code.exclude`와 같은 글롭 문법이다.
- 시나리오의 범위는 표면 키가 있으면 그것, 없으면 영역 키, 둘 다 없으면 범위 없음이다.
- 정책은 사람이 승인한다. 승인 뒤 고친 정책은 지금처럼 닫힌 채로 실패한다. 에이전트는 범위를 늘리지 못한다.
- 스타터 정책은 범위를 쓰지 않는다. 키가 없으면 어떤 판정도 바뀌지 않는다.

### F2 판정

- 대상은 모든 증거가 chore 승인 앞에 있고 마지막 증거의 트리가 지금 트리와 다른 시나리오다. 이 집합은 0.37과 같다.
- 범위가 있는 시나리오는 마지막 증거의 트리와 지금 트리의 차이를 구한다. 추가, 수정, 삭제, 이름 변경(옛 경로와 새 경로 둘 다)이 모두 바뀐 경로다. 차이가 범위의 패턴 어디에도 맞지 않으면 면제된다.
- ==**차이가 하나라도 맞으면 요구받고, 거절은 맞은 경로를 처음 몇 개와 총 개수로 말한다.**==
- 차이에는 승인 뒤 다른 변경이 고친 경로도 든다. 면제는 그 증거가 범위 안의 지금 코드를 본 것과 같다는 뜻이다.
- 증거의 신선도를 보는 다른 규칙(선언한 표면, 뒤처진 커밋 수)은 이 변경이 바꾸지 않는다.

### F3 읽는 곳

- 출하, 상태, 게이트 검사는 한 규칙을 쓴다. 면제된 시나리오 수와 그 범위 키를 chore 줄이 말한다.
- 요구가 없으면 증거 명령을 다음 단계로 이끌지 않는다.

### F4 되돌림

- 범위가 없는 시나리오, 증거에 트리가 없는 시나리오, 옛 트리를 더는 읽을 수 없거나 git이 없는 경우는 0.37의 규칙이다. 면제는 차이를 실제로 구했을 때만 선다.

### F5 잘못된 범위

- 현재 트리의 어떤 파일에도 맞지 않는 패턴과, 어떤 시나리오에도 맞지 않는 키는 `status`와 `gate check`가 경고로 말한다. 막지는 않는다.
- 이 경고는 범위 선언이 늘어난 저장소에서만 나온다.

### F6 변경 기록

- CHANGELOG의 Added에 새 정책 키를, Changed에 게이트가 덜 요구하는 경우를 싣고 키가 없으면 동작이 같음을 적는다.

## Acceptance

- F1:
  - 영역 키 `core`는 `core/**`, 영역 키 `app`은 `app/**`와 `core/**`를 가진 저장소에서 정책을 승인하면 범위가 선다.
  - 실패 경로: 승인 뒤 정책을 고치면 정책 승인이 닫힌 채로 실패하고 범위는 서지 않는다.
- F2:
  - chore가 `app/`의 파일 하나만 바꾸면 `core` 시나리오는 요구받지 않고 `app` 시나리오는 그 경로와 함께 요구받는다.
  - 실패 경로: ==**chore가 `core/`의 파일 하나를 바꾸면 `core`와 `app` 시나리오 모두 요구받는다.**== 이름을 바꾼 파일의 옛 경로가 범위 안이어도 요구받는다.
- F3:
  - 같은 저장소에서 출하, 상태, 게이트 검사가 같은 요구와 같은 면제를 말한다.
  - 실패 경로: 한 곳만 다른 답을 내면 시험이 실패한다.
- F4:
  - 키가 없는 정책, 범위 없는 영역, 증거에 트리가 없는 시나리오는 0.37과 같은 판정을 낸다.
  - 실패 경로: 증거의 트리 객체가 없으면 면제하지 않고 요구한다.
- F5:
  - `core/**`가 파일에 맞지 않으면 경고가 그 패턴을 말하고 종료 값은 그대로다.
  - 실패 경로: 경고가 막으면 시험이 실패한다.
- F6:
  - CHANGELOG 항목이 있다.
  - 실패 경로: 항목이 없으면 릴리스 확인 시험이 실패한다.
- `cargo test --workspace`와 `canon gate check`가 통과한다.

## Questions and assumptions

- 결정: 범위는 정책에 둔다. 경로 범위는 게이트가 덜 요구하게 하는 선언이라 사람이 승인하는 정책이 맞는 자리다. 설정 파일에 두면 승인 없이 줄어든다.
- 버린 설계 셋: (1) 기능이나 시나리오의 태그. 태그는 시나리오 다이제스트에 들어 범위를 바꿀 때마다 리뷰가 전부 stale이 되고, 선언을 한 번 하려고 시나리오 수만큼 다시 리뷰해야 한다. (2) 증거 기록의 `--surface-ref`. 기록자가 기록마다 정확한 파일을 적고 옛 증거에는 효과가 없다. (3) 묶인 시험이 건드리는 파일. 보고서는 시험 이름과 클래스만 담고 파일 경로가 없어 커버리지 도구가 따로 필요하다.
- 실패 방식: 범위가 실제 의존보다 좁으면 낡은 증거가 현재로 읽힌다. 공유 파일(잠금 파일, 빌드 설정, 픽스처)은 범위에 직접 적어야 한다. 사람의 정책 승인, chore의 변경 단위 리뷰, 면제 수와 키를 말하는 chore 줄이 이를 잡는다.
- 결정: 트리 차이를 구하지 못하면 항상 요구한다. 커밋하지 않은 작업 트리의 옛 트리 객체는 사라질 수 있다.
- 결정: 범위는 chore 승인 규칙에만 쓴다. 선언한 표면과 뒤처진 커밋 수 규칙, 블로커 발견 뒤 재검증은 그대로다.
- 결정: 이 변경은 게이트가 요구하는 것을 줄인다. 범위의 자리는 정책이고 사람이 정책을 승인한다.

## Out of scope

- 시나리오, 기능, 증거에 경로를 붙이는 태그와 옵션.
- 시험이나 커버리지에서 범위를 자동으로 알아내는 일.
- 코드 트리를 계산하는 규칙과 chore가 아닌 변경의 승인.
- 증거 신선도의 다른 규칙과 블로커 발견 뒤 재검증.
