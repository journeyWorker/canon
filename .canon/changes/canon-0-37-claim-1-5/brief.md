# canon이 atip/1 1.5를 선언하고 공백 패턴을 공백 속성으로 쓴다

Source: https://github.com/journeyWorker/atip 태그 v1.5.0 spec 15.1, 15.4, 15.7, 15.9, annex-domains.md V2, CHANGELOG 1.5.0, approaches/migration.md §10, approaches/checker.md의 L1.patterns, canon-0-36-claim-1-4

## Intent

canon은 `meta.contractVersion` 1.4와 L2를 선언한다. `canon schema`가 싣는 도메인 패턴은 공백 문자를 손으로 나열한다. 스페이스, 탭, 줄 끝 문자, U+0085, U+00A0, U+1680, U+2000부터 U+200A, U+2028, U+2029, U+202F, U+205F, U+3000을 선언마다 되풀이해 적는다. 읽는 사람은 그 목록이 맞는지 확인하지 못한다. 선언 54개가 이 목록을 갖는다. 계약 1.5는 공백 속성 `\p{White_Space}`와 `\P{White_Space}`를 1.5 문서의 패턴에 허용한다. canon은 1.5를 선언하고 모든 목록을 이 속성으로 바꾼다. 받아들이는 값은 바꾸지 않는다.

## Desired outcome

- 모든 봉투와 `schema` 답이 `contractVersion` `"1.5"`를 말하고 트리의 `level`은 `L2`이다.
- ==**선언된 어느 패턴에도 손으로 나열한 공백 목록이 없고, 바뀐 패턴이 받고 거절하는 값은 이전과 같다.**==
- 공백은 `\p{White_Space}`나 `\P{White_Space}`로 쓴다. `\s`와 별칭은 어느 패턴에도 없다.
- 1.4가 지키던 규칙(공백 없는 JSON, `--help --json` 거절, 기본값 생략, 호출 표면만 담는 명령 문서)은 1.5에서도 그대로다.
- CI의 `atip check`와 `just atip-deep`이 `--contract 1.5`로 통과한다. 검사기 픽스처가 1.5를 선언한다.
- 안내, 웹사이트, conformance, 시험, 생성 명세, CHANGELOG가 1.5를 말한다.

## User flow

1. F1 에이전트는 `canon schema --json`으로 트리를 읽는다 → `contractVersion`이 `"1.5"`이고 `level`이 `L2`이다 → ==**canon의 문서를 1.5 규칙으로 읽는다.**==
2. F2 에이전트는 `canon schema <명령> --json`으로 옵션의 도메인을 읽는다 → 공백이 속성으로 쓰인 짧은 패턴이 온다 → 패턴을 자기 엔진에 그대로 넘긴다.
3. F3 에이전트는 아무 명령이나 부른다 → 모든 봉투가 1.5를 선언하고 1.4의 규칙이 그대로다 → 지금처럼 읽는다.
4. F4 1.4를 선언한 호출자는 canon의 자기 설명을 읽는다 → 패턴에 속성 이스케이프가 있다 → 그 패턴을 거절하거나 검사를 건너뛴다.
5. F5 릴리스 담당은 CI를 본다 → `atip check`가 1.5 L2 `--deep`으로 통과한다 → 선언이 증명되었다.
6. F6 에이전트나 사람은 안내와 웹사이트를 읽는다 → 1.5 선언과 패턴 표기가 말해져 있다 → 그대로 읽는다.
7. F7 사람은 CHANGELOG를 읽는다 → 바뀐 것과 1.4 호출자가 할 일이 있다 → 호출자를 옮긴다.

## Step detail

### F1 선언

- 선언 상수가 `"1.5"`이고 모든 봉투, 거절, `schema` 답이 그 값을 말한다. 수준은 L2이다.
- 같은 빌드의 `schema` 답은 저장소와 환경 없이 매 실행 바이트가 같다. 이 성질은 1.4에서 그대로 온다.
- 크레이트에 있는 패턴과 문서 검사 함수는 canon이 선언한 minor를 받는다. 선언 minor 1.5에서 속성 이스케이프가 허용되고, 1.4에서는 문제로 나온다.

### F2 패턴

- 손으로 나열한 공백 목록은 클래스 안에서도 밖에서도 `\p{White_Space}`나 `\P{White_Space}`로 바뀐다. 이 변경이 바꾸는 선언은 54개이고 서로 다른 패턴은 30개이다. 구현자가 다시 센다.
- ==**패턴마다 받는 값과 거절하는 값이 이전과 같다.**== 각 행의 값표(안쪽 값, 바깥 값)를 실제 파서에 돌려 증명한다.
- 앞뒤 공백이 없는 한 줄은 `^\P{White_Space}([\P{White_Space}\p{Zs}\t]*\P{White_Space})?$`로 쓴다(계약 V2의 형태). 줄 끝 문자가 없는 문자 하나는 클래스 `[\P{White_Space}\p{Zs}\t]`로 쓴다.
- 이 변경은 어떤 규칙도 바꾸지 않는다. 앞뒤 공백을 거절하는 규칙은 거절하는 대로, 받는 규칙은 받는 대로 둔다. 규칙의 통일은 canon-0-37-option-values가 한다.
- `\s`, `\S`, 속성의 별칭(`space`, `WSpace`)을 쓴 패턴은 1.5 선언에서도 문제로 나온다.

### F3 1.4의 규칙

- 계약 15.1에 따라 1.4의 MUST는 1.5 문서에도 묶인다. canon의 1.4 선언 시험은 1.5에서 같은 뜻으로 돈다. 선언 문구만 1.5로 바뀐다.
- 명령 문서에 `path`, 내장 스키마, 기본값인 멤버가 없고 `--help --json`이 `USAGE`로 거절하는 동작이 그대로다.

### F4 1.4 호출자

- 1.4 호출자가 패턴을 자기 프로필로 검사하면 속성 이스케이프를 거절하거나 그 검사를 건너뛸 수 있다(15.9, 15.4). 패턴을 ECMAScript의 `u` 플래그나 Rust `regex`로 컴파일하는 호출자는 그대로 바르게 읽는다.
- canon은 도구이고 다른 도구의 자기 설명을 읽지 않는다. canon의 시험은 canon의 답을 선언 minor의 프로필로 검사하고, 프로필 밖 패턴을 건너뛰지 않고 문제로 낸다.

### F5 CI

- 검사기 픽스처 `canon.fixture.json`의 `contractVersion`이 `"1.5"`이다. CI의 canon 준수 job과 `just atip`, `just atip-deep`은 `--contract 1.5`를 쓴다.
- 실행이 `L1.patterns`를 포함한 L0, L1, L2의 모든 행을 통과한다. 보고서 요약과 실행 시간을 evidence에 남긴다.

### F6 소비자

- 안내의 생성된 블록, 웹사이트 `cli.mdx`의 두 언어, conformance 기대 출력, 생성 명세의 선언 문구가 1.5이다.
- `atip.claim*` 계열 시험과 평가 스크립트의 선언 문구도 1.5이다. 공백 목록을 보여 주던 예시는 속성 표기로 바뀐다.
- 시나리오 문장이 1.4 선언이나 목록 표기를 말하면 고친다. 고친 시나리오의 리뷰는 stale이고 다른 행위자가 다시 리뷰한다.

### F7 변경 기록

- CHANGELOG의 이번 릴리스 항목에 "canon이 atip/1 1.5를 선언한다"를 싣는다. 전후를 표로 보인다: 선언, 패턴 표기, 패턴 한 개의 길이 전후.
- 호출자 노트: 1.4 호출자가 패턴을 자기 프로필로 검사하면 canon의 패턴을 거절할 수 있다. 검사하지 않고 컴파일만 하는 호출자는 그대로 쓴다.

## Acceptance

- F1:
  - 아무 명령의 봉투와 모든 `schema` 답이 `"1.5"`이고 트리의 `level`이 `L2`이다.
  - 실패 경로: 선언 상수를 1.4로 두면 선언 시험이 실패한다. 선언 1.4의 문서에 속성 이스케이프가 있으면 크레이트 검사 함수가 문제를 낸다.
- F2:
  - `canon schema`의 어느 패턴에도 나열된 공백 목록이 없다. ==**값표 전체가 이전과 같은 결과를 낸다.**==
  - 실패 경로: `\s`를 쓴 패턴, 별칭을 쓴 패턴, 값표의 한 값이 이전과 다르게 처리되는 패턴은 시험이 실패시킨다.
- F3:
  - 1.4 선언 시험이 1.5 선언으로 모두 통과한다. 모든 JSON 문서에 공백이 없다.
  - 실패 경로: 문서에 기본값인 멤버나 공백이 생기면 시험이 실패한다.
- F4:
  - 1.4 프로필로 검사하는 시험 호출자는 속성 이스케이프를 문제로 읽고, 컴파일만 하는 시험 호출자는 같은 값을 받고 거절한다.
  - 실패 경로: 선언 minor가 1.4인 문서의 속성 패턴은 문제로 나온다.
- F5:
  - CI의 `atip check --level L2 --contract 1.5 --deep`이 통과하고 `L1.patterns` 행이 통과로 있다.
  - 실패 경로: 선언을 1.4로 낮추거나 픽스처 `contractVersion`을 바꾸면 같은 실행이 실패한다.
- F6:
  - 안내, 웹사이트, 생성 명세에 1.4를 선언으로 적은 곳이 없고 `just docs`와 `just conformance`의 차이가 이 변경의 것뿐이다.
  - 실패 경로: 선언 문구를 1.4로 적은 소비자를 시험이 찾아 실패한다.
- F7:
  - CHANGELOG에 선언 전후와 호출자 노트가 있다.
  - 실패 경로: 호출자 노트가 없으면 릴리스 확인 시험이 실패한다.
- `cargo test --workspace`와 conformance, 생성 문서 drift 시험이 통과한다.

## Questions and assumptions

- 확인함: 크레이트 0.2.0의 패턴 검사는 1.5에서 다음 형태를 받는다. 앞뒤 공백이 없는 한 줄 패턴, `[^\p{Cc}\p{Zl}\p{Zp}]`, 속성을 일반 범주와 함께 담은 부정 클래스, `/`를 뺀 부정 클래스이다. `\s`는 거절한다. 선언 1.4에서는 속성을 거절한다.
- 질문(계약 저자): 부록 V2의 예와 시험 사례는 `[^\P{White_Space}]`처럼 속성만 든 클래스를 보인다. canon은 `[^\p{Cc}\p{White_Space}]`처럼 속성과 일반 범주를 함께 담은 클래스도 쓴다. 크레이트는 받지만 계약의 뜻이 그것을 허용하는지 확인한다. 기본값: 허용한다.
- 가정: 15.4의 호출자 규칙이 canon에 닿는 곳은 canon의 시험이 canon의 답을 호출자처럼 읽는 곳뿐이다. canon은 다른 도구의 문서를 읽지 않으므로 건너뛸 패턴이 없다. 계약 저자가 이 해석을 확인한다.
- 가정: 속성 `White_Space`와 손으로 나열한 목록의 집합이 같아서 받는 값이 달라지지 않는다. 값표가 이를 확인한다. 다르면 이 변경은 규칙을 바꾸는 것이므로 사람에게 알린다.
- 정책 질문: 이 변경은 canon이 계약에 대해 하는 주장(1.5와 L2)을 바꾼다. 사람이 이 선언을 승인한다.

## Out of scope

- 값 규칙의 통일, 제어 문자 금지, 앞뒤 공백 처리(canon-0-37-option-values).
- `--approval-at`과 `--providers`(canon-0-37-option-forms).
- 1.5 밖의 기능, L3 같은 더 높은 수준의 주장.
- 이름 붙인 "앞뒤 공백 없는 한 줄" 도메인. 계약 1.5는 이를 더하지 않았다.
