# 코드 트리가 그대로인 chore 승인은 새 증거를 요구하지 않는다

Source: canon issue #130(작은 변경 뒤의 재승인 사례 댓글), canon-0-28 D11과 #116(코드가 안 바뀐 chore는 증거를 요구하지 않는다)

## Intent

승인된 chore가 있는 주제를 출하하려면 chore 승인 뒤에 기록된 증거가 시나리오마다 있어야 한다. 마지막 증거가 지금 코드 트리에 있는 시나리오는 면제된다. chore를 다시 승인하면(브리프 문구를 고친 경우도 같다) 승인 시각이 앞으로 간다. 다른 변경이 증거 뒤에 코드를 고쳤다면 마지막 증거가 옛 트리에 있는 시나리오가 많다. chore가 코드를 하나도 바꾸지 않았는데도 출하는 그 시나리오 모두의 증거를 다시 기록하라고 요구한다. 사례에서 시나리오 63개가 그랬다.

## Desired outcome

- 승인은 승인한 순간의 코드 트리를 기록한다. 재승인은 새 트리를 기록한다. 트리는 증거의 코드 트리와 같은 방식(`.canon/`, spec root, `code.exclude`를 뺀 작업 트리)으로 계산한다.
- ==**chore의 승인 트리가 지금 코드 트리와 같으면 그 chore는 증거를 하나도 요구하지 않는다.**== chore의 변경 단위 리뷰는 그대로 요구한다.
- 승인 트리가 지금 트리와 다르면 지금 규칙이 그대로 선다.
- 트리가 기록되지 않은 승인은 지금 규칙을 따른다.
- `canon subject move`, `canon status`, `canon gate check`가 같은 답을 낸다.

## User flow

1. F1 사람은 chore 브리프를 승인하거나 다시 승인한다 → 승인이 그 순간의 코드 트리를 기록한다 → ==**승인 트리가 승인 기록에 남는다.**==
2. F2 에이전트는 승인 뒤 코드가 바뀌지 않은 주제를 `canon subject move --to shipped`로 출하한다 → 승인 트리와 지금 트리가 같다 → 증거를 요구하지 않고 변경 단위 리뷰만 요구한다.
3. F3 에이전트는 승인 뒤 코드를 바꾼 주제를 출하한다 → 트리가 다르다 → 지금처럼 증거를 요구하고 배치 명령 하나를 낸다.
4. F4 에이전트는 트리가 없는 옛 승인의 chore로 출하한다 → 지금 규칙이 그대로다 → 지금처럼 증거를 요구하거나 면제한다.
5. F5 에이전트는 `canon status`와 `canon gate check`를 읽는다 → 출하와 같은 규칙으로 같은 답이 나온다 → 같은 다음 단계를 따른다.
6. F6 사람은 CHANGELOG를 읽는다 → 게이트가 덜 요구하는 경우와 승인 기록의 새 정보가 있다 → 알림을 읽는다.

## Step detail

### F1 승인이 트리를 기록한다

- `canon brief approve`와 대시보드의 승인이 같은 기록을 남긴다. 사람이 직접 한 승인과 릴레이한 승인이 같다.
- 트리는 작업 트리의 현재 상태로 계산한다. 커밋하지 않은 코드도 든다. 증거가 기록하는 코드 트리와 같은 계산이므로 같은 코드는 같은 트리이다.
- 기록은 브리프의 승인 다이제스트에 들지 않는다. 승인 줄의 다른 부분과 릴레이 표시를 읽던 곳(상태, 대시보드, 이전 명령)이 새 정보 때문에 깨지지 않는다.
- git 작업 트리가 없거나 커밋이 없으면 트리를 기록하지 않는다. 그 승인은 F4처럼 읽힌다.

### F2 같은 트리

- 승인된 chore마다 승인 트리와 지금 트리를 비교한다. 같으면 그 chore는 증거 틈을 만들지 않는다. chore의 코드 변경이 승인 뒤에 없었다는 뜻이다.
- 증거가 옛 트리에 있는 시나리오도 이 chore 때문에는 증거를 요구받지 않는다. 증거의 신선도는 게이트의 다른 규칙(선언한 표면의 변경, 뒤처진 커밋 수)이 계속 본다.
- 변경 단위 리뷰는 그대로 요구한다. 브리프를 고쳤으면 이전 리뷰는 stale이고 새 리뷰가 필요하다.

### F3 다른 트리

- 승인 뒤에 코드가 바뀌었다면 지금 규칙이 선다. 증거가 모두 승인 앞에 있고 마지막 증거가 지금 트리에 없는 시나리오가 요구 대상이다.
- ==**거절은 시나리오 목록과 이어서 실행할 배치 명령 하나를 낸다.**== 이 출력은 0.36과 같다.

### F4 옛 승인

- 트리가 없는 승인에서는 승인 시각과 지금 트리로 판정하는 규칙이 그대로다. 0.36까지 쓴 승인 줄을 다시 쓰지 않는다.

### F5 읽는 곳

- 출하, 상태, 게이트 검사는 한 규칙을 함께 쓴다. 상태의 다음 단계와 `meta.next`는 요구가 없을 때 증거 명령을 이끌지 않는다.
- 요구가 없는 이유를 읽을 수 있다. 상태의 chore 줄이 승인 트리와 지금 트리가 같다고 말한다.

### F6 변경 기록

- CHANGELOG의 Changed 항목에 "트리가 그대로인 chore 승인은 증거를 요구하지 않는다"와 승인 줄의 새 정보를 싣는다. 옛 승인의 동작이 그대로임을 적는다.

## Acceptance

- F1:
  - chore를 승인하면 승인 기록이 그 순간의 코드 트리를 담고 다이제스트는 바뀌지 않는다. 다시 승인하면 새 트리로 바뀐다.
  - 실패 경로: git 작업 트리가 없는 저장소에서 승인하면 트리 없이 승인되고 오류가 없다.
- F2:
  - 증거 뒤에 다른 변경이 코드를 고쳐 마지막 증거가 옛 트리에 있는 시나리오가 여럿인 주제에서 chore를 승인한다. ==**코드가 그대로이면 출하는 증거를 요구하지 않고 변경 단위 리뷰만 요구한다.**==
  - 실패 경로: 리뷰가 없으면 출하는 종료 값 2로 거절되고 리뷰 명령을 이끈다.
- F3:
  - 승인 뒤에 코드를 바꾸면 출하가 시나리오 목록과 배치 명령 하나를 낸다. 명령을 실행하면 틈이 닫힌다.
  - 실패 경로: 승인 뒤 한 파일만 바뀌어도 트리가 달라져 요구가 선다. `code.exclude`가 뺀 파일만 바뀌면 요구가 서지 않는다.
- F4:
  - 트리가 없는 승인의 chore는 0.36과 같은 판정을 낸다.
  - 실패 경로: 옛 승인 줄을 읽는 곳이 새 정보 없이도 오류를 내지 않는다.
- F5:
  - 같은 저장소에서 출하, 상태, 게이트 검사가 같은 요구를 말한다.
  - 실패 경로: 한 곳만 다른 답을 내면 시험이 실패한다.
- F6:
  - CHANGELOG 항목이 있다.
  - 실패 경로: 항목이 없으면 릴리스 확인 시험이 실패한다.
- `cargo test --workspace`와 `canon gate check`가 통과한다.

## Questions and assumptions

- 결정: 이 변경은 게이트가 요구하는 것을 줄인다. 승인한 뒤 chore의 코드가 들어오고, 그 코드에 증거를 기록하지 않은 채 chore를 다시 승인하면 트리가 같아져 증거를 요구하지 않는다. 이 틈을 받아들인다. 다시 승인하면 이전 변경 단위 리뷰가 stale이 되어 새 리뷰가 필요하다.
- 결정: 승인 트리를 승인 줄에 기록한다. 승인 시각 직전의 커밋에서 트리를 구하는 방법은 쓰지 않는다. 그 방법은 커밋 시각과 승인 시각이 어긋나면 틀리고 커밋하지 않은 코드를 못 본다.
- 결정: 모든 브리프 승인이 트리를 기록한다. 기능 브리프에서는 쓰이지 않는다.
- 결정: 마지막 증거가 옛 트리에 있는 시나리오의 신선도는 이 변경이 바꾸지 않는다. 시나리오가 의존하는 경로만 보는 범위 지정(이슈 130의 첫 본문)은 이 변경 밖이다.
- 결정: 트리가 기록된 새 승인에서 증거 틈이 사라지는 것은 chore가 코드를 바꾸지 않았다는 신호일 뿐이다. 변경 단위 리뷰가 그 확인을 맡는다.

## Out of scope

- 시나리오나 기능에 코드 경로를 붙여 증거의 신선도를 경로별로 판정하는 일(이슈 130의 첫 제안).
- 코드 트리를 계산하는 규칙(`code.exclude`, spec root) 바꾸기.
- chore가 아닌 변경의 승인, 증거 기록 방식, 증거 신선도의 다른 규칙.
- 변경 단위 리뷰의 요구.
